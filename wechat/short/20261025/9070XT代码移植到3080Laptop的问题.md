# 9070 XT (`0.44`) 代码移植到 RTX 3080 Laptop (`sm_86`) 暴露的两类问题与反哺清单

**记录时间**：2026-10-25  
**背景**：将 `dlss5-on-amd-9070xt-porting`（`0.44` 版，31 块 `0.5x Small` 模型）的独立引擎从 AMD RDNA 4 (`gfx1201`) 移植到 NVIDIA RTX 3080 Laptop (`sm_86` Ampere)，并经过 Phase 1～10 十轮深度优化，最终将 3080 Laptop 上的耗时从初始移植的 `208.75 ms`（V5 `43.10 ms`）一路压到 **720p `14.10 ms`、900p `23.48 ms`、1080p `31.26 ms`**（全面反超老黄原版 `310.9.16.0` PTX 满血 `O4` 补丁的 `15.83 / 24.47 / 32.04 ms`）。

在排查过程中抓出的所有“问题”，**都不是 9070 XT 代码的算术或画面错误（9070 XT 原版计算 100% 正确）**，而是清晰地分为以下两类：
- **第一类（占 95%）**：在 AMD RDNA 4 硬件与 `amdgcn` 编译器上是合理甚至最优的写法，但到了 NVIDIA Ampere 硬件与 `nvptx64` (`llc-14` / `ptxas`) 编译器上变成性能大坑；
- **第二类（占 5%）**：9070 XT `0.44` 代码里确实存在的两处“加速门控开关漏开”遗漏，后续可在 9070 XT 仓库未来的版本中反哺回去白捡性能。

---

## 一、第一类：在 9070 XT 上完全正常，到 N 卡上变成性能大坑的跨架构水土不服

### 1. `const unsigned char*` 的 `align 1` 导致 NVPTX 后端把 8B/16B 向量读写拆成单字节 `.u8`（Phase 6 砍掉 9.0～12.5 ms）
- **源码现象**：
  在 `wave_owned_mh.inc`、`wave_owned_c32.inc`、`deep_fast.hip` 等文件中，大量使用：
  ```cpp
  __attribute__((shared)) unsigned char plane0[64*C], plane1[64*C], plane_k[64*C];
  __builtin_memcpy(&a, p + ((qt*(C/16)+ct)*32+lane)*8, 8);
  __builtin_memcpy(&b, reinterpret_cast<const unsigned char*>(w) + offset, 16);
  ```
- **为什么在 9070 XT 上没问题**：
  在 C++ 中，`unsigned char*` 的自然对齐只有 **1 字节（`align 1`）**（`_Float16*` 只有 `align 2`），因此 Clang 生成的 LLVM IR 为 `load <2 x i32>, <2 x i32>* %ptr, align 1`（或 `load <4 x i32>, ..., align 1`）。AMD RDNA 4 硬件原生允许非对齐向量访存，所以 LLVM `amdgcn` 后端看到 `align 1` 依然会生成单条 `ds_read_b64`、`global_load_b64`、`global_load_b128` 宽指令。
- **为什么在 RTX 3080 上酿成惨案**：
  NVIDIA PTX 硬件规范严格要求向量访存（`ld.v2.u32` = 8B 对齐，`ld.v4.u32` = 16B 对齐）必须自然对齐，否则触发硬件异常 `CUDA_ERROR_MISALIGNED_ADDRESS (716)`。因此 LLVM `nvptx64` 后端（`llc-14`）只要看到 IR 上标着 `align 1`，就会强制把 **1 条 8B/16B 向量读写拆成 8～16 条 1 字节的 `ld.global.u8 / ld.shared.u8 / st.shared.u8` + 14～28 条 `shl / shr / or` 移位拼装指令**！全网 40 个模块里竟然拆出了 **141,625 条 `ld.global.u8`**！
- **解法**：
  因为物理偏移本身就是 `*8` 或 `*16` 对齐的，在 LLVM IR Pass 中将 `addrspace(3)` 共享内存全局数组统一升为 `align 16`、8B 向量读写升为 `align 8`、16B 向量读写升为 `align 16`。40 个模块的 `ld.global.u8` 从 `141,625` 骤降至 `9,669`（主用 `wave2` 核降为 `0`），单这一刀在 900p 省下 `9.0 ms`、1080p 省下 `12.5 ms`（ViT 各核提速 2.5～3.7 倍）。

### 2. GeForce 30 系消费卡的 FP32 累加 Tensor Core 硬件半速限位（Phase 1）
- **机制差异**：
  在 9070 XT（RDNA 4）上，`wmma_f32_16x16x16_fp8_fp8`（FP32 累加）是满速硬件指令。但在 NVIDIA 消费级 GeForce 30 系（GA102/GA104）上，老黄在硬件层面把 **FP32 累加（`.f32.f16.f16.f32`）的 Tensor Core 吞吐量砍掉了一半（256 FLOPs/clk/SM）**，只有 **FP16 累加（`.f16.f16.f16.f16`）才是满速（512 FLOPs/clk/SM）**。
- **解法**：
  切换为 `.f16.f16.f16.f16` 指令，并将 K 循环内部的累加器从 8 个 32 位寄存器（`sm86_f8`）压减为 4 个 32 位寄存器（`sm86_u4`，即 4 个 `f16x2`），既解锁了满速算力，又将累加器寄存器占用砍半。

### 3. RDNA 4 Wave32 与 Ampere Warp32 线程座位差异导致的运行期洗牌风暴（Phase 2 / 5 / 8 / 9）
- **机制差异**：
  9070 XT 原生就是 RDNA 4 Wave32 座位，0 次洗牌。搬到 Ampere 上后，输入 A/B 和输出 C/D 的线程座位不同：
  1. **静态权重运行期重复洗牌**：初期只预洗牌了激活，静态只读模型权重在每次进 WMMA 时都在运行期跑 `__sm86_prep_fp8`（4 条 `shfl.sync` + 6 条 `selp`），光 `c32_wave1` 每帧就白跑近 3,000 万条 `shfl.sync`。**解法**：在 Host 端 `packed_weights.h` 上传权重前，由 CPU 一次性按 `AmperePreshuffleTile` 将所有 8B/16B 权重块重排为 Ampere 座位，GPU 运行期直接 `sm86_unpack_e4m3x8`（0 次 `shfl.sync`）。
  2. **用 `wmma_f16(ones, x, sum)` 算行求和**：在 9070 XT 上是 1 条原生指令；在 Ampere 兼容层下每次要跑 12 条 `shfl.sync` + 36 条 `selp` + 2 条 `mma.sync`。**解法**：改为线程内 8 元素相加 + 1 条跨半 Warp 蝴蝶洗牌 `shfl.sync.bfly.b32(..., 16)`。
  3. **C/D 8-float 洗牌与逐元素激活往返 RDNA 4 中转**：初期 `__sm86_d_to_rdna4` 先拆成 8 个 `float` 跑 48 条 `selp.f32` + 8 条 `shfl`，做完逐元素激活打包后又跑 `sm86_preshuffle_fp8`（4 条 `shfl`）回 Ampere AB。**解法**：先将 C/D 洗牌升级为 4-`u32` 半精度向量化 Benes 网络（省 32 条 `selp`）；再推导出 **`2-shfl` Ampere D $\rightarrow$ Ampere AB 直通定理（`sm86_d_bytes_to_ab`）**，对 `expanded`、`contract`、`result`、`V`、`av` 直接在 Ampere D 座位做逐元素激活与打包，仅用 **2 条 `shfl.sync`** 直接转入 Ampere AB 座位（洗牌指令减少 83%）。

### 4. 软件 FP8 转换的三元运算符被 NVPTX 拆成 600 个发散分支基本块 `bra`（Phase 7 / 10）
- **机制差异**：
  9070 XT 有硬件 `v_cvt_pk_fp8_f32` 指令（但对 `>448.0` 不饱和，需外层先调 `fmed3f(x+0.f, -448.f, 448.f)`）。Ampere 没有硬件 FP8，软件函数 `sm86_f32_to_e4m3_byte` 里的 C++ 三元表达式 `(a < 0x3c800000u) ? sub : ...` 因分支内有 7 条指令，被 LLVM 拆成了 `@%p bra` 条件跳转基本块（`c32_wave1_prefix` 单核产生 617 条 `bra`），且内联 `asm` 版 `fmed3f` 阻止了常数边界 `-448 / +448` 与 `-4 / +4` 的折叠。
- **解法**：
  将 `sm86_f32_to_e4m3_byte` 写成无分支内联 `asm`（纯 `selp.b32`，`bra` 从 617 降为 10），并用 1 条硬件 `min.f32 fa, fa, 0f43e00000`（钳位到 `448.0f`，向偶舍入后天然等于 `0x7e`）替代内层 `p_sat / p_nan` 与外层冗余的 `fmed3f(..., -448.f, 448.f)`，每次 `pack8` 净省 40 条指令。

## 二、第二类：9070 XT (`0.44`) 代码自身的两个“门控漏开”遗漏（可在未来的版本中反哺 9070 XT）

以下两处在 9070 XT 的 `0.44` 源码中也同样存在，属于**已经写好了快速核、但 Host 门控或编译脚本漏开了非 1080p / 小通道分支**：

### 1. `hip_reference_network.h` 中紧凑 ViT W16 与 C256 `wave2` 整块融合写死了 `W==1920 && H==1152`
- **位置**：
  - `hip_reference_network.h` 的 `InitCompactContract()`（原第 478 行）和 `InitCompactProjection()`（原第 495 行）：
    条件里硬编码写死了 `fast_numeric && W==1920 && H==1152`！
  - `hip_reference_network.h` 的 `Body()` 中 `c == 256` 的 `wave_owned` 分支（原第 788 行）：
    条件里只写了 `(opt.width==1920&&(opt.height==1152||opt.height==1088))||(opt.width==2560&&opt.height==1472)`！
- **对 9070 XT 的影响**：
  - `CompactContractWeight`（`1024×4096`）和 `CompactProjectionWeight`（`1024×1024`）的矩阵形状与图像分辨率 `W, H` 完全无关，且是 `0 bit-diff` 无损布局；
  - 因为写死了 `W==1920 && H==1152`，哪怕在 **9070 XT** 上，当玩家跑 **900p 档（如 2K 质量档 `1707×961` 自动匹配的 `1600×960` / `1600×1024`）或 720p 档（`1280×768`）** 时，`compact_contract_fn` 和 `compact_projection_fn` 都是空指针！
  - 这导致 9070 XT 在 900p / 720p 下不仅没用上 `_compactw_w16` 16B 宽指令核，还导致第 886 行的 `inter_byte`（8 个 ViT 块之间的 1 字节 FP8 直连流）被连带关闭，每帧白白多跑了 8 次 `vit_pack_input` 和慢速的 `vit_stream_contract_frag_bout`！
- **反哺修法**：
  在 9070 XT 仓库中，同样将 `InitCompactContract()` 和 `InitCompactProjection()` 的 `W==1920 && H==1152` 放宽为 `(TierGeometry(W,H) || free_geometry)`，并检查 900p / 720p 下 `c256_wave2` 的收益。

### 2. `build-modules.ps1` 编译 `c64-wave2` 模块时漏传了 `W2_FFN_W16_SMALL 3` 和 `W2_FFN_QT_SMALL_MASK 3`
- **位置**：
  - 在 `hip_reference_network.h` 第 79 行和第 795 行，Host 端已经默认定义了 `#define HIP_SMALL_FFN_W16 1`，每次发射 `c64_wave2` 和 `c128_wave2` 时都会调用 `HasFn("c64_wave2", name + "_w16")` 去查找 16B 宽权重加载版核函数（如 `c64_wave2_bi_bo_w16`、`c128_wave2_bi_bo_w16`）；
  - 但在 `hip/build-modules.ps1` 第 66 行和第 71 行编译 `c64-wave2` 和 `c64-wave2-fast` 时，`defines` 列表里只传了 `'W2_FFN_W16 1'`（只开启 C256 的 `_w16` 导出）和 `'W2_FFN_QT_SMALL_MASK 0'`，**漏传了 `'W2_FFN_W16_SMALL 3'`（见 `wave_owned_mh.inc:785`，默认为 0）**！
- **对 9070 XT 的影响**：
  `c64-wave2.hsaco` 和 `c64-wave2-fast.hsaco` 里根本没有编译导出 `c64_wave2_*_w16` 和 `c128_wave2_*_w16` 符号，导致 Host 的 `HasFn` 永远返回 `false`，`C64` 和 `C128` 站一直回退在 8B 权重加载的旧核上。
- **反哺修法**：
  在 `build-modules.ps1` 的 `c64-wave2` 与 `c64-wave2-fast` 定义中补上 `'W2_FFN_W16_SMALL 3'` 和 `'W2_FFN_QT_SMALL_MASK 3'`，在 9070 XT 上做一次 ABBA 实测验证即可白捡提速。
