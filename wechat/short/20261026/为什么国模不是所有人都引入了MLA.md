# 为什么 DeepSeek 的 MLA 开源两年半了，国模不是所有人都引入了它？

**日期**：2026-10-26  
**标签**：`MLA` / `GQA` / `DeepSeek` / `MiniMax-M3.1-Flash` / `KV Cache` / `训练暗坑`

---

## 一、现象：MoE 和稀疏挑词大家都抄了，唯独 MLA 抄的人最少

今天在拆 `MiniMax-M3.1-Flash` 时算出一笔极反常的显存账：
同样标称 1M（100 万词元）上下文、同样叫 `Flash`，`DeepSeek-V4-Flash` 的 1M 静态 KV 缓存在 `BF16` 下只要 **`6.72 GiB`**（`FP8` 下约 `3.0 GiB`），`DeepSeek-V4.1-Flash` 靠跨层共享与半程丢弃更是压到了 **`0.89 GiB`**；而 `MiniMax-M3.1-Flash` 在 `FP8` 下居然高达 **`67.5 GiB`**（`BF16` 下 **`135 GiB`**）！

如果放到云端卖商业 API，一台留出 `400 GiB` 显存池的 8 卡服务器，跑 `DeepSeek-V4.1-Flash` 能同时接 **450 个** 1M 长文并发用户，而跑 `MiniMax-M3.1-Flash` 来 **6 个** 满载用户就把整台机器的显存彻底吃光了（单机长文并发容量差了整整 **75 倍**）。MiniMax 之所以敢挂出 `$0.15` / 百万 token 的白菜价，纯粹因为上市公司需要发新模型和低价招牌给二级市场讲故事——反正平时根本没多少真实用户拿它的 API 高并发跑 1M 上下文，没有真实调用量就不会真把服务器撑爆亏钱。

但顺着这件事往深处看，会发现一个更有意思的行业现象：
DeepSeek 定下的图纸里，**细粒度共享专家 MoE**、**无辅助损失路由偏置（`e_score_correction_bias`）**、**两棒接力式动态稀疏注意力（挑 2048 词元）**、**`DSpark / DFlash` 投机解码**，几乎被所有国产模型（甚至老黄和扎克伯格）抄了个遍；
**唯独早在 2024 年 5 月（`DeepSeek-V2`）就已经开源、省 KV 缓存最立竿见影的 `MLA`（多头潜注意力），两年半过去了，居然只有 Kimi（`K3`）和智谱（`GLM-5.2 / 5.3`）跟进，而阿里 `Qwen` 全系（直到 `Qwen3.8-Flash-Next`）、`MiniMax` 全系（直到 `M3.1-Flash`）、小米 `MiMo` 全系（直到 `V2.6`）以及美国三大厂，全都死守着传统的 `GQA` 不肯上 MLA！**

明明能把 KV 缓存砍掉大半，为什么一半以上的厂商宁可忍受肥胖的 GQA 缓存（或者靠砍掉 3/4 全局层换线性注意力/滑窗来凑合），也不敢碰 MLA？

因为 MLA 在论文公式之外，藏着三个大厂自己下场训过、写过底层算子才知道的**工程暗坑**。

---

## 二、暗坑一：MLA 在“训练阶段”不仅不省，反而比 GQA 更慢、更费激活显存

很多人有一个错觉：既然 MLA 在推理时能把 KV 缓存压到 `512` 维，那训练时肯定也省显存、算得快。**恰恰相反！**

1. **为什么推理（Decode）时 MLA 能省？靠的是“矩阵吸收（Matrix Absorption）”**：
   在单字解码阶段，当前步只有 1 个查询词元 $q_t$。MLA 利用矩阵乘法结合律，把负责将 `512` 维潜向量 $c_t^{KV}$ 还原成多头 Key 的解压大矩阵 $W^{UK}$，提前乘进查询矩阵 $W^Q$ 里。这样一来，推理时根本不需要把 `512` 维的 $c_t^{KV}$ 展开成 `64 个头 × 128 维 = 8192 维`，直接拿吸收后的宽查询向量去跟 `512` 维的潜向量做点积就行。
2. **为什么训练（Training）和长文预填充（Prefill）时绝对不能做矩阵吸收？**
   一旦在训练时把 $W^{UK}$ 吸进 $W^Q$，64 个查询头（Q）每个头的维度就会从 `128` 维暴涨 4 倍变成 **`512` 维**！
   在训练和预填充阶段，序列长度 $N$ 动辄几万到几十万，64 个头全都顶着 `512` 维的宽度去算 $O(N^2)$ 的注意力矩阵乘，计算量（FLOPs）当场暴增 **4 倍**，算力直接崩盘！
3. **训练时的真实代价**：
   因此，在整個预训练和后训练阶段，MLA **根本没法用矩阵吸收**，必须老老实实走两步：
   - 第一步：先把输入投影成 `512` 维的压缩潜向量 $c_t^{KV}$；
   - 第二步：再乘上巨大的升维矩阵 $W^{UK}$ 和 $W^{UV}$，**把 `512` 维重新展开成 `64 个头 × 128 维 = 8192 维` 的全尺寸 K 和 V**，再去做标准的多头注意力！

算一下训练账就明白了：对比 4 个 KV 头（仅 `512` 维）的 `16:1 GQA`，训练期间的 `GQA` 真的只需要算 `512` 维的 K 和 V；而训练期间的 `MLA` 却要**先压到 `512` 维、再展开成 `8192` 维全尺寸多头 K/V**——不仅在反向传播时要多存一套庞大的多头激活值（Activation Memory 暴涨），还白白多背了一道升维大矩阵乘法的算力开销！对算力紧巴或者追求训练吞吐的团队来说，这第一道门槛就够喝一壶了。

## 三、暗坑二：那根“单头 64 维解耦 RoPE 绳子”在训练动力学上极难伺候

这是 MLA 在训练稳定性上最大的暗礁，DeepSeek 在论文里只写了怎么设计，没写为了调通它废了多少卡时。

1. **为什么 MLA 被迫搞出“内容与位置分家（Decoupled RoPE）”？**
   刚才说到，MLA 在推理时必须靠矩阵吸收（$W^Q (W^{UK})^\top$）才能省显存。如果像普通 GQA 那样，在压缩后的潜向量 $c_t^{KV}$ 上直接乘旋转位置编码矩阵 $R_t$，那么 $W^Q$ 和 $W^{UK}$ 中间就夹了一个随位置距离 $(t - s)$ 动态变化的矩阵 $R_{t-s}$，两个固定权重矩阵就彻底没法提前合并吸收了！
   为了保住矩阵吸收，DeepSeek 被迫把每个头切成了两半：
   - **内容通道（NoPE）**：走 `512` 维共享潜空间压缩，绝对不沾位置编码；
   - **位置通道（Decoupled RoPE）**：在潜空间外面单独甩出 **唯独 1 个 `64` 维的共享键头 $k_t^R$（全层 64 个查询头共用这一根 `64` 维的位置绳子！）**，专门用来挂 RoPE 旋转位置编码，最后再把 `512` 维内容和 `64` 维位置拼成 `576` 维。
2. **训练时的灾难：64 个头抢 1 根 64 维位置绳子，极易引发范数失衡与长文坍缩**：
   你想想看：在普通 GQA 里，每个 KV 头都有自己完整的旋转位置编码；而在 MLA 里，**全层 64 个查询头关于“谁在前、谁在后、相距多远”的全部位置寻址信息，全被死死勒在同一根 `64` 维的单头细绳子 $k_t^R$ 上**！
   更要命的是，在算注意力点积 $q_t^\top k_s = (q_t^C)^\top k_s^C + (q_t^R)^\top k_s^R$ 时，左边是经过低秩瓶颈再升维出来的 `128` 维内容内积，右边是未经低秩瓶颈直通的 `64` 维 RoPE 位置内积——两路信号走过的矩阵层数不同、梯度缩放倍率不同，在从零预训练和长上下文扩窗（比如从 32K 扩到 1M）时，极容易出现**“位置内积的数值幅度把内容内积彻底淹没（只看距离不看语义）”**或者反过来**“内容内积淹没位置绳子（位置感彻底丢失）”**的训练崩溃！

**最有力的侧面铁证**：
你看仅有的两家跟进抄了 MLA 的大厂——**月之暗面的 `Kimi-K3`** 和 **智谱的 `GLM-5.3-Flash`**——他们在把上下文拉到 1M 的时候干了同一件怪事：**两家都不约而同地把 MLA 主注意力里那根 `64` 维的 RoPE 位置绳子给直接剪断了（设 `qk_rope_head_dim: 0` / `NoPE`）**，改成靠前面 3/4 的 `KDA` 线性注意力层去隐式记位置！连抄 MLA 最积极的两家都在 1M 长文上把 MLA 的解耦 RoPE 给扔了，足以说明那根单头 64 维 RoPE 绳子在超长上下文训练里有多难伺候。

## 四、暗坑三：推理端变成一个 `576` 维的畸形大头，离开手搓专用内核换张卡就瘸

就算熬过了训练关，到了推理部署阶段，MLA 还会给基础设施团队出一道大难题：

- **标准 `GQA` 是全行业硬件的“通用标准件”**：
  像 `MiniMax-M3.1`、`Qwen3.8` 或 `MiMo-V2.6` 用的 GQA，头维度是标准的 `128` 维（或 `64` 维），键值头是 2、4 或 8 个。无论你底层跑的是英伟达的 H800、B200、消费级 4090/5090，还是 AMD 的 MI300X/9070XT、华为昇腾、海光，任何现成的 `FlashAttention-2/3`、vLLM、SGLang 算子库拿过来直接就是满速，不需要改一行底层汇编。
- **而 `MLA` 矩阵吸收后是一个 `head_dim = 576`（K 为 576 维、V 为 512 维）的非对称怪胎**：
  在 GPU 的寄存器文件（Register File）和共享内存（Shared Memory）切分里，`128` 维是刚好卡在单个 Warp 寄存器容量甜点上的黄金尺寸；一旦单头维度暴涨到 **`576` 维**（而且 K 是 576 维、V 是 512 维，连 K 和 V 的宽度都不一样！），直接套用标准 FlashAttention 会导致寄存器严重溢出到 Local Memory，速度比不压缩还慢！
  为了跑满 `576` 维的 MLA，DeepSeek 是靠自家天下无双的底层算子团队，针对 Hopper（`sm_90`）和 Blackwell（`sm_100`）的张量核指令一针一线手搓出了 **`FlashMLA`**。
  但其他厂商没有这支算子铁军，或者需要适配多种硬件：
  - 比如**智谱 `GLM-5.2 / 5.3`** 为了在华为昇腾等国产卡的片上缓存里塞下 MLA，被迫打破 DeepSeek 的 512 维规格，自己砍半重训了一版 **`MLA-256`**；
  - 比如 **MiniMax** 在这次 `MSA` 论文（`arXiv:2606.13392`）第 1 节里专门写了一句意味深长的话：*“enabling efficient execution across a wider range of GPU architectures while relaxing the head-dimension constraints imposed by prior designs（在更广泛的 GPU 架构上高效执行，同时摆脱了此前设计强加的头维度约束）”*——这句“摆脱此前设计的头维度约束”，指着鼻子说的就是 DeepSeek MLA 那个让异构硬件头疼不已的 `576` 维畸形头宽！

---

## 五、小结：三种活法，各算各的账

把这三层暗坑摆在桌面上，现在再看国内各家为什么在 MLA 上分道扬镳，逻辑就严丝合缝了：

1. **DeepSeek 本尊**：既有顶级的预训练数值调校功底（驯服单头 64 维解耦 RoPE），又有顶级的底层 PTX/SASS 算子团队（手搓 `FlashMLA` + `DeepGEMM`），还得扛住全球几千万真实用户的高并发廉价 API 洪峰——所以它一步步从 `MLA` 推到 `CSA/HCA` 再推到 `< 1 GB` 的 `CSA2`，把静态 KV 缓存压到了物理极限；
2. **Kimi 与智谱（半跟进派）**：看中了 MLA 省缓存的红利，但为了绕开解耦 RoPE 在 1M 长文下的训练坑和异构芯片寄存器瓶颈，要么在 Flash 上用 3/4 的 KDA 线性层替掉 RoPE（搞主注意力 NoPE），要么把 512 维砍半成 `MLA-256` 迁就国产算力；
3. **阿里 Qwen、小米 MiMo 与 MiniMax（GQA 保守派）**：不想在预训练阶段背负 MLA 双倍展开的训练减速与 RoPE 失衡风险，也不想被 `576` 维特殊算子绑死硬件兼容性，于是干脆守住最稳妥的标准 `GQA`——其中阿里和小米靠“砍掉 3/4 全局层换 GDN 线性层或滑窗”把 1M KV 缓存控制在 `22~24 GiB` 的可用区间；唯独 `MiniMax-M3.1-Flash` 既不用 MLA、又把 60 层全开成全局稀疏，直接造出了一个单请求吃掉 `67.5 GiB` 显存的吞金兽，只适合单机跑分亮肌肉，真拿去卖高并发 API 纯属给自己挖坑。
