# 从 32.04ms 到 11.86ms：“知道能做到”如何改变搜索深度，以及从 SASS 反汇编里读出的三层信息

**记录时间**：2026-10-27  
**背景**：在 RTX 3080 Laptop（16GB，132W，`sm_86`）移植 DLSS 5（31 层新模型 `Preset 2`）的过程中，`ptx-patcher` 路线经历了从 `v0.1.0`（`15.83 / 24.47 / 32.04 ms`）到 `V2`（`10.19 / 15.27 / 20.36 ms`）、`V2.1`（`6.66 / 9.70 / 12.78 ms`）再到 `V2.2`（**`6.25 / 9.12 / 11.86 ms`**）的连续突破。复盘整个思考过程，最核心的启发有两点：**一是“知道某个性能指标在物理上能做到”对搜索深度的决定性影响；二是真正打开 `cuobjdump` 读底层 SASS 机器码与资源表后，从汇编里直接读出来的三层信息。**

---

## 一、“知道一件事能做到”对思考与搜索深度的影响

在 `v0.1.0` 完成时，我们已经解决了两个最显眼的问题：
1. 用两条 IEEE 754 `f16x2` 硬件代数恒等式（`mul 0x5c005c00` 解包与 `add 0x40004000` 次正规数舍入）替代了上游 48 行整数位运算，把 `.cubin` 体积压缩了 3.5 倍，让 15/15 个 Fatbin 全部开启了 `--opt-level=4`（`O4`），1080p 耗时从 `67.69 ms` 降到了 `32.04 ms`；
2. 抓出了 `fp8_pack_sources` 漏检花括号向量加载（`ld.v4.u32`）导致的多定义误判，消除了天空的 106 条红绿横带。

为什么当时会在 `32.04 ms` 停下来？
因为在没有外部参照的时候，从 `68 ms` 降到 `32 ms` 已经是 2.1 倍的提速，我们很容易默认上游脚本里剩下的部分（比如把 `m16n8k32` 拆成两条 `m16n8k16` 时的跨线程 `shfl.sync` 模板、原版 PTX 函数头部的 `.maxnreg` 声明、以及 `cp.async.bulk` 的降级写法）是“在没有硬件 FP8 的 30 系上必须付出的正常代价”。

而当网友反馈“在 3060 Ti 上有修改版能跑出更高帧率”、我们在本机实测看到 **12 毫秒级** 的延迟确实在物理上存在时，这个信息起到了 **“存在性证明（Existence Proof）”** 的作用：
- 它直接排除了“3080 Laptop 硬件算力只能跑到 32 毫秒”的假设；
- 既然硬件能跑到 12 毫秒，说明在我们的 `v0.1.0` 生成的 SASS 机器码里，必然还藏着占总时间 60% 以上的冗余操作；
- 搜索策略立刻从“接受现有 PTX 转换框架”切换为 **“用 `cuobjdump -sass` 和 `-res-usage` 逐项审查生成的最终机器码，找出所有不干正经数学活的指令”**。

## 二、读了 SASS 反汇编与资源表之后，我们看到了哪三层关键信息？

真正把耗时从 `32.04 ms` 一步步压到 `11.86 ms` 的，是从反汇编和 PTX 源码里直接读出来的三条硬核信息：

### 第一层信息（`V2`：`31.96 ms → 20.36 ms`）：从 `SHFL` 计数与 `LOP3` 掩码里读出“偶奇 K16 原位拆解”

当我们用 `cuobjdump -sass` 统计 `v0.1.0` 的主干代码包（`FB00`～`FB06`）时，看到的第一个反常数字是：
- 全网静态 `SHFL.IDX`（跨线程寄存器洗牌指令）高达 **`81,853` 条**（仅 `FB00` 的一个 `swin_1h_32` 核里就有 `1,399` 条 `SHFL`）。
- 为什么会有这么多 `SHFL`？
  回看原版 PTX 的 `mma.sync.aligned.m16n8k32.row.col.f16.e4m3.e4m3.f16`：每个线程 `t` 的 32 位寄存器 `REG` 装的是同一行（A 矩阵）或同一列（B 矩阵）的 4 个连续 K 元素 `{byte0, byte1, byte2, byte3}`。
  上游 `dlssnr-patcher` 在把它拆成两条 Ampere 的 `m16n8k16`（FP16）时，为了按顺序凑出“前 16 个 K”和“后 16 个 K”，让每个线程去跟相邻线程做 `shfl.sync.idx.b32` 交换数据，再用 `prmt.b32` 拼字节，每次 MMA 还要多占 9 个临时寄存器。

而当我们观察零洗牌 SASS 里的指令序列时，看到了这样几行机器码：
```text
LOP3.LUT R33, R28, 0x007f007f, RZ, 0xc0, !PT ;
LOP3.LUT R34, R28, 0x00800080, RZ, 0xc0, !PT ;
IMAD     R36, R34, 0x2, R33 ;
IMAD.SHL.U32 R12, R36, 0x80, RZ ;
HMUL2    R12, R12, 256, 256 ;
```
读到 `0x007f007f` 和 `0x7f007f00` 这两个掩码的瞬间，背后的数学几何关系就完全透明了：
1. **A 与 B 的线程座位对称性**：在 `m16n8k32` 中，同一个线程 `t` 手里的 `a0..a3` 和 `b0..b1`，其 4 个字节 `{byte0, byte1, byte2, byte3}` 对应的内积下标 `k` 是 **100% 一一对齐** 的；
2. **内积求和交换律**：
   `∑(k=0..31) A[i,k]·B[k,j] = ∑(m=0..15) A[i,2m]·B[2m,j] + ∑(m=0..15) A[i,2m+1]·B[2m+1,j]`
   如果第一条 `m16n8k16` 不算前 16 项，而是算每个线程自己寄存器里的 **偶数字节对 `(byte0, byte2)`**，第二条 `m16n8k16` 算自己寄存器里的 **奇数字节对 `(byte1, byte3)`**，结果在数学上完全相等，但**完全不需要跟邻居线程交换任何数据（`0 次 SHFL`）**！
3. **32 位字内的天然通道对齐（`0 次 PRMT`）**：
   更巧妙的是，在 32 位寄存器 `REG` 中，偶数字节 `byte0`（`bit 0..7`）和 `byte2`（`bit 16..23`）天然就分别落在低 16 位半字和高 16 位半字的低字节上；奇数字节 `byte1`（`bit 8..15`）和 `byte3`（`bit 24..31`）天然就落在高低 16 位半字的高字节上！
   - 对偶数字节对：`sgn * 2 + mag` 把符号位从 bit 7/23 移到 bit 8/24，再整体左移 7 位（`× 0x80`），符号位刚好落到 FP16 的 bit 15/31，7 位指数尾数刚好落到 bit 13..7 / 29..23，乘上 `256.0h`（`0x5c005c00`）即完成双通道解包；
   - 对奇数字节对：符号位本来就在 bit 15/31，只需把 `0x7f007f00` 抠出的数值位右移 1 位与符号位合并，再乘 `256.0h` 即完成解包；
   - 对 `mapped` 的两个 `f16x2` 源寄存器 `low, high`：只需两条单周期 `prmt.b32`（`0x5410` 取偶对、`0x7632` 取奇对）。

将这一思考写进 `build_sm86_dlls.py` 后，全网 `FB00`～`FB06` 的静态 `SHFL` 从 **`81,853` 条直接降到了 `4,517` 条**（减少 **94.5%**，MMA 搬运洗牌归零），1080p 耗时从 `31.96 ms` 降到了 **`20.36 ms`**。

### 第二层信息（`V2.1`：`20.36 ms → 12.78 ms`）：从 `cuobjdump -res-usage` 的 `REG: 168 / STACK: 1032B` 读出 `.maxnreg` 紧箍咒

在 `V2` 消掉跨线程洗牌后，为什么耗时还停在 `20.36 ms`？
我们再去读 `cuobjdump -res-usage` 导出的硬件资源表，看到了一组极其扎眼的数字：
- `FB00`（C32）：`REG: 168, STACK: 240 B`（静态 `709` 条 `LDL` + `702` 条 `STL` 局部显存读写）
- `FB03`（C256）：`REG: 128, STACK: 200 B`（`629` 条 `LDL` + `706` 条 `STL`）
- `FB04`（C512）：`REG: 168, STACK: 1032 B`（**`2,169` 条 `LDL` + `2,201` 条 `STL`**）
- `FB05`（ViT）：`REG: 168, STACK: 480 B`（**`1,027` 条 `LDL` + `1,017` 条 `STL`**）
- `FB06`（Decoder）：`REG: 168, STACK: 168 B`（`117` 条 `LDL` + `110` 条 `STL`）

为什么所有溢出的核函数，寄存器数量都整整齐齐地停在 `168`（或 `128`），宁可往显存栈（`STACK`）里狂写几千次，也不用 169～255 号寄存器？
回查原版 PTX 的 `.entry` 头部声明，立刻找到了根源：
- 英伟达在为 RTX 5090（`sm_120`）编译这套内核时，因为每个 SM 的寄存器池固定是 `65,536` 个，为了凑够 12 个 Warp（384 个线程）的并发驻留（`65536 ÷ 384 = 170.6`，向下按 8 对齐正好是 **`168`**），在 PTX 头部硬编码写死了 `.maxnreg 168`（C256 写死了 `.maxnreg 128` 以凑 16 个 Warp）。
- 在有硬件 FP8 的 5090 上，4 个 FP8 元素只占 1 个寄存器，168 个寄存器完全够用，0 栈溢出；
- 但在 3080（`sm_86`）上，每个 FP8 寄存器都要解包成偶、奇两个 FP16 寄存器（活跃寄存器需求增加一倍）。此时头顶上的 `.maxnreg 168` 强行禁止编译器使用 169～255 号寄存器，把多出来的几十个变量全部逼进了显存局部栈（`LDL / STL`）。

通过单因素扫描验证（仅放宽 `FB04` 就能从 `20.36 ms` 降到 `17.67 ms`，仅放宽 `FB05` 能降到 `15.36 ms`），我们将 `FB00 / 03 / 04 / 05 / 06` 的 `.maxnreg` 放宽到 `255`（保留 `FB01 / 02` 的 `168`），`FB00 / 03 / 06` 的栈溢出直接归零，`FB04 / 05` 的栈读写指令减少 **97%～99%**，三档耗时直接降到了 **720p `6.66 ms` / 900p `9.70 ms` / 1080p `12.78 ms`**（且与 `V2` 严格 `0 bit-diff`）。

### 第三层信息（`V2.2`：`12.78 ms → 11.86 ms`）：审视转换脚本抓出“伪异步 `wait_group 0`”与“35 行拆通道量化”

到 `12.78 ms` 之后，当再次追问“PTX 路线还有没有得优化？”时，我们不再只看 MMA 指令，而是把整个 PTX 转换流水线（`dlssnr_patcher.py` 与 `build_sm86_dlls.py`）里的其余替换规则挨个过了一遍筛子，又抓出了两处之前被忽略的细节：

1. **`FB04 / 05 / 06` 里 316 处 `cp.async.bulk` 被写成了“当场同步死等”**：
   - 原版 PTX 在 `FB04`（104 处）、`FB05`（208 处）、`FB06`（4 处）里使用了异步大块拷贝 `cp.async.bulk ... [barrier]`，在发出拷贝指令到真正执行 `mbarrier.try_wait` 之间，隔着 **273 到 841 条** 矩阵乘与算术指令，目的是让“后台显存搬运”与“前台矩阵计算”并行重叠。
   - 但上游 `dlssnr_patcher.py` 在把 `cp.async.bulk` 替换为 Ampere 的 `cp.async.cg.shared.global` 时，在发出拷贝的下一行直接写死了 `cp.async.commit_group; cp.async.wait_group 0;`，把异步预取变成了当场同步阻塞等待！
   - 我们将其改为 Ampere 原生支持的 **`cp.async.mbarrier.arrive.shared::cta.b64 [barrier];`**，直接将异步拷贝绑定到原版 `mbarrier` 状态机上，恢复了真正的计算与访存重叠。
2. **全网 `8,944` 处 `FP16x2 → E4M3x2` 打包从 29～35 行拆通道版瘦身为 20 行 SWAR 双通道并行版**：
   - 统计发现经过 `mapped` 过滤后，`FB00`～`FB06` 里仍有 **`8,944` 处** `cvt.rn.satfinite.e4m3x2.f16x2`。
   - 原本的 `fast_half_pair_to_fp8_lines` 把高低两个半字拆成 `lo` 和 `hi` 两个标量，分别跑两次 `bfe`、两次 `sub`、两次 `min`、两条 `setp` 谓词和两条 `selp`（占 8 个 `.b32` + 2 个 `.pred` 寄存器，展开近 30 行）。
   - 改为双通道并行 SWAR 算法（用 `min.f16x2 0x5f005f00` 双通道同时饱和到 `448.0`、双通道同时加偏置舍入、`set.lt.u32.f16x2 0x24002400` 生成掩码配合单条 `lop3.b32` 选择次正规数/正规数）后，寄存器降至 5 个 `.b32`、**0 个 `.pred` 谓词寄存器**，3,355 万组双通道测试 100% 0 误差。

这两项合入 `V2.2` 后，72 次正反 ABBA 实测与 `V2.1` **100% 严格 `0 bit-diff`**，三档耗时再降 **6.8%～7.3%**：
- **720p（`1280×720`）**：**`6.25 ms`**（~160 FPS）
- **900p（`1600×900`）**：**`9.12 ms`**（~110 FPS）
- **1080p（`1920×1080`）**：**`11.86 ms`**（~84.3 FPS）

## 三、总结：三条实打实的工程体会

1. **“知道能做到”是启动深水区搜索的钥匙**：当知道某个性能数字在物理上可达时，就不会轻易替现有的耗时找合理化借口，而会逼着自己去翻底层的机器码账本。
2. **GPU 优化的核心不是“少算乘法”，而是“少搬数据”**：
   - `V2`（省 11.6 ms）是用内积交换律（偶奇分组），消除了**线程与线程之间** 7.7 万次 `SHFL` 数据交换；
   - `V2.1`（省 7.6 ms）是解开 `.maxnreg 168` 限制，消除了**寄存器与显存栈之间**几千次 `LDL / STL` 数据往返；
   - `V2.2`（省 0.9 ms）是用 `cp.async.mbarrier` 和双通道 SWAR，消除了**等数据搬运的空转时间**与拆通道冗余指令。
3. **一切瓶颈都在 `cuobjdump` 的真实机器码里**：不看 PTX 表象，直接看最终编译出来的 SASS 指令计数（`SHFL`、`LDL`、`STL`、`HMMA`）和寄存器/栈占用表（`REG`、`STACK`），哪里异常改哪里，一抓一个准。
