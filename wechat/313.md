◆ 开篇：一个我判断错了的问题

━━━━━━━━━━━━━━━━━━━━

309 期（ https://mp.weixin.qq.com/s/mvUDHC6kLqqCKIag8VIERA ）讲的是 HLSL 那一版：在 D3D12 里钩住 FSR 的调用，用微软还在预览的 Shader Model 6.10 矩阵接口调 AMD 的矩阵指令。写那期的时候我们聊到一个问题：另一条闭源的移植路线走的是 HIP，AMD 自家的计算接口，不经过微软那层。**换成 HIP 会不会更快？**

当时 Claude 给的判断是：不值得。理由有三条。我们的耗时几乎全在矩阵乘之后的逐元素尾巴上，不在矩阵乘本身；换接口拿不到新算力；而且要丢掉整条 D3D12 的游戏接入链，跨接口搬一次数据，省下的可能还回去一半。

我说：万一能搞定呢。就开了个分支让它试。

三天之后的结果：**同条件下，HIP 版处理一帧约 15.5 毫秒，HLSL 版约 16.8 毫秒，耗时少了约 7.5%。** 后半程这些优化，测试输出和优化前的 HIP 基准逐位一致。发布包也摆脱了预览版 DirectX 组件的依赖，900p 游戏实测到了 52 帧。

中间曾经连续几版都是 30 帧，差点以为优化到头了。后来发现，那个 30 还有另一个原因。

原来的判断没全错，但把“眼前的瓶颈”当成了“已经没有空间”，也低估了换一套工具之后能看见的东西。这期讲这三天。

从 9 月 14 日深夜到 17 日清晨，两个 AI 轮班：前半程是 Codex，16 日早上六点它的额度用尽，Claude 接手。我做的事跟 304 期（ https://mp.weixin.qq.com/s/v3_KM8zqCg8bp01GglFvxQ ）一样：进游戏看画面、看帧率、在岔路口拍板。

◆ 第一章：HIP 是什么，跟上一条路差在哪

━━━━━━━━━━━━━━━━━━━━

先把两条路摆在一起。

**HLSL 那条路**：用高级着色器语言（High-Level Shading Language，HLSL）写计算，用微软的 DirectX 着色器编译器（DirectX Shader Compiler，DXC）编译，在 Direct3D 12（D3D12）里运行。矩阵乘走着色器模型（Shader Model）6.10 的线性代数接口。我们当时使用的这套矩阵功能仍在预览：要装预览版驱动、预览版 Agility SDK、打开系统的开发者模式。矩阵指令出厂就在卡里，只是“在 D3D12 里用标准写法调它”这件事还没转正。

**HIP 这条路**：异构计算可移植接口（Heterogeneous-compute Interface for Portability，HIP）是 AMD 提供的 GPU 计算接口，写法和 CUDA 很接近。我们用基于 LLVM/Clang 的 AMD 编译工具，直接生成 RX 9070 XT 能执行的机器码；矩阵乘通过内置函数调用波级矩阵乘加指令（Wave Matrix Multiply-Accumulate，WMMA）。网络计算这段不再经过微软的矩阵接口。

后面会反复出现三个词：**核（kernel）是交给 GPU 执行的一段程序；发射（launch）是把这段程序派出去；wave 是一起执行指令的一组线程，在这里是 32 个，组里每个位置叫 lane。** 至于 C32、C64、C128，只是在说一处特征有多少个通道——同一个像素位置带着 32、64 或 128 个数。先认得这些名字，后面就能跟着看。

────────────────────

💡 不装开发工具包，怎么把 HIP 代码编出来

常规开发可以安装 HIP 软件开发工具包（Software Development Kit，SDK）。不过 Codex 在这台机器上找到了一条更轻的路：**显卡驱动的安装目录里，已经有能编译 HIP 代码的库。**

这里容易把两件事混在一起：我们怎么编程序，玩家怎么运行程序。

D3D12 游戏通常带着着色器的中间码，叫 DirectX 中间语言（DirectX Intermediate Language，DXIL）。驱动到了玩家机器上，再把它变成适合这张显卡的机器码。很多游戏启动时的“正在编译着色器”，就包含这类工作。

GPU 程序也可以提前编成机器码，只是要指定目标架构。这次我们只盯着 RX 9070 XT，它的架构代号是 `gfx1201`，正好可以提前编好再打包。

**我们调用的是 `amd_comgr_3.dll`，也就是代码对象管理器（Code Object Manager，COMGR）。** 装了 AMD 驱动的机器上，它就躺在 `System32` 里。

这个 DLL 值得多说一句：**它不是什么小工具，是一整个 Clang。** AMD 的 GPU 编译器是拿开源的 LLVM/Clang 改的——前端连同 AMD 自己的后端一起编进了这个库。查一下版本，报的是 COMGR 3.0，里面那个 Clang 是 21 版。换句话说，**你机器上其实一直装着一个能编 C++ 的编译器，只是它没有命令行，只能用函数调用的方式使唤。** 驱动平时用它编游戏的着色器，我们换个入口，把自己写的 HIP 源码喂进去。

于是写一个小程序。**平时调用一个库，是 include 头文件、链接 lib；这里两样都没有**——头文件在 SDK 里，而我们不装 SDK。只能用最原始的办法：运行时把 DLL 加载进来，按函数名一个个把地址要出来，自己声明一遍每个函数长什么样，再当普通函数调用。

```cpp
// 从 System32 加载驱动自带的编译器
static HMODULE load(const wchar_t* n) {
  wchar_t dir[MAX_PATH]; GetSystemDirectoryW(dir, MAX_PATH);
  return LoadLibraryW((std::wstring(dir) + L"\\" + n).c_str());
}
HMODULE h = load(L"amd_comgr_3.dll");

// 先问它认不认识这张卡
for (size_t i = 0; i < count; i++) {
  get_isa_name(i, &n);
  if (n && strstr(n, "gfx1201")) found = true;   // RX 9070 XT 的架构代号
}

// 源码塞进去，说清语言是 HIP、目标是 gfx1201，编
action_info_set_language(action, 3);                       // 3 = HIP
action_info_set_isa_name(action, "amdgcn-amd-amdhsa--gfx1201");
std::vector<const char*> opts = {"-O3", "-nogpuinc", "-nogpulib"};
do_action(2, action, input, result);                       // 2 = 编译

// 取出编好的代码对象
action_data_count(result, 8, &count);                      // 8 = 可执行数据
```

代码里那些裸数字（`language=3`、`do_action(2,...)`、`kind=8`）看着很怪，**它们本来是 SDK 头文件里的枚举名**——不装 SDK 就没有那些头文件，只能照着文档把数值抄进来自己定义一份。整个项目跟 HIP 打交道的地方都是这个路数：运行时那个 `amdhip64_7.dll` 也是驱动自带的，函数签名自己声明一遍，动态加载。

最后得到的文件扩展名是 `.hsaco`，里面已经装着这张卡能执行的机器码。**我们负责把它编好，玩家拿到的是成品。** 运行时由驱动配套的 `amdhip64_7.dll` 加载这些文件，再把计算派到显卡上。

所以“不装 SDK”有两层意思：开发这边可以借驱动配套的编译库干活；玩家那边本来就不用编，装有 HIP 7 运行库的兼容驱动即可。后来的正式驱动用户反馈也确认这条路能跑，不必再跟着我们折腾预览版 DirectX 环境。

这个收获，比省下的那一毫秒更实在。

────────────────────

然后是第三条理由里那个“丢掉接入链”的问题。实际做法是：**保留游戏侧的 D3D12 接入，只把网络计算换成 HIP。**

两边怎么交接？先在 D3D12 里建一块可共享的显存，取得系统句柄，再让 HIP 凭这个句柄把它映射成自己能访问的指针。**名字不同，指向的是同一块显存。** 输入仍要从原来的缓冲区搬到共享区，但这次搬运就在 GPU 上，不必先绕回 CPU 再上传。

```cpp
// D3D12 侧：建一块可共享的缓冲区，要一个系统句柄
device->CreateCommittedResource(&hp, D3D12_HEAP_FLAG_SHARED, &rd, ..., &s.resource);
device->CreateSharedHandle(s.resource, nullptr, GENERIC_ALL, nullptr, &s.handle);

// HIP 侧：凭这个句柄把同一块显存导入，拿到能直接用的指针
md.type = 5;                                  // 5 = D3D12 资源
md.handle.win32.handle = s.handle;
hipImportExternalMemory(&s.imported, &md);
hipExternalMemoryGetMappedBuffer(&s.mapped, s.imported, &bd);
```

（`type = 5` 又是一个手抄的枚举值，来历同上。）

再解决“谁先做、谁后做”。用的是共享栅栏（fence）：一个两边都能读写的进度计数。

```cpp
queue->Signal(fence, ++value);                    // D3D12：输入写完了，进度 +1
hipWaitExternalSemaphoresAsync(&semaphore, ...);  // HIP：等到这个数，才开工
network->Enqueue(input.mapped, ..., output.mapped, seed);   // 跑网络
hipSignalExternalSemaphoresAsync(&semaphore, ...);// HIP：算完了，进度再 +1
queue->Wait(fence, value);                        // D3D12：等到这个数，才往下走
```

翻成大白话就是：

```text
D3D12：把输入放好，进度记为 1
HIP：等到 1，开始跑网络；算完把进度记为 2
D3D12：等到 2，接着做后处理和画面写回
```

下一帧继续用 3、4，计数往前走。**共享缓冲区解决“东西放哪”，共享栅栏解决“什么时候可以碰”。** 后面第二次进游戏的黑屏，恰恰就是有一处没守住这个先后顺序。

截帧、编码、时序采样、解码、写回这些部分都沿用原来的系统，再补两边的衔接。后来拿同一份输入做隔离对照，完整流水线比单跑 HIP 网络多约 0.13 到 0.28 毫秒。桥接连同前后处理的这点开销，解释不了当时两后端相差的八毫秒。

**我当初错在把“换计算接口”想成了“整套接入推倒重来”。** 实际换的是中间一段。

HIP 带来的另一个变化，是能更直接地摆弄这段计算：指定舍入指令、安排共享内存、查看编译后的汇编。这里的共享内存叫本地数据共享区（Local Data Share，LDS），是同一工作组里的线程临时交换数据的地方，比把中间结果写回显存再读更近。

但更直接不等于自动更快。后面三天，就是在学这些自由该怎么用。

◆ 第二章：第一夜，先让它对

━━━━━━━━━━━━━━━━━━━━

第一夜，第一个里程碑：HIP 的 8 位浮点数（Floating Point 8，FP8）矩阵乘和 HLSL 的小矩阵测试对上了。接着是完整的 512×512 参考图，786432 个 RGB 浮点数，和原版参考结果一位不差。

然后扩到 900p。**参考路径跑一帧，秒表量出来还是 576 毫秒，半秒多才出图。** 当时 HLSL 已经有十几毫秒的快版，而 HIP 还在走逐值复现的参考版，上传、回读也算在这个 576 里。能跑对了，离能玩还远。

这里的“对”有前后两把尺子。先做参考版，跟原版结果比；再接快速版，保留既有的近似计算，然后看每次优化有没有改变这个快速版的输出。**后面说的“逐位一致”，就是优化前后结果不变，像搬家只换摆法，东西一件不少。** HIP 与 HLSL 的快速版之间仍有数值差异。

后期固定下来的是三组回归：连续跑 40 帧；每 8 帧清空历史、总共跑 24 帧；再换随机种子和历史输入。每组结果算一个哈希值（hash），相当于给整份输出按一个指纹。指纹变了，就去找哪一步变了。中途没有收益的实验也会撤回，三天里撤回的比留下的多。

第一夜有一次差点误判。Codex 把软件写的半精度舍入函数换成普通 `_Float16` 转换，512 参考图上 779563 个值变了。但把转换单独拿出来测，一百多万组输入又全对得上。**单独那一下转换没错，放回整段表达式，编译器的优化却改变了结果。** 最后用内联汇编明确写出“先转半精度，再转回来”，整网才重新对上。

────────────────────

💡 换了一套编译器，逐位一致怎么保住

两个数相乘再相加，中间先舍入一次，和一路算完最后才舍入，末位可能不同。网络有很多层，这个差别不能随手忽略。

HLSL 那版摸出来的是一套动作顺序：哪里向零截断，哪里取最近的可表示值，哪里先舍入再继续算。**换成 HIP，要把这些动作重新交代给另一套编译器。**

例如“从 32 位浮点转成 16 位，再转回来”，那个数最后仍放在 32 位变量里，但多出来的精度已经被丢掉了。就像先把金额取到分，再写成四位小数：12.34 写成 12.3400，被舍掉的部分也不会回来。

原来软件要分情况处理大小、符号、溢出等情形；HIP 可以直接指定两条硬件指令：

```cpp
DEV float Hrtz(float x){
  uint h; float result;
  asm("v_cvt_pkrtz_f16_f32 %0, %1, %1" : "=v"(h) : "v"(x));
  asm("v_cvt_f32_f16 %0, %1"           : "=v"(result) : "v"(h));
  return result;
}
```

不用记这串指令。第一行做 32 位到 16 位的转换，`rtz` 是 round toward zero，意思是向零截断；第二行把结果转回 32 位。`DEV` 是项目自己的宏，标记这是在 GPU 上执行的函数。

**这里直接指定了那两下动作，而不是只告诉编译器“我要一个半精度结果”。** 编译器仍会安排周围代码，但这次就不能把指定的转换随手替换成另一种算式。

整帧的 hash 是最后一道门，前面还有单个核的对照：换不同大小、不同正负值的输入，逐个数比。后来做融合时，光 C128 就测了 72 组、C256 测了 96 组。

我不需要会写这些指令，但这件事得知道：**公式看着一样，不保证机器算出来每一位都一样。**

◆ 第三章：第二天，70 到 29，以及第一次进游戏

━━━━━━━━━━━━━━━━━━━━

第二天一整天是 Codex 的。它做的事和 304 期那两天一个路数：**每次改一处，量一次，核对输出，再写进日志。** 真有收益的候选补齐验证，没收益的撤回。

注意力计算先从输入生成三份数据：查询（Query，Q）、键（Key，K）、值（Value，V），日志里合写成 QKV。前馈（Feed-Forward Network，FFN）则是另一段计算，先把通道展开，再收回去。下面这些优化主要就在这两段之间，减少来回搬运：

| 改动 | 省了 | 为什么 |
|---|---|---|
| 权重在加载时预先打包成 FP8 | 5.2 毫秒 | 原来每帧都把浮点权重转一遍 |
| 截断舍入换硬件指令 | 4.2 毫秒 | 让硬件直接做，省掉软件模拟转换 |
| 多头块的中间张量直接写 FP8 字节 | 3.5 毫秒 | 不再写浮点再读回来打包 |
| 前馈隐藏层字节化 | 3.6 毫秒 | 同上 |
| 生成注意力的 Q、K、V，再做归一化：合成一个核 | 2.5 毫秒 | 算完接着用，省一次中间结果写回和一次发射 |
| C32 块的权重按 4 字节一次读 | 3.1 毫秒 | 原来逐字节读 |

傍晚 40 毫秒，夜里 28.8 毫秒。一天里 900p 从 70 压到 29，跟 304 期第一天从 1.47 秒压到 0.47 秒是同一种节奏：**这一阶段的大收益，主要来自少搬、少转换、少写一份中间结果。**

中间几次进游戏，接连碰到三个坎。

**早上第一次装进《剑星》，显示 INIT FAILED。** 查下来 HIP 初始化其实成功了，是桥接那一步判断“输入纹理是不是在同一个设备上”用了指针相等，而 ReShade 把 D3D12 设备包了一层，指针地址不一样。原来的代码里有一个专门解这层包装的函数，桥接没用它。改了。

**第二次进去，画面上人物变成黑色轮廓。** 不用上一帧的历史数据，照样黑。先关掉异步提交，改成等这一帧做完再继续，画面正常了。

根因到晚上才找到：GPU 还在用上一份输入，CPU 已经把记录输入位置的描述符改成下一份了。就像工人还照着纸条取货，纸条却被人换掉。修法是先等旧任务完成，再改那张“纸条”，之后才能重新打开异步。

**第三次，17 帧。** 我记得 HLSL 版 1080p 最好的时候 37 帧，这是 900p 才 17。晚上八点半异步提交修好，24 帧；九点半 34 毫秒的版本，26 到 27 帧；十点半 28.8 毫秒，30 帧。

随后修正测试程序的读回节奏，同条件对照落在 HLSL 16.7 对 HIP 26.3，差 9.6 毫秒。还有得追。

◆ 第四章：第三天，凭直觉改不动了

━━━━━━━━━━━━━━━━━━━━

第三天早上六点 Codex 额度用尽，Claude 接手。起点 HLSL 16.8 对 HIP 19.3。

到交班时，Codex 已经把差距从 9.6 压到 2.5，路数还是融合和预打包。但这一天白天的十几处改动，**几乎全是空的**：中间数据存得更紧凑，反而慢 0.1 毫秒；合并计算，少等两次同步，反而慢 0.11；换几种输入格式，差异小得分不出是不是测量波动。

后来还试过减少每个线程占用的寄存器，让更多线程能同时驻留。数字看着更健康，整帧却慢了 0.64 毫秒。**少搬数据、少同步、多安排线程——单独听都很有道理，放进这段程序却不一定快。**

这一天的日志里有一句总结：

> 别按自己的直觉猜瓶颈，把两边同一个核的源码并排逐段对，找“做同一件事但做法不同”的段。

**让方向重新变清楚的，是两次有收益的对照。** 早上把网络最深处的视觉 Transformer（Vision Transformer，ViT）注意力三个核合成一个，省 0.11 毫秒。晚上把两边的 C32 融合核并排看，发现 HIP 反复在算“这个数该去哪里拿”，而 HLSL 让一部分线程先算好地址，再广播给同组线程。照着减少重复算地址，省 0.14 毫秒。

然后顺着“只换打包不动结构”这一条，晚上又做了三处：C512 块的通道混合核权重预打包成半精度（half），下采样投影权重预打包，解码器上采样权重预打包，合计 0.4 毫秒。**这几个核原本每帧都在逐个读 32 位浮点权重，再转成计算要用的格式。权重没变，却每帧重新转一遍。现在加载时提前转好，核里直接成组读取。** 乘加的顺序不动，重复劳动少了。

这一天还发现了一个测量陷阱。

────────────────────

💡 隔离测试为什么骗人

这天上午，反复运行同一个 C64 块，测出来 HIP 比 HLSL 快；放回完整网络，HIP 这一家族却更慢。

原来隔离测试把工作集反复留在缓存里，跟整帧不断换数据不一样；对照工具挑的输入输出格式也未必就是生产路径。**单独练一段跑得快，接进全程未必还快。**

第一次换尺子：两边都跳过同一批块，看整帧少了多少时间。后来又发现 HLSL 的跳过并非零成本，还得拷贝数据，数字又被压低了。

最后换成更贴近原现场的办法：**输入不变，让指定的一段多做一遍，看整帧多了多少时间。** 好比想知道一道工序多费时，就在原生产线上加做一次。这样逐段对照，才发现 HIP 并非每一处都慢：有的家族已经领先，差距在另外几处。

还有一个更隐蔽的坑：HLSL 的基线从 18.8 漂到 26.6，一度看着像被 HIP 追平了。查下来，测试程序每帧把输出读回 CPU 扫一遍，这段时间不在计时区间内，但 GPU 等得闲下来了，频率也降了。把读回改成只在首尾做，保持连续负载，HLSL 又回到约 16.7 毫秒。

**计时器外面的事，也能改计时器里面的数。** 所以测速度和检查全部输出，后来分开跑。

────────────────────

这天夜里，HIP 18.69，HLSL 16.8，差 1.89。我进游戏看，还是 30 帧。

◆ 第五章：最后一夜，追平，以及那个 30 帧

━━━━━━━━━━━━━━━━━━━━

17 日零点到两点，Claude 顺着另一份东西查：**HLSL 那版实际启用的配置文件。** 之前试过的代码很多，只有这份配置能说明游戏里究竟开了哪些优化。拿着它，一条条问：“这个融合，HIP 做了没有？”

HLSL 版有一个开关叫 `C32_EPILOGUE`，意思是 C32 块尾巴上的两件事（RGB 输出头、主干和下采样的收尾）都合进了块的核尾，不写中间结果。HIP 版是写出来再起一个独立的核。照做，两处合计 0.7 毫秒。池化和投影的核形状照 HLSL 重写一遍，0.28。ViT 的两个投影换 HLSL 那种按片段打包的权重布局，0.27。

凌晨一点半，我先在当时的版本里看到了 **47 帧**。随后几项优化继续推进，到接近两点，离线 HIP 16.90，HLSL 16.8，已经只差不到 1%。

此前连续几版进游戏都是 30 帧，我一直以为是网络之外的部分卡住了。日志里甚至算过一笔账：就算追平 HLSL 也只能到 32 帧，剩下 14 毫秒是游戏渲染和编解码。**实际是游戏的渲染目标锁在 30 帧上限，网络快了也显示不出来。** 改成 60，47 帧。

这件事的教训比它看起来大：三个版本的优化收益在游戏里全被一个设置遮住了，两个 AI 和我谁都没去查那个上限。

◆ 第六章：凌晨两点，读汇编

━━━━━━━━━━━━━━━━━━━━

追平之后我说了一句：肯定是尽量超过之前的性能啊，毕竟换了一套更直接的接口。

目标从打平改成赢。

这套环境下，现成的 HIP 计时工具帮不上忙：事件时间戳居然能返回负数。Claude 换了个办法，**把编译器吐出来的 `.hsaco.s` 汇编文件拷回来，看 GPU 究竟拿到了什么指令。**

源码是我们让它干什么，汇编是编译器安排它怎么干。前面改了很多源码，到了这里，终于直接看安排。

汇编文件还是从第一章那个 COMGR 编译库取的：生成中间码之后，多调用一次“输出汇编”的动作，保存成 `.s` 文件。随后用 Python 按核名分段，数跳转，找哪些地方读完内存立刻停下来等。

**汇编不会直接告诉我们哪一行花了多少时间，但能让怀疑有个落点。** 看到一种可疑写法，改掉，再用同批新旧版交错测试。这种测法按 A、B、B、A 的顺序跑，叫 ABBA，免得把显卡一会儿快一会儿慢误当成代码的收益。

C32 链核扫出来：静态 4731 条指令，其中 128 条分支。对照 HLSL 那边同一个核（9 月 11 号用 AMD 的 Radeon GPU 性能分析器（Radeon GPU Profiler，RGP）抓过一次）是 7321 条。**光数指令解释不了快慢。** 接着看这些指令在什么地方让线程停下来，陆续找到了三种问题。

────────────────────

**第一种，饱和转换函数被编成了分支。**

网络里到处是一个叫 F() 的函数：把浮点数压到 FP8 能表示的范围（±448）再转回来。原来的写法是这样——

```cpp
DEV float F(float x){
  uint b = bits(x), a = b & 0x7fffffffu;
  if (a == 0) return 0.f;                                  // 零，早退
  if (a >= 0x43e00000u) return value((b & 0x80000000u) | 0x43e00000u);  // 超出范围，饱和
  int packed = __builtin_amdgcn_cvt_pk_fp8_f32(x, 0.f, 0, false);
  return __builtin_amdgcn_cvt_f32_fp8(packed, 0);
}
```

（`0x43e00000` 就是 448.0 的二进制写法。这里的 FP8 格式叫 E4M3，4 位指数、3 位尾数，加上 1 位符号；用到的版本最大有限值是 448。`DEV` 是这个项目自己定义的宏，意思是“设备端函数、强制内联”。）

看着很正常：零直接返回，太大的数夹住，其余才转换。但这段代码被编成了带跳转的分支。一个 wave 里 32 个线程一起执行，碰上不同线程要走不同路径时，就得先让一部分线程工作、另一部分暂停，再换过来。这叫发散分支。

**麻烦不只是 if 本身，还包括管理“现在轮到哪些线程”的动作。** 汇编里，一处 F() 连同判断、掩码切换和转换，能展开成大约五十条指令。

而 F() 在这个核里出现多少次？输入分段每个 token 一次（16 次），投影输出每个元素一次（16 次）。**光这一个函数就占了整个核静态指令的四成。**

改法是把两个 if 都变成没有跳转的算术：

```cpp
DEV float F(float x){
  uint a = bits(x) & 0x7fffffffu;
  float c = __builtin_fminf(__builtin_fmaxf(x, -448.f), 448.f);   // 夹住，没有分支
  float r = __builtin_amdgcn_cvt_f32_fp8(
              __builtin_amdgcn_cvt_pk_fp8_f32(c, 0.f, 0, false), 0);
  return a == 0 ? 0.f : r;                                        // 一条条件选择指令
}
```

这次编译出来，夹紧和最后的三元运算走的是数值运算与条件选择，没有跳转。**每个线程直接算，再选该留哪个值，不必为了这两个条件分头走。**

在这条路径的正常输入上，零仍然变成正零，超过范围仍然夹到 ±448，转换结果不变。**去掉 if，不是把检查忘了，是换一种方式得到需要的结果。**

────────────────────

**第二种，读取串行化。**

这里的 token 可以先理解成一份像素位置上的特征。一组线程要依次搬 16 份输入，每份有 32 个通道。原代码把三件事挤在一个循环里：判断地址有效、读取、转换。

```cpp
for (uint j = 0; j < 16; j++) {
  int src = __builtin_amdgcn_readlane(mine, j);   // 问第 j 号 lane 要地址
  if (src >= 0) {                                 // ← 问题就出在这个 if
    v = raw_input[uint(src) + l];                 // 读
    ...                                           // 转换
  }
  packed[row*36 + l] = fp8(v);                    // 存
}
```

（`readlane` 是 GPU 上的一种广播：16 个 lane 各自先算好“我负责的那份输入在显存哪个位置”，然后轮流把地址喊给全组，32 个线程一起去搬那一行。）

**读取被关在 `if` 里面，编译器就不敢把它提前。** 编出来的安排成了"读一个，等一个，处理完再读下一个"，汇编里能看到 16 组读取后各自紧跟一条等待。显卡算术很快，从显存等数据却要花几百个周期——这里把等待串成了一长排。

HLSL 那边的对应写法，能把这批读取先发出去，让多个请求一起在路上。

HIP 也改成两趟：

```cpp
// 第一趟：只管发，索引不带分支（越界的就读个占位）
float lv[16]; int srcs[16];
for (uint j = 0; j < 16; j++) {
  int src = __builtin_amdgcn_readlane(mine, j);
  srcs[j] = src;
  uint idx = src >= 0 ? uint(src) : 0u;    // ← 越界就读第 0 个，反正等下丢掉
  lv[j] = raw_input[idx + l];
}
// 第二趟：统一转换，这时候才把占位值挑出去
for (uint j = 0; j < 16; j++) {
  float c = F(lv[j]);
  float v = srcs[j] >= 0 ? c : 0.f;        // ← 占位值在这里归零
  packed[row*36 + l] = fp8(v);
}
```

关键在那个 `idx = src >= 0 ? uint(src) : 0u`。原来是“越界就跳过读取”，现在是“也读，但读一个确定安全的位置，最后丢掉”。**这样读取动作不用躲在分支后面。**

**多做几次没用的读，反而让整段更快。** 因为省下的是串行等待，不是字节数。编译后的汇编里确实变成了连续读取，再按需要逐个等结果，之前排成一条线的等待重叠起来了。

这两刀合起来：C32 核的分支从 128 条降到 60 条，静态指令 4731 降到 4036。**离线 HIP 16.19，HLSL 16.8，第一次反超。** 单独只做第一刀是 0.19 毫秒，两刀一起是 0.68——两项配合，比只减少分支管用得多。

────────────────────

**第三种，别名重载。**

投影的尾巴上，每个输出都要加上按比例缩放的残差。缩放系数只跟列号有关，原来却是在循环里现读。下面省略了无关的索引：

```cpp
for (...16 个输出...) {
  float prod = residual * w[8193 + col + rc()];   // 每次重新读取权重
  float v = Hrtz(acc[e] + prod);
  out[i] = ...;                                    // ← 中间夹着这个写
}
```

代码注释里那句诊断写得很直白：**这两次读中间夹着一个 `out[]` 的写，编译器没法断定写进去的地址不会碰到 `w[]`，只好每个输出都重新读一次**——汇编里就是同一个偏移量 `offset:32772` 反复出现八次，每次后面紧跟一条等待。这里的“别名”，就是两个不同名字的指针可能指着同一块内存。我们知道权重和输出分开存，编译器在这段代码里却没能确认，只好保守地重读。

改法很直接：循环外面先把这两个值读进寄存器，也就是线程手边存临时数的小空间。

```cpp
const float pw0 = w[8193 + rc()], pw1 = w[8193 + 16 + rc()];
// 循环里：
float prod = residual * (col == 0 ? pw0 : pw1);
```

省 0.05 毫秒。后来在别的核里照着找，也找到了类似重读，但改完未必省时间。**汇编负责指出哪里值得试，最后仍得跑一遍才知道值不值。**

────────────────────

💡 静态指令数不是钱，旧的空结果也不是永久的

顺着汇编继续查，还找到一个反例：多头块里有一段软件截断函数，展开后带出大量分支。换成硬件截断，整个核从 6936 条静态指令、435 条分支，降到 1575 条指令、35 条分支。时间却只省了 0.02 毫秒。

分支跳过的路径本来就不执行，指令少了不等于跑得快。在 C32 那次，收益大的反而是让读取能够重叠。指令数只能帮忙找线索。

另一面：之前没收益的两处改动，后来重测又有用了。一处把输入特征生成（prefix）并进第一个核，省掉整幅中间结果的写回；另一处把残差计算要用的对角矩阵提前打包。核瘦身后再试，一个省 0.27 毫秒，一个省 0.16 毫秒。瓶颈挪了，旧的结论就作废。**一处改动的收益是相对当时的瓶颈说的，不是这处改动本身的属性。**

────────────────────

到凌晨两点半，HIP 约 15.5，HLSL 约 16.8，少了约 1.3 毫秒，也就是约 7.5% 的耗时。三点半我进游戏：**52 帧。**

这一夜主要留下了下面这些改动。表里是各自同批对照的收益；不同批次基线会漂，不能把小数精确相加：

| 改动 | 省下的毫秒数 |
|---|---|
| F() 去分支 + 读取连发 | 0.68 |
| 多头核 q8 去分支 + 硬件截断 | 0.16 |
| 权重先读进寄存器 | 0.05 |
| prefix 内联（前一天判空，重测翻盘） | 0.27 |
| 残差对角权重（前一天判空，重测翻盘） | 0.16 |
| 前馈残差和输入的条件读改无分支 | 0.14 |

这些优化都保住了 HIP 基准输出，三组回归的 hash 没变。

顺便回答开篇那第二条理由。“换接口拿不到新算力”这句是对的，矩阵指令是同一批。**但换了工具链，查看机器指令方便了很多。** HLSL 也能通过 RGP 抓到驱动编译后的代码，我们之前就抓过。HIP 这边则是编译时顺手留下 `.s`，改完马上就能看。这个便利，最后真的换成了速度。

◆ 第七章：收官，还有哪些路试过了

━━━━━━━━━━━━━━━━━━━━

17 日早上六点我说不追了，打包。0.20 版发出去，两个包：游戏内接入的和 Magpie 窗口捕获版。**玩家最能感到的变化，是不必再装预览版 DirectX 环境、开开发者模式，兼容驱动带着 HIP 7 运行库就能跑。**

后面又加了自动选档，按输入窗口大小选择 720p、900p 或 1080p 的内部计算尺寸。实测 900p 52 到 54 帧，1080p 37 到 38 帧。

到了 0.22，还把 900 档的内部工作高度从 1024 行收到了 960 行。游戏输入仍是 900 行，网络为了分块计算会补边，原来补得更宽。这次少算了一部分补边，测试台又省了不到一毫秒。**这一步改变了输出，不属于前面保持 hash 不变的优化。** 它是后来单独做的尺寸取舍。

网络之外的部分也量了一次：游戏内 1080p 前处理 0.49 毫秒、网络 20.8、后处理 0.26。至少在这个场景里，大头还是网络。

最后试过的几条路，也留个印象：

| 路线 | 这次的结果 |
|---|---|
| 把整串任务录成计算图，再用 hipGraph 重放 | 确认重放了，速度没变，CPU 发任务不是当时的主要瓶颈 |
| 权重缓冲区里的空洞不分配物理显存，只保留地址 | 在这版驱动上，多块映射的内核访问失败，没采用 |
| 把整个 C64 块并成一个大核 | 输出一致，速度没变。少一次中间往返也没有兑现成提速 |
| 激活计算改用打包的半精度指令，一次处理两个数 | 反而更慢 |
| 改 ViT 的输入格式和线程分工 | 多次没收益；其中前馈合核更慢，400 个 token 只分出 25 个工作组，难以铺满显卡 |

这些是这次实现里的试验结果。前面已经吃过亏：核改了、瓶颈挪了，今天没用的办法，明天可能又有用。

还有个第三天挖出来的东西，跟网友问的“结构化稀疏”有关。检查多头块的前馈收缩矩阵时，发现它本来就有整齐的分组：**每 32 个输出通道，只用其中 128 个隐藏通道，组外权重全是零。**

比如一段本来要遍历 512 个隐藏通道，实际只有对应的 128 个会贡献结果，另外 384 个一直在乘零。现在加载权重时先确认那些位置确实是零，计算时直接略过。36 个矩阵利用这条规律，省了约 0.9 毫秒，输出不变。

我们没有把小数剪成零，也没调用硬件的稀疏矩阵指令。**只是终于看清了模型本来就没在用哪些位置，不再替它算那些零。**

◆ 收尾

━━━━━━━━━━━━━━━━━━━━

回到开篇那三条理由。

“慢在矩阵乘之外的零碎动作”，这个方向抓到了一部分问题。最后的分支、串行读取、重复转换，都在印证它。但这些零碎动作并没有优化完，换了工具才继续看清。

“换接口拿不到新算力”，硬件确实还是那张卡。我们也换过矩阵指令，比如 C512 的收缩阶段从半精度换到 FP8，拿到了一点收益。更大的进展，是让同一张卡少做重复劳动、少停下来等。HIP 把看汇编这件事变得顺手，才有了最后那一轮。

“要丢掉整条接入链”，这条错得最直接。两边共享显存和进度，原来的接入系统继续用，跨接口衔接的开销也远没有我担心的大。

三天里，我对优化的印象也变了：前半程是在搬数据、换存法、合并计算；追平之前，是逐项补上 HLSL 已经用起来的办法；最后那一毫秒多，才是顺着汇编里的读取和等待一点点找出来的。**接口换完只是拿到了一套新工具，速度还得自己找。**

仓库还是那个： https://github.com/lmxxf/dlss5-on-amd-9070xt-porting ，HIP 的源码在根目录 hip/ 下，21 个文件加一个编译脚本；实验过程的全部记录在 Development/DevHistory.md 的 9 月 14 到 17 日段，包括那几十次撤回。
