【DLSS5】换掉 DirectX，用 AMD 自家的 HIP 把网络重写一遍

━━━━━━━━━━━━━━━━━━━━

◆ 开篇：一个我判断错了的问题

━━━━━━━━━━━━━━━━━━━━

309 期（ https://mp.weixin.qq.com/s/mvUDHC6kLqqCKIag8VIERA ）讲的是 HLSL 那一版：在 D3D12 里钩住 FSR 的调用，用微软还在预览的 Shader Model 6.10 矩阵接口调 AMD 的矩阵指令。写那期的时候我们聊到一个问题：另一条闭源的移植路线走的是 HIP，AMD 自家的计算接口，不经过微软那层。**换成 HIP 会不会更快？**

当时 Claude 给的判断是：不值得。理由有三条。我们的耗时几乎全在矩阵乘之后的逐元素尾巴上，不在矩阵乘本身；换接口拿不到新算力；而且要丢掉整条 D3D12 的游戏接入链，跨接口搬一次数据，省下的可能还回去一半。

我说：万一能搞定呢。就开了个分支让它试。

三天之后的结果：**HIP 版网络时间比 HLSL 版快 7.5%，全部逐位一致，而且不再需要预览驱动。** 900p 下游戏里从 30 帧到 52 帧。

三条理由里，第一条对了，第三条错了，第二条对了一半。这期讲这三天。

先说时间线。从 9 月 14 日深夜到第四天清晨，两个 AI 轮班：前半程是 Codex（GPT 6 Astra），第三天早上六点它的额度用尽，Claude 接手到收工。我做的事跟 304 期（ https://mp.weixin.qq.com/s/v3_KM8zqCg8bp01GglFvxQ ）一样：进游戏看画面、看帧率、在岔路口拍板。

◆ 第一章：HIP 是什么，跟上一条路差在哪

━━━━━━━━━━━━━━━━━━━━

先把两条路摆在一起。

**HLSL 那条路**：着色器语言是微软的 HLSL，编译器是微软的 DXC，运行时是 D3D12，矩阵乘走 Shader Model 6.10 的线性代数接口。这套东西 2026 年 9 月还是预览版：要装预览版驱动、预览版 Agility SDK、打开系统的开发者模式。矩阵指令出厂就在卡里，只是「在 D3D12 里用标准写法调它」这件事还没转正。

**HIP 这条路**：HIP（Heterogeneous-compute Interface for Portability，异构计算可移植接口）是 AMD 自家的 GPU 计算接口，写法和 CUDA 几乎一样，`__global__` 函数、`<<<grid, block>>>` 发射、共享内存叫 LDS（Local Data Share，本地数据共享）。编译器是 AMD 自己的 Clang，直接编到 gfx1201 这张卡的机器码。矩阵乘用编译器内置函数直接调 WMMA 指令，不经过微软那层。

────────────────────

💡 不装 SDK，怎么把 HIP 代码编出来

正常做法是装 AMD 的 HIP SDK，几个 G。但这东西是要发给普通玩家用的，不能要求人家装开发工具。

Codex 做的第一件事就是绕开它：**显卡驱动本身就带着一个编译器**——`System32` 下的 `amd_comgr_3.dll`（Code Object Manager，代码对象管理器），里面装的是一个 Clang 21，能编 gfx1201。装了 AMD 驱动的机器上都有。

于是写了个两百行的小程序，运行时把这个 DLL 加载进来，一个个函数指针取出来用：

```cpp
// 从 System32 加载驱动自带的编译器
static HMODULE load(const wchar_t* n) {
  wchar_t dir[MAX_PATH]; GetSystemDirectoryW(dir, MAX_PATH);
  return LoadLibraryW((std::wstring(dir) + L"\\" + n).c_str());
}
HMODULE h = load(L"amd_comgr_3.dll");

// 先问它认不认识这张卡
for (size_t i = 0; i < count; i++) {
  get_isa_name(i, &n);
  if (n && strstr(n, "gfx1201")) found = true;   // RX 9070 XT 的架构代号
}

// 源码塞进去，说清语言是 HIP、目标是 gfx1201，编
action_info_set_language(action, 3);                       // 3 = HIP
action_info_set_isa_name(action, "amdgcn-amd-amdhsa--gfx1201");
std::vector<const char*> opts = {"-O3", "-nogpuinc", "-nogpulib"};
do_action(2, action, input, result);                       // 2 = 编译

// 取出编好的代码对象
action_data_count(result, 8, &count);                      // 8 = 可执行数据
```

代码里那些裸数字（`language=3`、`do_action(2,...)`、`kind=8`）看着很怪，**它们本来是 SDK 头文件里的枚举名**——不装 SDK 就没有那些头文件，只能照着文档把数值抄进来自己定义一份。整个项目跟 HIP 打交道的地方都是这个路数：运行时那个 `amdhip64_7.dll` 也是驱动自带的，函数签名自己声明一遍，动态加载。

用户那边因此什么都不用装。这是这条路最实在的一个收获，比后面那 7.5% 实在。

────────────────────

然后是第三条理由里那个「丢掉接入链」的问题。实际做法是：**游戏侧的 D3D12 链一根不动，只把网络这一段换成 HIP。**

两边怎么交接？靠 D3D12 的两样东西：共享缓冲区和共享栅栏。缓冲区在 D3D12 这边按「可共享」创建，拿到一个系统句柄，HIP 那边凭这个句柄把同一块显存导入进来——**两套接口指着同一块内存，不发生拷贝**：

```cpp
// D3D12 侧：建一块可共享的缓冲区，要一个句柄
device->CreateCommittedResource(&hp, D3D12_HEAP_FLAG_SHARED, &rd, ..., &s.resource);
device->CreateSharedHandle(s.resource, nullptr, GENERIC_ALL, nullptr, &s.handle);

// HIP 侧：凭句柄把这块显存导入，拿到一个能直接用的指针
md.type = 5;                                  // 5 = D3D12 资源
md.handle.win32.handle = s.handle;
hipImportExternalMemory(&s.imported, &md);
hipExternalMemoryGetMappedBuffer(&s.mapped, s.imported, &bd);
```

时序靠一个共享的栅栏，两边轮流拽同一根绳子：

```cpp
queue->Signal(fence, ++value);                    // D3D12：输入写完了
hipWaitExternalSemaphoresAsync(&semaphore, ...);  // HIP：等到这个数再开工
network->Enqueue(input.mapped, ..., output.mapped, seed);   // 跑网络
hipSignalExternalSemaphoresAsync(&semaphore, ...);// HIP：算完了
queue->Wait(fence, value);                        // D3D12：等到这个数再往下走
```

同一个栅栏、同一个单调递增的计数，D3D 和 HIP 轮流发信号、轮流等。截帧、编码、时序采样、解码、写回，全是原来的代码，一行没动。跨接口这一进一出的代价后来量过，**每帧 0.13 毫秒，不到 1%**。

**这就是我当初那条理由错在哪：以为换接口是换整条链，实际只换了中间一段。**

至于换过来拿到了什么，记录里明说的有这几样：

| 能力 | HIP 这边 |
|---|---|
| 舍入边界 | 内联汇编钉死每一次转换，编译器再优化也动不了 |
| 截断舍入 | 一条硬件指令 `v_cvt_pkrtz_f16_f32`，原来是十几行位运算 |
| FP8 往返转换 | 原生转换指令 |
| 共享内存（LDS） | 自己排布、跨 wave 复用、按 head 隔离 |
| 编译产物 | 能吐出 `.s` 汇编文件逐条看 |

最后一行后面会成为整篇的关键。

━━━━━━━━━━━━━━━━━━━━

◆ 第二章：第一夜，先让它对

━━━━━━━━━━━━━━━━━━━━

第一夜十一点，第一个里程碑：HIP 的 FP8 矩阵乘和 HLSL 那边 79 组 32 深度的矩阵逐位一致。接着是完整的 512×512 参考图，786432 个 RGB 浮点数和原版一位不差。

然后跑 900p。**第一次墙钟 576 毫秒。** HLSL 那版当时是 16.7。

差 34 倍。但这一夜的目标不是快，是「对」。验收只认三道 hash（跟 304 期那两天一样的规矩）：40 帧 HDR 完整跑一遍、每 8 帧重置一次跑 24 帧、换随机种子和历史。HIP 版每一次改动都得过这三道，过不了就撤。三天里几十次改动，撤回的比留下的多。

有一次差点走错。有人（这里指 Codex）试着把软件写的半精度舍入函数换成编译器内置的 `_Float16` 转换，512 参考图上 779563 个值不一样。撤回。**原因是 309 期第六章讲过的那件事：网络里显式的 f32→f16 转换走的是截断，矩阵内部的转换走的是就近，两种舍入混在一起，不能整个模块粗暴地改成同一种。** HIP 版最后是用内联汇编把每一处转换的方式钉死，编译器再优化也动不了它。

────────────────────

💡 换了一套编译器，逐位一致怎么保住

两套编译器对同一段浮点代码的优化不一样。HLSL 那版摸出来的舍入规则（哪里截断、哪里就近、累加器从哪一步开始清零）是规则，不是代码，换编译器要重新落地一次。

HIP 这边的做法：凡是舍入边界，不写成普通的类型转换，写成内联汇编里的一条具体指令。

原版那个「浮点转半精度、往零截断」的动作，用 C 写出来是这样——四层 if 嵌套，处理无穷、溢出、下溢、次正规：

```cpp
DEV float Hrtz(float x){
  uint b=bits(x), a=b&0x7fffffffu, sg=(b>>16)&0x8000u;
  int e = int(a>>23) - 127;
  if (a >= 0x7f800000u) return from_half(sg|0x7c00u|((a&0x7fffffu)?0x200u:0u));
  if (e > 15)  return from_half(sg|0x7bffu);
  if (e < -24) return from_half(sg);
  if (e < -14) return from_half(sg|(((a&0x7fffffu)|0x800000u)>>uint(-e-1)));
  return from_half(sg|((a>>13)-0x1c000u));
}
```

换成内联汇编，两行：

```cpp
DEV float Hrtz(float x){
  uint h; float result;
  asm("v_cvt_pkrtz_f16_f32 %0, %1, %1" : "=v"(h) : "v"(x));
  asm("v_cvt_f32_f16 %0, %1"           : "=v"(result) : "v"(h));
  return result;
}
```

指令名念出来就是说明书：`cvt` 转换、`pk` 一次转两个（这里两个操作数都传同一个 x，只取低的那半）、`rtz` round toward zero 往零截断、`f16_f32` 从 32 位转 16 位。约束符里 `"=v"` 是「结果放向量寄存器」，`"v"` 是「输入来自向量寄存器」。

**这么写不只是为了快，更是为了钉死。** 编译器不能重排一条它看不懂语义的汇编——它不知道这两行在干什么，也就不敢把它跟旁边的运算融合、不敢换个舍入方式、不敢提前算。旁边那句注释写得很清楚：*「让 f32 的表达式求值和两个舍入边界，对融合优化保持不透明。」*

三道 hash 是最后一道门，前面还有每个核的单元对照：一个核改完，先拿几十组不同形状的输入逐个浮点数比位，再上整帧。后面几天做多头块融合时，光 C128 就对了 72 组、C256 对了 96 组。

代价是代码丑。这是逐位一致的价格。

────────────────────

这一夜到第二天清晨，数字是这么下来的：

| 改动 | 900p 毫秒 |
|---|---|
| 首跑 | 576 |
| 归一化改成 wave 内求和 | 369 |
| 舍入边界改内联汇编 | 344 |
| 输入切成 64×64 的瓦片进共享内存 | 148 |
| 快路径接线、几段融合 | 70 到 72 |

第二天早上六点，我看到 70 毫秒，说可以开始优化了。

◆ 第三章：第二天，70 到 29，以及第一次进游戏

━━━━━━━━━━━━━━━━━━━━

第二天一整天是 Codex 的。它做的事和 304 期那两天一个路数：**每次改一个核，量一次，过三道 hash，写一行日志。** 一天下来四十多条记录。

省得最多的几处：

| 改动 | 省了 | 为什么 |
|---|---|---|
| 权重在加载时预先打包成 FP8 | 5.2 毫秒 | 原来每帧都把浮点权重转一遍 |
| 截断舍入换硬件指令 | 4.2 毫秒 | 代码对象从 55640 字节缩到 37976 字节，指令少了 |
| 多头块的中间张量直接写 FP8 字节 | 3.5 毫秒 | 不再写浮点再读回来打包 |
| 前馈隐藏层字节化 | 3.6 毫秒 | 同上 |
| QKV 投影和归一化合成一个核 | 2.5 毫秒 | 省一个全局张量和一次发射 |
| C32 块的权重按 4 字节一次读 | 3.1 毫秒 | 原来逐字节读 |

傍晚 40 毫秒，夜里 28.8 毫秒。一天里 900p 从 70 压到 29，跟 304 期第一天从 1.47 秒压到 0.47 秒是同一种节奏：**头一天的收益全是搬运和格式，不是算法。**

中间穿插了三次进游戏，三次事故。

**早上第一次装进《剑星》，显示 INIT FAILED。** 查下来 HIP 初始化其实成功了，是桥接那一步判断「输入纹理是不是在同一个设备上」用了指针相等，而 ReShade 把 D3D12 设备包了一层，指针地址不一样。原来的代码里有一个专门解这层包装的函数，桥接没用它。改了。

**第二次进去，画面上人物变成黑色轮廓。** 关掉时序也黑。当场先把异步提交整个关掉，画面正常了——问题定位到那条路上，但根因要等到晚上：网络还没算完，下一帧的描述符已经原位重写了输入纹理的引用。晚上的修法是纹理指针变了先等一次，异步才重新打开。

**第三次，17 帧。** 我记得 HLSL 版 1080p 最好的时候 37 帧，这是 900p 才 17。晚上八点半异步提交修好，24 帧；九点半 34 毫秒的版本，26 到 27 帧；十点半 28.8 毫秒，30 帧。

这一天结束时，同条件对照是 HLSL 16.7 对 HIP 26.3，差 9.6 毫秒。

◆ 第四章：第三天，十次白做，两次真金

━━━━━━━━━━━━━━━━━━━━

第三天早上六点 Codex 额度用尽，Claude 接手。起点 HLSL 16.8 对 HIP 19.3。

前一天晚上 Codex 已经把差距从 9.6 压到 2.5，路数还是融合和预打包。但这一天白天的十几处改动，**几乎全是空的**：把中间张量改成字节流，逐位一致但慢 0.1；把前馈和 QKV 的批量归一化合并少两道同步，慢 0.11；ViT 的输入格式改了三种，全在噪声里。（后来最后一夜还试过关掉 C32 核的循环展开，寄存器从 237 降到 99、占用率从 8 升到 10，照样慢 0.64——这类"看着更健康"的改动，一次没灵过。）

这一天的日志里有一句总结：

> 别按自己的直觉猜瓶颈，把两边同一个核的源码并排逐段对，找「做同一件事但做法不同」的段。

**当天仅有的两次真收益都是这么来的。** 早上把 ViT 的注意力三个核合成一个，省 0.11。晚上八点把 HIP 的 C32 融合核和 HLSL 的同一个核并排放着看，发现输入分段这一步：HIP 每个窗口算 2048 次映射索引，HLSL 是 16 个 lane 各算一次再用 readlane 广播。照 HLSL 改，省 0.14。

然后顺着「只换打包不动结构」这一条，晚上又做了三处：C512 块的 mix 核权重预打包成 half，下采样投影权重预打包，解码器上采样权重预打包，合计 0.4 毫秒。**共同点是这几个核都在逐个读 f32 权重再转换，把转换挪到加载时，核本身一行不动。**

这一天还发现了一个测量陷阱。

────────────────────

💡 隔离测试为什么骗人

这天上午的逐层对照说 HIP 的 C64 块比 HLSL 快，但整帧里 C64 家族 HIP 2.27 毫秒对 HLSL 1.56，反过来慢。

原因是这张卡有 64MB 的 Infinity Cache。隔离测试反复跑同一个核，权重和输入都留在缓存里，看不到帧内真实的搬运。换了工具：两个后端各跳过同一个家族的块，看整帧少了多少，这个数才是帧内成本。

前一天还有一个更隐蔽的：HLSL 的基线从 18.8 漂到 26.6，一度以为 HIP 追平了。查下来是测试程序每帧把输出读回 CPU 扫一遍，这段时间不在计时区间内，但 GPU 空闲了，频率从 2.8GHz 掉到 1.79。**计时器外面的事也能改计时器里面的数。**

────────────────────

这天夜里，HIP 18.69，HLSL 16.8，差 1.89。我进游戏看，还是 30 帧。

◆ 第五章：最后一夜，追平，以及那个 30 帧

━━━━━━━━━━━━━━━━━━━━

第四天零点到两点，Claude 换了一个找法：**不看 HIP 的源码，看 HLSL 那版的生产配置文件**，一条一条问「这个融合 HIP 做了没有」。

HLSL 版有一个开关叫 `C32_EPILOGUE`，意思是 C32 块尾巴上的两件事（RGB 输出头、主干和下采样的收尾）都合进了块的核尾，不写中间结果。HIP 版是写出来再起一个独立的核。照做，两处合计 0.7 毫秒。池化和投影的核形状照 HLSL 重写一遍，0.28。ViT 的两个投影换 HLSL 那种按片段打包的权重布局，0.27。

凌晨一点半，HIP 16.90，HLSL 16.8，差 0.1，不到 1%。离线追平。

同一时间我进游戏：**47 帧。**

前两天三次进游戏都是 30 帧，我一直以为是网络之外的部分卡住了。日志里甚至算过一笔账：就算追平 HLSL 也只能到 32 帧，剩下 14 毫秒是游戏渲染和编解码。**实际是游戏的渲染目标锁在 30 帧上限，网络快了也显示不出来。** 改成 60，47 帧。

这件事的教训比它看起来大：三个版本的优化收益在游戏里全被一个设置遮住了，两个 AI 和我谁都没去查那个上限。

◆ 第六章：凌晨两点，读汇编

━━━━━━━━━━━━━━━━━━━━

追平之后我说了一句：肯定是尽量超过之前的性能啊，毕竟换了一套更直接的接口。

目标从打平改成赢。

HIP 这边没有性能分析器可用（这套预览驱动上 HIP 的事件计时器返回负数，早就不能信了）。Claude 做的是**把编译器吐出来的 `.hsaco.s` 汇编文件拷回来，用 Python 数指令、看分支落点**。

先说这个工具是哪来的。上一节那个自己写的编译器，调用 COMGR 编译的时候多传一个动作码，它就把汇编也吐出来：

```cpp
// do_action(5, ...) = 编译到汇编。同一个 action，换个动作码
do_action(5, action, result, assembly);
// ... 取出来写成 <输出名>.s
std::ofstream af(std::string(out) + ".s", std::ios::binary);
```

**没有性能分析器，编译器库自己就是那台性能分析器。** 拿到 `.s` 之后用 Python 按 `^核名:` 切开，数每个核里有多少条分支指令（`s_cbranch`）、多少处「读内存之后紧跟一条等待」（`global_load` 后面几条之内出现 `s_waitcnt`）。

C32 链核扫出来：静态 4731 条指令，其中 128 条分支。对照 HLSL 那边同一个核（9 月 11 号用 AMD 的 RGP 抓过一次）是 7321 条。**指令更少，却更慢。** 逐条看分支落在哪里，三种病一眼可见。

────────────────────

**第一种，饱和转换函数被编成了分支。**

网络里到处是一个叫 F() 的函数：把浮点数压到 FP8 能表示的范围（±448）再转回来。原来的写法是这样——

```cpp
DEV float F(float x){
  uint b = bits(x), a = b & 0x7fffffffu;
  if (a == 0) return 0.f;                                  // 零，早退
  if (a >= 0x43e00000u) return value((b & 0x80000000u) | 0x43e00000u);  // 超出范围，饱和
  int packed = __builtin_amdgcn_cvt_pk_fp8_f32(x, 0.f, 0, false);
  return __builtin_amdgcn_cvt_f32_fp8(packed, 0);
}
```

（`0x43e00000` 就是 448.0 的二进制写法，E4M3 这种 8 位浮点能表示的最大值。`DEV` 是这个项目自己定义的宏，意思是「设备端函数、强制内联」。）

看着很正常：两个早退，一条转换。但 GPU 上一个 wave 是 32 个线程一起走，**只要这 32 个人里有一个走 if、有一个不走，硬件就得把两条路都跑一遍**，用一个执行掩码把不该生效的线程关掉，跑完再开回来——这叫发散分支。汇编里一处 F() 就是一套 `v_cmpx / s_and_saveexec / s_or exec`，大约五十条指令。

而 F() 在这个核里出现多少次？输入分段每个 token 一次（16 次），投影输出每个元素一次（16 次）。**光这一个函数就占了整个核静态指令的四成。**

改法是把两个 if 都变成没有跳转的算术：

```cpp
DEV float F(float x){
  uint a = bits(x) & 0x7fffffffu;
  float c = __builtin_fminf(__builtin_fmaxf(x, -448.f), 448.f);   // 夹住，没有分支
  float r = __builtin_amdgcn_cvt_f32_fp8(
              __builtin_amdgcn_cvt_pk_fp8_f32(c, 0.f, 0, false), 0);
  return a == 0 ? 0.f : r;                                        // 一条条件选择指令
}
```

`fmin/fmax` 和最后那个三元运算符在 AMD 卡上都编成单条指令，不产生跳转。**逻辑没变，跳转没了。**

代码里那条注释把边界条件写得很清楚：对所有有限和无限的输入，两种写法结果完全相同（±448 精确转换，447.75 到 448 之间两边都进位到 448，零保持正零）；**唯一的差别是输入 NaN 时新写法给 −448 而不是 ±448**——而这条链路上不会出现 NaN，所以逐位一致这个说法站得住。这种边界要写在注释里，不然三个月后没人敢动它。

────────────────────

**第二种，读取串行化。**

输入分段那一步，一个 wave 负责 16 个 token，每个 token 要从显存搬 32 个通道。原来的写法是循环 16 次，每次「算出地址、读一个、转换一个」：

```cpp
for (uint j = 0; j < 16; j++) {
  int src = __builtin_amdgcn_readlane(mine, j);   // 问第 j 号 lane 要地址
  if (src >= 0) {                                 // ← 就是这个 if
    v = raw_input[uint(src) + l];                 // 读
    ...                                           // 转换
  }
  packed[row*36 + l] = fp8(v);
}
```

（`readlane` 是 GPU 上的一种广播：16 个 lane 各自先算好「我负责的 token 在显存哪个位置」，然后轮流把自己算出的地址喊给全班，32 个人一起去搬那一行。）

问题出在 `if (src >= 0)` 这个越界判断上。**读内存的指令被关在分支里，编译器就不敢把它提前**——只能老老实实：读一个、等它到、转换、再读下一个。汇编里就是 16 组 `global_load → s_wait_loadcnt 0 → 分支`。显存延迟几百个周期，16 次就是排了 16 次队。

HLSL 那边是 16 个 Load 在一个没有分支的展开循环里一次全发出去，硬件自己去重叠这些等待。

改法是拆成两趟：

```cpp
// 第一趟：只管发，索引不带分支（越界的 token 读个占位）
float lv[16]; int srcs[16];
for (uint j = 0; j < 16; j++) {
  int src = __builtin_amdgcn_readlane(mine, j);
  srcs[j] = src;
  uint idx = src >= 0 ? uint(src) : 0u;    // 越界就读第 0 个，反正等下丢掉
  lv[j] = raw_input[idx + l];
}
// 第二趟：统一转换，这时候把占位值挑出去
for (uint j = 0; j < 16; j++) {
  float c = F(lv[j]);
  float v = srcs[j] >= 0 ? c : 0.f;        // 占位值在这里归零
  packed[row*36 + l] = fp8(v);
}
```

**关键是那个 `idx = src >= 0 ? uint(src) : 0u`：越界的 token 也照读不误，只是读个没用的。** 用一次无用的读，换掉一条分支——16 个 load 于是连着发出去，汇编里能看到 `s_wait_loadcnt` 从 0xf 一路递减到 0，等待重叠起来了。

这两刀合起来：C32 核的分支从 128 条降到 60 条，静态指令 4731 降到 4036。**离线 HIP 16.19，HLSL 16.8，第一次反超。** 单独只做第一刀是 0.19 毫秒，两刀一起是 0.68——**去分支本身值 0.19，它解锁的读取重叠值 0.49。**

────────────────────

**第三种，别名重载。**

投影的尾巴上，每个输出都要乘一个跟列号有关的缩放系数，原来是在循环里现读：

```cpp
for (...16 个输出...) {
  float prod = residual * w[8193 + col + rc()];   // 每次都从显存读
  float v = Hrtz(acc[e] + prod);
  out[i] = ...;                                    // ← 中间夹着这个写
}
```

代码注释里那句诊断写得很直白：**这两次读中间夹着一个 `out[]` 的写，编译器没法断定写进去的地址不会碰到 `w[]`，只好每个输出都重新读一次**——汇编里就是同一个偏移量 `offset:32772` 反复出现八次，每次后面紧跟一条等待。这在编译器里叫别名分析失败，C 语言里指针可能指向任何地方，编译器只能往最坏处想。

改法一行：循环外面先把这两个值读进寄存器。

```cpp
const float pw0 = w[8193 + rc()], pw1 = w[8193 + 16 + rc()];
// 循环里：
float prod = residual * (col == 0 ? pw0 : pw1);
```

省 0.05 毫秒。数字不大，但这类病在别的核里还有一堆——扫描脚本当时就指出 C512 的注意力投影核有 33 处串行等待、42 处同地址重读。

────────────────────

💡 静态指令数不是钱，旧的空结果也不是永久的

去分支那一步做完之后，同样的病在多头块的核里也有：一个核 6936 条静态指令、435 条分支。改完 1575 条、35 条分支。时间只省了 0.02。

分支跳过的路径本来就不执行，指令少了不等于跑得快。真正值钱的是那条被串行化的读取，不是指令数。

另一面：前一天判定为空的两处改动，prefix 内联和残差的对角权重，在核瘦身之后重测，一个省 0.27，一个省 0.16。瓶颈挪了，旧的结论就作废。**一处改动的收益是相对当时的瓶颈说的，不是这处改动本身的属性。**

────────────────────

到凌晨两点半，HIP 15.5，HLSL 16.8，快 1.3 毫秒，7.5%。三点半我进游戏：**52 帧。**

这一夜从 16.90 到 15.5 的每一步：

| 改动 | 省了 |
|---|---|
| F() 去分支 + 读取连发 | 0.68 |
| 多头核 q8 去分支 + 硬件截断 | 0.16 |
| 权重先读进寄存器 | 0.05 |
| prefix 内联（前一天判空，重测翻盘） | 0.27 |
| 残差对角权重（前一天判空，重测翻盘） | 0.16 |
| 前馈残差和输入的条件读改无分支 | 0.14 |

全部逐位一致，全部过三道 hash。

顺便回答开篇那第二条理由。「换接口拿不到新算力」这句是对的，矩阵指令是同一批。**但换接口拿到了看汇编的权利。** HLSL 那边编译产物是 DXIL 中间码，最后一步在驱动里，看不见；HIP 这边编译器直接吐机器码，那三种病才能被看见。这是第二条理由错的那一半。

◆ 第七章：收官，以及哪些路封死了

━━━━━━━━━━━━━━━━━━━━

第四天早上六点我说不追了，打包。0.20 版发出去，两个包：游戏内接入的和 Magpie 的。**用户那边的变化只有一条：不再需要预览驱动、预览 SDK 和开发者模式，只要显卡驱动自带的 `amdhip64_7.dll`。** 这是换接口最实在的收益，比那 7.5% 更实在。

同一天下午加了自动选档：窗口不超过 720 走 720，不超过 900 走 900，否则 1080。实测 900p 52 到 54 帧，1080p 37 到 38 帧。晚上又把 900 档的补边行数从 1024 降到 960，省 0.75 毫秒，这一步不逐位（对默认输出 31.5dB），我在游戏里看不出差别，定为默认。

网络之外的部分也量了一次：游戏内 1080p 前处理 0.49 毫秒、网络 20.8、后处理 0.26。**前后处理没肉可啃，剩下的只有网络核。**

然后是最后试过、封死的路，记下来免得再走：

| 路线 | 结果 |
|---|---|
| hipGraph 整帧一次提交 | 零收益。每帧 200 次发射的 CPU 提交本来就藏在 GPU 时间后面 |
| 显存稀疏映射省掉权重死区 | 驱动只认「保留区等于一个完整物理块」，多块挂死，封死 |
| C64 块按窗口合成一个大核 | 逐位一致，零收益。寄存器从 196 降到 136、占用率 6 到 8，时间不动，这个核是串行链绑着的 |
| 放宽精度（打包 f16 激活） | 更慢 |
| ViT 核形状的六种改法 | 全空。400 个 token 只有 25 个工作组，并行度不够 |

还有一个第三天顺手挖出来的东西，跟前几天网友问的「结构化稀疏」正好相关。多头块的前馈收缩矩阵，36 个矩阵每 32 个输出通道只对应 128 个隐藏层非零，其余全零。这是网络训练时留下的分组结构，不是我们剪的。**按这个结构把矩阵乘的深度从 256、512、1024 缩到 128，省了 0.9 毫秒，加载时逐值验证越界非零直接拒绝，逐位不变。** 这是这三天里唯一一次「稀疏」帮上忙，靠的是网络自带的零，不是硬件的稀疏指令。

◆ 收尾

━━━━━━━━━━━━━━━━━━━━

回到开篇那三条理由。

「耗时不在矩阵乘」，对。三天里没有一处收益是换矩阵指令换来的。

「换接口拿不到新算力」，对一半。算力是同一批，但拿到了汇编。凌晨两点那 1.3 毫秒全是从汇编里看出来的。HLSL 那边不是绝对看不到——用 AMD 的 RGP 也能抓到编译后的东西，但得绕一大圈，还会被驱动的着色器缓存骗到（抓出来是上一版）；HIP 这边是编译的时候顺手就吐出来，随时想看就看。

「要丢掉整条接入链」，错。只换了中间一段，跨接口搬运每帧 0.13 毫秒。

三天的收益分三段，性质各不一样：第二天从 70 到 29 是搬运和格式，第三天夜里到第四天凌晨从 19 到 16.9 是把 HLSL 那版做过的融合逐条补齐，最后从 16.9 到 15.5 是读汇编。**换接口本身没给一毫秒。**

仓库还是那个：https://github.com/lmxxf/dlss5-on-amd-9070xt-porting ，HIP 的源码在根目录 hip/ 下，21 个文件加一个编译脚本；实验过程的全部记录在 Development/DevHistory.md 的 9 月 14 到 17 日段，包括那几十次撤回。
