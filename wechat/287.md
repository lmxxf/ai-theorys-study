◆ 这期看车间

━━━━━━━━━━━━━━━━━━━━

这个系列写到第六期了，前五期其实都在讲"纸面上的事"：282 期（ https://mp.weixin.qq.com/s/4aDzx6lxkVxTUSj8NnCSYA ）讲三家明说只做后训练、难点转移到环境，283 期（ https://mp.weixin.qq.com/s/qBGsQ75RQYExZW1Vj0BhIg ）讲几万道训练题从哪来；284 期（ https://mp.weixin.qq.com/s/zHnVU5JG6ADr4WWyJrWwJw ）讲专家怎么合，285 期（ https://mp.weixin.qq.com/s/U4bZ0DNC_ktW5qpiUWv96Q ）讲老师怎么挑，286 期（ https://mp.weixin.qq.com/s/yIZfZVSi-m_r_ynTi9Qs3g ）讲为什么不直接混训。

出题组有了，教学大纲有了。这期掀开另一层：**这几万道题，真在机房里跑起来是什么样。**

几百张 GPU、几十万个沙箱同时开工。谁在算、谁在闲着、权重怎么在训练和推理两边倒手、机器突然被抢走了考卷怎么救——K3 和 V4 都给这一层留了大段基建章节，几套开源框架则把零件直接摊在代码里。读完这一圈，我能把它们装进一句话：

**RL 后训练的车间里，最贵的动作不是算，是等。** 整章基建，全是各式各样的消等术。

◆ 先算一笔节奏账：为什么这个车间特别容易闲着

━━━━━━━━━━━━━━━━━━━━

普通的预训练像流水线：数据源源不断喂进来，GPU 从头到尾满负荷做矩阵乘法，节奏整齐。Agentic RL 的一步完全是另一种节奏：

1. **先让模型做题（rollout）**：模型在沙箱里跑 agent 任务——读代码、改文件、跑测试；长任务跨几十到几百轮工具调用，极端轨迹累计到百万 token。这一步是**推理**，还夹着一次次等环境返回；
2. **判分**：可验证的任务给 0/1（开放任务也有用奖励模型打分的）；
3. **策略更新**：把分数换算成每个 token 的功过，反向传播一次，更新权重。

也就是说，做题占掉一步里的大头，昂贵的集群大部分时间在推理和等待，真正"训练"的那一下反而短。而"等"在这个车间里还不止一种——**沙箱在等模型、rollout GPU 在等环境、训练 GPU 在等数据，是三本不同的账**。下面一本一本看。

━━━━━━━━━━━━━━━━━━━━

◆ 第一种等：等最慢的那条轨迹

━━━━━━━━━━━━━━━━━━━━

做题不是一条条做的，是一批一批做的：一轮同时跑几千条轨迹，做完了才进下一步训练。

问题来了：**轨迹长短差得离谱。** 有的任务十几轮就结束，有的要磨几百轮工具调用。同步系统若坚持等整批结束，先做完的就只能陪最慢那条轨迹耗着——任务越长程，这条尾巴越长。

Kimi 的解法叫 **partial rollout**（部分完成就开工），从 k1.5 时代一路沿用到 K3。K3 报告里的机制是：

每轮对 N 道题各采 K 条轨迹，一共 N×K 条同时跑。**不等全部跑完——完成比例达到 λ 就叫停**，做完的直接送去训练；没做完的不作废，排进队列，**下一轮开始时优先接着跑**。一道题的 K 条轨迹全部到齐，才作为一组进入策略优化。

这里顺手把"权重什么时候更新"说清楚：车间是按**轮**转的，做题和训练轮流占同一批 GPU——做题阶段攒够 λ 比例就停，把这轮做完的轨迹打包成一批做一次更新，得到新版本模型，然后开下一轮。**更新不挂在某条轨迹做完上，挂在轮上。** 上一轮没写完的轨迹，下一轮由**升级后的模型**接着写——"一条轨迹跨好几个版本"就是这么来的。

翻译一下：全班考试，交卷的到了一定比例就先阅卷讲评，讲评完老师换了新讲义，没写完的下节课带着新讲义接着写，不让全班陪最后一名耗着。

至于为什么一道题的 K 条还得凑齐：这是 GRPO（261 期 https://mp.weixin.qq.com/s/nLFv6m-ONkXd7frHevgPOQ 讲过）的记分方式——验证器先给每份答卷一个原始分，但训练用的不是原始分，是**同题 K 份互相比出来的相对成绩**：比组内平均好的记功，差的记过。K 份没到齐，组内平均就是歪的，所以宁可等分身凑齐再算账。

但这刀切下去有一个直接的代价，K3 报告自己说得很坦白。被暂停的轨迹会跨训练迭代续写，**像连载一样由不同版本的策略共同完成**。举个示意：第 100 轮开头，第 101 轮的新模型续中段，第 102 轮收尾；完整轨迹进入更新时，前面的 token 已经来自旧版本。报告管这叫"极端的 off-policy 状态"（extreme off-policy regime，off-policy 就是数据并非全由当前策略生成）。解法是给每个 token 的更新加正则约束，把策略变化限制在局部邻域，以承受高度过期的数据。

**"不等"的账就是这么算的：省下的是 GPU 时间，付出去的是数据新鲜度。** 这笔交换后面还会反复出现。

◆ 第二种等：等环境——以及一个反转

━━━━━━━━━━━━━━━━━━━━

第二种等在沙箱那头。agent 做题得有个真实的工作环境：文件系统、能跑的测试、能装的依赖。

先看规模。K3 报告给了一个总数：**整个训练加评测过程，一共创建了 51,219,741 个沙箱实例，覆盖 1,505,678 个镜像。** 五千万个实例，实际负载里还可能要求几万个、各带一组镜像的沙箱在几秒内创建——环境这一侧自己就是个不小的分布式系统。

这里得把两本账分开看，因为它们各自坐实了一半直觉。

用过 AI 的人第一反应肯定是**环境在等模型**——命令一瞬间跑完，模型憋半天才蹦字。K3 报告给这个体感盖了章：

**一个沙箱的生命周期里，最多 98% 的时间在等模型的推理结果。**

agent 每次动作之间都要等模型生成下一步；在报告记录的极端情况下，这段等待可占沙箱生命周期的 98%。Kimi 的对策是给沙箱做暂停/恢复：模型推理时把沙箱 pause 掉，不占内存或 CPU，下一条命令来了最低 49 毫秒恢复现场。增量检查点最低 133 毫秒，真实负载中的内存超卖比最高做到 6.5 倍。

那反过来，GPU 有没有在等环境？有——**换到 GPU 的钟上看**：命令大多轻，但重的是真重——跑一遍完整测试套件、装一套依赖、编译一个工程，都是分钟级起步；再叠上等最慢轨迹的长尾，GPU 的空转就是这么攒出来的。**两边各有各的闲，闲的时刻还错开——车间里互相等，谁也没闲着地闲着。**

还有一个很有画面的细节。Kimi 早期用普通容器跑沙箱，结果：

**agent 的胡乱操作把宿主机内核搞出了 kernel panic 和死锁。**

模型是真敢什么都试的——而且 K3 就是要给它这种自由：允许 agent 挂磁盘、起容器、甚至在沙箱里再开虚拟机。要兼顾这种高自由度和不许碰宿主机，普通容器不够用，于是 K3 在原有的容器和 GPU 沙箱之外，新增了一档 microVM 运行时（轻量虚拟机，一人一个独立内核），叫 AgentENV，已经开源——三档并存，高权限的探索活儿走 microVM。

这一步像是绕了一圈回到古典技术：当 agent 需要高权限探索、又不能碰到宿主机时，microVM 提供了比普通容器更硬的内核边界。K3 用的 Firecracker 最初也服务于大规模、互不信任的 serverless 工作负载。**但选择不是"不可信代码一律只能上虚拟机"**——DeepSeek 后面正好展示了四档底座。新的地方在于调度强度：长时间等待逼出暂停恢复，几万个实例秒级拉起逼出镜像共享和内存超卖；旧虚拟化技术被重新按 RL 吞吐优化了一遍。

DeepSeek 那边同样单独建了沙箱平台，叫 DSec：单集群管理**几十万个并发沙箱**，底下四种执行底座——预热容器池、Docker 兼容容器、microVM、完整虚拟机——安全性和开销各在一档，**训练任务换个参数就能切**。快照是链式的，恢复毫秒级；每个沙箱还留一份全局有序的操作日志，训练任务被打断再回来时，直接回放已经执行过的命令的结果，不用重新执行（有些命令执行两遍会出事）。

环境这一侧值多少钱？2026 年 7 月有一篇论文专门量了这笔账：单容器、托管沙箱、K8s 容器、云虚拟机四种底座，**冷启动延迟最高差 110 倍**；把这个差距投影到一百万条、每条 150 步的轨迹上，总机器工时差 **1.8 倍——最慢的方案比最快的多烧 5,316 个小时**。作者把这叫 rollout 的"基建税"：环境方案选得糙，税单五千小时起步。开头说的 282 期那句"难点从模型转移到环境"，这期看到的是它的账单版。

◆ 第三种等：等一次抢占之后的重来

━━━━━━━━━━━━━━━━━━━━

第三种等最隐蔽：**机器不是你一个人的。**

V4 报告交代了他们的约束：GPU 集群采用全局抢占式调度，高优先级任务可以拿走正在运行的资源，大规模集群还会遇到硬件故障。**抢占不是普通排队，而是 rollout 运行到一半，资源被调度器收回。** 一条超长轨迹已经写到中途，机器没了，怎么办？

朴素的答案是重跑。V4 的做法讲究得多：给每条生成请求记一份 **token 级的写前日志**（Write-Ahead Log，WAL）——**每生成一个 token，立刻追加写进日志**。被抢占时暂停引擎、保存没跑完请求的 KV cache；恢复时接着往下解码。就算硬件彻底挂了、KV cache 丢了，也能拿日志里存下的 token 重跑一遍 prefill，把现场重建出来，从断点继续。

这套设计里最值得停下来看的，是报告里的一个论证——**为什么"从头重跑"不只是浪费，而是错的**：

> 从头重新生成没跑完的请求，在数学上是不正确的，因为这会引入长度偏差。

道理一想就通：**短的回答更容易在抢占来临前写完。** 如果每次被打断都把没写完的作废重来，那活下来进入训练数据的，就系统性地偏向短回答——模型会被这套基建悄悄训练得越说越短。**故障恢复策略居然会弯曲训练分布**——基建不中立，这是整章里我印象最深的一句。

────────────────────

💡 顺带一提：权重也在两边倒手

训练和推理通常由不同引擎负责，策略每更新一次，rollout 侧就得拿到新权重。K3 的显存调度像一支舞：训练迭代结束后，把模型权重和优化器状态卸到 NVMe，为外部 KV cache 的 CPU DRAM 池腾位置；rollout 结束后再释放这个池，避免跟训练争内存。连参照模型都不常驻 GPU——它借用策略模型的 FP32 梯度缓冲区，一块算、一块预取，流式过一遍。**显存、DRAM 和 NVMe 被排成了一张轮班表。**

────────────────────

三种等各有各的刀法，但把它们放在一张时间轴上，还有一个更大的分野。

◆ 同步还是异步：框架们的分家线

━━━━━━━━━━━━━━━━━━━━

上面讲的都是"零件"。零件装配起来，就是这两年冒出来的一批**后训练框架**，它们真正的分家线只有一条：**训练和做题，到底等不等对方。**

**同步共置**是一种常见配置：训练和推理装在同一批 GPU 上，做题、训练轮流占用，一轮采样完再更新。veRL/HybridFlow 的 3D-HybridEngine 很擅长这种训练—生成切换，但 veRL 本身也支持灵活设备映射，不能把整个框架钉死成只有这一档。同步的好处是 batch 内策略版本一致、账好算；代价是长尾和阶段切换带来的等待。

**全异步**是激进路线，代表是清华和蚂蚁的 AReaL：做题的机器和训练的机器分开，rollout worker 持续生成，trainer 攒够一批就更新。它的可中断 rollout 还能把正在写的请求暂停、换上新权重（旧权重算的 KV cache 丢掉用新权重重算）再接着写，于是一条轨迹可能跨多个策略版本。GPU 利用率上去了，代价是训练数据落后于当前模型、同一条轨迹内部版本也不一致。论文靠控制新旧程度上限和一个解耦版的 PPO 目标（decoupled PPO）兜底，报告同卡数下相对同步系统**最高 2.77 倍**训练加速。

智谱与清华开源的 slime 连接 Megatron 训练和 SGLang rollout，已经用于多个 GLM 版本。它不是固定站在中间：同一个框架可以共置或分离、同步或异步。面对跨集群甚至跨机房的分离部署，它还提供可选的 delta weight sync：训练侧把差量 checkpoint 写到共享存储，rollout 侧拉取、打补丁，再从磁盘更新权重。

于是异步调度绕回了同一笔交换：**少等一些，数据就可能旧一些。** 2026 年一篇理论论文在局部有界、分布平滑等假设下，把异步 GRPO 每步的代理梯度偏差写成 `O(S × η)`：S 是最大滞后版本数，η 是学习率。它不是普遍实测常数，但说明"旧几版"得和"每步走多远"一起看。K3 的 per-token 正则、异步框架里的重要性修正和裁剪，都是在给这笔偏差上保险。

而且"旧"还不是异步埋的唯一一颗雷。训练引擎和推理引擎可能采用不同并行布局、精度和 kernel，**同一份权重、同一段文字，两边算出的概率也可能出现数值偏差**。这属于训推一致性问题，和策略版本过期是两本账。

◆ 收一下

━━━━━━━━━━━━━━━━━━━━

把这期摊开的东西合上：

Agentic RL 的一轮大致包括做题、判分和策略更新；长程 rollout 往往是主要瓶颈。这个节奏让车间处处出现**等**：同步 batch 等最慢轨迹（K3 用 partial rollout 提前开工），沙箱等模型下一步（极端可达生命周期的 98%），GPU 又会等重命令和长尾环境；抢占之后还可能等重建（V4 用 token 级 WAL 断点续写，并指出从头重跑会引入长度偏差）。环境的基建税也量出来了：冷启动延迟差 110 倍，落到百万条轨迹的总工时上是 5,316 个小时。

消等术付的代价并不相同：暂停沙箱付的是恢复与存储开销，WAL 付的是日志和 KV cache 管理；只有 partial rollout、异步生成这类让旧策略数据继续流动的办法，才主要拿**新鲜度**付款。同步/异步也不是三个框架各占一个固定档位，而是 veRL、slime、AReaL 提供了不同默认设计和可配置范围。

开头提到的 284 期讲过 V4 十几位万亿参数的老师怎么在显存里排班上下场，当时当轶事看；这期看完会发现那是同一件事——**这一代模型的竞争，有相当一部分是车间对车间的竞争。** 工艺路线图（284 到 286 期）大家都看得到，车间是各家自己一根管子一根管子焊出来的。

这个生产规模没法在家里复现，但相当一部分零件已经摊在明面上：slime、AgentENV、checkpoint-engine、veRL、AReaL 都能直接读代码。论文给的是整厂数据，开源仓库给的是可以逐件摸的机器零件。我们打算回头把这些仓库拉下来慢慢看——看明白了，再接着写。
