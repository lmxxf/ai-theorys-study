【AI Agent】这两天热议的让大模型控制机器人的“MHS 协议”是个什么东西？

━━━━━━━━━━━━━━━━━━━━

◆ 开篇：一个还没有内容的标准

━━━━━━━━━━━━━━━━━━━━

8 月 27 日，Anthropic 发布了 MHS，全称 Model Hardware Standard，模型硬件标准。一句话概括官方的定位：MCP 让 AI 连上软件工具，MHS 让 AI 连上物理机器——机械臂、显微镜、离心机、移液器。

这两天中文圈把它讨论得挺热。我想弄清楚的是具体的东西：消息长什么样、字段叫什么、read 和 write 怎么握手、安全上限写在哪儿。

查完之后发现，这些**一个都没有**。

不是我没找到。是 Anthropic 到现在只发了一篇公告博客和一个申请表，规范文档、schema、软件开发工具包、参考实现、版本号，全部没有公开。想看规范得先申请，通过了才给。

所以这期是这么两半：**前半把“官方到底说了什么”原样摆出来，看看这个标准现在究竟有多少内容；后半从这几句话往回推，猜它可能长什么样。** 猜的部分我会明说是猜的。

一个还没有内容的标准，已经引出了不少东西，这本身值得看一眼。

━━━━━━━━━━━━━━━━━━━━

◆ 第一章：官方说了什么

━━━━━━━━━━━━━━━━━━━━

先把公告里所有带技术含量的句子摆出来。摆完你会发现，一页纸就够了。

**第一件，两个原语。** 官方原话是这样：

> The MHS driver uses a simple set of primitives—commands like "read" (for example, "get temperature") or "write" (for example, "set temperature")—that any hardware device can understand and act on.

翻过来：MHS 驱动使用一组简单的原语——像 read（比如“读取温度”）或 write（比如“设置温度”）这样的命令——任何硬件设备都能理解并执行。

注意这句话给了什么、没给什么。**它给了两个动词的名字和两个中文例子，没给函数签名。** 参数是什么、返回什么、错误怎么表示，一个字都没有。

**第二件，驱动是干什么的。** 官方定义：标准化驱动，是“在计算机操作系统和硬件设备之间做翻译的软件”。

**第三件，设备信息怎么进来。** 这条是我这次查到的最有信息量的一句：

> contains tags that let the user write this information directly in natural language (users can either do this themselves, or by chatting to an agent that interviews them about their hardware setup)

驱动里带着一些标签，让用户**直接用自然语言**把设备信息写进去——可以自己写，也可以跟一个 agent 聊，由它采访你的硬件配置。

然后：

> the MHS driver then automatically produces a reference file with information about a device's general characteristics, such as what it can measure, what can be adjusted, and what safety limits will be enforced

驱动据此自动生成一份**参考文件**，写明这台设备能测什么、什么可以调、会强制哪些安全上限。

**第四件，三个控制面。** 官方原话：“有三种这样的机制：MCP、命令行界面，以及代码文件（应用程序接口）。”

**第五件，跟 MCP 是什么关系。** 这条容易搞错，我一开始也说岔了。官方说 MHS 是模型无关的，“任何 agent 框架都可以用标准协议访问它，比如 Model Context Protocol”。**所以 MHS 不是 MCP 的扩展，也不是它的子规范，是一个并列的独立标准，MCP 只是访问它的方式之一。**

**第六件，开源时间。** 官方原话是“在把标准开源之前，我们还有工作要做”。没给日期。

以上就是全部。**两个动词、一个用自然语言填的标签、一份自动生成的参考文件、三个入口。** 没有传输层，没有消息格式，没有字段名，没有一行示例代码。

────────────────────

💡 “有标准”和“能读到标准”是两回事

USB 有公开规范，CAN 总线有 ISO 标准文本，任何人花点钱或者直接下载就能拿到完整定义，然后自己实现一个设备。这是硬件标准过去几十年的默认做法。

MHS 现在是申请制：要看规范，先填表，等批准。

Anthropic 给的理由站得住——物理世界的误动作不可回滚。软件里一个错误抛个栈追踪，机械臂里一个错误可能报废设备或者伤人，他们想先跟早期伙伴把安全评估做完。

但代价是实在的：一个只有被批准的人才能读的文档，现阶段还很难叫标准。Hacker News 上一位用户的说法是“你不该需要许可才能读一份标准”。这话有点重，不过指的是实情。

◆ 第二章：然后就没有了

━━━━━━━━━━━━━━━━━━━━

这一章把“没有”落实到具体位置。

**官网只有落地页。** modelhardwarestandard.com 上访问 /docs、/spec、/specification，服务器返回 200，但吐回来的是同一份首页 HTML——这是单页应用的通配路由，不是真有文档。docs 和 spec 子域名不解析。整个站点唯一的外链是一张 Google 表单，也就是申请入口。

**GitHub 组织是空的。** github.com/modelhardwarestandard 这个组织确实存在，页面上写着 This organization has no public repositories，公开仓库数为零。Anthropic 自己的 anthropics 组织、以及 MCP 的 modelcontextprotocol 组织下面，也没有 MHS 相关仓库。

**合作方一个都没放代码。** 公告里点名的伙伴不少：Doosan Robotics 在拿机械臂测试、Tecan 在给它的 Fluent 液体处理平台加支持、Universal Robots 拿到了早期访问、Hugging Face 在 LeRobot 里加 MHS 支持、Raspberry Pi 在给自家产品做集成。查下来，**公开代码或文档一份都没有**。

Raspberry Pi 官方账号发过一条推文，说在做树莓派摄像头的 MHS 驱动，测试结果让他们印象不错，接下来会探索其他产品。就这么一条，没有代码。

这里顺便更正一个我自己一开始的误解。树莓派板子边上有一排针脚，每根都能被软件单独控制成两种角色：往它写一个 1 就输出高电平、写 0 就是低电平，接个继电器就能开关电机；反过来读它，就能知道外面接的按钮按没按、限位开关有没有撞到。这排针脚叫通用输入输出（General-Purpose Input/Output，GPIO），玩硬件的人接传感器、接电机驱动走的都是这里。

它天生就是读和写两个动作，跟 MHS 那两个原语长得一模一样，所以社区看到 MHS 只有 read/write，第一反应就是拿它去包 GPIO。**但树莓派官方做的是摄像头驱动，不是 GPIO。** 摄像头要管的是分辨率、曝光、帧率这些参数，不是一根针的高低电平。网上那些“GPIO 引脚映射成 read/write”的说法，是社区项目自己实现的，不是官方的。

**最能说明问题的是这一条。** GitHub 上搜 MHS 能搜出十几个仓库，名字一个比一个正式：Open-MHS、open-mhs、OpenMHS、mhs-demo。全部是第三方按博客那几句话猜着重建的，字段名和协议形状都是作者自己发明的。社区维护的索引清单自己就标注了官方“仅申请制”、组织下零仓库，列表里的条目大多写着“与 Anthropic 无关联、未获其背书”。

其中一个仓库来自 Fastly 的官方账号，是个边缘安全网关。它的免责声明写得最直白：

> No public MHS spec exists yet.

后面接着说，仓库里注册的那两台设备（一台 qPCR 仪、一条机械臂）和那套 MHS 驱动的 HTTP 约定**都是占位符**，等真规范公开之后，请自行把线上格式调成它实际暴露的样子。

另一个社区项目的自述更干脆：这东西跑在模拟层上，是“为真规范落地的那天准备的”。

**连一家上市公司的官方仓库都只能拿占位符实现，这就是当前的公开程度。** 也是为什么这期不可能是协议解析——素材不存在。

━━━━━━━━━━━━━━━━━━━━

◆ 第三章：猜一猜它长什么样

━━━━━━━━━━━━━━━━━━━━

**这一章全部是推测。** 依据只有上面那六条官方表述，加上同类协议的通行做法。等规范公开，下面这些可能全错，我到时候再写一篇对账。

先看官方那几句话实际约束了什么。

**约束一：原语只有 read 和 write。** 这是个相当强的选择。设备控制其实有第三类操作——“执行一个动作序列”，比如机械臂走一条轨迹、离心机跑一个程序。只给读写两个动词，意味着这类动作要么被摊成一串写操作，要么被表示成“往某个可写项里写入一个程序名”。前者延迟敏感，后者等于把复杂度推回设备端。

我倾向猜是后者：**MHS 大概率不打算管实时轨迹，只管“选哪个已有能力、参数设成多少”。** 真正的运动规划留在设备原有的控制器里。

**约束二：设备要能被跨网发现。** 官方说设备和 agent 能“跨网络互相找到”，没说用什么机制。局域网自动发现的通行做法是 mDNS 那一类，也可以是中心注册表。考虑到实验室场景常有多台机器跨网段，我猜**注册表的可能性比纯广播大**，但这条我毫无把握。

**约束三：三个入口共用一层。** MCP、命令行、代码接口三条路进同一个驱动，说明驱动本身得暴露一个与语言无关的接口层。MCP 用 JSON-RPC 2.0，如果 MHS 想省事，沿用同一套传输是最自然的选择——但这是**从 MCP 的做法外推的猜测，官方一个字没提传输层**。

**约束四，也是最有意思的一条：设备信息用自然语言填。** 前面引过原话，标签里让用户直接写自然语言，或者由 agent 采访之后代填。

这说明一件事：**它不打算做一份让厂商去填的严格 schema。** 传统工业标准的路数是先定义几百个标准化数据类型，厂商照着映射。MHS 反过来，把“这台机器是什么”交给自然语言，由模型负责理解。

这很像 Anthropic 的风格——MCP 当年的工具描述也是自然语言。好处是接入成本极低，坏处也明显：**同一台设备，两个人写出来的描述可能完全不同，模型的行为也就跟着不同。**

那么参考文件里的“安全上限”是什么形态？官方只说会“强制”执行，没说在哪一层强制。我猜**至少有一部分是驱动层的运行时校验**，也就是命令发出去之前先比对一下数值范围。这个猜测的依据是官方自己举的例子——研究员说“MHS 强制设备级安全上限，我不用担心 agent 误用过大的激光功率”。这话听起来像是驱动拦下了越界的写操作，而不是设备自己拒绝。

如果真是这样，就直接引出下一章的问题。

━━━━━━━━━━━━━━━━━━━━

◆ 第四章：真问题在哪

━━━━━━━━━━━━━━━━━━━━

规范没公开，但已经有几个问题不必等规范就能问。

**第一个：那个上限是提示还是联锁。**

一个社区项目在自述里说得很清楚，我觉得这是整轮讨论里最扎实的一句技术判断：JSON Schema 里的 maximum 字段，是一个“模型被训练成会尊重的提示，不是一道能阻止命令的联锁”。

这个区分在软件里无所谓，在硬件里是全部。同一份自述里还有一句话，我觉得该记下来：

> 数据库查询写错了，抛个异常重试；文件路径写错了，看栈追踪；机械臂轨迹写错了，一台报废的八万美元设备。

原文那句是：一个 token 的爆炸半径，在它变成力矩的那一刻就完全变了。

所以关键问题是：MHS 参考文件里那些安全上限，究竟是驱动运行时的一道校验（可以被绕过、被配置错、被 agent 用别的路径回避），还是要求接到设备本身的硬件联锁上？

**官方没有回答这个问题。** 而这个答案决定了整套东西能不能负责任地用。

────────────────────

💡 拦在软件里，和拦在电路里

工业安全领域对这件事有很硬的分层，值得借来看 MHS。

**最外一层是软件校验。** 程序里写一句“转速不能超过 3000”，发命令之前比一比。它拦得住老实的调用者，拦不住走别的路径进来的命令、配置写错的部署，也拦不住这段校验本身没被执行的情况。

**最里一层是硬件联锁。** 急停按钮直接串在动力回路里，按下去电就断了，跟软件说什么没关系；安全门开关、限位开关也是这个路数。它不理解意图，只认物理状态。

这两层的区别不是可靠性高低，是**故障时的行为**。软件校验失效的方式是“它没拦住”，硬件联锁失效的方式被设计成“它把电断了”。

回到 MHS：参考文件里那句“会强制哪些安全上限”，落在这两层的哪一层，官方没说。如果落在最外层，那它是一道有用的护栏，但不能替代下面本来就该有的东西；如果它想落到最里层，那就得回答一个更难的问题——一份用自然语言写出来的标签，怎么变成一条电路。

我的猜测是前者。**这不是缺陷，是定位问题。** 麻烦在于，一个宣称能让 agent 安全操作设备的标准，如果不说清楚自己在哪一层，用的人很容易当成后者。

────────────────────

**第二个：datasheet 本来就骗人。**

MHS 的核心假设是，把设备手册里的信息结构化之后，agent 就知道该怎么用这台机器了。Hacker News 上一位做硬件的用户给了一条很实在的反驳：

> 我的经验是，datasheet 常常不完整，甚至有误导。大部分时间花在反复摆弄硬件上，搞清楚到底要做哪些事、按什么顺序、有时候命令之间还得留多长的延时，那玩意儿才能稳定工作。

这条我很有共鸣，因为最近几周我在做的正是这类活。DLSS 5 那套神经网络往 AMD 显卡上移植，规格书上写着的东西和实测跑出来的东西差着好几层，绝大部分时间都花在补那个落差上。

**把手册结构化，结构化的是手册里写了的那部分。** 老师傅脑子里那些“这个夹爪抓 2 公斤会翻”“这条命令后面得等 50 毫秒”，恰恰是手册里没有的。MHS 用自然语言标签让用户自己填，某种程度上就是想把这部分捞进来——但捞得进来多少，取决于填表的人愿意写多细。

**第三个：这在法律上可能不是一个配置文件。**

欧盟新的机械法规 2023/1230 在 2027 年 1 月 20 日强制适用，取代现行的机械指令。它有个变化跟这件事直接相关：**它首次把软件完整性、软件更新、联网功能，以及自学习系统，一并纳入了机械的安全评估范围。**

那么一份约束机械臂速度和关节角度的参考文件，算什么？它在执行一个安全功能。按新法规，高风险类别下，这类东西可能不是配置产物，而是**受监管的安全部件**。写这份文件的人，可能在不知情的情况下写了一个需要合规评估的东西。

这不是我的推论，是一家科技媒体分析这件事时提的角度，我核了法规的编号和生效日期，是对的。MHS 现在还是研究预览，暂时不用面对这个；但如果它真的成为通行接口，这一关躲不过去。

**第四个，我觉得最值得说的一条：真正该说话的人还没来。**

Hacker News 那个讨论帖我从头翻到尾，批评集中在两类：一类是标准政治——“又一个标准”、“凭什么是你来定”、“这不就是 USB HID 吗”；另一类是抽象层次——一位用户读到“驱动会告诉 agent 机械臂有多重”时的原话是“我看到这句时生理性地抽了一下”，接着问：让大语言模型对着机械臂用文本命令完成复杂物理操作、还不许出错，这真的是对的抽象层次吗？底下第一条回复只有一句：我们是不是把 Therac-25 给忘了。

Therac-25 是 1980 年代的放疗设备，软件缺陷导致患者受到过量辐射，有人因此死亡，是功能安全领域的经典教材案例。

这些批评都有道理。但我注意到一件事：**整帖里没有人讨论实时性、确定性、延迟抖动、EtherCAT，也没有人提 SIL 或者 ISO 13849 这些功能安全等级。**

换句话说，进场讨论的基本是软件工程师。真正天天跟安全 PLC、双通道回路、急停继电器打交道的自动化工程师，还没入场。

**而 MHS 要动的恰恰是他们的地盘。** 一个协议在软件圈热议了两周、自动化圈毫无声音，这个状态本身比协议内容更值得记一笔。

━━━━━━━━━━━━━━━━━━━━

◆ 第五章：那它跟已有的东西比，新在哪

━━━━━━━━━━━━━━━━━━━━

这块官方避而不谈。公告全文**没有提到 ROS 2、OPC UA、Modbus、SiLA 2、LabVIEW 中的任何一个**，一个字都没有。

而这些东西全都存在，而且成熟。SiLA 2 是实验室仪器互联的开放标准，底层用 gRPC 加协议缓冲区（Protocol Buffers）；OPC UA 是流程工业的通用信息模型，还有专门给实验室设备的扩展；ROS 2 是机器人领域的事实中间件。光是实验室控制软件这一格，社区随口就能列出 EPICS、TANGO、Bluesky、QCodes、Sardana、yaq 一串。有人的评语是：Anthropic 在造这些东西的第 n+1 版。

那个著名的“又一个新标准”漫画，在那帖里被贴了至少四次。

不过我觉得把 MHS 归成“重复造轮子”也不完全对。有一条区分值得认真对待，来自 Hacker News 上一位用户，我认为是全场最好的技术归纳——**再强调一遍，这是社区推测，不是官方说法**：

他给了一个分层：

```
Agent → MCP / 命令行 / 代码
      → MHS
      → 厂商 API / SCPI / OPC UA / ROS 等
      → CAN / Modbus / USB 等
      → 硬件
```

按这个理解，MHS 不取代下面任何一层，它是**加在最上面的一层面向 AI 的硬件抽象**。OPC UA 和 SiLA 解决的是“软件到机器”的语义和控制，MHS 想解决的是“AI 到机器”的那一层——描述能力、元数据、安全上限，外加读写和发现。他举的例子是：“能测温度”“这条臂重 X 公斤”“转速永远不要超过 X”，**而不是把这些埋在某份数据手册里**。

如果这个理解成立，那 MHS 的新意不在传输，也不在控制，而在**它假设读这份描述的是一个模型，不是一个程序员**。传统标准的描述是给实现者看的，写完之后由人翻译成代码；MHS 的描述是给 agent 当场读的，所以可以是自然语言，也必须包含那些“人会自己脑补、机器不会”的东西——重量、上限、注意事项。

**这个方向我认为是对的。** 现在市面上很多机器人的路数是先造一个身体再想办法给它装脑子，而实验室里那些机械臂、显微镜、移液器已经存在几十年了，身体不缺，缺的是让脑子够得着。MHS 不造身体，只铺接口，这一步的顺序是顺的。

问题在于，它赌的是“手册里那些默会知识可以被自然语言标签捞出来”。前面那位硬件工程师的反驳，赌的正是这一条捞不干净。

这场赌局的结果，得等规范公开、等真有人拿它跑坏过几台设备之后才知道。

不过顺着这个方向，我自己有个更长远一点的看法，跟标准无关，先记在这儿。

**先有成熟的大脑，再接上小脑，这个顺序我认为是对的。** 大语言模型这层已经跑通了，它知道“做完这步该做哪步”“这个结果不对劲”；机器人身上那些视觉—语言—动作模型（Vision-Language-Action，VLA）负责的是另一件事——把一个意图变成关节角度、变成力的大小，而且要在几毫秒里反复修正。这个分工很像大脑和小脑：一个管想干什么，一个管怎么把它干得稳。

有意思的是，前面提到的那个社区项目自己就补了一层，起名就叫小脑层，自述里写的是“大脑（大语言模型）提供意图，小脑处理实时控制”。**官方规范里没有这一层，社区自己长出来了**，这大概能说明缺口在哪。

但我不认为大脑和小脑之间会长期停在现在这种形态。**现在这套连接是离散的、文本的**：上面想清楚了，压成一句话或者一组参数发下去，下面再解开。中间必然有一次坍缩——意图在模型内部是高维的，落成文字就只剩下能被文字表达的那部分。

生物身上不是这么连的。运动皮层和小脑之间没有“发命令”这个环节，是持续的高维信号来回跑，而且下面一直在往上回传：现在的姿态、受了多大的力、偏了多少。这才是闭环。

所以我猜将来这两层之间更可能是某种连续的表示直接对接，而不是打印一句话再念给对方听。当然这有代价——两端得一起训过才能对齐，也就没法像协议这样随便换一头。**协议解决的是能不能连上，那个方向解决的是连得好不好，两件事大概会长期并存。**

这段是我的猜测，没有论文支撑，写下来是为了以后回头对账。

◆ 收尾：现在能下的判断

━━━━━━━━━━━━━━━━━━━━

查完这一圈，我的判断分三条。

**就现状而言，它还不能算一个标准，是一份意向声明。** 两个动词、一份自然语言参考文件、三个入口，加上一句“开源之前还有工作要做”。规范没有、代码没有、日期没有。中文圈这两天讨论的那些技术细节，凡是具体到字段名的，我查下来来源都是社区猜测，不是官方。

**方向我认为是对的**：不造身体，接现成的身体，而且承认读这份描述的是模型不是人。

**但有两件事现在悬着**，而且都不是小事：那些安全上限到底是驱动里的一道校验还是设备上的一道联锁；以及手册里没写的那部分，能不能靠让用户用自然语言填标签捞回来。

这两件事一个是工程问题，一个是认识论问题，官方都还没回答。

我自己填了那份申请表，等着。批下来能看到规范，我就写一篇真的协议解析，把这期猜的部分逐条对账，猜错了就认。批不下来，那就等它开源，或者等第一份被公开的驱动源码。

最后说一句我觉得这件事最有意思的地方：**这个标准现在还没有内容，社区已经开始替它编内容了。** 三个不同的人分别注册了叫 Open-MHS 的仓库，一家上市公司的官方仓库里跑着标注为“猜的”占位协议，还有人抢注了包名，自述里写着“还不是一个发布的 SDK”。

大家都在为真规范落地的那天做准备。这个场面本身，比协议规范更能说明现在这个行业的状态。
