【DeepSeek-V4-Flash@DGX Spark】从 12 到 24 token/s，速度为什么翻倍？

━━━━━━━━━━━━━━━━━━━━

◆ 起因：换了套社区方案，速度翻倍，但不知道为什么

━━━━━━━━━━━━━━━━━━━━

DGX Spark 上跑 DeepSeek V4 Flash，社区的方案从 jasl 的 Marlin kernel 加 eugr 的构建脚本，升级到了 tonyd2wild 的方案。我自己的实测速度从 12 tok/s 提升到了 24.5 tok/s（不考虑 DSpark 投机解码的加速）——同一对机器、同一个量级的模型，单流解码速度直接翻倍。很好奇其中缘由，于是调查一番。

先交代坐标：老方案是我们 5 月份手搓的——jasl 的 vLLM fork（ https://github.com/jasl/vllm ）打底、eugr 的构建镜像做环境，我们在上面缝了个混合后端（185 期 https://mp.weixin.qq.com/s/dEc-wD0JcM5WhKicOUR1pQ 记的就是这笔账）；新方案是社区 8 月的成熟货——预编译好的 Docker 镜像加 tonyd2wild 的双机配方（ https://github.com/tonyd2wild/Deepseek-v4-Flash-TP2-DGX-Spark-500k-CTX ），拉下来改几个参数就能跑。想自己对代码的读者，两个仓库都在这儿了。

速度翻倍这件事，最省事的解释是"新的当然比旧的快"。但这个解释等于没解释——中间隔了三个月，代码从上到下全换过一遍，到底是哪一层在起作用？调查方法很朴素：老方案的 fork 本来就是 git 仓库躺在盘上；新方案的代码活在 Docker 镜像里，用 `docker cp` 把镜像里的 vLLM 整个抽出来（390MB），摊成普通目录，两边对着读。翻倍前后，每生成一个 token 的时间从约 80 毫秒缩到约 41 毫秒——省下来的这 40 毫秒，逐项找出处。

结论先说：**真正的大头是两条，外加一条中等的；而几个"听起来最像原因"的候选，读完代码发现根本不是**。先讲有功的，再讲那几笔容易记错的账。

━━━━━━━━━━━━━━━━━━━━

◆ 1. 真正起作用的：两个大头，一个中等

━━━━━━━━━━━━━━━━━━━━

**大头一：CUDA graph——从"逐个派活"到"整图重放"。**

老方案是带着 `--enforce-eager` 跑的。这不是我们不想快：当年 CUDA graph 在 sm_121（DGX Spark 的 GPU 架构）上有非法内存访问的坑，只能整个关掉。eager 模式下，43 层网络每层几十个 GPU kernel，生成一个 token 要靠 CPU 逐个下发上千次启动命令——而这台机器的 ARM CPU 单线程并不快，光派活就吃掉每步时间的一大块。

新方案不但开了 CUDA graph，而且开得很彻底：读代码确认，它的 FULL 模式是**把整个模型的前向计算录成一张完整的图**，连双机之间的通信操作都包在图里一起重放。单流解码的稳态下，CPU 每步只发射一次，43 层的计算加通信全在 GPU 侧自己滚完。

**大头二：MoE kernel 从"均码成衣"换成"量体裁衣"。**

老方案的 MoE 矩阵乘走 Marlin——vLLM 里的通用 4 比特量化 kernel 家族，从各种架构各种模型一路服务过来的老将，在 sm_121 上"能跑但不顺"（它的数据布局是给前代架构设计的，185 期那桩乱码案的根子就在这儿，最后一层还得换后端兜底）。

新方案的 B12X 后端则是**专门为这一款 GPU（sm_121）加这一个模型（V4 Flash）的固定解码形状写的窄范围 kernel 库**：权重预先打包成专属布局、按专家路由密度预排计算块、复用预规划的显存、针对这颗芯片调寄存器占用。没有黑科技，就是特化对通用的差距。这条的贡献和 CUDA graph 不相上下。

**中等一条：注意力少了一轮中间搬运。**

这条得先给老方案正名：jasl 的 fork 不是随便改改的通用货，它有专用的 FP8 KV cache 格式、专用的 FP8 矩阵乘、专门的稀疏注意力解码 kernel，是下过功夫的。真正的差距藏在一个中间步骤里——老路径在部分解码形状下，要先把 FP8 压缩的 KV **解压、收集成 16 比特的临时大张量**再做矩阵乘，多一轮显存搬运、多几个 kernel 阶段；新方案的 kernel 直接消费 FP8 格式的分页缓存，中间不落地。短上下文时这条不如前两条显眼，上下文越长占比越大。

────────────────────

💡 CUDA graph 为什么对小 batch 解码是生死项

GPU 干活要 CPU 派活：每个 kernel 启动都是 CPU 侧的一次系统调用级操作，单次几微秒。大 batch 训练时一个 kernel 算几十毫秒，几微秒的派活开销九牛一毛；但单流解码正相反——每个 kernel 就算几十微秒的活，派活开销能占到两三成，而且 43 层网络串行走完，上千次派活攒出十几毫秒，全是 CPU 在拖 GPU 后腿。CUDA graph 的做法是把整套派活序列预先录制成一张图，之后每步只说一声"重放"——上千次派活变一次。这也是为什么各家推理引擎把小 batch 场景的 graph 支持当头等大事，而当年 sm_121 上 graph 有 bug 只能裸跑的我们，等于天生慢一档。

────────────────────

有功的讲完了，下面这几条更有意思——它们是调查前"听起来最像原因"的候选，读完代码发现账全记错了。

━━━━━━━━━━━━━━━━━━━━

◆ 2. 容易安错的功劳：三笔错账

━━━━━━━━━━━━━━━━━━━━

**错账一："肯定是激活降到 8 比特了。"**

这是调查前我们最有把握的一条。Marlin 是 W4A16——4 比特权重解包后喂 16 比特激活；直觉上新方案这么快，肯定是换了 W4A8（8 比特激活直进计算单元），激活带宽减半嘛。

结果新方案的 MoE 后端代码里硬编码着 `quant_mode="w4a16"`—— **它跟 Marlin 一样是 W4A16**，激活压根没降。快出来的部分全在上一节说的"特化"里，位宽一比特都没变。这笔账要是不读代码，几乎必定记给"更激进的量化"——毕竟那是最顺嘴的故事。

**错账二："新版调度把通信藏进计算里了。"**

新镜像日志里有一行"异步调度已启用"，很容易让人以为：双机张量并行每层要同步两次通信，新调度把这个等待重叠掉了。

翻代码，两个反转：一，老 fork 里**一模一样的异步调度代码躺在那儿，而且默认开启** ——根本不是新版独有；二，所谓"通信藏进计算"，两边都不存在——张量并行的每一层至今都是老老实实的"本地算完 → 同步等通信 → 下一层"，代码就那几行，谁也没重叠谁。异步调度真正干的事是让引擎流水线里同时存在两个批次，和单流解码的每步延迟基本无关。这条贡献接近零。

**错账三："反正是新版本，隔代红利呗。"**

这是最偷懒也最常见的一笔糊涂账。隔代红利确实存在——但把它当解释，等于把 40 毫秒记到"时代进步"头上，什么都没学到。逐项剥开后，"新版本"里真正起作用的就是第一节那三条，剩下的零散优化（执行器换代、模型级融合之类）合计只是小头。 **"版本新"不等于"每个部件都新"** ——异步调度那条就是现成的反例：老版本早就有了。

────────────────────

💡 两种最容易记错账的习惯

复盘这三笔错账，错法其实就两种。一种是**拿现成的叙事框架去套**：此前研究过 Marlin 的量化语义问题（224 期的乱码案），"W4A16 对 W4A8"这个框架在脑子里现成放着，看到新方案更快，顺手就把旧框架按了上去——框架越熟，越懒得去查证。另一种是**把整体的新旧当成每个部件的新旧**："新版本更快"没错，但具体到某个特性，老版本可能早就有了。两种错法共享同一个解药：结论过一遍代码（或者数据）再落笔。这次调查立的规矩是"每条判定必须带文件加行号"——行号这东西，是逼着人真去看的机制。

────────────────────

功过都盘完了，最后把账本合上。

━━━━━━━━━━━━━━━━━━━━

◆ 3. 合上账本

━━━━━━━━━━━━━━━━━━━━

| 排名 | 因素 | 贡献 |
|---:|---|---|
| 1 | 整模型 CUDA graph（对 eager 逐 kernel 发射） | 大头 |
| 2 | 为 sm_121 加 V4 Flash 特化的 MoE kernel（对通用 Marlin） | 大头，与第 1 不相上下 |
| 3 | 注意力直读 FP8 缓存（对先解压成 16 比特再算） | 中等，长上下文放大 |
| 4 | 其他零散优化（执行器换代、模型级融合等） | 小 |
| 5 | 异步调度 / 激活位宽 / 泛泛的"版本红利" | 接近零或纯属误会 |

两条附注，都是诚实账：

一，**这两个数字不是严格的对照实验** ——12 tok/s 量的是 preview 版模型（284B），24.5 量的是正式版 0731（304B）。模型更大了反而更快，说明执行栈的优化是实打实的，但"12 到 24.5"没法折算成精确的百分比归因。想分干净有个最小实验：在新方案上什么都不动、只加一个 `--enforce-eager` 再跑一遍，CUDA graph 的独立贡献就量出来了。一条命令的事，留给以后手痒的时候。

二，读代码只能确认 eager 模式下每步有"大量"kernel 发射，具体是八百次还是一千五百次，得上性能剖析工具才知道——方向没有疑问，精确数字标"未核实"。

━━━━━━━━━━━━━━━━━━━━

◆ 尾声：没有魔法开关

━━━━━━━━━━━━━━━━━━━━

调查做完，最初那个问题的答案可以一句话说清：

**社区没有找到魔法开关，而是把我们当年为了"先跑通"留下的三个妥协，逐个换成了正规实现**：被迫关掉的 CUDA graph，换成了整模型录制；将就能用的通用 Marlin，换成了量体裁衣的专用 kernel；注意力里那轮解压搬运，换成了直读压缩缓存。三个"绕"字换成三个"直"字，速度翻倍。

回头看，当年的妥协没有一个是错的——sm_121 刚出、没人支持的时候，"先跑通"就是唯一正确的目标。但生态跟上来之后，每一段绕路都会被正规军拉直，这是必然的事。而且拉直的速度比想象快：这篇调查写到一半，发现配方作者已经又开了个新仓库（ https://github.com/tonyd2wild/DeepSeek-v4-Flash-0731-DSpark-1M-NVFP4-KV-2x-DGX-Spark ）——KV cache 压到 4 比特存储，还顺手修了个上游 vLLM 没人发现的 bug：DSpark 投机解码的草稿头有 12 个权重张量被加载器静默丢弃，接受率从该有的六成掉到两成半，所有人都在跑残血版而不自知。我们照着新仓库当天部署验证：**峰值 83.8 tok/s，代码生成 52.6** ——本文分析的"新方案"在它作者眼里已经是旧方案了，而 12 tok/s 那个起点，此刻已经是上上代的事。

最后说个这次调查最大的感触：出问题时人人都会去查，变快了没人查。**但"为什么变好了"和"为什么变坏了"是同一枚硬币——不搞清楚变好的原因，下次变坏时就少一半线索。**而且不查的话，那三笔错账大概率就当成正确答案记住了：往后逢人就说"W4A8 快"、"新版调度厉害"，传得有鼻子有眼，其实一行代码都对不上。

◆ 技术名词速查

━━━━━━━━━━━━━━━━━━━━

| 术语 | 一句话解释 |
|------|-----------|
| eager 模式 | GPU kernel 由 CPU 逐个即时下发，灵活但派活开销大 |
| CUDA graph | 把整套 kernel 发射序列预录成图，每步一次重放，消灭派活开销 |
| Marlin | vLLM 里的通用 4 比特量化 GEMM kernel 家族，为前代架构设计 |
| W4A16 | 4 比特权重 + 16 比特激活的矩阵乘语义，本文两套方案其实都是它 |
| MoE（混合专家） | 参数分成多个专家、每 token 只激活一小撮的稀疏架构 |
| KV cache | 注意力的"记忆"缓存，V4 Flash 用 FP8 压缩格式存储 |
| Triton | 用 Python 写 GPU kernel 的编译器，快速实现的常用选择 |
| 张量并行（TP） | 把每层权重切开分给多机同时算，每层结束同步一次通信 |
| sm_121 | DGX Spark（GB10 芯片）的 GPU 架构代号，生态支持曾长期缺位 |
| 异步调度 | vLLM 让引擎流水线同时处理两个批次的机制，新老版本都有 |
