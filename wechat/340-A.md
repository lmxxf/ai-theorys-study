【Gemini 4 Argon】面板写着 1M，背地里偷偷砍成 256K：给 Google 的 Antigravity CLI 动一次二进制手术

━━━━━━━━━━━━━━━━━━━━

◆ 第一章：刚为 Gemini 4 高兴两天，就被客户端泼了盆冷水

━━━━━━━━━━━━━━━━━━━━

10 月 13 日到 14 日，Google 终于端出了新一代旗舰推理模型 **Gemini 4 Argon**，紧接着把自家的命令行开发工具 **Antigravity CLI（`agy`）** 升级到了 `v1.3.5`。

纸面参数相当漂亮：主打长程软件工程与多步智能体任务，DeepSWE v1.1 拿到 77.9%，支持 low、medium、high 三档推理强度，最吸引人的是它标配的 **100 万（1M）tokens 上下文窗口**。

切到 `Gemini 4 Argon (Low)`，在终端里敲一下 `/context`，面板上明晃晃地写着：

`Gemini 4 Argon (Low) · 1.0M tokens`

本来是很开心的事——1M 窗口意味着可以把整个项目的长文档、历史论文和几十个源码文件一口气塞进上下文里对质。

结果真拿它干起活来，刚读完一批文件、上下文爬到 25 万 tokens 出头，诡异的一幕出现了：

再发一轮请求，面板上的总 token 数没有往上涨，反而从 **255,921** 掉到了 **247,567**；再问一句，又掉到了 **241,167**。

第一反应是：难道触发了 `v1.3.5` 的自动上下文压缩（checkpoint）？

但即使把自动 checkpoint 关掉，只要总长度一逼近 25.6 万，下一轮请求发出去之前，前面的对话历史还是会被神秘地吃掉一截。更离谱的是，我突然发现模型连项目根目录下最核心的规则文件 `AGENTS.md`（约 118KB，1022 行）都没记住——问它里面写了什么，它只能支支吾吾去现场调工具读文件。

面板上明明写着 `1.0M`，为什么一到 25.6 万就偷偷砍历史？原本自动加载的 `AGENTS.md` 为什么人间蒸发了？

不信 UI 面板，直接去扒 `agy` 落在本地磁盘上的会话数据库（`~/.gemini/antigravity-cli/conversations/<会话ID>.db`）。打开 `gen_metadata` 和 `executor_metadata` 两张表一看，Google 藏在客户端底层的两把暗锁当场现了原形。

━━━━━━━━━━━━━━━━━━━━

◆ 第二章：第一把锁——面板标 1M，底层请求锁死 256K

━━━━━━━━━━━━━━━━━━━━

在会话数据库里解开每次模型调用的 `ContextWindowMetadata`，刚才那三次 token 回落的请求，落盘记录写得清清楚楚：

- `max_context_tokens = 256000`
- `truncation_reason = 2`

**什么 1.0M 上下文窗口，在客户端发请求的那一刻，上限被硬生生锁死在了 256,000！**

这里需要纠正一个很容易踩的误区：**token 数回落，不代表客户端生成了摘要。** 哪怕你关掉了自动 checkpoint（没有生成总结），只要当前会话逼近 `max_context_tokens = 256000` 这条红线，客户端在发送请求前依然会按 `truncation_reason = 2` 直接把早先的历史记录裁掉。

为什么 `/context` 面板显示 1.0M，实际请求却变成了 256K？

把本机 `~/.local/bin/agy`（Linux ARM64，`v1.3.5`，一个 204,820,664 字节的 Go 二进制文件）拆开逆向，顺着配置加载链路追下去，发现我们之前对 `agy` 窗口机制的理解太天真了，一路连踩了好几个坑：

1. **只改 `GetCheckpointConfig` 里的 256000 常量没用。** 那两组 256000 常量参与的只是早期 `min(模型可用额度, 上限)` 的计算，改大之后，依然挡不住后续步骤的配置覆盖。
2. **只改模型内嵌的实验配置字符串也没用。** 逆向发现，`Gemini 4 Argon (Low)` 在内部的模型编号是 **1419**（对应枚举 `MODEL_PLACEHOLDER_M419`），它的内嵌模型映射继承自 **M408**。在 M408 的 `CASCADE_USE_EXPERIMENT_CHECKPOINTER` 内嵌配置里，确实写着 `max_token_limit="256000"`。但当我们把二进制里这份内嵌配置改成 `1000000`、甚至尝试加上内置的 `contextWindow: "900K"` 重启后，发出的真实小请求落盘一看——`max_context_tokens` 依然顽固地停在 **256000**。（排查中途还闹过一个乌龙：把一个 10 月 13 日残留的 `T (stopped)`、终端早已关闭的僵尸进程误认成了当前窗口，以为是没重启客户端；核对日志确认正常退出重启后，才彻底死心——单纯改内嵌静态配置根本压不住。）

真正的总阀门，在 **`config.applyFeatureProviderCheckpointOverrideConfig`**。

不管前面常量怎么算、内嵌表怎么改，这个函数在合并完所有特征提供方（Feature Provider）的覆盖配置后，会在出口处把最终合并出来的 `CheckpointConfig` 指针写回运行配置。只要在这个合并出口动手，才能真正把 1M 窗口从 Google 手里抢回来。

━━━━━━━━━━━━━━━━━━━━

◆ 第三章：第二把锁——解开 24KB 截断，反而触发整份丢弃

━━━━━━━━━━━━━━━━━━━━

在动手改窗口之前，还得先弄明白另一桩冤案：为什么 118KB 的 `AGENTS.md` 连一行都没加载进去？

这又是 Google 设下的一套**双层连环锁**。

**第一层锁：单文件 24,000 字节硬截断。**
在原版 `agy` 的 `readGlobalRules`（偏移 `0x77395dc`）、`parseRuleFile`（`0x773a2d0`）和 `convertSkillPath`（`0x773d724`）三个函数里，读取本地规则文件时都有一条写死的 ARM64 指令：

```text
mov x2, #24000    ; 原指令字 0xd28bb802
```

也就是说，任何超过 24KB 的 `AGENTS.md`，原版只会读前 24,000 字节，后面的全部削掉。为了装下 118KB 的完整规则文件，我们早已把这三处指令改成了 `0xd2a00202`（即 `1,048,576` 字节，1MB 上限）。

**谁能想到，解开了第一层 24KB 的锁，反而精准踩爆了第二层雷！**

在 `customizations.(*Manager).computeTruncatedCustomizations` 函数里，客户端还藏着第二道审查：**规则（rules）与自定义内容（customizations）的 token 总预算，默认上限各为 20,000 tokens。**

最损的设计就在这里——

当第一层 24KB 截断还在的时候，你的 `AGENTS.md` 被砍成 24KB（折合大约七八千 tokens），塞进 `computeTruncatedCustomizations` 一算，没超 20,000 tokens 预算，于是前 24KB 能顺利内联注入给模型；

可一旦你把 24KB 的锁解开了，118KB 的完整 `AGENTS.md` 整份送进来，折合大约 4 万 tokens，当场超出 20,000 tokens 的规则总预算！

而 `computeTruncatedCustomizations` 面对超预算的规则文件，采取的策略**不是按 20,000 tokens 截短，而是整份直接踢出内联注入**！落地到数据库的 `user_rules` 字段里，118KB 的内容荡然无存，只剩下一句通知：

```text
The following user-defined rules exceeded the rules token budget and were excluded from inline injection. View the file for further instructions when relevant:
- /home/lmxxf/work/ai-theorys-study/AGENTS.md
```

这就是为什么解开 24KB 限制之后，模型反而从“读了半截”变成“连 `AGENTS.md` 的一个字都没读过”。两道锁必须一起砸开，只开第一道，死得更惨。

◆ 第四章：借尸还魂——在死代码区手搓 ARM64 跳板

━━━━━━━━━━━━━━━━━━━━

病灶全部定位清楚，接下来就是给 `~/.local/bin/agy` 动外科手术。一共两刀：一刀切开 1M 上下文窗口，一刀扩开规则 token 预算。

先看第一刀：**在 `config.applyFeatureProviderCheckpointOverrideConfig` 合并配置后的出口（文件偏移 `0x718d094`），把 Argon Low（模型编号 1419）的 `CheckpointConfig.max_token_limit` 强制写为 `1000000`。**

在 `0x718d094` 处，原版指令是：

```text
str x1, [x0, #16]   ; 机器码 0xf9000801
```

此时寄存器 `x0` 指向外层的 `CascadeConfig` 结构体，`x1` 指向刚刚合并完的 `CheckpointConfig` 结构体。我们要做的，是在这里拦一道：读取 `CascadeConfig.planner_config.plan_model`，检查是否等于 `1419`；如果匹配，就把 `[x1, #16]`（即 `max_token_limit` 字段）覆写成 `1000000`，同时不动任何其他模型的窗口配置。

这需要大约 10 条 ARM64 指令。但改 ELF 二进制最忌讳插入字节改变文件大小，这 40 字节的跳板代码（Trampoline）往哪儿放？

现成的空地就在旁边：**借用已被废掉的 `hooks.checkpointNeeded` 函数体（`0x76f7c80`）。**

为了彻底禁止客户端自动打断会话做 checkpoint，我们本来就要把 `hooks.checkpointNeeded` 在函数入口 `0x76f7c80` 直接短路返回 `false`。一旦入口直接 `ret`，它后面从 `0x76f7ca0` 开始的一大片原有函数体就成了永远执行不到的死代码，正好拿来当跳板机房！

这里还真刀真枪踩了一个 **Go 语言 ARM64 ABI 多返回值**的坑：

`hooks.checkpointNeeded` 在 Go 里的返回值签名不是单个 `bool`，而是 `(bool, error)`。在 ARM64 寄存器约定下，`x0` 放布尔值 **`false`（0）**，而 **`x1` 和 `x2` 存放 `error` 接口的动态类型指针和数据指针**。

第一次打补丁时，我们在 `0x76f7c80` 只写了 `mov x0, xzr`（清零 `x0`）就接 `ret` 返回。结果一发请求，调用方检查 `x1/x2` 发现不为零，把寄存器里残留的旧数据当成了一个非空的 `error` 接口对象去解引用，进程当场段错误崩溃！

回退之后，老老实实把 `x0`、`x1`、`x2` 三个寄存器全清零再 `ret`：

```text
0x76f7c80:
  mov x0, xzr      ; 0xaa1f03e0 (return false)
  mov x1, xzr      ; 0xaa1f03e1 (error.tab = nil)
  mov x2, xzr      ; 0xaa1f03e2 (error.data = nil)
  ret              ; 0xd65f03c0
```

紧接着，从死代码区 `0x76f7ca0` 开始写入 10 条指令的跳板：用死寄存器 `x3` 取出 `planner_config` 指针（若为空则跳过），读取偏移 `#64` 处的 `plan_model` 与 `1419` 比较；相等则用 `movz/movk` 拼出立即数 `1000000`（`0xf4240`）写入 `[x1, #16]`，最后补做被替换的原指令 `str x1, [x0, #16]`，无条件跳回 `0x718d098`。

不新增函数调用、不改栈帧、不增减一字节文件长度（保持 `204,820,664` 字节）。

再看第二刀：**解除 `AGENTS.md` 的 20,000 tokens 规则总预算锁。**

在 `customizations.(*Manager).computeTruncatedCustomizations` 里，把规则（rules）和自定义内容（customizations）两项预算的**配置读取路径和默认路径**一共 4 处指令，全部改成加载立即数 **131,072 tokens（128K）**：

| 文件偏移 | 原指令字 | 新指令字 | 作用说明 |
| :--- | :--- | :--- | :--- |
| `0x773e864` | `0xb98000e7` | `0xd2a00047` | 自定义内容预算（配置读取路径），`x7 = 131072` |
| `0x773e874` | `0xd289c407` | `0xd2a00047` | 自定义内容预算（默认路径，原为 20000），`x7 = 131072` |
| `0x773e8c4` | `0xb98000c6` | `0xd2a00046` | 规则预算（配置读取路径），`x6 = 131072` |
| `0x773e8d4` | `0xd289c406` | `0xd2a00046` | 规则预算（默认路径，原为 20000），`x6 = 131072` |

为什么连配置读取路径（`ldrsw`）也一起覆写成 `movz`？因为单改内嵌默认值仍然可能被显式下发的配置盖掉，直接改在消费预算的寄存器赋值上，谁来都改不回去。

◆ 第五章：三步实盘验尸——一口气灌进 30 篇长论文

━━━━━━━━━━━━━━━━━━━━

踩过前面那么多坑，现在的铁律就一条：**面板数字不算数、`agy --version` 能启动不算数、模型嘴上自称“我读过了”也不算数，一切以 SQLite 会话数据库落盘的真实字节与实盘高压测试为准。**

补丁脚本跑完（最终二进制 SHA256 为 `d64feb0f3c39825b5d20a2bcf11c90624c89da8862942da8c6380950e130a40f`），重启 `agy` 开启新会话，分三步验货：

**第一步：查验真实上下文窗口上限。**
在独立测试会话里发一条最小请求，打开数据库查 `executor_metadata` 与 `gen_metadata`。落盘的实际请求上下文上限变成了：

`983,040 tokens`

算一下这笔账：`1,048,576 (1M) - 65,536 (64K 输出预留) = 983,040`。之前阴魂不散的 `256000` 彻底消失。

**第二步：查验 `AGENTS.md` 全量内联注入。**
进入项目目录发起新会话，直接提取数据库中保存的 `user_rules` 字段：总长度为 **119,283 字节**，逐字节比对，完整包含了本地 `AGENTS.md` 的 **118,908 字节原文**，那句“exceeded the rules token budget”的排除提示不复存在。此时敲 `/context`，面板上的 `System prompt` 实打实占到了 **43.2k tokens**。

**第三步：长会话跨过 256K 实盘压力测试。**
小请求配置对了，万一长会话冲过 256K 还有别的暗桩呢？
我直接在当前会话里下指令：让 `Gemini 4 Argon (Low)` 从第 96 篇论文开始，一口气连续调用工具读取仓库里的 **30 篇中英双语长文**。

30 篇论文全部读完进场，再敲开 `/context`：

```text
Gemini 4 Argon (Low) · 474.8k/1.0M tokens (45.3%)
Token usage by category
◉ User messages: 395 tokens (0.0%)
◉ Agent responses: 3.8k tokens (0.4%)
◉ Tool calls: 414.1k tokens (39.5%)
⛁ System prompt: 43.2k tokens (4.1%)
⛁ System tools: 11.9k tokens (1.1%)
⛁ Skills: 681 tokens (0.1%)
⛁ Subagents: 686 tokens (0.1%)
□ Free space: 573.8k (54.7%)
```

**474.8k tokens（45.3%）！**

一路冲过 256K 的旧生死线，直接来到 47.4 万 tokens，没有任何 token 回落，没有任何发送前静默裁剪，最早第一批读进去的第 96 篇论文和第一轮敲的 `wc -l` 命令完好无损地躺在上下文最前端。

◆ 尾声：云端画的饼，得靠本地的刀来兑现

━━━━━━━━━━━━━━━━━━━━

复盘这一整晚的折腾，其实挺让人感慨的。

Google 发布了强大的 Gemini 4 Argon，在宣传页和客户端面板上都高调写着 `1.0M tokens`，甚至连 Google AI Ultra 订阅门槛都拉满了；但在闭源 CLI 客户端的二进制深处，却用层层叠叠的实验配置把实际请求锁在 `256K`，又用“24KB 单文件截断 + 20K 规则预算整份丢弃”把重度用户的长规则文件拒之门外。

普通开发者如果只看 UI 界面，遇到聊到一半上下文失忆、`AGENTS.md` 写了不生效，大概率只会骂一句“Gemini 4 怎么也这么笨”，根本想不到是脚下的客户端在发请求前偷偷动了手脚。

另外还顺手验证了一件事：直接让云端模型在对话里分析它自己的二进制、打印大段反汇编时，偶尔会撞上外层安全过滤被拦截；少让模型在对话框里吐大段无关汇编，优先用本地 Python 脚本静默解析定位、只输出关键偏移，干净利落得多。

好在客户端终究跑在我们自己的 Linux 机器上。只要二进制文件还在本地磁盘，它虚标的窗口就能补成真窗口，它暗埋的锁就能一把把拆下来。
