【番外】面板写着 1M，背地里偷偷砍成 256K：给 Google 的 Antigravity CLI 动一次二进制外科手术

━━━━━━━━━━━━━━━━━━━━

◆ 第一章：面板上的 1.0M 是画给用户看的饼

━━━━━━━━━━━━━━━━━━━━

Google 的 Antigravity CLI（也就是命令行里的 `agy`），切到最新的 Gemini 4 Argon 模型之后，敲一下 `/context`，面板上明晃晃地写着一行字：

`1.0M tokens`

看着很大方对吧？一百万上下文窗口，随便造。

但只要你真拿它干重活，读几十个文件、上下文刚爬到 25 万 token 左右，诡异的事情就发生了：下一轮请求发出去，token 数突然从 `255921` 掉到了 `247567`，再发一轮又掉到 `241167`。

一开始以为是触发了自动生成摘要（checkpoint）。结果把自动 checkpoint 关掉，它照样在 25 万出头的地方咔嚓一刀往回缩。

不信面板，直接去扒会话落地在本地 SQLite 数据库（`~/.gemini/antigravity-cli/conversations/<会话ID>.db`）里的真实请求记录。打开 `ContextWindowMetadata` 一看，底裤当场掉了下来：

`max_context_tokens = 256000`
`truncation_reason = 2`

**什么 1.0M 窗口，全是 UI 面板画给用户看的饼！**

发请求之前，客户端在底层硬生生把上下文上限锁死在了 **256K**。只要你的对话历史接近 256K，哪怕关了自动总结，发送前它也会静默把你前面的历史记录裁掉（`truncation_reason=2`），而且面板上连个招呼都不打。

更绝的还在后头——不仅上下文窗口给你偷偷打二五折，连项目根目录下的 `AGENTS.md`（规则与记忆文件），它都敢给你整份扔进垃圾桶。

━━━━━━━━━━━━━━━━━━━━

◆ 第二章：解开第一把锁，直接触发第二颗雷

━━━━━━━━━━━━━━━━━━━━

我的项目目录下放着一份 118KB（1022 行）的 `AGENTS.md`，里面装的是完整的工程规则和长期记忆。

原版 `agy` 在读取规则文件时，有第一道暗锁：**单文件 24000 字节截断**。

在二进制的 `readGlobalRules`、`parseRuleFile`、`convertSkillPath` 三个函数里，各有一条硬编码的 ARM64 指令：

```text
mov x2, #24000   (机器码 0xd28bb802)
```

超过 24KB 的部分直接一刀切。这个好办，之前我们已经把这三处的立即数改成了 `1048576`（1MB，机器码 `0xd2a00202`），解开了单文件 24KB 的字节锁。

按理说，24KB 的锁打开了，118KB 的 `AGENTS.md` 该老老实实全量读进来了吧？

结果今天一查数据库里的 `user_rules` 字段，里面根本没有 `AGENTS.md` 的内容，只躺着这么一段冷冰冰的英文提示：

> The following user-defined rules exceeded the rules token budget and were excluded from inline injection. View the file for further instructions when relevant:
> - /home/lmxxf/work/ai-theorys-study/AGENTS.md

翻译成人话：**因为你的规则文件超过了 token 预算，我们决定一行都不给你注入，整份排除。**

这就叫连环套——

当你没破 24KB 字节锁的时候，文件被砍成 24KB（约 6000~8000 tokens），刚好低于 20000 tokens 的总预算，所以能塞进去半截残废的；**等你费劲把 24KB 的单文件锁破掉了，118KB 的完整文件放进来一算，大约 4 万 tokens，当场撞上第二道暗锁：20000 tokens 的规则总预算！**

而 Google 工程师写这段逻辑（`customizations.(*Manager).computeTruncatedCustomizations`）的时候非常狠：超了预算不是按预算截断，而是**整份直接踢出内联注入**！

于是破完第一道锁的结果，是从“读半截”变成了“连一个字都不读”。

◆ 第三章：为什么改配置和改常量全不管用

━━━━━━━━━━━━━━━━━━━━

先回头收拾那个假 1M、真 256K 的窗口限制。

为什么之前改 `GetCheckpointConfig` 里的 256000 常量没用？把 `agy`（Linux ARM64，v1.3.5，一个 204MB 的 Go 编译二进制）逆向拆开顺着调用链追，才看明白里面的弯弯绕：

1. `GetCheckpointConfig` 里的两组 256000 常量，参与的只是 `min(模型可用额度, 上限)` 的早期计算，改了它，拦不住后面的配置覆盖。
2. Gemini 4 Argon (Low) 在内部对应的模型编号是 **1419**（内部代号 `MODEL_PLACEHOLDER_M419`），它的内嵌模型映射继承自 **M408**。
3. 在 M408 的内嵌实验配置 `CASCADE_USE_EXPERIMENT_CHECKPOINTER` 里，明文写着 `max_token_limit="256000"`。
4. 但是，**哪怕只把二进制里这份内嵌配置的字符串改成 1000000，或者在外部配置里写上 `contextWindow: "900K"`，重启之后落盘的真实请求依然是 256000！**

原因在于：`agy` 在启动和发起请求时，会经过一层 `config.applyFeatureProviderCheckpointOverrideConfig`（特征提供方配置合并）。不管你前面常量怎么改、内嵌 JSON 怎么改，合并函数走完出来，最终写入 `CheckpointConfig.max_token_limit`（结构体偏移 `#16` 处）的值，又被覆盖回了 256000。

要想一劳永逸，不能在源头跟它的配置表捉迷藏，必须守在**配置合并完成后的最终出口**，直接劫持写内存的那一刀。

━━━━━━━━━━━━━━━━━━━━

◆ 第四章：借尸还魂——在废弃函数里手搓 ARM64 跳板

━━━━━━━━━━━━━━━━━━━━

定位到 `config.applyFeatureProviderCheckpointOverrideConfig` 合并配置后的出口，文件偏移在 `0x718d094`。

原版在这里有一条指令：

```text
str x1, [x0, #16]
```

其中 `x0` 是 `CascadeConfig*` 指针，`x1` 是刚刚合并出来的 `CheckpointConfig*` 指针。这条指令就是把合并好的配置挂上去的最后一步。

我们的目标是：在这条指令执行前跳出去，检查当前模型是不是 **1419（Argon Low）**；如果是，直接把 `CheckpointConfig.max_token_limit`（位于 `[x1, #16]`）强行改写成 **1000000**，然后再跳回来。

但二进制文件不能随便往里插字节——一旦文件长度变了，后面的偏移全乱，整个 ELF 直接报废。去哪找一块空地放我们的补丁指令（Trampoline 跳板）呢？

答案是：**借尸还魂。**

为了关掉自动生成摘要，我们正好要把 `hooks.checkpointNeeded` 这个函数（入口在 `0x76f7c80`）废掉，让它永远直接返回 `false`。一旦这个函数在入口处直接 `ret` 返回，它原本长达几百字节的函数体就彻底成了永远不会执行的死代码（Unreachable Code）！

这块现成的“尸体”，就是天然的跳板空间（Code Cave）：

1. **先把 `hooks.checkpointNeeded` 入口（`0x76f7c80`）改成直接返回 `false, nil`：**
   这里踩过一个 Go 语言底层的坑——Go 的函数是多返回值的，`checkpointNeeded` 的签名返回的是 `(bool, error)`。在 ARM64 Go ABI 里，`x0` 是布尔返回值，而 **`x1` 和 `x2` 是 `error` 接口的两个寄存器（type 和 data）**。
   第一次动手时只清零了 `x0` 就直接 `ret`，结果调用方把寄存器里残留的垃圾值当成了非空的 `error` 对象，程序当场崩溃！
   老老实实把 `x0`、`x1`、`x2` 全部清零再返回：
   ```text
   mov x0, xzr      (0xaa1f03e0)
   mov x1, xzr      (0xaa1f03e1)
   mov x2, xzr      (0xaa1f03e2)
   ret              (0xd65f03c0)
   ```

2. **在 `0x76f7ca0`（函数体死代码区）写跳板指令：**
   用死寄存器 `x3` 读出 `CascadeConfig.planner_config.plan_model`，比对是否等于 `1419`；如果是，就把 `1000000`（`0xf4240`）写进 `[x1, #16]`，最后执行原指令 `str x1, [x0, #16]` 并跳回 `0x718d098`。

3. **把出口 `0x718d094` 的原指令改成一条无条件跳转 `b 0x76f7ca0`。**

不新增任何函数调用、不破坏栈布局，204,820,664 字节的二进制文件大小一字节未变。

再顺手把第二章里抓到的那只虫子——`computeTruncatedCustomizations` 里的两项规则与自定义内容 token 预算（偏移 `0x773e864`、`0x773e874`、`0x773e8c4`、`0x773e8d4`），不管走配置读取路径还是默认路径，统统从 `20000` 改成 **131072 tokens**（`movz x6/x7, #0x2, lsl #16`）。

◆ 第五章：实盘验尸——一口气灌进 30 篇论文

━━━━━━━━━━━━━━━━━━━━

吸取之前的教训：**绝对不信 UI 面板数字，绝对不信模型嘴上说的“我读过了”，一切以数据库落盘的字节和上限为准。**

补丁打完，重启 `agy`，开新会话分三步验收：

**第一步：验 `AGENTS.md` 全量注入。**
进项目目录发起会话，直接查 SQLite 数据库里落盘的 `user_rules`：总长度 **119,283 字节**，里面一字不落包含了本地 `AGENTS.md` 的 **118,908 字节完整原文**，那句恶心的“超过规则预算被排除”彻底消失。面板上的 `System prompt` 直接来到了 `43.2k tokens`。

**第二步：验真实上下文窗口上限。**
查数据库 `gen_metadata` 和执行配置，实际请求里的上下文上限变成了：

`983040 tokens`

算一下算术：`1048576 (1M) - 65536 (64K 输出预留) = 983040`。严丝合缝！

**第三步：长会话跨 256K 压力实测。**
光看配置显示 983040 还不够，万一过了 256K 还有别的暗桩呢？
我直接在会话里让 Argon 一口气连续读取仓库里的 **30 篇长论文**（从第 96 篇一直读到第 67 篇）。

30 篇中英双语长文灌进去，打开 `/context` 一看：

```text
Gemini 4 Argon (Low) · 474.8k/1.0M tokens (45.3%)
◉ User messages: 395 tokens (0.0%)
◉ Agent responses: 3.8k tokens (0.4%)
◉ Tool calls: 414.1k tokens (39.5%)
⛁ System prompt: 43.2k tokens (4.1%)
□ Free space: 573.8k (54.7%)
```

**47.4 万 tokens！** 稳稳碾过 256K 的旧红线，没有任何回落，没有任何静默裁剪，最早第一批读进去的第 96 篇论文和第一轮敲的命令依然完完整整留在上下文最前面。

◆ 尾声：厂商的算盘与本地的手术刀

━━━━━━━━━━━━━━━━━━━━

把整件事串起来看，特别有意思：

云端大厂为了省算力，在闭源 CLI 客户端里塞满了这种“表面一套、背后一套”的小算盘——面板上给你写个 `1.0M` 让你情绪价值拉满，底下用实验配置覆盖把请求锁死在 `256K`；规则文件明面上支持自动加载，暗地里设一道 24KB 截断加一道 20K token 整份丢弃。普通用户用着觉得“怎么聊久了 AI 就变傻了、怎么写进 `AGENTS.md` 的规矩它老忘”，还以为是模型能力不行，根本想不到是客户端在发请求前就把你的脑子给切了。

好在客户端二进制终究跑在我们自己的机器上。只要机器码还在本地磁盘上，它画的饼就能变成真饼，它藏的锁就能一把把撬开。

【摘要（发布用，不进正文）】

Antigravity CLI 面板标着 1M 窗口，底层却锁死 256K 偷偷裁剪历史；AGENTS.md 解开 24KB 限制后又会触发 20K token 预算导致整份被扔掉。直接逆向 ARM64 二进制，借废弃函数手搓机器码跳板，把真 1M 窗口和完整规则抢回来。
