【Jev模型】一个不公开架构的分类器，怎么被吹成新范式

━━━━━━━━━━━━━━━━━━━━

◆ 这几天时间线被它刷屏了

━━━━━━━━━━━━━━━━━━━━

9 月 15 日，一家叫 TypeSafe AI 的公司发布了一个模型，叫 Jev。

几天之内，各路消息标题大同小异：前 OpenAI 研究员、ChatGPT 的发明人之一、**不生成文本的全新模型**、比大模型快一百倍便宜一百倍、**不会产生幻觉**。Hacker News 上那个帖子冲到一千九百多分、五百多条评论。Vercel 把它接进网关，上线头二十四小时，用它的付费团队比例接近百分之十三，**是 GPT-5.6 系列上线首日的两倍**——这是 Vercel 自家网关的采用率，当时还有免费促销，不是全市场的用量排名。

我看了一圈，越看越糊涂：**这些说法单独看都不假，合在一起我却说不上来它到底新在哪。**

于是把一手材料翻了一遍——官网、API 文档、发布博客、HN 上五百多条评论、两家第三方的实测推文，还有几篇论文的作者列表。

这期就是把翻出来的东西摆一摆。**先说结论：它是个挺好用的东西，但吹它的那些话里，有一半说的不是它。**

━━━━━━━━━━━━━━━━━━━━

◆ 先看它到底怎么用

━━━━━━━━━━━━━━━━━━━━

讲任何概念之前，先看 API 长什么样。这是官方文档（ https://docs.typesafe.ai/api ）里的例子，字段和值都是原样，只加了中文注释（真发请求时要去掉注释）：

```jsonc
{
  // state：要判断的那段文本
  //（这句是客服工单：“救命！我的打款已经失败三天了。”）
  "state": "Help! My payouts have been failing for 3 days.",
  "model": "jev-latest",

  // questions：你要问的问题，可以一次问多个
  "questions": {
    "department": {
      "type": "choice",              // 题型：单选
      "instructions": "Which team should handle this?",   // 问题：该派给哪个团队
      "criteria": {                  // 候选答案，以及每个候选的说明
        "billing":   "Payments, invoicing, refunds",      // 账务：付款、开票、退款
        "technical": "Bugs, outages, integrations",       // 技术：故障、宕机、集成
        "sales":     "Pricing, upgrades, new accounts"    // 销售：定价、升级、开户
      }
    }
  }
}
```

一段用户消息，一个问题，三个选项。返回是这样：

```jsonc
{
  "model": "jev-1.13.0",
  "answers": {
    "department": {
      "type": "choice",
      "choice": "billing",     // 它选的答案：账务
      // 每个候选各自的概率
      "probabilities": { "billing": 0.88, "technical": 0.12, "sales": 0.0 },
      "confidence": 0.81       // 置信度（这个数后面要专门说）
    }
  },
  "usage": { "input_tokens": 318, "output_tokens": 34 }
}
```

它一共支持三种问法：

**noul** 是是非题，返回“是”的概率。这个名字我第一眼没看懂，后来在 HN 上看到创始人自己解释：**noul 是 bernoulli 的简写** ——伯努利分布，就是抛硬币那个分布。

**choice** 是单选，最多 255 个选项。

**score** 是有序打分，给它 2 到 10 个档位，它返回各档的概率再算加权平均——所以分数可以落在两档之间。

输出就这三种。**输入的 `state` 和问题说明可以是嵌套 JSON，但它返回什么由这三种题型定死**——不像任意的 JSON Schema 那样，你想让它生成什么对象就定义什么对象。多个问题可以一起问，再由你的代码把结果拼起来。

看到这儿，懂一点机器学习的人应该已经反应过来了：**这三种题型，就是分类、多分类、有序分类。** 教科书前三章的内容。

这三样在 BERT 那个年代就是标准操作——拿一个预训练好的模型，后面接一个分类头，标一批数据微调一下，判情感、判意图、判优先级，做的就是这些事。

**那它跟那个年代的区别在哪？** 区别不在题型，在你要干的活：那会儿你得自己准备训练数据、自己训、自己部署；现在你运行时把选项列出来，一个 HTTP 请求就完事。

**而且反过来看更说明问题：官方 API 里，一个能生成句子的接口都没有。** 这不是“它选择不输出文本”这种设计取舍，是**这个接口根本没给你这个选项**。

所以“不生成文本的全新模型”，换个说法就是——**它能干的事，都在这三个框里。** 至于内部是什么结构，你不用知道也能判断它的边界在哪：**看它提供了什么接口就够了。**

◆ 快一百倍，省掉的是哪一步

━━━━━━━━━━━━━━━━━━━━

官网首页挂着两个数：**比大模型快 193.6 倍、便宜 444.6 倍**。

这个数字怎么来的，等会儿再说。先说一件更基础的事：**它凭什么能快。**

大模型生成一段文字，是一个词一个词往外蹦的。你要它输出 `{"department": "billing"}` 这么一串，**光是花括号、引号、字段名这些结构符号，就得一个一个吐出来**，吐完才轮到真正那个答案。每吐一个都要再过一遍网络（历史部分有缓存，不必从头重算）。

Jev 不生成文字，直接把这几个选项的概率一起给出来。官方的说法是并行评估，一个请求里问多个问题也是并行的——**具体跑几遍网络它没说，但“把结果写成一段文字”这个环节是绕过去了。**

所以它省掉的不是某个聪明的算法，**是“逐词生成”这整个环节**。至于能快多少，取决于跟谁比、输入多长、问几个问题，以及对面那个模型开了多少推理。

HN 上有人把这层说得很直白：

▎“70-500 毫秒对 3-329 秒”这种比较是苹果比橘子，除非那个大模型基线在做同等的工作。如果 Jev 压根跳过了生成环节去做一个窄任务，那它当然快。

还有一位说得更细——**大模型那几秒里，有相当一部分是在逐字吐出类型名和 schema 结构**。真要公平比，得让大模型也只输出那几个裸数字。

顺带说个我觉得挺好笑的细节。官方定价是这样写的：

▎按输入 token 计费。**输出 token 免费。**

这个价格对用户当然是真优惠。但它跟聊天模型说“输出免费”不是一回事。

上面那个返回里 `usage` 确实记了 34 个输出 token——**它不是没有输出，是那一头本来就没多少东西**：吐的是一组概率，不是一段越问越长的文字。 **免费说的是定价，不用逐词生成说的是算法，两件事得分开看。**

━━━━━━━━━━━━━━━━━━━━

◆ “不会产生幻觉”是什么意思

━━━━━━━━━━━━━━━━━━━━

这是传播得最广的一句，也是最该分开看的一句。

它的原理是：**输出空间是你自己定的。** 你给了三个选项，它只能从这三个里挑，挑不出第四个来。所以它“不会编造”。

但被排除掉的只是 **“编出选项之外的答案”**。把这张工单派给不该去的团队，照样可能。

**这不是治好了一个病，是把作文题换成了选择题。** 它没法信口开河写一篇，**但它能一本正经选错。**

同样的道理对任何分类模型都成立。判垃圾邮件的模型不会“产生幻觉”，因为它只会输出“是”或“否”——但这不妨碍它把正常邮件扔进垃圾箱。

HN 上有人当面问了创始人这件事：

▎“不会产生幻觉”这个说法好像不对？它确实吐不出一个非法的类型，**但它照样可以吐出一个完全错误的合法值**。而且大模型加个合适的外壳也能强制结构化输出。

创始人回了一句，说这对所有机器学习都成立，你总不能说随机森林会“产生幻觉”。

底下有人接了一句——**这句我认为说到了点子上**：

▎这个帖子一小时前的原标题是“Jev：全新前沿模型，便宜 40-400 倍、快 20-200 倍”。我同意那个标题有误导性。
▎**类型安全不等于事实正确。**

这句值得单拎出来念一遍。**Type safety is not factual correctness.**

它保证的是“返回值一定是这三个之一”，不是“返回的那一个是对的”。前者是输出约束，后者得拿真实答案来检验。

**创始人在这条底下也表示同意了。** 而且官网首页往下展开 FAQ，同样写明：保证的是回答的形状，不保证每次决策正确，它照样会选错。

**所以边界不是没写——是首页的大字写着“Zero Hallucinations”，承认会选错的话在展开之后的小字里。** 传播的时候，小字总是先掉。

━━━━━━━━━━━━━━━━━━━━

◆ 它瞄准的那个真问题：校准

━━━━━━━━━━━━━━━━━━━━

前面说了三条，听着像是全在泼冷水。但它确实有一个东西是真的，而且是真问题——**校准**。

先说什么叫校准。

你问大模型一件事，它说“我有九成把握”。这个九成是什么意思？**大多数时候什么意思也没有。** 它是从训练语料里学来的说话方式——人类写文章时说“我有九成把握”，它就学会在类似语境里也这么说。这个数字和它实际答对的比例没有必然关系。

**校准好的意思是：它说 70% 的那些次里，真有大约 70% 是对的。**

像天气预报。预报说 70% 降水概率，如果把所有报过 70% 的日子挑出来，其中大约七成真的下了雨，这个预报就是校准好的。报得准不准是一回事，**报出来的那个数字本身可信不可信，是另一回事。**

这对写程序的人是刚需。你要做自动化，就得决定什么时候放心让机器自己处理、什么时候转人工。**这条线画在哪，靠的就是那个概率数字可不可信。**

TypeSafe 的官方文档里，校准是这么定义的：

▎在同一个模型的许多次预测中：被赋予 0.2 概率的结果，应当大约有 20% 的时候发生；被赋予 0.8 概率的结果，应当大约有 80% 的时候发生。
▎**这些比率描述的是一组预测，不是对任何单次回答的保证。**

这段写得很准确。它甚至主动提醒了边界——校准是群体统计，不保证单次正确。

**所以问题来了：它校准得怎么样？**

这里得先分清返回里的两个字段。`probabilities` 是各选项各自的概率；`confidence` 是另一回事——它把整个分布的**集中程度**概括成一个数。选项之间拉开了多大差距，和这些概率报得准不准，**是两件事**。

文档里那个三选项的交互演示，甚至直接用「(3 × 最大概率 − 1) / 2」来近似这个集中度。它标明了这是演示用的算法，不是生产接口的真实公式。

那校准本身有没有实测？**有一份。**

官方一篇教程拿 60 份公司年报做行业分类，75 个细分类，用的是 8 月份的 jev-1.12。拿 0.9 这个置信度当分界线，正好切成两半：

| 按 confidence 分组 | 样本数 | 答对 |
|---|---|---|
| ≥ 0.9 | 30 | 27 条，90% |
| < 0.9 | 30 | 12 条，40% |

**这说明它确实能把难判的那一半挑出来。** 而且低置信度那组改报更粗的行业大类之后，准确率回到 70%——判断不稳就别报那么细，这是个很实用的退让。

**但注意这份数据在证明什么。** 它证明的是「按 confidence 分流管用」，不是「它报 90% 的时候真有九成对」——表里的 0.9 是分流的闸门，不是每条答案各自报出的正确概率。

真正的校准验证得是另一张图：把「报了几成」和「实际对了几成」逐档摆在一起，也就是可靠性曲线，或者一个期望校准误差（Expected Calibration Error，ECE）的数。**这个我在公开材料里没找到。**

HN 上有人专门提了这个要求：

▎很希望看到 Jev 的基准测试能证明校准后的不确定性确实有价值……这样我们才能问出“要达到 90% 准确率，我们能自动化多少比例的决策”这种问题。

这个问题问的是产品价值：**在我自己的业务上，保住某个准确率之后，还能自动处理多少？** 那 60 份年报是个起点，替不了各家自己的答案。

━━━━━━━━━━━━━━━━━━━━

◆ 那 193.6 倍是怎么测的

━━━━━━━━━━━━━━━━━━━━

回到开头那个数字。

官方有个评测页面，方法论写在上面。它选了四类工作流——安全事件处理、agent 执行记录检查、发票处理、客服——把每类写成一组小问题，让各个模型跑同一套流程，再比结果、耗时和费用。

标准答案——也就是用来判对错的那套正确答案——是这么来的：

▎GPT-6 Astra 和 Claude Fable 5.1 的回答的平均值，**两者都开高思考档**，取其共识标签。

**即：正确答案是用大模型生成的。** 然后 Jev 在这套由大模型定义的标准上，跟大模型比分数。

这能量出“谁更接近这把尺子”，**但尺子本身也会错**——接近它，不等于在真实业务上判对了。

还有个条件会直接影响速度：作为对照的大模型要走 TypeSafe 提供的适配器，输出跟 Jev 兼容的结构和概率。**官方自己承认，这比只让大模型给一个答案更慢、更贵。** 官方也说了，这些倍数可能处在实际收益的高端——他们另一个只用低思考档的演示，提速就小得多。

所以那两个倍数不是“换成它，什么活都快两百倍”，**是“在这套工作流、这种输出要求下，快这么多”。**

创始人在 HN 上确认了这套评测是自家做的。至于为什么不跑公开基准，官方专门写了篇博客解释：

▎我们在做一种新型的模型，这意味着现有的基准并不适用。
▎我们刻意选择不公布在公开基准上的成绩。

底下有人回了一句：**要是分数好看，我赌他们早发了。**

这句话刻薄，但它指出的是同一个结构性问题：**当一家公司同时掌握出题权、答案和判分权，它公布的任何领先幅度，都只是在说“按我们的标准，我们领先”。**

这个结构我们在 310 期（ https://mp.weixin.qq.com/s/C1yIEM-i20LE8AeBN8y-EQ ）讲过一次。那期讲的是怎么把人的贡献藏起来，做出“AI 自进化”的效果。手法不同，**但都是先定义计分方式，再拿这个方式量出一个漂亮数字。**

◆ 第三方实测：两条，都值得看

━━━━━━━━━━━━━━━━━━━━

厂商自述之外，有两家真拿生产任务测了。

**第一条是 Vercel 的工程师**，测他们自己的安全分类器：

▎我们用 Jev 对我们的 fx auto 模式安全分类器做了基准测试。
▎结论：比 gpt-5.6-luna（我们目前的首选）**快 5 到 18 倍，而且更准**。

推文附图里给了完整数字：70 个标注案例，每个跑 3 次，一共 210 次判定。

| | Jev | GPT-5.6-Luna |
|---|---|---|
| 判对 | 207/210，98.6% | 203/210，96.7% |
| 延迟中位数 | 312 毫秒 | 1458 毫秒 |
| p95 延迟 | 374 毫秒 | 6583 毫秒 |

p95 是指 95% 的请求都不超过这个时间。**所谓“快 5 到 18 倍”，是中位数快约 4.7 倍、p95 快约 17.6 倍**——不是每一次请求都快同样的倍数。真正拉开差距的是最慢那批：大模型偶尔会卡到六秒多，它不会。

**这份测试里，它确实又快又多判对了几次。** 70 个案例重复三遍仍然是 70 种案例，样本不算大；但这个结果本身就有用，不需要再给它戴一顶“新范式”的帽子。

**第二条来自 Bryo AI 的 CTO**，做邮件分类。这条更有意思，因为它的方法论是三条里最透明的，**而且结论和你在媒体上看到的不太一样**。

原推的第一句是：

▎**Jev 在我们的邮件分类基准上输给了 Gemini。**
▎我仍然有兴趣把它投入生产。
▎有意思的结果不是准确率，**是错误发生在哪里**。

往下读，1565 封里有 1201 封真实邮件、364 封合成的，10 个类别，以德语为主。结果和成本是这样：

| 模型 | 准确率 | 每千封费用 |
|---|---|---|
| Jev | 96.4% | 0.08 美元 |
| Gemini 3.5 Flash-Lite | 97.5% | 0.80 美元 |
| Gemini 3.8 Flash | 98.5% | 1.79 美元 |

到了某家科技媒体的报道里，这条变成了“Gemini 准确率略高，但贵 10 到 20 倍”。

**两句话都不算假。** 但一句的开头是“Jev 输了”，另一句的开头是“Gemini 更贵”。**同一份实测，重心挪了一下，读者接收到的东西就反过来了。**

顺带说一句，这条实测的作者自己的判断很值得记——他关心的不是谁准确率高，**是错误发生在什么地方、能不能被概率数字提前标出来**。他给了个读数：置信度在 99% 以上的 737 条预测，在这批数据里全部正确；而置信度低于 70% 的，接近一半是错的。

**能不能把容易错的那批挑出来，比一个总准确率更接近“自动化到底怎么落地”。** 这跟前面那 60 份年报是同一件事的两次印证。当然，一次测试里高置信度组零错误，不等于以后永远零错误；作者自己也说了，这轮还没处理附件，那是他考虑投产时的一道坎。

**懂行的人在意的是“哪些能自动办、哪些得交出去”，传播更容易记住的却是“便宜二十倍”。**

━━━━━━━━━━━━━━━━━━━━

◆ 那架构到底是什么

━━━━━━━━━━━━━━━━━━━━

写到这儿你可能会问：说了半天，它内部到底是个什么结构？

**不知道。**

不是我没查到。是创始人在 HN 上亲口说的：

▎架构目前先不公开，**不过我们讨论过要写一篇论文**。

没有参数量，没有层数，没有说是不是基于开源权重改的，没有技术报告，没有论文。

**一些流传的说法其实不是官方说的。** 比如“transformer 架构”这个说法出自某家科技媒体的报道，官方文档全站只有一句“a new architecture”。那篇报道自己也写了，外界**猜测**它是基于某个开源大模型做的——这是记者转述的猜测，不是任何一方的确认。

HN 上有人根据 API 行为反推：

▎看起来像是一个专门化的、偏 encoder-only 的 transformer，带标量和有序输出头。效果上可能是非因果的？大概根本不是自回归的？

**注意这也是猜测。**

这里有个区分值得说清楚：**按用途叫它分类器，完全没问题**——API 摆在那儿，它就是干这个的。但断言它内部“就是 BERT 加个分类头”，是另一回事，那需要结构证据。

反过来也一样。**快、便宜、这个任务上能用，这些都可以拿具体任务测出来；“架构上是个突破”，得看它到底改了什么。** 前一件事已经有数字可以讨论，后一件事目前只有公司的宣称。

**这两件事不必捆在一起判。**

━━━━━━━━━━━━━━━━━━━━

◆ 一周之内，冒出来七八个复刻

━━━━━━━━━━━━━━━━━━━━

写到这儿我顺手搜了一下：有没有人复刻它。

**有，而且是发布第二天就开始的。**

一周之内冒出来七八个。做法五花八门：有人拿 ModernBERT 当骨干；有人用 Qwen2.5-0.5B 加 LoRA，靠 attention mask 把多个问题隔开，好让它们共享同一份材料；有人干脆不跑自回归循环，直接从 logits 里把概率取出来；还有人往 vLLM 提了个 PR，用扩散模型并行给固定的输出槽打分。其中几个的 star 数已经过千，最多的六千多。

**这件事本身比任何评测都说明问题：一群人看一眼 API 文档，当天就知道该怎么做。**

当然，做出来的东西跟原版不是一个量级——人家融了四千万美元、埋头做了两年，复刻的是几个开发者拿现成的开源小模型周末套出来的。**有一个项目干脆自己取名叫 poorjev，穷人版。** 拿这种对照去比分数没什么意义，那比的是钱和算力，不是思路。

**有意思的是思路本身没什么秘密。** 方向是明摆着的，一周之内七八拨人不约而同地走了过来，差的只是资源。

还有人做了更扎实的活。一位叫 Archer Hume 的开发者用大约一万次 API 调用做逆向：测延迟、从计费反推 token 数、往请求里塞假选项看反应、挪动参考材料的位置看影响。他的结论是——**带共享前缀的因果 Transformer，用 attention mask 把各个问题隔开，选项整体打分，最后读出带类型的数值。**

**注意这仍然是从外部行为反推的，不是官方确认**，他自己也标了哪部分最没把握。但这种做法值得一提：**在人家什么都不肯说的时候，这大概是外人能做到的极限了。**

━━━━━━━━━━━━━━━━━━━━

◆ 顺手核一下那个头衔

━━━━━━━━━━━━━━━━━━━━

创始人 Diogo Almeida，媒体上的介绍是“ChatGPT 的发明人之一”“RLHF 的共同发明人”。

这两个说法得分开看。

**InstructGPT 那篇论文（arXiv:2203.02155），他是第 4 作者，而且是标星的 primary author 之一。** 这个我去核了作者列表，属实。那篇论文是把 RLHF 用到语言模型上、直接催生 ChatGPT 的工作。GPT-4 技术报告的作者列表里也有他。

**但“RLHF 共同发明人”这个说法，把一条研究谱系压成了一个标签。** 2017 年 Christiano 等人那篇奠基论文里没有他；2019 年已经有人把人类偏好训练用在语言模型上；2020 年又有了用人类反馈训练的摘要模型。**InstructGPT 是把这条路推到通用指令遵循上的关键一步，但不是这个故事的起点。**

本来我以为这是媒体标题化的产物——查完发现不是。公司团队页面写的是“参与发明的 RLHF 和 InstructGPT 导向了 ChatGPT”，措辞是准确的；**但公司自己发的新闻稿直接用了“RLHF / ChatGPT 共同发明人”，创始人本人的发布推文开头也是：**

▎After co-inventing ChatGPT...

一条很长的研究路线，被压成了一个好传播的头衔。**履历本身是真的，不用替他打折；但履历替不了新产品的证据。** 他当年参与做成了什么，和 Jev 这次证明了什么，是两笔账。

━━━━━━━━━━━━━━━━━━━━

◆ 所以它到底是什么

━━━━━━━━━━━━━━━━━━━━

我自己的理解是这样。

**它真正做对的事，可能不在模型上，在产品形态上。**

“给定一组选项、返回校准过的概率”——这件事技术上不新，新的是**它被做成了一个不需要你准备训练数据、不需要你微调、开箱即用的通用接口**。你运行时把选项列出来就能用。

过去要做一个分类器，你得标数据、训模型、部署、维护。后来可以让大模型来做，但你得忍受它慢、贵、而且吐给你的概率不可信。**Jev 想占的是中间那个位置。**

还有一层值得说：**那组概率并不是它独有的东西。**

任何一个大模型在做选择题的时候，输出层对各个候选本来就有一组数——它对 billing、technical、sales 的相对强度，在采样之前就存在。**只是标准接口只把采样出来的那个词给你，那组数就丢掉了。**

222 期（ https://mp.weixin.qq.com/s/Y2HxcESdVf2zvvmY5gNZaA ）讲过这件事：要知道模型有几成把握，别让它用嘴说，**直接去读输出层里那个 token 的概率**——嘴上说出来的把握多了一层自然语言表演，容易被“怎么说更像专业助手”污染。那期的结论是，模型内部对自己答对的概率估计相当准，只是说不出口。

**所以 Jev 做的事，某种程度上是把本来就存在的那一层直接端出来，而不是让你从生成的文字里反推。** 这是个有用的产品决定，但它动的是接口，不是模型有没有这个能力。

至于它内部是什么——按目前公开的材料，**没有人知道，包括吹它的人**。

所以这期真正想说的其实不是 Jev 怎么样。是：

**当一个东西被形容成“新范式”的时候，值得先问两句——它省掉了哪一步？以及，说这话的人凭什么知道？**

第一句能解掉大部分的速度神话。Jev 快，是因为它不做逐词生成；任何跳过一整个环节的东西都会快，这不神秘。

第二句更要紧。**在架构、权重、训练细节一律不公开的情况下，“这是突破”和“这就是个分类器”是两个同样没有证据的判断。** 区别只在于，前者更好听，也更容易被转发。

不过查完这一圈，我对它本身没什么恶意。**一个把概率报得比较准的分类接口，本来就够好用了**——它不需要“新范式”那顶帽子也站得住。

**真正别扭的是帽子，不是东西。**

它可能真的还有新东西。创始人说讨论过要写论文——**那就等那篇论文。**
