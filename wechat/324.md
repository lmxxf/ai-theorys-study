◆ 第一章：一个 HIP 程序长什么样

━━━━━━━━━━━━━━━━━━━━

HIP（Heterogeneous-computing Interface for Portability，异构计算可移植接口）是 AMD 的 GPU 编程接口，写法几乎照抄 NVIDIA 的 CUDA：把 `cuda` 前缀换成 `hip`，大部分代码能直接用。

一个最小的程序，给数组每个元素加 1：

```cpp
#include <hip/hip_runtime.h>

// 核（kernel）：GPU 上跑的函数。写的是【一个线程】要干的事
__global__ void add_one(float* x, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;  // 我是第几号线程
    if (i < n) x[i] += 1.0f;                         // 只管自己那一个元素
}

int main() {
    const int n = 1 << 20;
    float* d;                                        // 显存里的指针
    hipMalloc(&d, n * sizeof(float));                // 在显存里开空间
    hipMemcpy(d, host, n * sizeof(float), hipMemcpyHostToDevice);   // 拷上去
    add_one<<<(n + 255) / 256, 256>>>(d, n);         // 发射：4096 组，每组 256 线程
    hipMemcpy(host, d, n * sizeof(float), hipMemcpyDeviceToHost);  // 拷回来
    hipFree(d);
}
```

编译：`hipcc add.cpp -o add`。

两个角色要分清。`__global__` 那个函数是**设备代码**，在 GPU 上跑；`main` 是**宿主代码**，在 CPU 上跑，负责开显存、搬数据、发射核。`<<<组数, 每组线程数>>>` 这一句就是一次 launch：CPU 说一声，GPU 上几十万个线程同时执行 `add_one`，每个线程靠 `blockIdx`、`threadIdx` 算出“我是谁”，去处理自己那一格。

318 讲过的层级在这里对上号：每组 256 个线程叫一个工作组（workgroup，CUDA 叫 block），硬件把每 32 个相邻线程捆成一个 wave，32 个人听同一个口令。9070 XT 是 RDNA4 架构，wave 是 32 宽；AMD 数据中心卡（CDNA）是 64 宽，从网上抄代码时这一点要留意。

────────────────────

💡 我们的项目为什么不用 hipcc

这个项目的核不在游戏机器上现编，也不装 HIP SDK。整条链是这样的：

1. 核的源码 `.hip` 交给显卡驱动自带的编译器库 `amd_comgr_3.dll`（在 System32 里，装了驱动就有），分三步编出 `.hsaco`——一个 ELF 格式的 GPU 代码文件。同一步顺手吐出一份 `.s` 汇编。
2. 游戏插件运行时用 `LoadLibrary` 加载系统里的 `amdhip64_7.dll`，按函数名取出 `hipModuleLoadData`、`hipModuleGetFunction`、`hipModuleLaunchKernel` 这几个入口。
3. 读 `.hsaco` 文件 → 取出核函数 → 带着参数数组发射。

也就是说，`<<<>>>` 那种写法是 hipcc 帮你把第 2、3 步藏起来了；我们的插件是注进游戏的一个 DLL，没法要求每个玩家装 SDK，所以把这几步摊开自己做。每个架构 30 个 `.hsaco`，9070/9070 XT（gfx1201）和 9060（gfx1200）各一套，发布包里一共 60 个。

────────────────────

看一个真实的核。下面是项目里第一个验证矩阵指令能不能用的探针，一个 wave，32 个线程合伙算一块 16×16 的矩阵：

```cpp
typedef int   int2   __attribute__((ext_vector_type(2)));
typedef float float8 __attribute__((ext_vector_type(8)));

extern "C" __attribute__((global)) void wmma_probe(const int* packed, float* out) {
    unsigned lane = __builtin_amdgcn_workitem_id_x();        // 0..31
    int2 a = {packed[lane*4],   packed[lane*4+1]};           // 我手里的 8 个 FP8（A 的一片）
    int2 b = {packed[lane*4+2], packed[lane*4+3]};           // 我手里的 8 个 FP8（B 的一片）
    float8 c = {0,0,0,0,0,0,0,0};
    float8 d = __builtin_amdgcn_wmma_f32_16x16x16_fp8_fp8_w32_gfx12(a, b, c);
    for (unsigned i = 0; i < 8; i++) out[lane*8 + i] = d[i];  // 我负责结果里的 8 个数
}
```

`__builtin_amdgcn_wmma_...` 是编译器内置函数，一句对应一条 WMMA（Wave Matrix Multiply-Accumulate，wave 矩阵乘累加）指令。一个 16×16 的矩阵块，分散在 32 个线程的寄存器里：每个线程拿 A 的 8 个数、B 的 8 个数，一条指令下去，32 个人合力算完，每人手里分到结果的 8 个数。**写矩阵核，一半的功夫在“哪个线程手里拿着哪几个数”这张排布表上。** 后面几乎每一处优化，都在这张表上做文章。

◆ 第二章：改一处核，要过哪几道关

━━━━━━━━━━━━━━━━━━━━

写出一个能跑的核不难，难的是证明它“改对了、而且真的快了”。这四天做了几十个候选，每个都走同一条流水线：

| 步骤 | 做什么 | 为什么 |
|---|---|---|
| 1. 加开关 | 新写法包在一个编译期宏里，默认关 | 默认关时，编出来的机器码必须和旧版一字不差，否则说明改动漏到了别处 |
| 2. 读汇编 | 看 `.s`：指令条数、寄存器用量、有没有溢出到显存 | 源码看着省了，编译器未必照办 |
| 3. 逐位回归 | 7 组场景 × 12 帧（静止、运动、带历史、三种分辨率），输出每一位和基准比 hash | 不用人眼判画质 |
| 4. ABBA 计时 | 基准、候选、候选、基准四段，每段 1000 帧、扔掉前 200 帧，跑两轮 | 显卡频率随温度和功耗漂，只有相邻的对照可信 |
| 5. 过门槛 | 两个分辨率档里至少有一档稳定快 0.5% 以上才进生产 | 小于这个数的，重跑一次方向就可能反过来 |
| 6. 装游戏 | 换进《剑星》，我读右上角黄字帧率 | 离线快了，游戏里不一定兑现 |

第 4 步的四段顺序有讲究。如果只跑“基准、候选”两段，显卡从凉到热，后跑的那段天然吃亏或占便宜；ABBA 让两边各占一次前、一次后，温度漂移互相抵掉。

第 6 步真抓到过事。9 月 29 日早上一处改动，离线 900 和 1080 档都快了约 2%，装进游戏，帧时间日志里的平均值纹丝不动，现在还在查是场景差异、没走到新路径，还是那段时间本来就被别的工作盖住了。**离线快是必要条件，不是充分条件。**

这条流水线大部分是 GPT（Codex）按任务单一轮一轮自己跑的：编译、回归、计时、写报告。9 月 25 日晚上我放了权：耗时的实验让 agent 自己跑，不用再叫我手动执行，从那以后速度明显上来了。Claude 这边负责装游戏、打包、记录。我负责读帧率——和决定哪些规矩可以破。

◆ 第三章：一个头交给一个 wave（0.31，约 −6%）

━━━━━━━━━━━━━━━━━━━━

这四天里单独拿出来最大的一步，改的不是某个核的细节，是分工方式。

改法是什么，要回到 318 第四章那张表。我们原来的做法是：一个 8×8 窗口（64 个位置）交给一个工作组，组里 4 个 wave，每个 wave 管 16 个位置。注意力要“每个位置看所有位置”，于是 4 个 wave 必须经共享内存交换数据，每一步都要栅栏对齐——318 量出来 wave 一辈子里八成时间在搬数据、等同伴。

换个分法：注意力本来就是按“头”分的，每个头各看各的。**让一个 wave 负责一个头的全部 64 个位置。** C64 有两个头，就是两个 wave 各干各的；C32 只有一个头，一个窗口整个交给一个 wave。一个头的 Q、K、V 全待在这个 wave 自己的寄存器里，用不着和别人交换，栅栏也就没了——32 个线程天生同步，不需要对齐。

```text
原来：一个窗口 = 1 个工作组 = 4 个 wave，按位置分
      wave0: 位置 0-15    ┐
      wave1: 位置 16-31   ├─ 算注意力要互相要数据 → 共享内存 + 栅栏
      wave2: 位置 32-47   │
      wave3: 位置 48-63   ┘

现在：一个窗口的每个头 = 1 个 wave，按头分
      wave0: 头 0 的全部 64 个位置   ← Q/K/V 都在自己寄存器里
      wave1: 头 1 的全部 64 个位置   ← 互不打扰
```

代价是寄存器。一个 wave 要装下整个头，C32 的首版每线程用了 240 个寄存器，一个 SIMD 上能同时挂的 wave 就少了。后来把窗口的 4 块改成外层循环逐块滚动，降到 165 个，零溢出。首版只换 4 块时整网约 0.5%，扩到 8 块并改成滚动之后到了 1.5%。

C32、C64、C128 全换、C256 只换注意力段，整网 900 档 −6.0%、1080 档 −6.6%，逐位不变。游戏里 2K 质量档 47～48 帧到 49～50。

318 把“一个窗口四个 wave 靠共享内存交换”算进了必要损失里的“形状税”。现在看，那是我们选的分工方式付的税，不是网络形状本身要求的。**算“必要损失”时，得先确认那个结构是不是真的不能换。**

────────────────────

💡 同一个思路的反面：C512 为什么没赚

一头一 wave 在 C512 上试了，逐位，但整网 −0.02 毫秒，等于没变。

原因在数量。C512 在最深层，一帧只有一百来个窗口，一个窗口 16 个头就是一组 16 个 wave，每个工作组处理器（WGP）只能同时住 3 组左右，全卡铺不满，还要排出第二轮，最后半轮空转。原版是上千个小工作组，反而铺得开。后来试着把组数翻倍，也更慢—— **C512 缺的不是并行度。**

C512 后来真正赚到的，是另外两处：一是一个 wave 从算 16 个位置改成算 32 个，每读一遍权重喂两倍的活（整网约 −1.2%）；二是 9 月 28 日把 QKV 和注意力融进一个核，QKV 的结果只在核内的共享内存里过一下，不再写回显存（连同 C64/C128 的一处权重复用，900 档 −3.6%）。

────────────────────

一头一 wave 解决的是“等同伴”。等同伴的时间省下来之后，wave 自己在干什么，就露出来了。

◆ 第四章：数指令（0.33～0.35，约 −9% 加一串小的）

━━━━━━━━━━━━━━━━━━━━

一头一 wave 之后，瓶颈换了地方。读 C64 那个核的汇编：矩阵指令 150 条，普通向量指令（VALU，vector ALU，向量算术单元）约 3900 条。矩阵单元在等向量单元。

向量指令都花在哪？这张网每一块的输入输出是 FP8（8 位浮点，E4M3 格式），而中间计算用 32 位浮点。每算完一个数，都要转回 FP8 字节，塞进下一条矩阵指令要的那个位置。原来这一步是这么写的：

```cpp
// 原来：一次转一个数
uint q8_fused_round(float x) {
    uint a = bits(x) & 0x7fffffff;          // 取绝对值的位
    uint q = q8(clamp(x, -448, 448));        // 夹到 FP8 能表示的范围，再转
    return a == 0 ? 0 : q;                   // 正负零都变成 +0
}
// 调用处再把这个字节移位、或进 32 位字里：
frag[e/4] |= q8_fused_round(v) << (8 * (e % 4));
```

摊到汇编，每个字节大约 6 条向量指令：夹值、一条只用了一半的转换指令、移位、与、比较加选择（处理正负零）、或。转换指令 `v_cvt_pk_fp8_f32` 本来一次能转**两个**数，写进 32 位字的指定半边——原来的写法每次只喂一个，另一半浪费了。

改成：

```cpp
// 现在：两个一组，直接写进片段字
int lo = __builtin_amdgcn_cvt_pk_fp8_f32(z(t[0]), z(t[1]), 0,  false);  // 写低 16 位
lo     = __builtin_amdgcn_cvt_pk_fp8_f32(z(t[2]), z(t[3]), lo, true);   // 写高 16 位
// z(x) = clamp(x + 0.f, -448, 448)
```

正负零那一步也换了：`x + 0.f` 在默认舍入下永远不会得到 −0，−0 加 +0 等于 +0，其他所有值（包括 NaN）不变——一条加法代替了比较加选择。

C64 这个核静态指令 −25%，向量指令 −30%。同样的打包法推到 C32，两处全开：**整网 900 档 −8.7%、1080 档 −9.1%**，逐位不变。游戏里 EXACT 模式简单场景 51～52 帧到 53～54。

这是四天里单处收益最大的改动，改的只是“数怎么装进寄存器”，一个运算没动。为什么向量指令这么贵？开源项目 mochizuki 的 DLSSNR-AMD（Vulkan 写的，整网 1080 档在 Linux 上约 6.0 毫秒、Windows 上约 9.4，Linux 上的效率相当高）在注释里说：RDNA4 上 FP8 矩阵指令和向量指令不重叠执行。矩阵单元干活的时候向量单元闲着，反过来也一样，所以向量指令多一条，就是实打实多一条的时间。

────────────────────

💡 没有 AMD 卡，也能看别人的汇编

mochizuki 的项目是 Vulkan 着色器，由 Mesa 驱动里的 ACO 编译器（AMD COmpiler）编成 GPU 指令。想拿它和我们的汇编逐条比，得先让 ACO 把它编出来——这需要一张 9070 XT。

9 月 27 日是在家里的 DGX Spark 上做的，这台机器是 ARM 加 NVIDIA 显卡，没有 AMD 卡。办法是：从源码编 Mesa 的 RADV 驱动，加载一个叫 drm-shim 的假内核接口，告诉它“我是 gfx1201”，驱动就以为自己插着一张 9070 XT，照常把 46 条管线编出来，再通过 Vulkan 的调试扩展把每条管线的汇编和统计取出来。GPU 程序一条都没执行，只借了编译器。

一比就清楚了：C64 每个窗口的矩阵指令，我们 456 条、它 416 条，基本对得上；向量指令我们约 7490 条、它约 2199 条，差 3.4 倍。C64 这一族我们 1.83 毫秒、它注释里写 0.71——差距几乎全在向量指令上。这张对照表后来指导了 0.34 到 0.36 的一串小改动。

────────────────────

后面那串小改动，每个都只有 0.2% 到 2%，但有几个过程值得记下来，因为它们正是“写 HIP 时编译器在想什么”：

**夹值写成一条指令，−0.5%。** `fminf(fmaxf(x, -448), 448)` 编出来前面总多一条 `v_max_num x, x`——编译器为了处理 NaN 的规范化自己加的。改成内置函数 `__builtin_amdgcn_fmed3f(x, -448, 448)`（取三个数的中位数），一条指令，对所有输入输出同一个字节，这一个核里这类规范化从 1826 条降到 84 条。

**手改汇编发现编译器漏了一招，−0.2%。** 做了个小工具，把 `.s` 汇编重新汇编成可加载的模块，直接在汇编里改。激活函数那里是 `x * poly` 后面跟 `+ 0`，手工把两条合成一条 `fma(x, poly, 0)`（乘加一步完成，只舍入一次），输出逐位不变、每窗口少 192 条指令——LLVM 自己不做这种合并。顺带发现：那个 `+ 0` 删不得，激活多项式在夹值边界 −4 处正好等于 +0，所有 x ≤ −4 算出来都是 −0，必须靠它变回 +0。汇编里验证通过之后，再回到源码里用 `__builtin_fmaf(x, y, 0.f)` 写出同样的东西。

**让硬件自己饱和，但只在那一小段里。** RDNA4 有个 MODE 寄存器，里面一位打开后，FP8 转换指令遇到超出范围的数会自动夹到 ±448，夹值那条指令就可以省掉。第一次在核的入口打开一次、整个核生效，结果一个运动场景的输出变了——这一位同时改变了 16 位半精度转换的溢出行为。后来改成只在四次 FP8 转换前开、转完立刻关。又发现编译器会把转换挪出这个开关区间，汇编里出现 38 个“刚开就关”的空段；最后在源码里把“开 / 四次转换 / 关”写成固定的一小段，编译器才挪不动。这一位还有个代价：输入是无穷大或 NaN 时，结果和原来不一样。于是专门做了一次普查，在所有回归场景里统计进入这些转换的值：最大 388，从没超过 448，一个非有限值都没有。

这三件事是同一个教训：**源码只是请求，汇编才是编译器的答复。** 每次改完都要回去读 `.s`。

◆ 第五章：少发几次核（0.36，214 → 182 次）

━━━━━━━━━━━━━━━━━━━━

318 第五章讲过 launch 的尾巴：一次发射几百个工作组，最后半轮铺不满全卡，空转。那时算的是“结构税”，这四天从两头往回拿。

**一头：让下一次发射提前开始。** 先量了驱动：这块 Windows HIP 上两条 stream（命令队列）完全不并发，只有一条硬件队列。同一条 stream 里，用 `hipExtAnyOrderLaunch` 可以让下一个核在上一个收尾时就开始派发——但这样就没了“等上一个跑完”的保证。于是把依赖搬进核里：上游每个 wave 算完，往一个计数器上 +1；下游工作组开头先看它要的那几块上游计数到了没有，到了再干。NVIDIA 有个同类的官方功能叫 programmatic dependent launch（程序化依赖发射），这是在 AMD 上土法做了一个。0.30，900 档 −1.6%。它的正确性后来还审出一个边界：32 位计数器会回绕，累计到上限之后旧计数会直接满足新目标，靠宿主在快溢出时同步清零补上。

**另一头：干脆少发几次。** 把相邻的几个核合成一个。9 月 28 日一天做了三轮：C256 整块融合（只在 1080 档启用，900 档反而慢，−1.65%）、C512 的 QKV 并进注意力（连同权重复用，−3.6% / −2.6%）、上采样并进下一块的开头（约 −2%）。1080 档一帧的核发射次数从 214 次降到 182 次。

C256 整块融合 9 月 26 日试过，那次慢了 0.21 毫秒。这次换了组织方式——两组查询共用同一遍 FFN 权重读取，每个 wave 的权重请求减半——1080 档就赚了，900 档依然慢。318 那句“同一个改法赚不赚，看那个核当下被什么卡住”，这里又应验一次：连分辨率档不同，答案都不同。

────────────────────

💡 省掉 35MB 拷贝，只快了 0.03 毫秒

网络前后，原来要把游戏的颜色纹理拷进 HIP 的共享缓冲，算完再拷回来，一帧两趟，输入那趟就 35MB。9 月 28 日做了零拷贝：让生成输入的那个图形着色器直接写进 HIP 共享缓冲，输出让 FSR 直接读网络的结果纹理。

按 640 GB/s 的显存带宽估，35MB 一趟约 0.05 毫秒以上，两趟应该省 0.1 毫秒量级。实测：0.02～0.05 毫秒。**省下来的比带宽算出来的少得多，说明网络之外的那段开销主要不在拷贝本身**，更可能在 D3D12 和 HIP 两套接口之间交接、互相等信号。这一处留在 0.36 里当默认，但下一步要查的是交接，不是再省字节。

顺带说一个 HIP 和 D3D12 共享显存的坑：`hipImportExternalMemory` 导入的共享缓冲，释放之后显存一个字节都不还。裸测导入释放 40 次，漏了约 3GB。游戏里每切一次分辨率档位就漏 70 到 90 MB。现在改成进程级的池子，释放时还给池子不真销毁，切档不再涨。

────────────────────

到这里为止，每一处改动的输出都和上一版逐位相同。0.36 里有一处不是。

━━━━━━━━━━━━━━━━━━━━

◆ 第六章：第一次主动放弃逐位

━━━━━━━━━━━━━━━━━━━━

318 说过，逐位不变“不是为了洁癖，是为了不用人眼判画质”。0.36 是第一个和上一版**不逐位**的版本。

起因是回头核对 NVIDIA 原版的 GPU 代码。激活函数那段，原版用的是两次半精度融合乘加（HFMA2）再加一次半精度乘法；我们的实现是 32 位浮点分开乘、分开加。两边本来就不逐位——我们逐位对的是自己的旧版本，不是 NVIDIA。改成 32 位浮点的融合乘加（两步乘加各只舍入一次），整网快 1.2%，输出变了。

变了算不算坏？拿 NVIDIA 原版在同一输入上的输出当裁判，量误差：改前 RMSE 0.0080384，改后 0.0080366，五帧连续跑 0.0080369 到 0.0080011。离 NVIDIA 没远，还略近了一点。我拍板：**0.36 起，新写法就是新的逐位基准**，以后的改动对它比 hash。

这里还栽过一次。第一轮比误差时报的是“改后更接近原版 0.1%”，后来发现裁判那边的输出没有做最后那步移位、我们这边做了，两边不是同一个设置，那个 0.5% 撤回。统一设置重算，才是上面那组几乎不变的数。

逐位规则破了一次，但破的方式有讲究：先证明新写法离真正的裁判（NVIDIA 原版）没更远，再换基准。**逐位对的是“上一版的自己”，那只是方便，不是正确性本身。**

━━━━━━━━━━━━━━━━━━━━

◆ 第七章：不是核的那几处

━━━━━━━━━━━━━━━━━━━━

有两处帧率涨幅，和核一点关系都没有。

**分档规则。** 2K 质量档，游戏内部渲染 1707×961。网络有 720、900、1080 三个固定尺寸档，旧规则是“超过 900 档就进 1080 档”，于是 1707×961 被**双线性放大**到 1920×1080 再算——网络多算的 35% 像素全是插值出来的。改成“超出一档不到 10% 就往下缩进这一档”，1707×961 缩进 1600×900。同场景 49～50 帧到 56～57。一行比较条件，比这四天任何一处核优化都大。

**看帧时间，不只看帧率。** 加了一个帧时间分布日志，每 5 秒一行：平均、中位数、99 分位、最大值。站着不动时 99 分位和平均只差 0.5 毫秒；跑图时偶尔有一两帧 30 毫秒的顿挫，对照日志，网络那几帧照常执行，顿挫来自游戏自己的流式加载。帧率只有一个数，分布才能回答“卡是谁卡的”。

◆ 收尾：一份给自己的 HIP 入门清单

━━━━━━━━━━━━━━━━━━━━

这四天加起来，大约三成：一头一 wave 约 6%，两个一组的打包约 9%，融合约 6%，剩下是一串 0.2% 到 2% 的小改动和一次基准变更（数字来自不同批次，不能直接相加）。

回到开头的承诺，把这期出现过的东西收成一张表：

| 概念 | 一句话 |
|---|---|
| 核（kernel） | GPU 上跑的函数，写的是一个线程的事，靠线程号找自己那一格 |
| 宿主（host） | CPU 上的程序：开显存、搬数据、发射核、等结果 |
| 工作组 / wave | 一组线程共享一块共享内存；每 32 个一捆是 wave，同一时刻执行同一条指令 |
| `.hsaco` / `.s` | 编好的 GPU 代码文件 / 它的汇编，后者是判断优化有没有生效的唯一依据 |
| 模块加载 | `hipModuleLoadData` → `hipModuleGetFunction` → `hipModuleLaunchKernel`，不用 SDK 也能发射 |
| 内置函数 | `__builtin_amdgcn_*`，一句对应一条硬件指令，矩阵乘、FP8 转换、取中位数都靠它 |
| 片段排布 | 矩阵指令要求“哪个线程拿哪几个数”，写矩阵核一半功夫在这里 |
| 编译期开关 | 新写法包在宏里默认关，关时机器码必须和旧版一致 |
| 逐位回归 | 输出每一位比 hash，免去人眼判画质 |
| ABBA 计时 | 基准、候选、候选、基准，抵掉频率和温度漂移 |

如果真要自己动手，顺序大概是：先装 HIP SDK 用 hipcc 跑通第一章那个加 1 的程序；再写一个 32 线程的核，调一次 WMMA，把 16×16 的结果拷回来和 CPU 算的对一遍，搞清楚片段排布；然后养成每次改完读 `.s` 的习惯。剩下的，都是在自己的网络上一个变量一个变量地量。

仓库还是那个： https://github.com/lmxxf/dlss5-on-amd-9070xt-porting ，0.36 三个包的下载链接在首页；这期每一处改动的原始数据、没采用的候选和它们为什么不赚，都在 Development/results/ 下按名字加日期归档。
