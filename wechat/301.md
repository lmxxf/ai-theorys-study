◆ 第二章：60 帧的假象，根因在游戏配置里

━━━━━━━━━━━━━━━━━━━━

周六傍晚 Codex 把矩阵接口扩到尾端四层和最后一块，让我进游戏试。我看到的是 60 帧，但不流畅。

日志里三个数字说明了一切：`backend_ready=0、ffx_frames=0、frame_contract_1080=0`。**神经网络一帧都没跑。** 60 帧是游戏原生画面，什么都没加。

排查走了四步。先怀疑新代码，切回上午发布的版本，还是 0。我让 Codex 把源码整个回退到最后一次成功的提交，还是 0。代码不是根因。Codex 加了临时追踪，发现反复查询 FSR 配置函数的是 Steam 的游戏内覆盖层，不是 AMD 驱动；游戏取 `ffxDispatch` 的那个槽还是指向我们的入口。**钩子完好，只是没人来调。** 再抓 `ffxCreateContext`，失效的时候这个函数根本没被调用过，不是创建失败，是压根没创建。

最后只读反查游戏的控制台变量：FSR3 是开的，原生 DX12 是开的，但 `r.PostProcessAAQuality=0`。菜单上明明显示“FSR3，质量档”。往 Engine.ini 里强写抗锯齿等级 4，被游戏启动时覆盖回 0。真正的开关在 `GameUserSettings.ini` 里，`AntiAliasing` 那一项是 OFF。改成 HIGH，重启，FSR 上下文创建成功，71 块全部恢复执行，19.2 帧。

机制是这样：虚幻引擎里 FSR 的升频挂在时序抗锯齿的管线上，抗锯齿关了，升频上下文就不会被创建，`ffxDispatch` 这个函数就没人调。我们钩的是那个函数，函数没被调，钩子就是个摆设。日志里没有追认这个 OFF 是谁写进去的，可能是我某次改画质时顺手点的。

这一段的教训还算普通：**“补丁失效”和“游戏没走那条路”从外面看一模一样。** 真正要命的在下一章。

◆ 第三章：画面根本没变，因为合成从来没提交给 GPU

━━━━━━━━━━━━━━━━━━━━

修好抗锯齿之后，我让 Codex 在主菜单和洞窟各拍三张：网络开、显示旁路、左半原生右半神经。拍完我看不出差别。日志里这次没有辩解，写的是：“用户‘看不出差别’的反馈不能以‘网络确实在执行’来反驳。”

于是我要求 Codex 证明最终输出真的进了游戏画面。Codex 加了一个审计模式：同一帧里抓合成前的画面、合成后的画面、拷回游戏后台缓冲区之后的画面，外加最后一块的中间量和那 384 字节的输出权重，等 GPU 栅栏走完再读回来。

**第一轮读回来的东西全是零。** 不只是网络输出是零，游戏画面是零，连常量权重都是零。这不可能，所以是抓取本身没生效。

Codex 去翻 ReShade 的源码。我们的插件是挂在 ReShade 上的，合成用的是 ReShade 的即时命令列表。那个列表的 `flush()` 函数开头有一句：如果 `_has_commands` 是假，直接返回。而我们在 `on_present` 里做合成时，为了省事拿了原生的 D3D12 指针，直接调 `CopyResource` 和 `Dispatch`，绕过了 ReShade 的 API。**绕过 API 的后果是那个标记位永远不会被设上。** 命令录进了列表，列表从来没有被提交到 GPU 队列。

也就是说，从 09-04 接进游戏那一刻起，网络确实每帧都在算，但算完的结果每帧都被扔掉了。我看到的一直是游戏原生的 FSR 画面。周六下午传到网盘的那个 dll 也是这样：装上去 19 帧是真的，GPU 也真的在算，只是画面从来没换过。之前日志里那个每帧递增的“显示代数”计数，只是 CPU 侧的计数，不证明 GPU 执行了任何东西。

────────────────────

💡 CPU 记了一笔，不等于 GPU 做了一件事

D3D12 的执行模型是三段：CPU 往命令列表里录命令、把命令列表提交到 GPU 队列、GPU 从队列里取出来执行。三段之间都是异步的。录完不等于提交，提交不等于执行完，执行完要靠栅栏（fence）信号才知道。

我们的验收指标“显示代数每帧加一”是在第一段加的，那一段永远成功，跟后两段发生了什么无关。ReShade 那个 `_has_commands` 标记就是第一段到第二段的门，门没开，后两段就不存在。

正确的验收只有一种：**等栅栏走完，把 GPU 侧的结果读回来，和 CPU 按同样公式算出来的比。** 这次修好之后做的正是这个，合成后的画面和游戏后台缓冲区逐字节一致，CPU 按真实权重重算的残差和 GPU 输出逐值一致。这才叫“输出进了画面”。

────────────────────

修法两行：拷入改走 ReShade 的 `copy_resource` 接口（这一路会设标记），原生合成做完之后显式调一次 `flush_immediate_command_list()`。

修好之后，网络输出第一次真正落到了屏幕上。主菜单 99.6% 的像素被改动，平均每像素变了 2.6 个灰度级；洞窟 99.9%，平均 3.5 个。**然后 8×8 的网格回来了。** Codex 把残差按 (x mod 8, y mod 8) 分成 64 组算方差，固定相位的均值能解释主菜单 95.4%、洞窟 74.3% 的残差方差。周期伪影就在神经输出本身，不是截图时动画的差异。

回头看，周六早上那次“修好小方格”是怎么修好的？合成没提交，屏幕上本来就是原生画面，方格当然“消失”了。再往前，周五那篇的“画面清晰，三门闭合”，那张主菜单截图看的也极可能是原生画面。日志没有回头去改这两处措辞，但因果链已经摆在那里了。

到这里主线换了。日志的原话：“后续主线应是消除真实输出的周期错误，不是继续追 FPS。”周六一整天的性能优化，GPU 时间戳的数字都是真的，但都是在一个没人看见的输出上量的。

━━━━━━━━━━━━━━━━━━━━

◆ 第四章：周日，从“像”退回到“一样”

━━━━━━━━━━━━━━━━━━━━

周六晚上先修了两处最后一块的低级错误：稀疏矩阵的偏移量写成 8200，实际是 8196，整段错读一项；主输入的 512 个元素不是 4×4×32 的自然排列，是 2×4×4×16 按 bank 排的。修完网格还在，相位方差解释率 96.2%。这说明错的不在最后一块，在上游。

于是周日整天做的是一件之前没做过的事：**不再拿“我的新版对我的旧版”比，而是每一层拿 NVIDIA 原版核心当裁判，要求逐值一致，误差为零。** 裁判在 DGX Spark 上跑：泄露的 CUDA 核心能直接在它上面加载，想喂什么输入就喂什么，几秒出结果；5090 只负责从真游戏里抓那些 dll 里没有的运行时参数，比如随机种子和归一化系数，抓到了就不再折腾那台远程机器。之前的验收标准是相关 0.99 以上加平均误差小于一个量化刻度，这两天证明那个标准太松，四个地方漏了。

**第一，block0 的权重布局表是错的。** 297 期说过，dll 里的权重是 153 条连续的字节记录，block0 那条是 21696 字节的一整块，没有任何字段名。要用它得先有一张地图：第几个字节到第几个字节是前馈的第一个矩阵，哪一段是 QKV，哪一段是缩放系数。这张地图之前是靠探针猜出来的，直接读 sm_120 的汇编去核对，发现 QKV 和缩放系数的起点各偏了 8 个元素。

更要紧的是类型判错了。汇编里主体用的矩阵乘指令是 `QMMA.16832.F16.E4M3.E4M3`。MMA 是 Tensor Core 的矩阵乘加指令（matrix multiply-accumulate），一条做一个 16×8×32 小块的 D = A×B + C；前缀 Q 是 quarter，FP8 输入，对应 FP16 输入的叫 HMMA。后两个 E4M3 说明两个输入操作数都是 FP8：记录开头那 8192 字节是两张 FP8 矩阵，每个元素 1 字节，不是旧地图以为的 4096 个 FP16、每个 2 字节。之前做探针实验往里写 FP16 的 1.0，字节序列是 `00 3c`，被硬件当成两个 FP8 读，`00` 是 0，`3c` 是 1.5。于是每两个输入里只有一个有响应，当时还以为发现了门控结构。假象，是把一个数写成了两个数。

**第二，随机场之前根本没实现。** 298 期结尾埋过一个钩子：输入七通道，RGB 之外四路是 Box–Muller 高斯噪声，留到后面追。这两天追到了，追到的方式是发现之前的移植把它当成“高斯开关为零”直接跳过了。汇编里随机种子来自参数区偏移 c8，旧的辅助程序往那里填的是浮点 1.0 的位模式。按原版的 uint32 乘法、异或、移位重建哈希，四组均匀分布，三路 Box–Muller，三个种子各 192 个值和原版逐值一致。后面为了让 AMD 侧也逐值一致，连 `MUFU.LG2`、`SQRT`、`COS`、`SIN` 这几条 NVIDIA 特殊函数指令的舍入行为都复刻了，最后落成一张 192 MB 的函数表。

**第三，前馈是 32 到 128 再到 32。** 字节探针恢复出两个矩阵各 4096 条连接，隐藏维是 128，旧实现写的是 64。累加合同也不一样：FP8 输入、FP16 结果、每 32 个 K 舍入一次，残差作为矩阵乘的初始累加器先加进去。

**第四，Tensor Core 的累加不是顺序加法。** 这是最后一个卡点，也是最有意思的一个。

────────────────────

💡 相关 0.999 和逐值一致之间差了什么

前三处修完，128×64 的小夹具上前四层逐值一致了，但换成 512×512 的大夹具，块 0 的下采样输出有 5 个值不一样，最大差 0.03125，就是一个 FP8 量化刻度。5 个值，二百万分之五，按老标准这叫通过。

沿着这 5 个值往上游追，追到输入混合那一步：16 项点积的精确和是 −0.2108764603290183，离 FP16 的一个舍入边界只差 4.5e−9。CPU 用 FP32 累加再转 FP16，落在边界这一侧；原版落在那一侧。一个 ulp 的差别，经 FP8 量化变成一整个刻度，再经后面几层扩散。日志里有一组数：块 0 的平均误差 0.0008，三层之后变成 0.097，放大一百倍。

试了“精确求和转 FP32 再转 FP16”，那 5 个点对上了，但全幅冒出来 337 处新差异，撤回。真正的规则是直接跑 WMMA 测出来的。WMMA 是 CUDA 里调用 Tensor Core 的 API（warp-level matrix multiply-accumulate），Codex 用它在 Spark 上跑了几百万组 FP16 小块乘法，拿结果反推硬件的累加方式：取两个操作数指数之和的最大值 E，每一项按 2 的 (E−27) 次方对齐、向零截断，精确求和，最后做一次 FP16 的四舍五入。把 16 项的顺序倒过来、随机打乱，结果不变，说明它确实不是顺序浮点加法。按这条规则实现之后，838 万个混合值全部一致。

**所以“相关 0.999”和“一样”之间差的不是 0.001，是“误差从哪里来”这个信息。** 相关高只说明大部分值对了，说不出剩下那一点是量化必然的还是实现错了，而后者会在下游放大。

────────────────────

第四处修完，AMD 上从 512×512 的 RGB 输入连续跑到 ViT 第 38 块，三帧对原版 different=0。

━━━━━━━━━━━━━━━━━━━━

按块列一下。“逐值一致”指 AMD 实机连续链输出对原版核心零误差，不是相关系数。

| 块 | 内容 | 状态 |

| 5 到 8 | 64 通道四层，下采样到 128 | 逐值一致 |

| 15 到 22 | 256 通道，下采样到 512 | 逐值一致 |

日志傍晚最后一段的结尾照例是那句：“游戏 DLL 未改。”真实 1080p、最终 RGB、游戏内画面验收都还没到。

也就是说，周日这一天把编码器、底部和大半个上坡重做了一遍，剩下的尾巴还是周五那套“相关 0.99”的近似。AMD 机上装的 dll 还是周六晚上那个带网格的版本，网盘上的还是周六下午那个 19 帧的版本，那个版本的画面现在知道了是原生的。

目前还必须完成的工作，按日志里自己列的顺序：

1.**上坡剩下的 62 到 70 接进连续链。** 上坡比编码器快得多，一小时推了二十几块，因为块的类型都见过。但第一站就翻出两个旧假设：block39 的权重之前按 FP16 解释，实际和 block0 一样是 FP8 矩阵；上采样试了双线性各种变体全部失败，实际是最近邻 2×2 重复，再和 skip 做一次融合乘加，提前舍入 skip 都会差 256 个值。
2.**最后一块的全分辨率 skip。** block70 要的 skip 是 1920×1088 的，之前游戏 dll 里喂的是 960×544 那份，日志原话“不能拿它冒充”。这一条得等上坡做完才能接。
3.**1080p 真实几何。** 现在全部验证是在 512×512 的夹具上做的，ViT 只验了 64 token 的调用；1080p 是 540 个 token，而 16 和 32 token 的原版行为已经发现异常，540 会不会异常还没测。
4.**随机函数表挪出上传堆。** 那张 192 MB 的表是正确性原型，放在上传堆里每次访问都走 PCIe，进游戏之前要么搬进显存要么换成算的。
5.**游戏内 dll 重接。** 周六那个 dll 用的是旧的近似链，新的逐值链是一堆独立测试程序，要重新装进常驻的游戏 dll 里，同帧抓合成前后的画面做数值和目视验收，这次栅栏走完再读回。
6.**然后才是帧率。** 目标没变，1080p 先到 10 帧，再往 30 帧走。周六那些优化里哪些还能用，得在新链上重新量一遍。

前两条是这两天内的事，三到五条各是半天到一天，第六条不知道。

◆ 收尾：问了那几句，还是漏了一个

━━━━━━━━━━━━━━━━━━━━

周五那篇结尾我列了几句派活时该问的话：标准答案从哪来，验收线定在哪，逐字节一致才算过，加速是哪一段的功劳。这两天证明光问这几句不够，有一个东西在问题之外：**我用来判断“它跑了”的那个数，量的是 CPU 记账，不是 GPU 执行。** 从这个指标往下推的所有结论，包括周五的“三门闭合”、周六早上的“方格修好了”、周六一整天的帧率数字，全部建立在一个从没显示过的输出上。

回头看，两天里最有价值的一句话不是任何一个数字，是我周六晚上那句“看不出差别”。它是唯一一个直接量最终结果的观察，而它和所有过程指标矛盾。日志里那句“不能用‘网络确实在执行’来反驳”是对的：**过程指标和结果观察打架的时候，信结果。** 然后去找过程指标为什么不准。

另一个变化是验收标准本身。周五之前的标准是“相关 0.99 以上，误差小于一个刻度”，这两天换成了“逐值一致，零误差”。代价是周日一天只推进到第 61 块，前一天那套近似版本一天就“跑通”了 71 块。但近似版本的画面上有 8×8 的网格，逐值版本还没走到出画面那一步，走过的每一层都对上了。哪个快，取决于返工算不算进去。

dll 什么时候能做出来，现在不知道。上坡还剩九块，然后是 1080p 几何和游戏内重接，顺利的话一两天，前提是不再撞上新的“累加规则”。撞上了就是再一天。

关心 DLSS 5 神经网络的同学，可以看看我们目前调研出来的东西接着往下做：仓库还是那个， https://github.com/lmxxf/dlss5-on-amd-9070xt-porting ，工作日志 `porting-worklog.md` 从 2026-09-05 那一节往后就是这两天的部分。对的和错的都在里面，每一次撤回都没删。我们干了什么，对不对的，都往外说。
