◆ 第一章：先看这个文件分成几段

━━━━━━━━━━━━━━━━━━━━

DLL 是 Windows 上的一种程序文件。它内部不是一锅粥，而是分成若干“段”（section）：一段放能执行的代码，一段放只读常量，一段放数据，还有一段叫资源段，本来是给图标、版本信息用的。

有个叫 `objdump` 的标准工具，能把这些段列出来（`objdump -h 文件名`）。对着这个 DLL 跑一遍，几个主要段的大小是这样：

```
.text    （代码）      0.67 MiB
.rdata   （只读常量）  0.20 MiB
.data    （数据）     16.38 MiB
.rsrc    （资源）    140.85 MiB
```

第一眼就能看出反差：真正的可执行代码（`.text`）不到 1 MiB，而资源段（`.rsrc`）独占 140 多 MiB，几乎就是整个文件。

这本身就透露了这个文件的性质。正常的程序，代码是主体，资源段放点图标顶天了。这里正相反——代码小得像个零头，一个巨大的资源段占了全部体积。**这说明它不是一个“以代码为主的程序”，而是一个“以数据为主的、背着一大坨东西的壳”。** 那一大坨，就是我们要找的模型。

━━━━━━━━━━━━━━━━━━━━

◆ 第二章：140 MiB 的资源段里，到底是不是权重

━━━━━━━━━━━━━━━━━━━━

看到 140 MiB 挤在资源段，很容易顺口就说“这就是权重”。但严谨一点，不能光看段的总大小就下结论——资源段里可以塞很多种东西，得再往里看一层。

资源段内部是一棵树，每个“叶子”是一份具体资源。把这棵树解析出来，结果干净得出乎意料——**整个 140 MiB 的资源段里，只有两个叶子**：

```
WEIGHTS_HT      147,695,410 字节  （140.85 MiB）
版本信息              1,184 字节  （几乎为零）
```

一个是 1184 字节的 Windows 版本信息，可以忽略。另一个叫 `WEIGHTS_HT`，147,695,410 字节，几乎就是整个资源段。

这个名字基本上把身份写在脸上了：**weights，权重**。一份接近 1.48 亿字节的数据，单独作为一个资源嵌在文件里，名字就叫权重——它就是这个神经网络的全部参数。

────────────────────

💡 “解析资源树”不是黑魔法，是照死格式查表

听到“把资源树解析出来”可能觉得挺玄，其实这一步没有任何猜测，就是照着一份公开的文件格式查表。

PE 文件（也就是 Windows 的 exe、dll）的资源段，格式写在微软的规范里，是死的。它是一棵三层树：第一层按**类型**分（图标、字符串、版本信息、自定义数据……），第二层按**名字**分（具体是哪一个），第三层按**语言**分（中文、英文）。最底下的叶子只记一件事——**这份资源在文件的哪个位置、有多大**。

每一层都是一张小表，表头写着“我下面有几个条目”，后面跟着条目列表；每个条目要么指向下一层的子表，要么指向一个叶子。解析就是从根表出发，顺着这些指针一层层往下走，走到叶子为止。走到 `WEIGHTS_HT` 这个叶子，读出它记的那两个数——文件偏移和大小——就知道它在文件里 offset 多少、长 147,695,410 字节。**这个数不是我数出来的，是目录表里写好的，照着读就行。**

整件事没用到任何深度学习工具，也没有估：一份公开的文件格式，一层层查表查到底。想自己动手的，PE 资源目录的格式网上能查到，几十行代码就能把这棵树走完。

那反过来，NVIDIA 为什么要把权重塞进这个本来放图标的资源段？因为资源段有个方便的性质：里面的东西会随程序一起加载进内存，运行时按名字就能取到。神经网络的权重正好符合这个用法——它不是代码，但程序一跑起来就要整个用到。把这一大块参数命名成 `WEIGHTS_HT` 放进资源段，运行时按名字取出来、搬进显卡，顺理成章。这也解释了上一篇那个现象：为什么换个 DLL 就能换模型的版本——因为模型本来就整个打包在这个资源段里，换文件就等于换了那 140 MiB 参数。

────────────────────

到这里，“模型和代码的分离”就完成了。我们不需要任何 AI 工具，只靠读文件结构，就把一个 158 MiB 的 DLL 切成了两半：

```
一小块 CPU 代码     ——  负责加载、调度
一大块权重资源      ——  就是模型本身
```

而“GPU 上具体怎么算”的那些预编译核心，主要在中间那 16 MiB 的数据段里，跟权重是分开放的。上一篇初稿这里我写岔了，把权重和 GPU 核心混着说了，这次直接读文件才看清：三块各是各的。

顺便说一句参数量。权重资源是 147,695,410 字节，而这个模型主要用 FP8（一种 8 位、每个参数占一个字节的低精度格式）保存。字节数除以每参数一字节，得到约 **1.48 亿参数**这个量级。

这里是估算，不是文件自带的一张参数表：资源里可能还有一些头信息、缩放因子之类的杂项，所以精确参数数会有些出入。但量级是靠得住的——1.48 亿上下。

◆ 第三章：从名字认出模型的几大块

━━━━━━━━━━━━━━━━━━━━

权重是一大坨浮点数，光看那 1.48 亿个数字，看不出结构。但幸好，编译进 DLL 的那些 GPU 核心，是**带名字**的——每个计算步骤都有一个字符串标签，像 `cc_vit_attention`、`swin_1h_32_1`、`upsample` 这样。

有个更基础的工具叫 `strings`，能把一个二进制文件里所有可读的文本片段抠出来。对着这个 DLL 跑一遍，再筛掉无关的，模型的骨架就从这些名字里浮出来了。

不做机制分析，光看这些名字分个类，能认出这么几大块：

```
入口          layer0.conv_weight        （一层卷积，先把画面接进来）
编码器        swin ×4 级，逐级缩小       （一路把画面压缩成抽象特征）
瓶颈          cc_vit_attention          （最深处，全局看一遍）
解码器        upsample ×4 级，逐级放大   （一路还原成新画面）
出口          out_conv_weight           （一层卷积，把结果送出去）
```

这就是一张**先压缩、再还原的 U 形结构**：左边一路往下把画面读懂，右边一路往上把画面重画，中间最窄处是全局理解。这种形状在图像处理里很常见，它有个俗称叫 U-Net，因为画出来像个字母 U。

再看细一点，编码器和解码器是**对称**的。编码器那四级，名字里带着通道数和一个逐级变化的参数：

```
第 1 级   32 通道
第 2 级   64 通道
第 3 级  128 通道
第 4 级  256 通道
```

一路下去通道翻倍、画面尺寸缩小；解码器则是镜像的反过程，一路把通道减回来、尺寸放大。两边同一级之间还有“跳线”（名字里的 `UpsampleSkip`），把编码时的细节直接接到解码对应的层——防止压缩过程中丢掉的细节还原不回来。

还有一个值得记一笔的点：**这不是一个纯 Transformer，也不是一个纯卷积网络，是两者混着用的。** 名字里既有 `attention`（注意力，Transformer 那一套），又有 `ConvBlock`（卷积块）。粗略地说，卷积擅长看清局部的纹理，注意力擅长把画面里离得很远的部分关联起来——一帧画面既要局部清晰又要全局协调，两样都得要。它们各管一段，具体怎么配合，是下一期的事。

◆ 第四章：能说到哪儿，不能说到哪儿

━━━━━━━━━━━━━━━━━━━━

这一步很关键，尤其是拿逆向工程当方法的时候，得给自己划条线：从这些名字里，什么能下结论，什么不能。

**能说的**（名字直接支持）：
- 它是一个 U 形的编码器—解码器网络
- 编码器用了注意力，一共四级，通道逐级翻倍
- 有卷积块，跟注意力混用
- 编码和解码之间有跳线
- 权重约 1.48 亿参数，主要是 FP8

**不能说的**（名字给不了）：
- 每一级具体有几层、每层多宽
- 完整的连接图长什么样
- 它是怎么训练出来的、用了什么数据
- 每帧精确做多少次运算

换句话说，靠读名字，我们能画出这张地图的**街道走向**，但画不出**每栋楼的内部结构**。现在可以说“看见了一个 U 形混合网络的骨架”，还不能说“拿到了 NVIDIA 的完整设计图”。这条线得守住——上一篇就是因为一时说过了头，把骨架当成了全图，被自己后来读文件的结果纠正了回来。

◆ 收尾：地图画出来了

━━━━━━━━━━━━━━━━━━━━

这一期的收获，其实就是一套朴素的手法：

```
objdump   看段  ——  发现代码很小、一个资源段独大
资源树     看叶子 ——  找到 WEIGHTS_HT，锁定权重
strings   看名字 ——  认出 U 形结构的几大块
```

不需要任何深度学习框架，靠三个标准工具，就把一个“黑箱”二进制拆成了“一小块代码 + 一大块模型”，还认出了模型的大致轮廓：**入口卷积 → 四级编码器 → 瓶颈 → 四级解码器 → 出口卷积，一个卷积和注意力混用的 U 形网络。**

地图画出来了。下一期开始逐个街区走：编码器用的那种注意力到底是怎么算的、为什么图像不能像文字那样直接全局注意、那些“窗口”是干嘛的。那才是这台“电影画质”机器真正有意思的地方。
