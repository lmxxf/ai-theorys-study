◆ 第一章：先看这个文件分成几段

━━━━━━━━━━━━━━━━━━━━

DLL 是 Windows 上的一种程序文件。它内部不是一锅粥，而是分成若干“段”（section）：一段放能执行的代码，一段放只读常量，一段放数据，还有一段叫资源段，本来是给图标、版本信息用的。

有个叫 `objdump` 的标准工具，能把这些段列出来（`objdump -h 文件名`）。对着这个 DLL 跑一遍，几个主要段的大小是这样：

```
.text    （代码）      0.67 MiB
.rdata   （只读常量）  0.20 MiB
.data    （数据）     16.38 MiB
.rsrc    （资源）    140.85 MiB
```

第一眼就能看出反差：CPU 侧可执行代码（`.text`）不到 1 MiB，而资源段（`.rsrc`）独占 140 多 MiB，接近整个文件的九成。

这本身就透露了这个文件的性质。很多 DLL 以代码为主，资源段只放版本信息、图标或少量数据；这里正相反——CPU 代码小得像个零头，一个巨大的资源段占了九成。**这说明它不是一个“以 CPU 代码为主的程序”，而是一个“以数据为主的、背着一大坨东西的壳”。** 那一大坨，就是我们要找的模型。

━━━━━━━━━━━━━━━━━━━━

◆ 第二章：140 MiB 的资源段里，到底是不是权重

━━━━━━━━━━━━━━━━━━━━

看到 140 MiB 挤在资源段，很容易顺口就说“这就是权重”。但严谨一点，不能光看段的总大小就下结论——资源段里可以塞很多种东西，得再往里看一层。

资源段内部是一棵树，每个“叶子”是一份具体资源。把这棵树解析出来，结果干净得出乎意料——**整个 140 MiB 的资源段里，只有两个叶子**：

```
WEIGHTS_HT      147,695,410 字节  （140.85 MiB）
版本信息              1,184 字节  （几乎为零）
```

一个是 1184 字节的 Windows 版本信息。另一个叫 `WEIGHTS_HT`，147,695,410 字节，几乎就是整个资源段。

────────────────────

💡 “解析资源树”不是黑魔法，是照死格式查表

听到“把资源树解析出来”可能觉得挺玄，其实这一步没有任何猜测，就是照着一份公开的文件格式查表。

PE 文件（也就是 Windows 的 exe、dll）的资源段，格式写在微软的规范里，是死的。它是一棵三层树：第一层按**类型**分（图标、字符串、版本信息、自定义数据……），第二层按**名字**分（具体是哪一个），第三层按**语言**分（中文、英文）。最底下的叶子只记一件事——**这份资源在文件的哪个位置、有多大**。

每一层都是一张小表，表头写着“我下面有几个条目”，后面跟着条目列表；每个条目要么指向下一层的子表，要么指向一个叶子。解析就是从根表出发，顺着这些指针一层层往下走，走到叶子为止。走到 `WEIGHTS_HT` 这个叶子，读出它记的那两个数——文件偏移和大小——就知道它在文件里 offset 多少、长 147,695,410 字节。**这个数不是我数出来的，是目录表里写好的，照着读就行。**

整件事没用到任何深度学习工具，也没有估：一份公开的文件格式，一层层查表查到底。想自己动手的，PE 资源目录的格式网上能查到，几十行代码就能把这棵树走完。

────────────────────

那个几乎占满资源段的 `WEIGHTS_HT`，名字基本上把身份写在脸上了：**weights，权重**。一份接近 1.48 亿字节的数据，单独作为一个资源嵌在文件里，名字就叫权重——它是这个神经网络的嵌入权重包。里面还夹着名字、长度、对齐和量化信息，不能把每一个字节都叫参数。

────────────────────

💡 `WEIGHTS_HT` 里的 HT 是什么？只能猜

`WEIGHTS` 没悬念，`HT` 这个后缀却查不到出处——它是 NVIDIA 内部命名，DLL 里只出现这一处，没有任何地方把它拼全。所以下面几个都是猜，标清楚是猜：

- **H-Net 的缩写**（我觉得最可能）：这个网络在代码里的类名前缀全是 `HNet`，比如 `CCNetwork@HNetCpp`。既然网络自己叫 H-Net，那“H-Net 的权重”缩成 `WEIGHTS_HT` 很顺。
- **Hash Table（哈希表）**：权重包正是一串“名字 → 数据”的记录，按名字查——这结构本身就像张哈希表。
- **Half Tensor（半精度张量）**：上面刚验过权重是 FP16，也就是 half precision。

到底是哪个，DLL 里没留全称，查不出来。**能确定的只有 `WEIGHTS`，`HT` 就到此为止**——这也是逆向的常态：很多命名是厂商脑子里的，文件里不会替你解释。

────────────────────

至于 NVIDIA 为什么把权重塞进这个本来常放图标的资源段：因为 Windows 已经给了现成的按类型、名字、语言定位资源的机制，程序用 `FindResource`、`LoadResource`、`LockResource` 就能取到内存指针，不必再发明一套外部模型文件的查找协议。这也解释了上一篇那个现象——为什么换个 DLL 就能换模型版本：因为模型跟着运行时一起打包进了资源段。

到这里，“模型和代码的分离”就完成了。我们不需要任何 AI 工具，只靠读文件结构，就把一个 158 MiB 的 DLL 分成了三块：

```
一小块 CPU 代码     ——  负责加载、调度
一块 GPU 核心与数据  ——  负责在显卡上执行
一大块权重资源      ——  就是模型本身
```

而“GPU 上具体怎么算”的那些预编译核心，主要在中间那 16 MiB 的数据段里，跟权重是分开放的。上一篇初稿这里我写岔了，把权重和 GPU 核心混着说了，这次直接读文件才看清：三块各是各的。

顺便说一句参数量。顺序解析权重包后，153 条记录全部满足 `payload 字节数 = 元素数 × 2`——每个参数正好占 2 字节。所以合计约 **7380 万个参数**，不是 1.48 亿。（上一篇按每参数一字节估的“约 1.48 亿参数”这一篇要修正：字节数没变，但每个参数占两字节，所以参数量是它的一半。至于为什么是两字节，下面这块讲。）

────────────────────

💡 到底是 FP8 还是 FP16？——存的和算的不是一回事

DLL 里的 GPU 核心名字大量带 `_fp8`，很容易让人以为权重是 FP8（8 位、每个数 1 字节）存的。但直接解开权重包一看，不是：

- 每条记录都满足“字节数 = 元素数 × 2”，**每个参数占 2 字节**；
- 按 FP16（16 位、半精度）解码，抽样数据全是合理的有限数，单个 `blend_scale` 干净地读出 `0.73974609375`。

所以**文件里存的是 FP16**，这一步是确定的。

那 `_fp8` 从哪来的？我们把原版 GPU 核心也反汇编看了一眼：**运行时并不直接吃这份 FP16。加载时它把权重重新打了一次包**——压成 8 位的 FP8（配一份 FP16 缩放系数把精度找补回来），GPU 真正算的是这份 8 位数据。

一句话：**文件里存 FP16（图省事、好分发、精度高），芯片上算 FP8（省一半带宽、吃满显卡加速），中间隔着一次加载时转换。** `_fp8` 说的是后者——**模型的存储精度和计算精度，本来就是两件事。**

────────────────────

到这儿，权重这块摸清了：多大、多少参数、什么精度、怎么从文件里分离出来。但那 7380 万个数堆在一起，还只是一坨料——它拼成了一个什么形状的网络？这就得换个地方看：不看权重本身，看那些带名字的 GPU 核心。

◆ 第三章：kernel 名字暴露了六档宽度

━━━━━━━━━━━━━━━━━━━━

权重是一大坨量化数字，光看内容很难认出结构。但幸好，编译进 DLL 的 GPU 核心是**带名字**的——每种计算程序都有一个字符串标签，像 `cc_vit_attention`、`swin_1h_32_1`、`upsample` 这样。

有个更基础的工具叫 `strings`，能把二进制文件里所有可读的文本片段列出来。对着这个 DLL 跑一遍，再筛掉无关项，最先浮出来的是一条非常整齐的宽度阶梯：

```
cc_tinlayout_fused_swin_1h_32_1       1 head    32 通道
cc_tinlayout_fused_swin_2h_64_2       2 heads   64 通道
cc_tinlayout_fused_swin_4h_128_4      4 heads  128 通道
cc_tinlayout_fused_swin_8h_256_8      8 heads  256 通道
cc_split_swin_16h_..._512            16 heads  512 通道
CCVitAttentionLayer                  输入宽度 1024
```

`1h/32 → 2h/64 → 4h/128 → 8h/256 → 16h/512 → ViT/1024`，每升一档，注意力头数和通道数一起翻倍。初稿只认到 256，漏掉了 512 那组 split Swin，以及专门写着“输入 1024 通道”的 ViT Attention。

为什么 512 那档突然从 `fused` 变成 `split`？名字只能告诉我们：到这一档，同一块计算被分成了 QKV、projection、feed-forward 等多个核心。最自然的解释是宽度大了，原先一口吞掉的融合核心不再合适；但这是工程推断，不是 NVIDIA 留在文件里的注释。

1024 那档则更直接。DLL 里的报错字符串写着：

`CCVitAttentionLayer specialized for Cin=1024`

紧跟着还有一个解码入口：

`cc_dec_input_upsample_1024_512`

也就是从 1024 通道上采样回 512。这一上一下，说明 1024 很可能就是 U 形底部，随后回到外面那档 512；精确位置仍要等执行图确认。

────────────────────

💡 U 形不是靠“看起来像”猜的，回程和跳线都留下了报错

只有一条通道阶梯，还不能证明网络会沿原路回来。真正把 U 形钉住的，是另一批名字和报错文本。

32、64、128、256 四档 Swin 核心都各自带 `_ds` 和 `_upsample` 变体：前者下采样，后者上采样。512 与 1024 之间则有刚才那条 `1024_512`。这说明同一组宽度不只往深处走，也有往外还原的回程。

跳线的证据更直白：

```
CCTinlayoutFusedSwin... (upsample) requires 2 inputs (main + skip)
CCDecInputUpsampleLayer requires 2 inputs (main, skip)
CCTinlayoutFusedPostBlock... requires 2 inputs (main + enc0 skip)
```

`main + skip`、`enc0 skip` 都是程序自己报错时写出来的输入名。也就是说，解码时除了上一层的主干，还会拿编码端保存的特征一起算。到这里，**下采样、1024→512 的解码入口、上采样，以及编码端到解码端的跳接**，都有二进制里的直接证据；把它们合成一张 U 形骨架，则是这些证据共同指向的结构判断。

再加上 `ConvBlock`、`conv_weight` 和 `out_conv_weight`，这套运行时指向的不是纯 Transformer，而是卷积和注意力混用的 U 形视觉网络。

◆ 第四章：工具箱不等于执行顺序

━━━━━━━━━━━━━━━━━━━━

走到这里还有一个陷阱：**DLL 里有某个 kernel，不等于当前模型一定调用了它。** `strings` 列出来的是编译进运行时的整只工具箱，里面可能同时放着 FP8 和非 FP8、普通版和 tile-sync 版、不同输入视图和等待方式。把工具箱里的扳手按尺寸排好，不等于已经知道工人今天按什么顺序拧螺丝。

权重包又给了另一层线索。它不是一整坨无名数字：开头 8 字节正好等于资源总长度，后面出现名字长度、名字、记录跨度、数据长度和权重数据。按记录跨度顺序跳转，不必搜索下一个名字，可以连续读出 153 条记录并精确走到包尾。其中能看到：

```
block0.layer0.layer
block1.layer0.layer
...
block70.layer0.layer
```

编号从 0 连续到 70，说明这份权重包至少按 **71 个 block** 序列化；有些 block 下面还带 layer1、layer2、layer3、layer4，另有一条 `block70.layer0.blend_scale`。但名字只给编号，没有把 `block31` 直接写成“512 通道 Swin 第三层”。

所以现在手里有三张不完整的纸：

```
kernel 名字      有哪些算子和宽度档位
权重记录         有哪些 block、每块带几组数据
运行时构图代码    负责把 block 和 kernel 接成执行图
```

前两张已经能读，第三张还藏在不到 0.7 MiB 的 CPU 机器码里。只有把 network descriptor 或 `CCNetwork::build_blocks` 那段构图逻辑继续还原，才能把“71 个权重 block”逐个贴到“哪一种 kernel”上，得到真正的层级顺序。

到这里，能下的结论比初稿多，也更窄：**我们看见了 32→64→128→256→512→1024 的宽度阶梯、下采样与上采样、真实的 skip 输入、卷积入口和出口，以及 71 个编号权重 block；但还没有完整执行顺序。**

这不是少走了一步，恰恰是逆向工程最重要的一步：知道哪条线是文件里读出来的，哪条线还等着下一件证据。

◆ 收尾：地图画出来了

━━━━━━━━━━━━━━━━━━━━

这一期的收获，其实就是一套朴素的手法：

```
objdump   看段  ——  发现代码很小、一个资源段独大
资源树     看叶子 ——  找到 WEIGHTS_HT，锁定权重
strings   看名字 ——  认出 U 形结构的几大块
```

不需要任何深度学习框架，靠三个标准工具，就把一个“黑箱”二进制分成了“一小块代码 + 一大块模型”，还认出了模型的大致轮廓：**宽度从 32 一路长到 1024，再沿上采样和跳接返回，一个卷积、Swin Attention 和 ViT Attention 混用的 U 形网络。**

地图的外轮廓画出来了，但门牌号还没贴上：下一步不是继续猜，而是去找把 71 个权重 block 接到这些 kernel 上的构图逻辑。那张映射表一旦出来，才算真正拿到网络结构。
