## 已直接核实的事实

- 原评测自述使用 Lemonade 2026.39.1，其 llama.cpp 版本为 b10825。具体 ROCm/Vulkan 二进制的构建参数及源修订，不能由服务版本号单独推出。
- 两台设备分别做同机后端比较；不是把 R9700 与 395 的绝对分数相除。两机 Linux 软件环境不同。
- Lemonade 是本地 AI 服务和运行管理层，本次调用 llama.cpp 后端。不能说“Lemonade 和 llama.cpp 是两套独立引擎，各自证实同一结论”。
- 测试名字是 Qwen3-14B-GGUF、Qwen3.5-4B-GGUF、MiniCPM4-8B-GGUF、Qwen3-Coder-Next-GGUF、DeepSeek-Qwen3-8B-GGUF。转述中的 Qwen3.5-14B 与原文不符。
- 原文区分生成吞吐（tokens/s）与首 token 延迟。后者不是已被拆分证明的纯 prefill 用时。

## 可以写入草稿的趋势

| 设备及项目 | 原文呈现的结果 |
|---|---|
| 395：Qwen3-14B 的代码类场景 | Vulkan 吞吐较高，ROCm 首 token 延迟较低 |
| 395：Qwen3.5-4B | 同样大体呈现吞吐与首 token 分别占优 |
| 395：Qwen3-Coder-Next，code-debug | ROCm 获得吞吐胜利，不能概括所有模型都输 |
| R9700：Qwen3-14B，多种代码场景 | Vulkan 吞吐胜，ROCm 首 token 延迟胜 |
| R9700：Qwen3.5-4B，图列出的代码及长输出场景 | Vulkan 两项都胜，不能把指标分工说成无例外定律 |
| R9700：Qwen3-Coder-Next | 多个场景 ROCm 吞吐胜；首 token 延迟存在 Vulkan 胜项 |

这些来自原文正文及每张图的标题/胜者文字。它们不等于已经拿到图中全部精确数字。

## 目前不能据此写死的内容

- 1.5 倍和 3 倍：用户转述的图未随消息提供；Phoronix SVGZ 图和 OpenBenchmarking 原始页面请求被拒，尚未逐图核准。草稿不使用这些倍数，也不把无法读取当成数据不真实。
- 各 GGUF 的精确量化、全部运行参数、缓存/投机状态，以及 ROCm、Mesa/驱动的完整版本：当前拿到的正文不足以补齐，不能凭模型名称猜。
- 具体慢在哪个算子、有无 CPU 回退、哪项指令未启用：该评测没有提供足够的算子性能分析，不能拿其他版本的 issue 充当本轮根因。
- “Vulkan 兼容多个 GPU 厂商”不等于“任何跨 GPU、跨节点组合都能高效并行”。
- 不能由这份 llama.cpp / Linux 测试推出 Windows Strata 换 Vulkan 就会更快；执行引擎、模型与计算路径不同。

## 解释的边界

同一模型、同一 GPU，不同后端使用不同的算子实现、编译和驱动路径，因此速度不由 API 名字保证。批量处理输入与小批量逐 token 生成的计算形状不同，允许两阶段出现不同强弱。这是机制解释，不是已经对本轮具体内核完成归因。

总响应时间的简化关系可写成：`首 token 等待 + (实际输出 token 数 − 1) / 后续生成速度`。只用于说明两项指标的取舍；需先确认实际工具的吞吐计时定义，不能直接拿口径不明的表格拼出精确总耗时。
