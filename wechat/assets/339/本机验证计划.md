# 339：RX 9070 XT 的 ROCm / Vulkan 简单对照

状态：未执行。用户准备切到家里的电脑验证。目标是检查相同机器、相同模型换后端后的表现，不是宣称完整复现 Phoronix 的 Linux R9700/395 测试。

## 机器与隔离

- 目标：家中 Windows 原生 RX 9070 XT 16GB、48GiB RAM、Core Ultra 7 270K Plus。338 曾用过的配置仅作线索，现场复核驱动、运行库、空闲资源和 GPU 选择。
- 在独立目录准备测试，不覆盖 Strata 的可执行文件、运行库或模型配置。正式计时不与 Strata、DLSS5 或游戏实验争抢 GPU，沿用试验区的 GPU 使用约定。
- 安装/下载/编译和正式模型运行按用户习惯分步执行；先探测版本和可用后端，再决定部署，不预填未经核实的安装命令。

## 一份模型，两条后端

优先使用原评测出现过的 Qwen3-14B。选择能全部驻留 16GB 显存、并留出上下文空间的 GGUF 量化文件，例如经实际容量检查可运行的 Q4_K_M；记录文件来源、revision、文件名、字节数和 SHA-256。原文的精确量化尚未核准，不能说这个选择一定与原测一致。

可先用 Lemonade 的 ROCm/Vulkan 后端做应用层对照。记录两个实际 llama-server 二进制各自的版本/commit和启动日志；同一个 Lemonade 版本不自动保证后端构建完全一致。如果二进制来源不同，结果称“这两套部署配置比较”。

若要进一步隔离后端差异，再从同一个 llama.cpp commit 构建 HIP 与 Vulkan 两份程序；先确认相应构建工具可用，不为初步验证强行扩大安装范围。官方入口：

- https://github.com/lemonade-sdk/lemonade/blob/main/docs/guide/configuration/README.md
- https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md
- https://github.com/ggml-org/llama.cpp/blob/master/tools/llama-bench/README.md

## 初轮只做这些

1. 纯文本、单请求、同一份 GGUF、相同上下文容量、KV 精度、batch/ubatch、CPU线程数和 GPU offload 设置。Flash Attention 等优化两边尽量对齐；若只一边支持，明确写成配置差异。
2. 都关闭 MTP、其他投机解码和前缀缓存。确认选中 RX 9070 XT，而非核显或 CPU；从日志确认 offload 层数和内存分配，不能只看请求成功。
3. 用短提示和约 1K–2K token 的代码/文本提示各一组，保存确切文本与实际 token 数。先用短上下文和小输出预算跑通，两后端均正确输出后再计时。
4. 正式测试固定最大输出预算，例如 256 token，temperature=0；记录实际输出数、终止原因和原始回答，不把提前 EOS、循环或垃圾输出当成公平的速度优势。
5. 每个后端先暖机，加载时间另记；AB/BA 交错，每个条件至少三次，不挑最快一轮。模型加载首用、模型已加载但无前缀缓存、相同前缀复用是不同情形，不混算。

## 记录哪些指标

| 指标 | 含义 |
|---|---|
| 首内容等待 | 从发请求到收到第一段非空回答；不把 HTTP 头、空 SSE 或角色字段当成首 token |
| 输入处理速度 | 引擎报告的 prefill token/s，记录实际输入数与计时定义 |
| 生成速度 | 实际输出 token 数和相应生成用时，注明是否含首 token |
| 请求总耗时 | 用户从发出请求到完整结束的时间 |
| GPU/CPU与内存状态 | 显卡型号、offload层数、显存/系统内存、是否回退或换页 |
| 输出 | 全文、哈希、EOS/长度终止和明显错误，避免后端数值差异改变输出长度却被当成算子速度变化 |

若用 `llama-bench`，先看该版本帮助，分别做固定长度的 prompt-processing 与 token-generation 测试。其合成 microbenchmark 不等于 API 的首内容等待，单独放表。应用测试与微基准互相补充，不混口径。

## 结果怎么接回正文

- 写“我们这台 9070 XT、这个系统/模型/量化/构建下”的观察，不借 R9700/395 的结论代替本机数据。
- 如果 Vulkan 吐字快、ROCm 首内容早，分别报告；短输出与长输出的体验可能不同。
- 如果方向相反，保留结果，先核构建版本、实际设备、内存驻留和开关，再考虑具体算子分析。
- 第一轮只验证现象，不凭速度差猜 CPU fallback 或某项硬件指令缺失；确需解释根因，再收 profiler 证据。

尚无本机结果，请不要把计划填写成已跑通或生成空成绩表。
