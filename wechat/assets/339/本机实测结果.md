# 339：本机实测——HIP 读输入更快，Vulkan 连续生成更快

2026-10-13，在 Windows 的 RX 9070 XT 上，用同一份 **Qwen3-14B Q4_K_M** 和同一版本 llama.cpp 对照：**HIP 的输入处理速度领先约 30%，Vulkan 的连续生成速度领先约 8.3%。这台机器也没有出现“Vulkan 全面碾压 ROCm”。**

## 先拆开看计算速度

| llama-bench 项目 | HIP（token/s） | Vulkan（token/s） | 本次领先幅度 |
|---|---:|---:|---|
| 处理 512 token 输入 | 2216.61 | 1711.46 | HIP +29.52% |
| 处理 2048 token 输入 | 2159.74 | 1661.09 | HIP +30.02% |
| 从空上下文连续生成 128 token | 60.30 | 65.33 | Vulkan +8.34% |

每格有 **3 个独立进程 × 每进程 3 次内部重复，共 9 个样本**，不是 9 次独立启动。六个进程按 HIP → Vulkan → Vulkan → HIP → HIP → Vulkan 顺序运行，保留 llama-bench 的暖机；六个进程退出码均为 0。表中取全部样本的平均值，没有挑最快的一次。

这些是分阶段计算速度。llama-bench 不计入分词和采样，生成项从空上下文开始，不能直接当成聊天界面的首字等待或长对话生成速度。[汇总与波动](hip-vulkan-20261013/bench-summary.json) · [六进程收据](hip-vulkan-20261013/formal-receipts.json)

## 再看实际请求要等多久

另起 llama-server，统一为 4096 token 上下文，输入固定为 512 或 2048 token，每次生成 128 token：

| 输入长度 | HIP 首内容等待 | Vulkan 首内容等待 | HIP 请求总时间 | Vulkan 请求总时间 |
|---|---:|---:|---:|---:|
| 512 token | 232.25 ms | 308.85 ms | 2.387 s | 2.299 s |
| 2048 token | 953.50 ms | 1232.06 ms | 3.172 s | 3.277 s |

HIP 两档都更早开始输出；但短输入时，Vulkan 靠后续生成速度把总时间追回了一点。输入变长，HIP 的输入处理优势又让总时间略短。**“先开始说”和“后面说得快”确实是两件事。**

这里的“首内容等待”从客户端发请求前计时，到 SSE 流中第一段非空 `content` 到达；总时间计到流读取结束。首内容等待包含输入处理、首个输出及接口开销，**不是纯 prefill 时间**，也不包含服务启动和模型加载。

每个后端、每种长度先暖一次，再测三次。关闭前缀复用：`cache_prompt=false`、`cache-ram=0`；实际响应逐项核对 `cache_n=0`，输入处理完整 512/2048 token，输出均为 128 token。请求走原始 `/completion`，使用同一组重复英文文本生成的 token 序列，不套聊天模板；`temperature=0`、`seed=123`、`ignore_eos=true`。因此，128 指原始模型输出 token，不是剔除思考过程后的最终答案长度，本轮也不评价回答质量。

**服务测试先跑 Vulkan，再跑 HIP，没有跨后端交错复测。** 它是接口体验的补充观察，不能用两列总时的细小差距推断底层原因。[服务汇总](hip-vulkan-20261013/server-summary.json) · [HIP 原始响应](hip-vulkan-20261013/server-hip-timings.json) · [Vulkan 原始响应](hip-vulkan-20261013/server-vulkan-timings.json)

## 显存与 CPU 部分也核对了

两后端实际日志均为 **41/41 层 GPU offload**，GPU 模型缓冲为 **8161.75 MiB**。同时仍有正常的 **417.30 MiB CPU 映射输入嵌入缓冲**，所以这里不声称“每一个权重都在显存”，也没有把它藏起来当成全 GPU。

服务器 4K 上下文的 KV 缓冲为 640 MiB。实际短回答前后，Windows 进程专用显存约为 HIP **8.95 GiB**、Vulkan **8.79 GiB**，留有余量。共享显存计数原样保留，不能仅因非零就断言权重发生了换页。

## 这组结果能说明什么

它验证的是：**在我们的 9070 XT、Windows、Qwen3-14B Q4_K_M 和这两套实现上，输入处理与生成阶段的赢家不同。** 把完整回答压成一句“Vulkan 比 ROCm 快很多”，会丢掉这个区别。

它没有证明 Vulkan 或 HIP 天生更快，也不是原文 R9700、Linux、Lemonade 环境的严格复刻。量化格式、模型、驱动、算子实现或负载变化，都可能改变结果。本轮只验证现象，没有采集足以解释差距来源的 GPU profiler 证据。
