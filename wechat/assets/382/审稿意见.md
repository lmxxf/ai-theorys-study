## 一、应优先处理的实质问题

### 1. cuPhoton.xBeam 的“闭源、未公开源码”描述错误

涉及开篇学科表、模块六“原版开源状态”、巡礼之后“剩下两个干脆连源码都还没发”的结论。

官方 [NVIDIA/cuPhoton 仓库](https://github.com/NVIDIA/cuPhoton) 已公开，README 明列 `cuphoton.xbeam`，提供交叉谱、时延相关及射电可见度处理；[LICENSE](https://github.com/NVIDIA/cuPhoton/blob/main/LICENSE) 为 Apache-2.0。应改为“官方已开源；本实验另写同源 FX 原型”，不能继续称没有源码仓库。自写原型的耗时仍成立，但不能据此说成功移植了官方 xBeam 整套实现。

### 2. Daviator 状态过度断言，VASP 需区分专有许可与不提供源码

开篇写“闭源预览，尚未公开”，模块五写“官方完全闭源”“仅预告即将集成”。官方 [Daviator 技术说明](https://developer.nvidia.com/blog/tackling-gpu-bottlenecks-in-plane-wave-dft-with-k-point-batching-and-mixed-precision/) 已说明通过 ALCHEMI VASP 微服务启用的参数。能确认产品入口，不能用“本地没拿到源码”证明全部代码完全闭源、或仍只有预告。建议只写“通过 ALCHEMI VASP 微服务提供；本实验未取得其内核源码，独立实现批处理原型”。

VASP 为收费、专有许可软件这一层没错；但[官方安装文档](https://vasp.at/wiki/Installing_VASP.6.X.X) 明确持证者可下载源码。因此不要让“收费闭源”读成“连持证者也拿不到源码”。

### 3. 封面非键力场仍是旧版成绩，且“八大”与正文“七大＋彩蛋”冲突

`cover382.svg` 模块 2 仍列 GB10 `27.19 ms`、AMD `22.43 ms`，对应原始历史快照；最新默认 v0 同轮记录为 `27.137404 / 20.9478 ms`，应显示 `27.14 / 20.95 ms`。正文与 fig6b 已更新，封面未更新。

封面副标题写“八大科学算子 + 深势…Uni-Mol”，实际正文为七模块，另加 Uni-Mol；若八项已经包含 Uni-Mol，再加一次就重复计数。封面各项顺序也与正文模块 4/5/6/7 的编号不同，读者无法直接对号，应统一。

### 4. 模块 2 的预开方候选成绩只列 AMD，漏掉 GB10 回退事实

正文、总表、金句及 fig6b 的 `6.256 / 19.85 ms` 有真实记录，不是假数字；但属于 **v2 AoS7＋预开方候选**，不能与默认 GB10 v0 拼成同源优化后的比较。

### 5. 全部 CPU 都“在 Cortex-X925 大核编译测得”没有测试证据

正文总表前与表头两处明确指称 X925。记录支持“DGX Spark 主机 CPU 单线程”，但未提供 CPU affinity、`taskset` 或实际运行核心日志。GB10 同时有 X925/A725，不能从主机型号推出每个单线程测试都落在 X925。应改为“GB10 主机 ARM CPU 单线程”；此项是证据缺口，不能断言实际一定跑在小核。

### 6. cuSpa 数组数量与源码范围表述

总表及 fig4b 写“200 万点归属与四个 CSR int32 数组”。实际核对的四个数组是：`assignment[2000000]`、`indptr[50001]`、`indices[780563]`、`data[780563]`。即 **1 个归属数组＋3 个 CSR 数组，共4个**，不是归属之外另有4个CSR数组。

`2,378` 行、`11` 文件、commit `2df9fa78` 均通过，但统计范围仅 **`cpp/src/`**，不是整个仓库。fig4a 的“全库仅 2,378 行”、正文“整个底层代码”宜写清该范围。脚本 `hipify_headers.py` 确为 `1,114` 字节，但不仅替换两个头文件，还替换 `cub::`、CUDA runtime 标识与错误字符串，实际抽取转换5个头文件并使用自建 C++ 入口。“原核函数算法未改”可以；“整个库原封不动搬过来”不成立。

### 7. cuPotential 参考资料 commit 对不上本地审计

文末写 `b2380537`。当前本地 cuPotential HEAD 与 `module3_source_audit.json` 均为 **`fbfc4cb6282cd52d33f7adbbcbaeaa5c19b47d74`**；本地对象库不存在 `b2380537`，在线对应 raw VERSION 请求亦未取得。应改为实际审计 commit，或另附该旧 commit 的可验证来源。

`v0.3.5` 正确：本地 VERSION 与[官方版本头](https://github.com/NVIDIA/cuPotential/blob/main/include/cupo/package_version.h) 均为 0.3.5。外层 OpenMM 插件 Apache-2.0、`libcupo.so` 专有许可基本准确；API headers 亦属专有许可，不应把整个仓库统称 Apache-2.0。证据见本地 `cuPotential/LICENSE`。

### 8. “七战全胜”只有混合粒度的明确限定才成立

cuSpa 全流程 AMD `6.0502 ms` **慢于** GB10 `5.759897 ms`，耗时高约 `5.04%`；只有射线查询 AMD 更快。当前总表已诚实列出两项，末尾金句也写“射线查询”，但封面“七大科学算子全胜”及概括句容易变成七个完整流程全胜。最小修正是明确“六个完整算例＋cuSpa 射线查询阶段”，或“七项所列指标领先”。不能推成 cuSpa 全流程领先。

### 9. 模块六“两阶段均快整整2倍”不精确；CPU 预热次数与图注有差异

同源 v2 FFT 阶段 GB10 `17.435406 ms`、AMD `8.9639 ms`，约 **1.945倍**；X 阶段 `22.205913 / 11.0567 ms` 约 **2.008倍**；F+X 总体约 **2.001倍**。正文宜说“整体约2倍”，不能说两个阶段都整整2倍。

fig10b 底部“5预热7测量”适用于 GPU；CPU 是 **1预热3测量**，见 `module11_optimized_results.json.CPU`。fig13b 同样 GPU 5＋7、CPU 1＋3，不应把统一脚注套给三端。

### 10. 模型与输入的真实范围需保留

- 模块1为合成细胞八边形和转录点，正文“测序仪打出来的”是机制说明，但应加一句“本次输入为合成数据”；不是实际组织切片。
- 模块3实测 **81原子／27个合成中性三原子分子**；正文及图未给出原子数，容易与前一模块128K原子衔接误读。应补81原子。这是完整PME原型，但不是128K原子跑1000步。
- 模块5为周期余弦势生成的384维模型哈密顿量，**没有自洽DFT、没有真实VASP晶体材料输入**。CPU教学Davidson与GPU持久核子空间策略不同；CPU11.655秒不能称“同算法完全同实现”。文中已列NumPy0.906秒是好的；补一句模型输入即可。
- 模块6本实验是**合成光子环与合成天线电压**，不是16座真实望远镜采集；fig10a已明确合成，正文应同口径。CLEAN为共同CPU后处理，`19.81/39.64 ms` **仅FX，不含CLEAN成像**；“恢复图跨卡误差”指分别对两端可见度用同一CPU成像流程所得结果，不是两卡各跑一套GPU CLEAN。
- 模块7的99500随机背景＋500植入域与AUC=1记录真实；**ROC-AUC不是检出率**。该56位点轮廓的M发射来自8733条真实GB1序列；I/D转移为显式先验，并非从含插入删除的湿实验对齐学得。`pm/pi/pd`是每线程滚动数组，源码不能证明“全在寄存器”，可能使用local memory；建议删去寄存器保证。
- Uni-Mol与前七核的原生HIP实现真实，但“在A卡装ROCm PyTorch原本就能跑”没有本项目Windows环境实测支撑；尤其不能由Linux ROCm支持直接推断此Windows组合。建议限定支持的平台，或不作该环境保证。

### 11. 构象 CPU RDKit 66.61秒不是同一计算任务的速度基线

`66.607885 s` 是 fresh ETKDG＋真实显式氢 MMFF94，GPU算例是已有初始坐标上的简化重原子力场200步；GPU计时也不含 `3.533790 s` 的8进程ETKDG准备。当前主要倍数已使用同源CPU `10.561 s`，正确；总表括号“旧RDKit66.61s”应明确“另一流程”，不能推导为本核与MMFF等价替代。

1000条ESOL记录实际991个去重母体，10000构象正确。8320个构象共享内存缓存，1680个使用全局scratch回退；“全部拓扑都常驻共享内存”不成立，正文“分桶”可保留。

### 12. Uni-Mol 显存单位与trace误差范围

`peak_estimated_device_bytes=434831360` 是设备空闲量差估计，约 **414.69 MiB / 434.83 MB**；正文“峰值约415 MB”单位不对，应写“约415 MiB（空闲显存差估计）”。不是严格分配器峰值。

FP64预测最大差 `7.105427e-15`、节点trace最大差 `9.086065e-13`、pair最大差 `7.704948e-13`、50501632元素均匹配。trace的 `9.09e-13` 是**中间张量最大绝对差**，不是相对L2；目前图文这一点基本正确。

### 13. 往期299链接真实，但它的早期结论已在301翻案

299/338/339/381期号、标题主题与链接均与发布索引吻合。索引同时明确299的“三门闭合／进真游戏”在301被翻案。382只把299当作AMD跑DLSS神经网络的早期工程入口尚可；若用其证明当时已经完整接入真实游戏，应改引301或后续验收记录。此处不是URL错。
