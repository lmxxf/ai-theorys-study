# Strata：家用 9070 XT 的实验计划

状态：计划，尚未远程检查机器、安装 Strata 或运行模型。2026-10-12 讨论形成。

用户确认的目标机：48GB 系统内存、RX 9070 XT 16GB 显存。CPU、系统、内存速率、SSD、PCIe 实际链路和驱动版本待现场读取。先完成并通读公众号草稿，再进入远程实验；此文件不代表实验已经执行。

## 1. 要回答的问题

1. 完整专家的 Q2_0 能否在这台机器上稳定运行，系统和显存各实际占多少？
2. 简单聊天、长文检索和代码修改的首 token 等待及生成速度差多少？差异与专家缓存、CPU/GPU 分工、MTP 接受率有什么关系？
3. 同一专家被多个 token 使用时，MTP 是否实际减少了每个有效输出 token 的权重搬运和等待？
4. 提前预测下一层专家，是否能在这台 AMD 机器上减少等待？
5. 单独训练预取预测器是否优于原样借用下一层路由器？预测更准之后，端到端速度是否真的提高？

不把“预测准确率提高”“输出 token/s 提高”和“完成同一任务更快且正确”合并成同一个结论。

## 2. 初始配置与记录

- 模型：Qwen3.8-Flash-Next，ISTA-DASLab 的 Q2_0 完整专家量化版；不换成删半专家的 Coder。
- 当前研究锚点：Niko1221/Strata commit `7695859aa13afb248bdb4d36f9b2e95707db079d`。部署若使用更新版，另记实际 commit、引擎版本、构建参数和包校验值，不沿用旧版本结论。
- 模型文件记录 HF revision、分片名和校验值；MTP 文件单独记。
- 模型两分片约 66.4GB，MTP 另约 6GB。运行时 pack 是否生成、生成多大，按实际日志记录，不把下载体积当成内存占用。
- 先用短上下文、纯文本、单请求、不并发；记录采样设置、KV 精度、专家缓存槽数与字节数、内存驻留模式、MTP 状态、尾部专家省略状态。
- 容量分析中的约 34GB 专家是文档约数。实测统一记录字节和 GiB，向文章转换成 GB 时标清口径。
- 先核实 HIP 构建是否支持专家预测、预测统计和 Foresight 显存预取。环境变量被接受不等于路径实际启用，须有日志或代码分支证据。

## 3. 第一阶段：跑通与速度基线

### 对照配置

| 配置 | 用途 |
|---|---|
| 安装器推荐配置 | 看普通用户实际拿到什么行为、速度和输出 |
| 相同配置，关闭尾部专家省略 | 建立路由选出的专家均参与计算的调度对照基线；仍是 Q2_0 量化，不叫原精度 |
| 上述基线，开／关 MTP | 看投机收益及其资源占用 |
| 上述基线，切换缓存容量 | 看显存容量与实际调用命中率、CPU 开销的关系 |

尾部专家省略开关为 `STRATA_ROUTE_TAIL_SKIP=0`；当前研究快照中的 CUDA 及部分 RDNA4 路径均可能默认启用。每次以实际启动日志为准。后面的预取对照保持这项设置相同，不把少算专家得到的收益算到预测器上。

MTP 对照分两种口径：

- 固定专家缓存容量，尽量分离“多 token 验证”本身的影响。
- 允许关闭 MTP 后把释放显存分给专家缓存，评估实际部署哪种更快。

两种结果分别记录，不混成一组提升百分比。

### 提示集合与冷热状态

先准备每类多个独立样本，固定输入、文件、采样与输出预算。建议先测 4K、16K、32K；确认余量后再扩长。

| 场景 | 内容 | 主要观察 |
|---|---|---|
| 短聊天 | 日常中文问答，使用多个不同话题 | 低成本输出下的缓存与 MTP 行为 |
| 长文检索／关系核对 | 固定文档、可核答案，同时测单点检索与多处信息组合 | 首次读入开销、回答准确性 |
| 代码修改 | 固定仓库片段与改动要求，含可执行检查 | 草稿重用、专家路由与有效任务耗时 |
| 任务切换 | 聊天后转代码、代码后转长文 | 原来的热门专家集合能否继续命中 |

冷热状态分开：新会话首次读入、同一前缀的后续请求、已有专家缓存但换新前缀。程序重启不等于 OS 文件缓存已冷；不为每次小测试清空全机页缓存。确需磁盘冷启动对照时单列，不能混进会话缓存对照。

初轮每格至少 3 次，交错 A/B 顺序，保留全部运行及异常，不只挑最快一轮。输出预算可先统一 256 token，但记录实际输出数、EOS 和有效内容；循环或空话不能凭高 token/s 算作成功。

### 每次保存

- 实际输入／输出 token 数，预填充时间与速度、首 token 延迟、解码时间与速度、完整请求耗时。
- 进程内存峰值、显存峰值、专家缓存字节数与槽数、KV 与临时缓冲区占用。
- GPU 缓存命中、CPU 执行、PCIe 临时传入分别计数；附原始指标定义。
- CPU 专家计算时间、GPU 等待时间、传输字节、MTP 提议数和接受数、每轮实际接收 token 数。
- SSD 实际读取量，以及读取属于词组表还是专家文件。专家都在 RAM 不代表词组表也不读 SSD。
- 原始回答、代码检查／问题答案和明显重复等质量记录。

项目自带 `hit_rate` 的统计口径会受 PCIe 分担影响，不直接当成“所有路由调用中多少已在显存”。能取路由 trace 时，另算以 `(token, layer, expert)` 调用为分母的命中比例，并与按验证窗口去重后的专家数分开。

## 4. 第二阶段：现有专家预测和预取

Strata 的 look-ahead 用当前层的较早表示送入下一层已有路由器，预测下一层专家。它不是另外训练的网络，也不是 MTP 预测 token。

- 文件预读：让预测到、且未在 GPU／RAM 驻留的专家页提前进入文件缓存；48GB Q2_0 常规模式可能没有多少专家文件读取可省，先看实际 I/O。
- Foresight 显存槽：给刚未命中及预测专家准备临时显存位置。它会挤占长期热门缓存，官方多机实验曾出现负收益。
- 先确认 `STRATA_LOOKAHEAD_STATS`、`STRATA_FS_SLOTS` 等在目标 HIP 版本的实现范围。若不支持，先离线评估预测质量，再决定是否移植，不把 CUDA 开关当成 AMD 已实现功能。

若可运行，对照“不开预取”“只预取刚未命中专家”“加入下一层预测”，保持总显存预算、其他开关和提示相同。记录预测耗时、预取到达时机、白搬字节、被预取槽挤掉的缓存量及最终耗时。测量型 profiling 开关可能增加开销，预测质量采集与正式速度测试分开。

## 5. 第三阶段：训练独立的预取预测器（猜想实验）

前提：已经找到足够大的等待瓶颈，且预取通路能在 AMD 上执行。原模型和真实路由器全部冻结，保持真正选择专家的逻辑不变。

最小方案：复制下一层路由器，副本接收当前层可提前获得的表示，预测下一层真正的 top-10 专家。先核对实际 hook 位置、归一化和残差合并方式，确保训练和部署看到的是同一种输入。

1. 正常推理收集“提前可用的表示 → 下一层真实路由分数／专家 ID”。先采少量层、抽样 token，限制文件体积，不一次保存所有层全部激活。
2. 训练副本，可比较匹配真实路由分布与直接学习 top-k 标签。先追求便宜可用，不增设庞大网络。
3. 按整份提示／文档／任务划分训练与测试，不能将同一段上下文相邻 token 分散到两边。
4. 比较未训练路由副本与训练后副本，在不同候选数、预取字节预算下，对真正未缓存专家的覆盖率、误取量、按路由权重加权的覆盖率。
5. 接入预取后测端到端。预测计算和复制队列要能与当前层计算重叠；提前猜中但到得太晚，也没有收益。

预测器只给调度建议，实际模型仍执行真实路由。预测失败不授权删掉真正选中的专家。CPU/GPU 执行位置变化可能改变浮点舍入，不能仅凭设计宣称逐位一致；保存输出差异，必要时做固定序列的概率对照及任务正确性检查。

## 6. 停止与升级条件

- 若基线内存压力造成换页或重复输出，先把稳定性定位清楚，不在异常基线上计提速。
- 若等待主要在别处，或预取挤占缓存造成净退化，记录负结果；不因猜想好听而继续堆复杂机制。
- 只有在固定任务集、包含不同任务类型的重复对照中，同时看到有效时间下降和质量保持，才把结果写成该配置下的收益。

源材料见同目录 `机制核查.md`、`性能与门槛核查.md`；专家预测说明见固定提交的 `docs/DETAILS.md` 中 RAM budget、lookahead stats、Foresight swap space 三处。
