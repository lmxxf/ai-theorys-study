## 二、发布前必须处理的事实与逻辑问题

### P1-1：138 不仅数错，还被误推广成各家推理模型的固定协议

位置：正文 **46–49、95、197、301–302 行**；封面 45 行；`three-tier-agent-api-model.svg` 的“保住 138B 思考签名”。

问题有三层：

1. 现场字段是 125 bytes，见上表。
2. 这是一次工具调用的 opaque 字节串长度，不是 Gemini 协议常数，更不是 Claude/OpenAI 共用的常数。
3. `thinking_signature`、API `thoughtSignature`、Anthropic thinking block 的 signature、OpenAI reasoning 项不是同一套跨厂商字段。是否强制回传、由客户端还是服务端管理、丢失后的行为，要看模型/API/交互阶段。

Google 文档把 thought signature 解释为用于保持思考上下文的加密表示；本轮证据没有证明这 125 bytes 的主要目的就是正文注释所说的“验真、防客户端篡改思考记录”。Anthropic 对真实性验签有自己的说明，不能嫁接成 Gemini 本地字段的已证实用途。当前 Google Interactions API 还可由服务端自动管理签名，直接反驳“所有壳子都必须手动回传固定字节串”的总括。

建议：实盘示例写“首个调用附有 125 字节不透明签名”；机制段写“部分模型/API 要求保留并正确回传相应思考状态或签名”。删除固定长度和“丢掉就一律当场断链”的普遍断言。

来源：[Google thought signatures](https://aistudio.google.com/docs/thought-signatures)、[Firebase 对 thought signatures 的说明](https://firebase.google.com/docs/ai-logic/thinking)、[Anthropic context windows / thinking tool use](https://platform.claude.com/docs/en/build-with-claude/context-windows)。

### P1-2：第一章的“第三眼”是重建示意，不能包装成拿到了闭源推理输入

位置：正文 **18、28、57–61、117–153 行**；`three-layer-pipeline.svg` 下半部；速查表 302 行。

已验证的是客户端 XML、请求类型、HTTP JSON/SSE 构建链、部分实际历史状态。**没有截获首轮 HTTP body，没有 Google 后端 renderer/tokenizer 代码，也没有最终 token IDs。** 因此这些说法超出了证据：

- `thinkingConfig → EFFORT LEVEL: 0.05` 的具体映射；
- 努力指令、工具声明、XML 必然按所画顺序全部塞进同一个 system 车头；
- 工具边界恰为示例所列控制词元；
- 最终前缀必然停在未闭合 `<|thought|>`，历史思考原文恰为 `OK.`。

模型内部口述可作为线索，但不是独立协议取证；搜不到字面串也不能单独证明后端精确实现。括号里只注明“控制边界用 `<|...|>` 示意”不够，因为正文仍把**整个排序、映射和末尾开口**当作已证事实。

建议保留三层图，但把整段标为“根据结构化字段解释的概念示意，闭源模型 token 边界及顺序未直接观测”；JSON 也标为“按协议字段重建、内容节选”，不要称“这包跨网卡 JSON”的实际抓包。`includeThoughts:true`、`models/gemini-4-carbon`、示例 response 包装键也都不是本次截获值。

### P1-3：各大模型“基本告别 JSON”的总规律及统一母语样例不成立

位置：正文 **184、201–217 行**；`three-tier-agent-api-model.svg` 底层三栏。

**特殊 token / 消息边界，与参数正文是否使用 JSON，是两个独立问题。** 外层有专用定界 token，里面仍然可以是 JSON。OpenAI 官方 Harmony 文档就展示了：带 recipient/channel 的消息头 + JSON 函数参数正文。文中把 Gemini/DeepSeek/OpenAI 合写成一套 `default_api`、`<|tool_call|>`、`<|str|>` 语法，没有这些模型逐一对应的公开依据。

Qwen 3.5/3.8 的 `<function=…><parameter=…>` 示例能在官方模板中找到，可以保留并限定具体版本；其模板对 mapping/list 参数仍会使用 `tojson`，所以也不是“参数一概不用 JSON”。Claude 的 `<antml:invoke>` 若没有本轮可追溯的版本化原始记录，只能注明历史/示意来源，不能称所有当前闭源 Claude 统一母语。

“彻底杜绝与代码里的 `</xml>` 撞车”也过满：普通文本 XML 风格分隔符本来就可能与代码/数据撞名；单个 special token 与可见字面拼写的区别，还取决于编码器是否允许普通输入触发 special token。不能靠画一对括号证明彻底免疫。

建议把灯泡改为“消息控制边界和参数格式可以分开设计”，用**有公开模板的 Qwen 和 Harmony**做对照；删除闭源三家的统一伪语法与“基本不用裸 JSON”的总括。

来源：[OpenAI Harmony 格式，含 JSON 函数参数例](https://raw.githubusercontent.com/openai/harmony/main/docs/format.md)、[Qwen3.5 官方模板](https://huggingface.co/Qwen/Qwen3.5-35B-A3B-GPTQ-Int4/blob/3af5ca2972faf6de1fd6f4efc4d8d319ca751e8b/chat_template.jinja)、[Qwen3.8-27B 官方模板](https://huggingface.co/Qwen/Qwen3.8-27B/blob/main/chat_template.jinja)。

### P1-4：15% 有出处，但现在的因果解释、适用范围和迁移动机写错了

位置：正文 **193–197 行**；`three-tier-agent-api-model.svg` 的“费注意力 + 丢签名”“省 15% 词元+真并发”；速查表 302 行。

- 这是**Cline 该次实现迁移的产品观测**，不是“模型看外语标签平白消耗 15% 注意力”的测量，也不是 Roo/Aider/所有模型通用比例。

- 公告明确说，不支持 native 的模型仍走文本路径。因此“全都废弃标签”不成立。

建议：收窄为两个具体版本迁移案例，15% 明确归 Cline；“原生接口更便于可靠解析、并行和保存模型特有状态”可作工程分析，别写成已证明的集体历史原因。顺便将 Aider 标记拼写修正为其文档的 `<<<<<<< SEARCH`，或干脆不在此处混用编辑格式。

来源：[Cline v3.35 公告](https://cline.bot/blog/cline-v3-35)、[Roo v3.36.0 公告](https://roocodeinc.github.io/Roo-Code/update-notes/v3.36.0/)、[Aider edit formats](https://aider.chat/docs/more/edit-formats.html)。

## 三、机制描述中还应收窄的几处

1. **TTFT ≠ 预填充算了 16.3 秒（11 行）。** TTFT 可含排队、网络、请求处理、prefill 和首 token 生成。建议直接写“首字返回耗时 16.3 秒”。同理 usage 是服务返回统计，不是 GPU 事件计时；“真实计费”还需对应计费规则/账单，而不只是 token 字段。
2. **“此时尚未拼”“每次现读 AGENTS.md”不能由未持久化字段推出（32–40、59 行）。** DB 是持久化状态，不是程序执行阶段的录像；内存里可以已经构建/缓存 prompt。昨夜完整快照还说明 gen_metadata 可以曾保存完整 system_prompt/tools，不能断言整个本地库永远只有散装开关。应写“本例 steps 不把 system prompt 作为第 0 步保存；配置/规则另行参与构建”。`executor_metadata.planner_model/tools/prompt_sections` 也只是压缩伪字段路径，真实嵌套是 cascade_config → planner_config → declarative_mixin_config 等；`response_text` 实际字段为 `response`。标“字段节选/结构简化”即可，别让读者按伪路径查库。
3. **SSE 是响应流，不是上传 JSON 的传输编码（59 行）。** 正确关系是 HTTP POST JSON 请求、SSE 响应；“通过 SSE 发给服务器”易读错。
4. **“四个平级字段”图画错层级。** `three-layer-pipeline.svg` 把 thinkingConfig、tools、systemInstruction、contents 并排；正文自己的 JSON 却正确显示 `thinkingConfig` 属于 `generationConfig`。若要四个同级抽屉，应画 `generationConfig / tools / systemInstruction / contents`，再在 generationConfig 内标 thinkingConfig。
5. **user/model 严格交替不是可由这些字段推出的普遍协议铁律（115、253 行及动态图）。** 本例工具响应可经 user 承载；merge 也是“符合条件时并入前工具结果”，不是每条通知都必定合并或用于强制交替。`disable_system_message_merging=0`、`append_ephemeral_to_previous_tool_result=1` 支持“允许/启用该策略”，不支持“任何插入都不影响旧前缀”。不要把示例序列说成所有 Gemini/API/智能体的强约束。
6. **缓存失效不总是全部 4.4 万，也不只有 compact 一种原因（233、267、305、320 行及动态图）。** 前缀缓存通常能保留修改点以前的共同前缀；修改系统尾部不等于开头一字也不能复用。模型切换、工具/section 变化、历史裁剪或编辑、merge 改写已有工具结果等都可能影响缓存。建议用“常见提醒尽量靠近最新内容添加，减少稳定前缀变化”；删除“统统”“绝不”“唯一”。把四类明确为本文归纳，别说 serializer 源码本身就硬分四类。
7. **工具本地执行、API 中转直触模型也不是绝对（182–191 行）。** 本例 read_file/run_command 在客户端运行成立；其他工具可在远程 MCP、服务器托管执行，模型也可本地部署。普通第三方反代通常只是 API JSON↔另一种 API JSON，不会接触隐藏 token 流；真正 renderer/parser 往往仍在模型服务端。`functionCall` 是 Gemini 字段，不是 Claude Code/Codex 原生接口的通用返回对象名。三层图应区分“模型服务网关”和“普通 API 反代”。
8. **装饰器读数有，但描述过度机械（257–259 行）。** 本次 step 8 实际是带 Command output 的 run_command 输出裁剪，不是直接证明源笔记文件恰好 27,982 bytes；两组 Created/Completed At 还出现在返回内容中，并非永远只套两行。写“工具结果 27,982 字节”最稳。Created→Completed 是工具生命周期用时，也不必等于命令纯执行耗时。
9. **注册了不等于本会话启用/触发（265 行）。** `request_artifact_feedback_stop` 在注册面存在，但不在本会话显式 stop_hooks 三项中；不能作为“当前启用清单”的第三例。可以注明“其他模式还注册了产物反馈停手钩子”。同理 goal_stop 已配置不代表本会话已经开启 goal。
10. **compact 的内容和条件不是无条件全装（267 行）。** 最近用户请求最多 10 条，本配置还有 `max_user_request_bytes=1024`；不应说必然完整保留“最近 10 条原始请求”。artifacts、subagents、代码记录、日志指针依数据/选项，`include_conversation_log=0` 也需留意。可写“摘要与按配置附带的近期请求/恢复线索”，不要把旧报告模板所有可选项合成每次必有的一份。
