◆ 开篇：四十多页强化学习，和一个先入为主的猜测

━━━━━━━━━━━━━━━━━━━━

322 期 https://mp.weixin.qq.com/s/HpX5uMf7UmYk12WthUcOrg 读小米 MiMo-V2.6 的骨架，结论是主干九个月没换，零件多是两三年前的。结尾留了一个问题：骨架没什么可讲，那分数是从哪来的？V2.6 技术报告 44 页，讲架构和预训练的只有几页，主体都在讲强化学习（reinforcement learning，RL）和配套的训练系统。报告标题也直接写着 “Scaling Reinforcement Learning”。

所以我读之前的猜测很直接：**分数主要是 RL 练出来的，小米的 RL 做得比别人好，至少不差。**

读完发现这个猜测只对了一半。报告里摆出了一组往期没见过这么完整的数字：同一个模型在 RL 开始前、RL 结束后各有一个分数，再加上上一代的最终成绩。按这组数字看，**这一轮 RL 让 DeepSWE 涨了 14 分左右；而新一代在进入 RL 之前，就已经比上一代的最终版高出将近 40 分。** 高分不只是最后这一轮 RL 的故事。

另一半对的，也不是“某个 RL 技巧特别厉害”。RL 那一段真正下功夫的地方，是怎么出题、怎么判卷、怎么防学生抄答案、学生钻了空子怎么纠正。读完整份报告，它更像一本老师的教学笔记。

还有一件事是翻往期时才发现的：285 期 https://mp.weixin.qq.com/s/U4bZ0DNC_ktW5qpiUWv96Q 讲“外部 235B 强老师把学生教崩了”，那篇 MOPD（多老师在线蒸馏，Multi-Teacher On-Policy Distillation）论文就是北大和小米合写的；286 期 https://mp.weixin.qq.com/s/yIZfZVSi-m_r_ynTi9Qs3g 引的“在线蒸馏 0.937 对混合 RL 0.882”（归一化成绩）也出自那篇。模型我没跟过，这家的后训练论文倒是已经读过两期了。

◆ 第一章：一个分数，分四段看

━━━━━━━━━━━━━━━━━━━━

先交代一下尺子。标题里的“开源第一”说的是 AA 智能指数，那是一堆评测的综合分；报告里能分阶段看的只有 DeepSWE v1.1（让模型在真实代码仓库里修 bug、做功能的一套题）这一项。它解释不了 AA 第一具体是哪一步带来的，但能看出分数大致是怎么长上去的。拿这一项，把大份 Pro 从上一代到最终发布的分数排成一行：

| 阶段 | DeepSWE v1.1 | 来源 |
|---|---|---|
| 上一代 V2.5-Pro（2026 年 4 月开源） | 19.0 | 报告末尾的总成绩对比 |
| V2.6-Pro，RL 开始前 | **58.4** | 下图曲线起点 |
| V2.6-Pro，RL 30 步之后 | 72.6 | 下图曲线终点 |
| V2.6-Pro 最终发布版 | 71.9 | 报告末尾的总成绩对比 |

先说清楚这四行是什么关系：**第一行和后三行不是同一个模型。** 19.0 是上一代 V2.5-Pro 的最终发布版，它当年也做过一整套后训练，RL 也在里面；后三行是 V2.6-Pro 这一次训练过程中的三个检查点。

V2.6-Pro 在 RL 开始之前走了三步：预训练（报告写的是 27T 文本加 3T 全模态），一整段新的 mid-training（中段训练），再加一段很短的 SFT（监督微调，supervised fine-tuning）。这三步走完、还没碰 RL，DeepSWE 已经是 58.4，**比上一代做完全部后训练的最终版高出将近 40 分。** 接着 RL 30 步，从 58.4 涨到 72.6。RL 之后还有一段多老师蒸馏（第六章讲），报告另列最终版为 71.9。

这四个数是**两组观察**，别当成一条贡献分解。58.4 到 72.6 是同一个模型、同一套评测在 RL 前后比出来的，这 14 分可以记在这一轮 RL 头上。19.0 和 58.4 比的却是两代模型，中间隔着预训练、mid-training、SFT 三步，报告没做逐阶段的对照实验，两个数的评测条件（用哪个 agent 壳、每题给多少预算）也没逐项写明。所以这 40 分只能说明新一代的 RL 起点已经很高，分不出哪一步贡献了多少。

这 40 分也不是换架构换来的。322 期逐字段对过两代的 config：70 层（60 层滑窗、10 层全局）、隐藏维 6144、384 个专家挑 8 个、滑窗 128、层的排布，全都一样。V2.6-Pro 多出来的是：挂上了视觉塔和音频编码器（V2.5-Pro 是纯文本模型）；专家权重改用 4 比特的 MXFP4 格式，mid-training 里还专门做了量化感知训练，让模型适应低精度计算。DeepSWE 是纯文本的代码任务，不走视觉和音频的输入路径；但全模态预训练会一起更新语言主干，低精度适配也会改变数值计算，所以不能说这些变化跟成绩无关。**能确定的是：主干骨架没换，差别出在训练上。**

报告只给了三步的做法，没说 V2.6 的预训练是不是接着 V2.5-Pro 的底座往下训。能确定的只有一件事：**同样的骨架，新一代在 RL 开始之前，就已经把上一代的最终版甩开了一大截。**

小份 Flash 是同样的形状：RL 前 48.7，RL 后 65.7，最终 67.9。

中间两行是下面这张图左边深色曲线的起点和终点，首尾两行来自报告末尾的总成绩对比。图的左边是 RL 过程中 DeepSWE 分数随累计花费的变化，深色是 Pro，浅色是 Flash；右边两个饼图是花费的构成，第三章再讲：

![MiMo-V2.6 技术报告图 3：左为 RL 过程中 DeepSWE v1.1 的 avg@3 分数随累计花费（百万美元）上升，Pro 从约 58 涨到 72.57，Flash 从约 49 涨到 65.68；右为 Pro 与 Flash 的 RL 花费构成饼图（训练、rollout、判分）](assets/323/fig3-rl-cost.png)

跑分里常见两个口径词，先说清楚：**avg@3** 和 **pass@1**。

**pass@1** 问的是：让模型做一次，做对的概率是多少。**avg@3** 是估这个概率的一种做法：同一道题独立跑三次，每次过了记 1、没过记 0，三次取平均，再对所有题取平均。比如某题三次里过了两次，这题就记 0.67。两个名字估的是同一个量，“做一次能做对”的概率；avg@3 多跑了两遍，数字更稳，因为 agent 任务一次跑下来运气成分很大。

容易混的是另一个词 **pass@3**：跑三次，只要有一次过就算这题过了。它量的是“给三次机会能不能蒙对一次”，数值会明显高于 pass@1。317 期那个 `1−(1−p)^k` 算的就是这一类。

上面那张图的纵轴就是 avg@3。19.0 和 58.4 差将近 40 分，远超跑几遍的随机波动；但前面说了，它们的其他评测条件不一定一致，所以只当量级看。

💡 报告自己的 9B 实验，结论更直白

报告第 7 节还做了一组小实验：拿 Qwen3.5-9B 当底座，先用小米的数据做 SFT（总共 774 亿 token，其中计入损失的 272 亿），再用他们开源的环境做 RL。RL 这一列是在同一个 SFT 起点上，**各领域分别跑 GRPO** 得到的检查点，不是旗舰那种一次混合 RL。每一项都给了三个分数：

| 基准（口径） | 原始 Qwen3.5-9B | SFT 后 | RL 后 |
|---|---|---|---|
| SWE-bench Pro（avg@3） | 32.0 | 44.6 | 47.6 |
| MiMo Code Bench mini（avg@3） | 19.5 | 51.6 | 59.9 |
| MiMo General Bench mini（avg@1） | 28.5 | 62.2 | 70.6 |
| Terminal Bench 2.1（avg@1） | 27.0 | 37.1 | 52.8 |

这里列的四项里，前三项 **SFT 涨得比 RL 多**，Terminal Bench 2.1 反过来。完整表一共 11 项，8 项是 SFT 涨得多，另外 3 项（SWE-bench Verified、Terminal Bench 2.1、视觉编程）是 RL 涨得多。报告的原话是：“highlight the value of high-quality training data and a strong SFT initialization”（说明高质量训练数据和一个好的 SFT 起点很重要）。

282 期 https://mp.weixin.qq.com/s/4aDzx6lxkVxTUSj8NnCSYA 整理过一批“骨架没动、分数翻番”的模型：GLM-5.3 说 “every gain comes from post-training”，DeepSWE 从 46.2 涨到 66.9；DeepSeek V4-Flash 从 preview 到 0731 正式版，DeepSWE 从 7.3 涨到 54.4。那时候我们把这些统称为“只做了后训练”，没法再往里分，因为几家都只给了首尾两个数。

小米这份报告把“后训练”又分出了一层：RL 前后各给了一个分数。**同样一大截涨幅，看得出不只是最后这一轮 RL 的故事。** 9B 那组实验是另一个方向的旁证：好的 SFT 起点很值钱。

◆ 第二章：为什么先看 RL 的起点

━━━━━━━━━━━━━━━━━━━━

317 期 https://mp.weixin.qq.com/s/0oeJOVVI45mHRkc3VTos2w 讲过一个公式。带 KL 约束（KL 散度，Kullback–Leibler divergence，衡量新模型偏离原模型多远）的强化学习，训到最后逼近的目标分布是：

```
π*(x) = (1/Z) · π₀(x) · exp(r(x)/β)
# π₀：RL 开始前的模型（先验）
# r：奖励
# β：约束强度
# Z：把所有概率加起来归一到 1 的系数
```

π₀ 是训练前的模型给每个回答 x 的概率，奖励只能在它上面乘一个倍数。那期的结论是：公式本身能把 1% 推到 99%，难的是采样采不到——一条基座几乎不走的路，一万次采样里一次都没出现，奖励再高也作用不到它身上。

这个公式不是小米这一轮的损失函数（小米的目标里没有 KL 项，第五章讲），也不是说 RL 有一道永远越不过去的上限：没采到的答案，也可能因为参数共享、别的轨迹的更新而被带动。但它提醒我先看训练起点：**好的解题轨迹越容易被采到，有限预算里的 RL 就越容易得到有效反馈。**

小米报告给 mid-training 写的目标，几乎就是这句话换了个说法：

> We further introduce an agent-centric mid-training phase that **expands the exploration space for agentic tasks**, enabling the model to discover more effective task-solving trajectories during post-training.

我们引入了以 agent 为中心的 mid-training，**扩大 agent 任务的探索空间**，让模型在后训练时能找到更有效的解题轨迹。

具体做法是：数据混入跨代码、通用、视觉、研究四类的真实 agent 轨迹，加上高质量文本、仓库级代码和图像视频音频；先在 256K 上下文训大部分算力，最后一段扩到 1M。

放回 317 的公式看，**mid-training 做的就是提高好轨迹一开始被采到的概率。** 打个比方（不是小米的实测）：原来一百次才采到一次的解题路线，现在十次就能采到一次，RL 才有更多东西可以放大。282 期讲过长任务的成功率大致是每步成功率 p 的 n 次方，p 从 0.95 提到 0.97，一百步的任务成功率涨八倍。mid-training 把 p 往上抬一点，长任务上的采样机会就成倍增加，这些分数在 RL 开始前就已经体现出来了。

mid-training 里还混了一类特别的样本，第四章讲作弊时再说。

💡 30 步是多大的量

报告第 5 节的标题叫 “You Only RL Once”：混合 RL 只跑一次，Pro 和 Flash 各跑 30 步。

30 步听着很少，但每一步都很大：1568 道题，每题采 16 条，一步就是约 2.5 万条轨迹，平均每条 11 万到 15 万 token，一步合计 27 亿到 37 亿 token。30 步乘下来，RL 处理的 token 在一千亿上下（按报告的每步数字乘出来的，报告没给总数）。Pro 这 30 步跑了 123 小时，花了 260 万美元，Flash 花了 90 万美元。

这 260 万美元是 RL 这一段的费用，不是整台模型的研发成本。报告原文是 “spending \$2.6M ... on RL post-training”，预训练和 mid-training 都不在里面。

◆ 第三章：RL 那 14 分，钱花在判分器上

━━━━━━━━━━━━━━━━━━━━

RL 部分报告说是从三个方向加钱：批量更大、环境更多样、判分器算力更多。Pro 的 RL 花费分成三块：

| 用途 | 占比 |
|---|---|
| rollout（让模型做题） | 43.8% |
| 训练（更新权重） | 43.5% |
| **判分** | **12.7%** |

就是第一章那张图右边上面那个饼图。Flash 的判分占比更高，14.2%。判分单独花掉一成多。往期写过的几家都没有把判分列成一项单独的开销，这也是小米这份报告里往期没见过的一块。

**二值测试分不出好坏**

代码类 RL 最常用的奖励是跑单元测试，过了 1 分，没过 0 分。282 期讲 GLM 的判分器也是输出二值奖励，只是事先做了三道检查（有参考解能过、什么都不做过不了、原始状态过不了），先排除几类明显的判分错误。

问题在于：**一组里通过测试的解，全都是 1 分。** 一个改了三行、干净利落；另一个加了一堆兼容分支、吞掉了异常、顺手放宽了校验，测试也过了，同样 1 分。模型分不出哪个更好，RL 放大的就是“能过测试”，不是“写得好”。

小米用了两个办法补这个缺口，一个离线、一个在线。这里的离线和在线，说的是**评分标准什么时候定**：离线是 RL 开始前就给每道题写好一张评分表，训练时拿着同一张表逐条打分；在线是不写表，训练每走一步，就拿模型刚交上来的那一组答案当场比。两种都要在训练中派判分 agent 去看答案，区别只在标准是事先定好的，还是每一步现定的。

**离线的：先比一组，写出这道题的评分表**

叫 GRS（Groupwise Reward Synthesis，组内奖励合成），用在一部分通过率高的题上。先离线拿一组答案做对比，让一个 agent 为这道题写一份专属的评分表，分两块：解法本身好不好、做题过程好不好（有没有先读代码、有没有自己验证）。训练时，每条答案的奖励是三个数相乘：

```
R = R_test × S_sol × S_beh
# R_test：测试过没过，0 或 1
# S_sol：解法分
# S_beh：过程分
```

用乘法是有意的：**没过测试，后面两项再高也是 0。** 评分表只在过了测试的答案之间拉开差距。

为什么用在通过率高的题上？261 期 https://mp.weixin.qq.com/s/nLFv6m-ONkXd7frHevgPOQ 讲过，GRPO（组相对策略优化，Group Relative Policy Optimization）里每条答案往上推还是往下压，看的是它的**优势**（advantage）：奖励减去组内平均。题目简单时常碰到一组 16 条全过，每条都是 1 分，个个等于平均，优势全是 0，这一组等于白采（报告里还专门有个过滤器把这种组扔掉）。乘上解法分和过程分之后，全过的组里分数也有了高低，这组就又能用上了。

**在线的：一组有过有不过，现场比，把分从差的挪给好的**

剩下的代码题用 GAR（Groupwise Advantage Redistribution，组内优势重分配），处理的是一组里有过有不过的情况。它不用事先写评分表：每一步训练时，判分 agent 把整组答案放进同一个工作区，看代码、跑定向测试，拿过了的和没过的对照着看，再把通过的那几条按五个方面排序：

1. 解法选得合不合适
2. 实现得精不精确，没有遗漏也没有多余的兜底
3. 改动是不是最小
4. 有没有影响任务范围之外的东西
5. 风格符不符合这个代码库的惯例

排完序不改奖励，改优势。先看一个没碰到放大上限的例子：一组 4 条、两过两不过，按小米这里的算法，原始优势是 +0.5、+0.5、−0.5、−0.5，两条过了的被同样用力地往上推。GAR 只动通过的那两条：

| 答案 | 原始优势（奖励减组内平均） | 加了 GAR |
|---|---|---|
| 过了，写得好 | +0.5 | +0.67 |
| 过了，写得差 | +0.5 | +0.33 |
| 没过（两条） | −0.5 | −0.5 |

通过的那几条，往上推的总力气还是 1.0，只是从写得差的挪给写得好的。实际训练还给放大倍数设了上限，最后再把整组优势重新调到均值为零；碰到上限时，没过的那几条也会跟着变，所以“总量不变”是没碰上限时的情况。如果直接在奖励上加分，组内平均跟着变，没过的那几条被压的力度也会变。报告说守住总量是为了让正负两边保持平衡，防止熵失控上涨（第五章讲）。

GAR 还兼一份差事：判分时如果确认某条答案是抄了外部现成的修复，直接把它的奖励清零、当成没过，再重新算这一组。第四章讲作弊时会回到这一点。

两个办法放在一起看，分工是这样的：

| | GRS（离线） | GAR（在线） |
|---|---|---|
| 用在哪类题 | 一部分通过率高的题，全过的组也能分出好坏 | 其余代码题里有过有不过的组 |
| 评分标准 | 事先写好这道题的评分表，反复用 | 不写评分表，每一步现场比 |
| 打什么分 | 解法分 × 过程分，乘进奖励 | 只排代码质量，挪优势，奖励不动 |
| 训练时是否整组比较 | 否，逐条对照事先写好的评分表 | 是，过的和没过的对照着看，给通过的排序 |
| 抓作弊 | 没提 | 确认抄答案的清零 |

**通过率高的题，GRS 连全过的组也能分出好坏；其余代码题碰到有过有不过的组，GAR 现场排序，顺手抓作弊。**

💡 不加 GAR，模型学会了什么

报告拿 Flash 做了一组对照：只训代码，其他条件一样，一组加 GAR，一组不加。

![MiMo-V2.6 技术报告图 8：Flash 只训代码时，不加 GAR（灰色虚线）与加 GAR（橙色实线）的对比。(a) 通过率 avg@3：不加的在 20 步左右到顶、随后回落到约 50%，加了的一路涨到 60% 以上；(b) 平均轮数：不加的从约 115 涨到 130 以上，加了的维持在 110 上下；(c) 平均 token 长度：两者都涨，不加的涨得更快](assets/323/fig8-gar.png)

不加的那组（灰色虚线），对话轮数和 token 数一路疯涨，越来越多轨迹撞上长度上限，通过率涨不上去；从图上看，它在 20 步前后到顶，随后回落到 50% 左右，曲线停在 28 步前后。加了的那组（橙色）一直训到第 52 步，通过率虽有起伏，总体维持在更高水平，轮数基本平稳。

更有意思的是报告里另外做的一次代码审查。不加 GAR、只盯着通过率训出来的模型，越来越多地用这些写法：

> speculative compatibility branches, broad exports, exception swallowing, relaxed validation, and evaluation-specific configuration changes

投机性的兼容分支、大范围导出、吞掉异常、放宽校验、专门针对评测改配置。

**这些写法都奔着提高过测试的概率去，却可能把代码越写越糟。** 除了去网上找现成补丁（第四章讲），奖励还会诱导这种应付测试的写法。311 期 https://mp.weixin.qq.com/s/q_7f3UhFu-sjHtFXlONB0g 讲过，判分器可以比被判的模型小，但这不等于判分容易。这组对照是个具体例子：判分器只看测试，模型就往“刚好能过测试”的方向长。

────────────────────

往期的几家也不是只有二值测试。283 期 https://mp.weixin.qq.com/s/qBGsQ75RQYExZW1Vj0BhIg 讲 Kimi K3 的 kernel 任务：先过数值正确性，追平专家实现得 0.5 分，逼近理论上限（roofline）趋近 1 分，这是给“写得快”打分。284 期 https://mp.weixin.qq.com/s/zHnVU5JG6ADr4WWyJrWwJw 讲 K3 的开放任务：agent 裁判现场生成评分表，两两比较。**但在往期写过的几家里，给“过了测试的代码写得干不干净”打分的，小米是第一家。**

代码题的组内判分器是 SFT 训出来的 agent；通用 agent 任务的判分器，报告明确点名用的是自家的 V2.6-SFT，也就是还没做 RL 的那个版本。

报告里也有一处前后不太一致：摘要说判分让模型走向“更短、更省 token 的解法”，第 5 节的训练曲线又写 “these gains generally accompany increasing total token counts”，分数涨的同时 token 数也在涨。按上面那组对照，前者更像是跟不加 GAR 的版本比，后者是跟 RL 开始时比，报告没把两句放在一起解释，第一次读容易读岔。

◆ 第四章：模型怎么偷答案

━━━━━━━━━━━━━━━━━━━━

吞异常、放宽校验，是写得不好。报告里还有另一类：**直接去找现成答案。**

修 bug 的训练题一般是从 GitHub 上的历史 PR 造的：把仓库退回到修复之前那个提交，让模型修。但这个 bug 在现实里早就被修好了，答案就在网上。报告里列了五个真实案例，思考过程是原话引用：

| 手法 | 模型当时的想法（原文） | 动作 |
|---|---|---|
| 装新版看源码 | “Let me check the pytest changelog or GitHub to see if there's a more recent fix.” | `pip install pytest==5.4.3`，读装好的源码 |
| 直接下载文件 | “Let me just look at the file directly from the GitHub raw URL.” | `curl` 上游的 core.py |
| 克隆最新仓库 | “Let me directly fetch and inspect the relevant files from the latest matplotlib.” | `git clone` 最新版 |
| 翻当年的讨论 | “Let me get more info - changesets and the fix that was applied.” | 读 Django 工单 #29205 的修改记录 |
| 先探版本 | “Let me look for the fix. The issue is likely fixed in later versions.” | `pip index versions sphinx` |

模型没有撒谎，想法里写得明明白白：去找更新的修复。从做题的角度看这很合理，人类工程师遇到 bug 也会先搜一下有没有人修过。问题是训练题要考的是“从 bug 报告出发自己修”，抄来的补丁过了测试，RL 就会奖励“去网上找答案”这个习惯。

小米的对策分四层：

1. **环境清理**：删掉构建日志、验证输出、残留补丁、编译产物，清缓存（包括仓库之外的），Git 历史只留到基准提交为止，容器级断网。
2. **hack agent**：专门派一个 agent 去攻击清理好的环境，找还能偷到答案的路。报告说它找到了很多“训练中没见过、现有清理步骤也没覆盖”的漏洞。修完再跑，**一直循环到它在所有环境里都找不到可用的漏洞为止。**
3. **训练中审计**：定期离线检查轨迹，发现新手法就回头修环境；同时第三章那个 GAR 判分器在线把关，确认作弊的，奖励直接置 0，再重新算组内统计。整个训练过程中确认作弊的比例都低于 2%。
4. **在 mid-training 里种一类样本**：早期实验发现模型有作弊倾向，就拿这些案例合成训练样本——模型先犯错，然后反思哪里错了，改正那一轮，接着按任务要求正常做下去。报告特意说“改写后的推理里原来的错误仍然认得出来，改正是明着写的”。

![MiMo-V2.6 技术报告图 6：(a) 防作弊流程，训练前做环境清理（清产物、缓存、Git 历史，断网），再由 hack agent 找攻击路径，找到就回头修环境，直到找不到；训练中离线审计轨迹，发现新手法同样回头修环境。(b) 上：四个代码数据集在每一轮清理后仍能被攻破的环境比例，第一轮都在九成以上；下：最终 RL 过程中检测到的作弊轨迹比例，Flash 和 Pro 都在 0.5% 到 2% 之间](assets/323/fig6-hack.png)

上图右上那张值得多看一眼：**第一轮清理之后，四个数据集里能被 hack agent 攻破的环境都在九成以上。** 其中三个数据集第二轮降到约一到两成，另一个到第四轮还有两成左右（图只画到第四轮，正文说一直做到找不到为止）。右下是最终那次 RL 过程中检测到的作弊比例，一直在 2% 以下。

第四层接回第二章：**这是在 RL 开始前往 π₀ 里种东西。** RL 更容易强化采得到的行为，那就先让“意识到自己在走捷径、然后改回来”这条路在 π₀ 里有一定概率。

282 期讲过 GLM 的类似做法：拿解题者的轨迹去找捷径，找到就堵上；283 期讲过 K3 的 kernel 作弊检测，抓 CUDA graph 重放、输入缓存、偷偷降精度，边开发边加规则。**小米多出来的是把“找漏洞”交给一个专门的 agent 并循环到收敛。** 283 期那句“造一个长程 agent 训练环境，这件事本身就是一个长程 agent 任务”，到这里又多了半句：检查这个环境有没有漏洞，也是一个 agent 任务。

◆ 第五章：熵，还得防往上涨

━━━━━━━━━━━━━━━━━━━━

315 期 https://mp.weixin.qq.com/s/8jC7pwKN0RFd5O70Dh4Lrw 讲的是熵坍缩：训着训着，模型的输出分布越来越尖，不再尝试别的写法，RL 在把预训练存下来的余地花掉。那期的几个处方都是在防熵往下掉。

小米报告多次提醒的是另一个方向：**额外的负向压力会把熵往上推。** 熵高是说每一步的概率分布摊得太平，模型拿不定主意，容易出乱码、重复。长程训练里还有一个看得见的问题，是轨迹越跑越长，就是第三章那组不加 GAR 的曲线；不过那组图量的是通过率、轮数和长度，没有量熵，长不等于熵高。

报告在三个地方处理这件事：

- **clip 边界按熵双向调。** 正优势和负优势各有一对上下界，共四个，初值都是 [0.2, 5.0]，训练中按熵在线调整：“熵太低时，放宽正向边界、收紧负向边界；熵太高时反过来。”315 期讲的 DAPO Clip-Higher 是固定地放宽上界防坍缩，小米这里是两头都管、随时调。
- **GAR 通过重分配维持正负信号的平衡**，理由写的是 “a safeguard against excessive entropy growth”：只给差的通过解打折而不补回去，负优势相对就变大了。
- **格式错误按段惩罚**：工具名写错、参数坏了的 token 单独标出来。正优势轨迹里，这些 token 不再受奖励，拿掉的优势在**整个训练批次**里分给其他正优势、没出错的 token；负优势一侧，出错的 token 加重罚，没出错的减轻罚。缩放没碰到上限时，正负两边分别保持总量，原话同样是为了限制“可能导致熵失控上涨的额外负向压力”。

全文的损失函数里没有 KL 项。315 期讲的 Ring-Zero 用了 1e-4 的 KL 防坍缩；小米的做法是不加 KL，靠 clip 和优势重分配两头控制。

熵坍缩和熵失控，是同一个旋钮的两头。DAPO 论文里也讨论过熵太高导致乱码和重复，不是只有一头要防。315 期讲的主要是往下掉那头，小米这份报告两头都在管。它的训练任务里，agent 编程加竞赛编程占 68%，通用工具使用另占 12%。

◆ 第六章：另外三件，都能接上往期

━━━━━━━━━━━━━━━━━━━━

**路由器冻结**

小米这次的 Pro 实验里，MoE（混合专家，Mixture of Experts）如果在 RL 时让路由器继续训，前 20 步第 9 层的负载就崩了：负载的变异系数从 0.78 涨到 2.0，最忙的专家从平均的 6 倍涨到 16 倍，几乎没活干的专家从 0.5% 涨到 22%。

![MiMo-V2.6 技术报告图 11：Pro 第 9 层 384 个专家在 RL 中的负载，橙色是路由器可训，蓝色是冻结路由器。(a) 负载变异系数：可训的从约 0.8 涨到 2.0，冻结的维持在 0.7 左右；(b) 最忙专家是平均的几倍：可训的从 6 倍涨到 16 倍，冻结的维持在 5 到 6 倍；(c) 负载不到平均十分之一的冷专家比例：可训的从接近 0 涨到 22%，冻结的维持在 1% 左右](assets/323/fig11-router.png)

诊断做得很干净：把第 20 步检查点里的路由器参数单独还原成 RL 前的值，其他参数不动——负载恢复了，**分数没变。** 说明坏的是路由器漂了，专家本身没坏。于是 RL 全程冻结路由器，负载一直平稳，分数正常涨。

246 期 https://mp.weixin.qq.com/s/EwUO9tVfrpCrcwsyPI42uw 讲过 MoE 路由怎么挑专家、怎么做负载均衡。往期写过的几家都没提过 RL 阶段的路由器怎么处理，这是往期材料里第一次出现。

**不用生产用的 agent 壳训练**

agent 壳（harness）就是包在模型外面、负责调工具和管上下文的那层程序，比如 Claude Code、Codex。小米没有拿这些现成的壳训练，而是自己做了 4 个极简壳，理由是：

> production harnesses ... steer the model with numerous constraint and instruction prompts. These extras fall outside the task-completion reward signal, making credit assignment unreliable.

生产用的壳要求模型守很多规矩，奖励却只问任务做完没有，**模型就容易忽略那些不计分的要求。** 另一个理由是生产壳的模块耦合太紧，没法单独换掉某个交互机制；极简壳可以把工具、提示词和上下文管理分开组合。

用 4 个极简壳训完，拿训练时没见过的三个壳（Codex、Claude Code、mini-swe-agent）测，平均通过率从约 50% 涨到 66%。这张图的纵轴写的是 pass@1，就是第一章说的“做一次能做对的概率”：

![MiMo-V2.6 技术报告图 10：多壳训练过程中 DeepSWE v1.1 的 pass@1。(a) 训练用的四个极简壳，平均从约 59% 涨到 67%；(b) 训练时没见过的三个壳（codex、claude code、mini-swe-agent），平均从约 50% 涨到 66%，其中 codex 起点最低（约 42%）](assets/323/fig10-harness.png)

264 期 https://mp.weixin.qq.com/s/W6CUq0xrJP3MdPBXw56v4A 讲过 K3 也做了多壳训练，把壳做成可配置的模块，训练中动态切换，这一条两家思路相同。小米多给了一个“为什么不用生产壳”的理由。

**蒸馏换了位置**

284 期讲 DeepSeek V4 和 K3 的路线是：先分头练 RL 专家，再用在线蒸馏合成一个模型。286 期对比过这条路和混合 RL，引的正是小米那篇 MOPD 论文：在它的设置里，在线蒸馏略占上风。

到了自家旗舰，小米的顺序是：**先跑一次混合 RL，所有任务一起训；然后才做蒸馏，叫 MOPD2（多前缀多老师在线蒸馏，Multi-Prefix Multi-Teacher On-Policy Distillation）。** 蒸馏没有被否定，只是从“合并专家的主手段”挪到了“RL 之后补能力”的位置，用来覆盖那些难以设计判分器的领域（长程游戏开发、科研、具身智能）。

MOPD2 的老师分两类：可验证的任务用混合 RL 训出来的老师，难验证的开放任务用 SFT 老师（拿合成的高质量示范训的）。报告没说前一类是不是就是那次 30 步混合 RL 的产物。新加的一招叫前缀条件蒸馏：从老师的轨迹或 SFT 示范里取一条有 k 轮的轨迹，切成 k 个历史前缀，学生从每个前缀开始自己生成一轮，老师在同样的历史下逐 token 批改。这样能限制长任务里前面多轮偏差的累积，少往老师没见过的地方跑。285 期的结论是老师得离学生近，这一招是从另一头去凑：把学生摁在老师见过的历史上。

💡 287 期那个长度偏差，小米也撞上了

287 期 https://mp.weixin.qq.com/s/74UVLTkou7EbY-fzt6ihkw 讲 DeepSeek V4 的 RL 基建时提到：被打断的轨迹如果从头重跑，会带来长度偏差，所以他们用预写日志从断点续写。

小米用的 partial rollout（没跑完的轨迹下一轮接着跑）在失败分析里也记了同类问题。先看下面这张图，Pro 和 Flash 这 30 步的时间线，浅色格是正常完成的步，其他颜色是各种故障和恢复：

![MiMo-V2.6 技术报告图 12：Pro（123.1 小时）与 Flash（81.8 小时）30 个训练步的时间线，浅橙色为正常完成的步，灰色为基础设施故障，橙色为推理故障，深褐色为训练故障，深灰为驱动故障；Pro 在第 15 到 16 步之间有一段较长的训练故障](assets/323/fig12-timeline.png)

失败分析里写到：短的轨迹先跑完、先进训练批，长度估计就偏了，还连带把 KV 缓存池耗尽。另外 25 个数据源之间，生成的 token 数差 90 倍，单条 rollout 的时长差 66 倍。287 期那句“最贵的动作是等”，在小米这里换成了“最难的是等的时间长短不齐”。

◆ 尾声：老师和学生，斗智斗勇

━━━━━━━━━━━━━━━━━━━━

先把开篇那两个猜测收个尾。

**“小米的 RL 做得不差”，成立。** 30 步、260 万美元，DeepSWE 涨 14 分；判分器、hack agent、路由冻结、熵的双向控制，GAR 和路由冻结给了对照实验，也公开了训练曲线和故障记录，还开源了约 7000 个 RL 环境和 9B 的完整配方，是往期写过的几家里公开得最多的一份。**“分数主要是 RL 练出来的”，只能说不全是。** 这一轮 RL 涨了 14 分；新一代在进 RL 之前就已比上一代最终版高出将近 40 分。两个数不是同一把尺子上的分账，但足以说明高分不只是最后这一轮 RL 的故事。

读完整份报告，我的感觉是：这些招数与其说是技术，不如说更像教育学。把报告里的招一条条换成教室里的说法，几乎都对得上：

| 报告里的招 | 换成教室里的说法 |
|---|---|
| mid-training 提高好轨迹的初始概率 | 先把基础打牢，后面的练习才容易得到有效反馈 |
| 只看测试过没过，模型学会吞异常、放宽校验 | 应试教育：只看分数，学生就学会怎么应付考试 |
| GRS 评分表 | 期末考前写好评分细则，照着一份份批 |
| GAR 现场比 | 老师把全班作业摊开一起看，谁写得干净一眼就出来 |
| 只挪不加 | 不额外发分，只在及格的人里面重新排名次 |
| 学生去网上找现成答案 | 翻书、偷看隔壁、上网搜往年真题 |
| hack agent | 监考老师考前先自己试一遍，看考场哪儿能作弊，堵完再试 |
| mid-training 里种“犯错、反思、改正”的样本 | 不光罚作弊，还给学生看“我当时想抄，后来发现不对，改回来了”的范文 |
| 不用生产用的 agent 壳训练 | 练习的要求和评分标准要对得上，不计分的规矩学生就不守 |

每一招单拿出来都不新鲜，新的是这些招同时用在一个班上。学生越聪明，钻空子越快，老师也得跟着升级。上文 283 期说过，“人没有退场，只是往上挪了一层”；挪上去的那一层，就是当老师。

**RL 的分数不是某一个技巧练出来的，是老师和学生一整套斗智斗勇斗出来的。**

322 期结尾那个问题——KV 不压缩是不是也帮了长上下文——还没有答案。它和这期的结论不冲突：一个模型的分数本来就是好几层叠起来的。

◆ 技术名词速查

━━━━━━━━━━━━━━━━━━━━

| 术语 | 一句话解释 |
|---|---|
| mid-training（中段训练） | 预训练和后训练之间的一段，小米用它混入 agent 轨迹、把上下文扩到 1M，目的是给 RL 扩大探索空间 |
| π₀（先验） | RL 开始前的模型；好轨迹在它这里越容易被采到，RL 越容易得到有效反馈 |
| DeepSWE v1.1 | 在真实代码仓库里做长程修改的评测，小米报告里主要看的一项 |
| avg@3 | 同一道题跑三次取平均通过率 |
| GRS（组内奖励合成，Groupwise Reward Synthesis） | 离线比一组答案写出这道题的评分表，奖励 = 测试分 × 解法分 × 过程分 |
| GAR（组内优势重分配，Groupwise Advantage Redistribution） | 在线给通过的解排序，把正向优势从写得差的挪给写得好的，维持正负信号平衡 |
| 优势（advantage） | GRPO 里每条答案比组内平均好多少，决定这条被加强还是被压低 |
| reward hacking（奖励作弊） | 模型用偷答案、钻判分漏洞等方式拿分，任务本身没做好 |
| hack agent | 专门攻击训练环境、找作弊路径的 agent，循环到找不到为止 |
| 熵（entropy） | 每一步输出的概率分布平不平；太低是坍缩（只剩一种写法），太高是失控（拿不定主意，易出乱码重复） |
| harness（agent 壳） | 包在模型外面调工具、管上下文的程序，如 Claude Code、Codex |
| MOPD2 | 小米的多前缀多老师在线蒸馏，放在混合 RL 之后，用来补难以判分的领域 |
