◆ 权重还在往下拽，账先摆清楚

━━━━━━━━━━━━━━━━━━━━

7 月 31 日，DeepSeek 发布了 V4-Flash 正式版，编号 0731。写这篇稿子的时候，我家里那两台 DGX Spark 正在往下拽 167GB 的权重——进度条走得不紧不慢，正好留出时间把账摆清楚。

preview 版这几个月我们一直在用，也一直在等这个正式版：等它把 agent 能力练齐，等它把投机解码装上，也等一个理直气壮升级的理由。现在它来了，理由给得很足——足到有一项分数涨了七倍，这个后面细说。

这期回答三个问题：**相比 preview 改了什么？分数多少？家用机怎么跑？** 前两个靠核对 config.json 和官方跑分表，第三个是这期真正的主菜——短短几个月，围绕这个模型长出来的家用机部署生态，比模型本身还热闹：Redis 之父下场手写引擎，48GB 内存的 Mac 有人玩出邪道，双机原生精度的部署配方（行话叫 recipe——照着做就能复现的一整套配置加命令）已经能抄作业。

先交代一下背景坐标：166 期给 V4 的技术报告做过精读（ https://mp.weixin.qq.com/s/iLObYwtZYqCWwRRYJVcpyA ），168 期把 MHA/MLA/DSA/CSA-HCA 这条注意力演化线捋过一遍（ https://mp.weixin.qq.com/s/YqcTnIrGKEYZ2n-sMAelKg ）。架构的细账都在那两期里，这期不重讲，只讲变化和落地。

◆ 1. 改了什么——架构一个字没动

━━━━━━━━━━━━━━━━━━━━

每次大厂发"正式版"，第一个要回答的问题都是：这到底是个新模型，还是老模型换了个牌子？回答方式也只有一种——别听发布稿怎么说，去对 config.json。

拿到权重第一件事，我们把正式版和 preview 的两份 config.json 并排放着逐字段对了一遍（这是本地实测核过的，不是转述）。结论先说：**主干架构一个字没动。**

逐项过一遍相同的部分：

- 43 层、hidden 4096——没动
- MLA 加 DSA 索引的注意力方案——没动
- 256 个路由专家加 1 个共享专家、每 token 激活 6 个——没动
- FP8 block-128 主体精度、专家权重原生 FP4——没动

全部与 preview 逐字段相同。对着两份文件逐行往下滚的过程其实有点无聊——直到滚到文件末尾，新东西才出现。真正的新增只有两处：

**第一处：4 个 DSpark 字段。** dspark_block_size=5、target_layer_ids=[40,41,42]、markov_rank=256，外加一个专用的 noise token。DSpark 是 DeepSeek 自家的投机解码（speculative decoding）方案——大模型旁边挂个会猜的小弟，一次猜 5 个 token，猜对了白赚。原理 236 期（ https://mp.weixin.qq.com/s/fQc0hRxEIZxkPzGTDhj78g ）讲过 DSpark，这里不展开，只看配置：草稿模块挂在第 40 到 42 层上，块大小 5，正好对上 dspark_block_size 那个数。

**第二处：compress_ratios 数组加长了两项。** config 里有个 compress_ratios 数组，一层一项，写明这一层 KV cache 的压缩倍率。数值就三种：4 和 128，对应 168 期讲过的两级压缩——4 就是 CSA 的"4 个 token 打包成 1 块"，128 就是 HCA 的更狠一档；0 是不压，按原始形态存。preview 里这个数组 44 项：前 43 项对应 43 个主干层——开头两层 0（浅层不压），中间一长串 4 和 128 交替（轻压层当高保真锚点，狠压层管省内存，第三节说的"KV cache 只有传统的 2%"就是这么省出来的），第 44 项是附加预测层的位子。正式版变成 46 项——**原有 44 项一个数字都没动，只在尾巴追加了两个 0**。也就是说主干每一层的压缩方案原封不动；多出来的两项，对应的应该是 DSpark 草稿模块自己新增的层——第一处多出来的那约 20B 参数——它们的 KV 不压缩。官方没写文档，这是拿两份 config 逐项 diff 出来的读数；草稿模块内部长什么样，等跑起来读官方推理代码再核。

参数量的账也对上了：284B 涨到 304B，权重文件 149GB 涨到 167GB——差值就是 DSpark 模块的体积。加的这 20B 不参与"想什么"，只负责"猜下一步"，属于纯粹的推理加速件。

所以正式版是什么？**骨架没变，是拿同一副身体又练了一大轮 agent 后训练。** 这句话值得多咀嚼一下：架构相同、参数量几乎相同，但下一节你会看到有的分数涨了七倍——涨幅全部来自训练，一分都不来自结构。后训练管线这几年是怎么从"微调一下"膨胀成"再造一遍"的，265 期梳理过四年演化史（ https://mp.weixin.qq.com/s/EyYgiHDPAMabHBuF64ljIQ ）；0731 就是这条演化线上最新的一个脚印。

这也解释了一个下载体验上的坏消息：虽然架构没动，但既然是重练，权重值就全刷新了——没法增量下载，167GB 一个字节都省不掉。我家那两台 Spark 对此深有体会。

────────────────────

💡 为什么"架构不动、只练后训练"反而是最值得高兴的发布方式

如果每次提分都要换架构，那生态就永远在推倒重来：推理引擎重适配、量化方案重调、部署配方重写。0731 架构逐字段不变，意味着 preview 时代社区攒下的所有工程资产——ds4 的 kernel、mlx 的量化配方、vLLM 的并行配置——几乎原样可用，正式版发布当天就有全套部署方案等着它。模型厂把创新压进训练管线、把接口冻结给社区，这是开源生态最舒服的分工。

────────────────────

改动的账就这么多——两处新增、一处闭环，剩下的全是训练的功劳。训练练出了什么，看分数。

◆ 2. 跑分——13B 激活反超 49B 激活

━━━━━━━━━━━━━━━━━━━━

官方跑分表来自 HF README，下面这张是逐项核对过的（GLM-5.2 在 Cybergym 上官方未列数字，表内留空）：

| 基准 | Flash-0731 | Flash preview | Pro preview | GLM-5.2 | Opus-4.8 |
|---|---|---|---|---|---|
| Terminal Bench 2.1 | 82.7 | 61.8 | 72.1 | 81.0 | 85.0 |
| NL2Repo | 54.2 | 39.4 | 38.5 | 48.9 | 69.7 |
| Cybergym | 76.7 | 38.7 | 52.7 | — | 83.1 |
| DeepSWE | 54.4 | 7.3 | 12.8 | 46.2 | 58.0 |
| Toolathlon-Verified | 70.3 | 49.7 | 55.9 | 59.9 | 76.2 |
| Agents' Last Exam | 25.2 | 15.8 | 16.5 | 23.8 | 25.7 |
| AutomationBench Public | 25.1 | 10.8 | 12.8 | 12.9 | 27.2 |
| DSBench-FullStack | 68.7 | 37.0 | 41.8 | 61.8 | 71.6 |
| DSBench-Hard | 59.6 | 25.8 | 31.1 | 54.5 | 71.7 |

这张表有三个看点，按震撼程度排序：

先说明这九项基准是什么成色：全是 agent 向的——终端操作、真实仓库级软件工程、安全攻防、工具链调用、数据科学全栈。没有一项是"背知识点"的老式问答，全部要模型自己动手干活。DeepSeek 这轮后训练练的是什么，选题已经说明白了。

**看点一：Flash 全线反超自家 Pro preview。** 注意这两个模型的身价差距——Flash 每 token 激活 13B，Pro preview 激活 49B，将近四倍的算力差。结果九项基准 Flash 全赢，最夸张的 DeepSWE 从 preview 的 7.3 涨到 54.4，涨了七倍不止，把 Pro preview 的 12.8 远远甩在身后。7.3 分是什么概念？基本等于"这活它干不了"；54.4 是"多数任务能收尾"——同一副骨架，从不及格边缘练到了能上工。这不是"小模型追上大模型"，是"小模型的新一轮后训练碾过了大模型的旧一轮"——训练配方的进步在这一年里跑赢了参数规模。

────────────────────

💡 为什么偏偏是 agent 分数爆涨：单步的小修补，链条上的大相变

对比一个表格外的数字才能看出蹊跷。第三方机构 Artificial Analysis 有一个综合智能指数（后面看点三还会说它），偏重单步的推理和知识——这个指数上 0731 从 40 涨到 50，涨了 25%，进步是温和的。可表格里的 DeepSWE 涨了 7 倍。如果后训练真给模型长出了新能力，这两个数该同步涨才对。

解释藏在 agent 任务的结构里。一个仓库级修 bug 任务是几百步的因果链：读代码、定位、改、跑测试、根据报错再改——每一步都得走对，走岔一步全盘皆输。设单步成功率是 p，任务 200 步，整链成功率就是 p 的 200 次方。拿这个式子算笔账：单步 97% 时，0.97 的 200 次方约等于 0.2%——基本干不成，这就是 7.3 分的世界；单步磨到 99%，0.99 的 200 次方约等于 13%——开始能收尾了，这就是 54.4 分的方向。**单步只改进了 2 个百分点，链条上放大成了几十倍**。指数是个放大器：喂进去修修补补，吐出来沧海桑田。

这也把第一节那句"涨幅全部来自训练"落到了机制上：这轮后训练没让模型每一步聪明多少（智能指数的 25% 就是证据），它干的是把几百步里每一步的岔路填平——用 265 期的话说，预训练买潜能，后训练买"成为谁"；agent 基准量的恰恰是"成为谁"那半边，所以它对后训练的进步最敏感，敏感到指数级。

────────────────────

**看点二：跟 Opus 4.8 的差距缩到几分。** Agents' Last Exam 差 0.5 分，AutomationBench 差 2.1 分，Terminal Bench 差 2.3 分。当然也有还没追平的：NL2Repo 差 15.5 分，DSBench-Hard 差 12.1 分——长程复杂仓库任务上闭源旗舰还压着一头。但一个开源权重、13B 激活的模型把差距压到这个量级，本身就是新闻。

**看点三：第三方独立评测也对得上。** 官方报表历来要打折看——不是说厂商造假，而是基准的选取、harness 的配置、采样的参数都是自己定的，天然往有利处倾斜。所以第三方数字更要紧：Artificial Analysis 的 Intelligence Index 给了 50 分（preview 是 40 分），只比 GPT-5.6 Luna max 低一分；GDPval-AA v2 这个 agent 实战 Elo 从 1189 涨到 1559——三百多分的 Elo 涨幅，在对战类评测里是换了一个段位的意思。官方表格和第三方读数方向一致、幅度相当，这轮提升基本可以坐实，不是报表魔法。

────────────────────

💡 怎么读厂商跑分表：先看对照组选了谁，再看数字

一张跑分表最诚实的信息往往不在数字里，在列的选取里。这张表把自家旧版（Flash preview）、自家大哥（Pro preview）、国内同行（GLM-5.2）、闭源标杆（Opus-4.8）都摆上了——旧版衬托进步、大哥衬托效率、同行标定位置、标杆承认差距。敢把 Opus-4.8 放在最右边并且九项里九项都低于它，反而是自信的表现：差距摆出来给你看，说明其余数字也经得起看。最该警惕的是那种只跟弱对手比、或者对手一栏全是两年前旧模型的表。

────────────────────

价格侧没有变化：OpenRouter 挂牌每百万 token 输入 0.14 美元、输出 0.28 美元，缓存命中打 98% 折扣。分数涨了一大截、单价一分没动，等于性价比曲线整体上移；98% 的缓存折扣对 agent 工作流尤其友好——agent 每一步都要把前面的上下文重发一遍，缓存命中率天然极高，实际账单常常远低于挂牌价的直觉。

推理支持 low/high/max 三档 effort（推理努力档位），官方建议高档配 384K 最大输出——agent 长任务确实吃得下这个量，一次长程修 bug 任务的思考加工具调用记录，几万 token 只是起步价。

◆ 3. 为什么 304B 能进家用机——三个数字

━━━━━━━━━━━━━━━━━━━━

在讲部署生态之前，先回答一个前提问题：一个 304B 参数的模型，凭什么惦记家用机？直觉上这是荒唐的——304B 参数，按老规矩 FP16 存储就是 600GB 上下，哪台家用机装得下。荒唐感的来源是拿稠密模型的旧账本算新模型的账。新账本上真正要紧的是三个数字，架构细节 166 和 168 期都讲过，这里只记结论：

1.**激活只有 13B。** MoE（Mixture of Experts，混合专家）的稀疏路由，256 个专家每次只叫 6 个干活——304B 是仓库容量，13B 才是每个 token 的运行成本。生成一个 token 实际过手的计算量，跟一个 13B 稠密小模型同级。算力上一台家用设备够用。

2.**KV cache 只有传统 GQA 约 2%。** CSA/HCA 的多级压缩把长上下文的内存账压到地板上：FP8 KV 下，100 万 token 的上下文只占约 5GB。传统架构里这是几百 GB 的量级，长上下文在家用机上从"不可能"变成"顺便"。

3.**专家权重原生 FP4。** 参数大头本来就以 4 比特存储和计算，167GB 权重不是量化阉割出来的，是训练时就住在这个精度里——这决定了 128GB 级别的内存就摸得到门槛。

三个数字对应家用部署的三座大山：算力、上下文内存、权重体积——每座山各有一项架构设计专门来削。这不是巧合，这个模型从设计第一天起，成本就是一等公民。

────────────────────

💡 1M 上下文只占 5GB 意味着什么：长上下文从奢侈品变日用品

拿旧账本对照一下才知道这个数字多离谱：传统 GQA 架构下，百万 token 的 KV cache 是几百 GB 的量级——等于说"记住一本长书"这件事比模型本身还占地方，所以长上下文一直是数据中心才养得起的奢侈品。压到约 2% 之后，5GB 的 KV cache 塞进 128GB 家用内存毫无压力，双机方案能顺手把上下文往百万级开就是这么来的。对 agent 场景这是质变：长程任务最怕的就是"干到一半上下文装不下了"，现在这个天花板在家用机上都够不着头顶。

────────────────────

一个 token 在这套架构里的完整旅程，169 期走过一遍（ https://mp.weixin.qq.com/s/mnbaXhQmQjDAyGD1dDdq5Q ）；这些数字底下的算子层实现，239 到 247 期的算子系列（合集导读 https://mp.weixin.qq.com/s/w3zBkGtpN0Xe3AXNJqoqhQ ）逐个讲过一轮。这里不再展开，直接看这三个数字在真实硬件上开出了什么花。

◆ 4. 家用机部署生态——本期主菜

━━━━━━━━━━━━━━━━━━━━

先划定范围：这一节只谈家用机——数据中心的配置（H200/B200 集群跑 vLLM/SGLang 那套）不在讨论之列，那是另一个世界的账本，官方文档写得很全，轮不到我们操心。这里只看普通人买得起、放得进书房的硬件。

正式版发布时，围绕 V4 Flash 的家用部署已经不是"能不能跑"的阶段了，是各条路线摆开摊子任君挑选的阶段。挨个看。

**◆ 4.1 ds4/DwarfStar——antirez 手写的 C 引擎**

先讲最有故事性的一个：ds4，又名 DwarfStar，作者是 Redis 之父 antirez——那位写了二十年 C、坚持不用依赖库的老派工匠，这次把手艺用在了推理引擎上。一个数据库领域的传奇人物，为一个中国开源模型手写推理引擎，这件事放在两年前是想都不敢想的组合。

ds4 是一个专为 V4 Flash 写的 C 语言推理引擎（兼容 V4 Pro 和 GLM 5.2），Metal/CUDA/ROCm 三个后端，苹果、英伟达、AMD 全覆盖。它的量化策略很讲究：**只量化路由专家（2bit 或 4bit），其余部分原精度保留**——注意力、共享专家这些失稳敏感区一个比特不动。道理不难想：路由专家占了参数的绝对大头，而且 256 个专家里每个 token 只用 6 个，冗余度高、扛得住压；注意力和共享专家是每个 token 必经之路，压坏一点全模型跟着晕。刀口选在最肥、最不敏感的地方。GGUF 权重由 antirez 自己发布。

实测数字：单台 DGX Spark 上 q2 量化生成 13.75 tok/s、prefill 343.81 tok/s；M5 Max 128GB 上生成 25.90 tok/s。日常对话和轻量 agent 任务，这个速度完全可用——尤其注意 prefill 那个 343.81：喂一万 token 的代码上下文进去，半分钟就读完了，这对编码场景是体验分水岭。

项目还自带 OpenAI/Anthropic 兼容的 server 和一个编码 agent，下载完权重开箱即用——不用装 Python 环境、不用配依赖，一个 C 程序从推理引擎包办到 agent，这种"整机交付"的做派在推理框架里是异类，也是它讨人喜欢的地方。

作者对项目的自我定位值得抄下来：「自包含且故意狭隘，不是通用 GGUF 运行器」。不追求兼容天下模型，只把这一个模型伺候好——这个味道和 Redis 一脉相承。

**◆ 4.2 Mac 生态——从 128GB 到 48GB 都有人玩**

苹果这边路线更杂，丰俭由人：

- **mlx-lm 正统路线**：mlx-community 发布了 2bit-DQ 量化版（配方是专家 2bit、其余 4bit 起步的动态混合精度，作者自己说还是听了 antirez 的建议），磁盘占约 90GB，128GB 内存的 Mac 用 mlx-lm 直接跑，最省事的一条路。实测 M5 Max 约 34 tok/s、M3 Ultra 约 30 到 34 tok/s——统一内存架构在这种场景下是真金白银的优势，90GB 权重整个躺进内存，不用操心显存和内存之间倒腾
- **SSD 流式加载邪道**：有人在 48GB 内存的 Mac 上搞专家权重的 SSD 流式加载——内存装不下所有专家，就用到哪个从 SSD 现读哪个，跑到 4.5 到 5 tok/s。速度谈不上快，但 48GB 内存跑 300B 级模型这件事本身就值得记一笔。而且这条邪道能走通，靠的还是 MoE 的稀疏性：每个 token 只需要 6 个专家在场，其余 250 个躺在 SSD 里睡觉完全不碍事
- **llama.cpp Metal**：M4 Max 上 3 到 8 tok/s，胜在生态熟悉，手边工具链全是现成的

**◆ 4.3 双机原生精度路线——不量化的那条路**

以上路线都要量化。量化再讲究也是有损的——想跑原生 FP8+FP4、一个比特都不打折的完整体，社区也有了成熟答案：双 DGX Spark 跑 vLLM TP=2（张量并行），tonyd2wild 的 repo 给了完整配方——两台机器用 200Gbps RDMA 直连，权重对半劈开各扛一半，每一层的计算两台机器同时做、中途交换一次结果。

这条路的巧处在于它不需要"额外"量化：V4 Flash 的专家权重训练时就是 FP4、主体就是 FP8，原生精度本身已经足够小，167GB 劈两半，单台 128GB 的 Spark 各装一半绰绰有余，剩下的内存正好留给 KV cache——上下文能一路开到模型支持的 1M 上限，社区已经有专门冲着 1M 配置的双机方案。

配方作者的实测：单流约 40 tok/s，8 并发合计 92 tok/s。

这里可以插播一条第一手消息：写这篇稿子的下午，权重下完了，我们照着这份配方在自己那对 Spark 上跑通了 0731 正式版——还往前多走了一步，把 0731 新带的 DSpark 投机解码也点亮了（原配方用的还是 preview 时代的 MTP，这个组合网上还没有公开记录）。自家实测：**单流 51 tok/s**（关掉投机的纯自回归是 24.5），44K token 的长 prompt 预填充 1265 tok/s，35 秒读完一个中型代码库的上下文。中间踩了四个坑——旧镜像不认新草稿头、sm_120a 二进制在 GB10 上不兼容之类——完整流程和排障记录放在 GitHub 了： https://github.com/lmxxf/deepseek-v4-deployment-on-dgx-spark ，有同款硬件的可以照抄。

不过发稿前得补一句诚实的：51 这条快路后来在真实场景里翻车了——测速脚本跑得欢，换成贴长文的多轮对话，某个新形状触发 CUDA 非法内存访问，整个引擎当场去世。DSpark 双机这条路还太新，目前只能算"benchmark 能跑"；日常挂机我们退回了不开投机的稳定配置，24.5 tok/s。这个反转本身就值一条经验：**测速脚本全绿不等于能用，真实负载才是验收标准**——排障细节都在上面那个 GitHub 仓库里。

即便按 24.5 算，这也不是"家里玩玩"的水平——一个原生精度、50 万上下文的前沿开源模型服务，跑在两台桌上的小盒子里，速度和主流 API 的体感相当。

AMD 阵营也没缺席：Strix Halo（Framework Desktop 那颗）走 ds4 的 ROCm 后端，同样在支持名单里。

**◆ 4.4 摆在一起看**

| 路线 | 作者/出处 | 硬件 | 精度 | 生成速度 |
|---|---|---|---|---|
| ds4 q2 | antirez（Redis 之父） | 单台 DGX Spark | 路由专家 2bit | 13.75 tok/s |
| ds4 q2 | antirez | M5 Max 128GB | 路由专家 2bit | 25.90 tok/s |
| mlx-lm | mlx-community 社区 | M5 Max 128GB | 2bit-DQ | 约 34 tok/s |
| SSD 流式 | 社区个人项目 | Mac 48GB | 量化+流式 | 4.5 到 5 tok/s |
| llama.cpp | llama.cpp 社区 | M4 Max | 量化 | 3 到 8 tok/s |
| vLLM TP=2 | tonyd2wild 的 recipe | 双 DGX Spark | 原生 FP8+FP4 | 40 tok/s（单流） |
| vLLM TP=2 + DSpark | 我们的实测（0731） | 双 DGX Spark | 原生 FP8+FP4 | 51 tok/s（尚不稳定，见上文） |

这张表每一行的取舍逻辑都不一样：ds4 用精度换单机可跑，SSD 流式用速度换内存门槛，双机路线用一台机器的钱换原生精度。没有哪条是"正确答案"——手里是什么硬件、任务吃不吃精度、能不能忍慢，答案就落在哪一行。这种"同一个模型、按预算自选配置"的局面，本身就是生态成熟的标志。

────────────────────

💡 为什么同一个模型能长出这么多条部署路线：稀疏架构给了工程师下刀的缝

传统稠密模型量化是一刀切：所有权重同一个精度，切狠了全模型一起变笨。MoE 加 MLA 的架构天然把模型分成了"敏感区"和"耐操区"——注意力和共享专家小而关键，路由专家大而冗余（256 个专家里总有冷门的）。ds4 只量化路由专家、SSD 流式只换出路由专家，都是照着这条缝下的刀。架构的稀疏性不只省推理算力，还给了社区工程各显神通的自由度——这是稠密模型时代不存在的生态。

────────────────────

把这一节收个尾。一个 304B 的模型，128GB 内存的 MacBook 能跑，两台加起来五六万人民币的小盒子能跑出生产级速度，AMD 迷你机也在名单上——两年前，这个体量的模型是数据中心的专利，个人用户连权重都摸不到，更别提在自家书桌上开百万级上下文。

这个局面是两股力量拧出来的：模型厂把成本设计进架构（那三个数字），社区把工程做到每一种硬件上（这四条路线）。缺一不可——没有稀疏架构，antirez 的 C 引擎再精巧也塞不下 304B；没有社区工程，架构再省也只是论文里的数字。**开源权重加社区工程，等于家用机的黄金时代。** 这句话每隔几个月就要重新验证一次，而每次验证的门槛都比上次低。

◆ 尾声：说点自己的账

━━━━━━━━━━━━━━━━━━━━

最后说点私账。preview 时期，我们那两台 Spark 上是没有开箱即用方案的——当时的路子是站在两位社区先行者肩膀上：jasl 的 vLLM fork（Marlin kernel 的 sm_120 适配是他打的底）加 eugr 的 spark-vllm-docker 构建镜像（这位后来直接被 NVIDIA 招进了官方 Spark 团队），我们在上面接着手搓混合后端，坑踩得头破血流：sm_121 上 Marlin kernel 乱码、逐层二分锁定出事位置、最后一层换后端兜底，反复改了很多轮才收敛，185 期（ https://mp.weixin.qq.com/s/dEc-wD0JcM5WhKicOUR1pQ ）记的就是这场仗的收官——从 4.1 到 12 tok/s，中英文全对，还把修好的镜像发上了 Docker Hub，当时挺得意，觉得自己在无人区插了面小旗。

如今照着社区 recipe，当天下午就跑到了 24.5 tok/s 稳定档（快路 51 还得等社区把坑填平），附赠百万级上下文和多并发——我们那套 12 tok/s 的混合后端可以光荣退休了。说实在的也没什么可感慨的：当时就是觉得这事有意思，做了一下，跑通了，写了几期文章，完事。现在有更好的方案就用更好的，唯一的额外收获是读那份配方时格外亲切——里面每一个"注意这里要设成 X"，我们都能对上一段自己撞过的墙。

这篇稿子开头写的是"权重正在往下拽"，写到结尾，权重下完了、双机跑通了、快路试过也翻过车了，稳定档正在后台安静吐字——部署表里那两行数字都是今天下午现量的。账本可以合上了：改动清楚、分数硬、路子多，0731 是一个把权重拽完不会后悔的版本。

◆ 技术名词速查

━━━━━━━━━━━━━━━━━━━━

| 术语 | 一句话解释 |
|------|-----------|
| DSpark | DeepSeek 的投机解码方案：挂在最后几层上的草稿头一次猜 5 个 token，236 期讲过 |
| 投机解码（speculative decoding） | 小模型打草稿、大模型批改，猜对的 token 白赚生成速度 |
| MoE（混合专家） | 参数分成多个专家，每个 token 只激活一小撮——304B 仓库、13B 运行成本 |
| MLA | 低秩 KV 压缩注意力，DeepSeek V2 首创，168 期讲过演化线 |
| CSA/HCA | V4 的多级 KV 压缩方案，把长上下文内存压到传统 GQA 约 2% |
| FP8 block-128 | 每 128 个数共享缩放因子的 8 比特浮点，V4 系主体精度 |
| ds4/DwarfStar | antirez 手写的 C 推理引擎，专为 V4 Flash，三后端 |
| GGUF | llama.cpp 生态的权重打包格式，ds4 也用它分发量化权重 |
| TP（张量并行） | 把每层权重切开分给多卡/多机同时算，双 Spark recipe 用 TP=2 |
| RDMA | 绕过 CPU 的网卡直读内存技术，双机 200Gbps 直连靠它 |
| effort（推理努力档位） | low/high/max 三档思考深度，高档建议配 384K 最大输出 |
| prefill | 处理输入提示词的阶段，吞吐远高于逐 token 生成阶段 |
