◆ 起因：家用机大模型不只 V4 一家

━━━━━━━━━━━━━━━━━━━━

上一篇 268 期（DeepSeek-V4-Flash-0731 正式版，https://mp.weixin.qq.com/s/EwUO9tVfrpCrcwsyPI42uw ）写完之后，评论区反复出现的一个问题是："家用机大内存能跑的开源大模型，除了 V4，还有别的选择吗？"

回答是：**有。而且不止一家。** 今天要提的这个叫 **Step 3.7 Flash**，阶跃星辰（StepFun）2026 年 5 月底发的开源模型，198B 总参数、约 11B 激活/token，量级和 V4-Flash 完全同档。上架当天登上 OpenRouter Trending 全球第 2，被适配进 Claude Code、OpenClaw、Hermes Agent 这些主流 agent 框架。128GB 内存的 Mac + mlx-lm、或者带大内存的工作站，同样能跑。

但这一期不是给它做技术精读——真要精读，官方博客和 Step 3.5 Flash 那篇 67 页论文都在，读者感兴趣自己翻。今天想干的是另一件事：**V4-Flash、Kimi K3、Step 3.7 Flash 这三个开源大模型，规模都在同一档（百亿激活、千亿量级总参数），但它们在架构上押的是完全不同的赌注。** 把这三条赌注并排放一下，比单独讲某一家都更有意思——因为这三家其实代表了当前"大模型架构该往哪走"这个问题的三种主流答案。

先剧透结论：

- **V4 押"存储先爆"** → 把 KV cache 压到骨头（CSA + HCA）
- **K3 押"注意力太贵"** → 3/4 的层换成线性注意力（KDA），不存 KV cache 了
- **Step 3.7 押"吞吐才是硬指标"** → 老老实实用 GQA，把力气砸在投机解码上

三条路互不重叠，也互不否定。它们不是"谁对谁错"，是 **对未来最要紧的瓶颈是什么，三家判断不同** 。下面挨个讲。

◆ 1. Step 3.7 Flash 是谁——先补三句公司背景

━━━━━━━━━━━━━━━━━━━━

阶跃星辰不像 DeepSeek、Kimi 那么大众脸熟。三句话交代完：

- **成立 2023 年 4 月**，创始人姜大昕在微软干了 16 年做到全球副总裁。和智谱、月之暗面、零一万物、百川智能、MiniMax 并称"大模型六小虎"，2026 年初完成一笔超 50 亿的 B+ 轮融资。
- **首席科学家是 ResNet 的作者张祥雨**（那个把深度学习从二十几层拉到一百多层的经典工作），CTO 朱亦博原来是字节 AI Infra 负责人。班底比公司名气大。
- **战略押的是"原生多模态 + Agent"** 。Step 3.7 Flash 是这条路线上的最新一发——一个从设计上就为 agent 场景优化的开源模型。

三个数字定位它在"家用机 flash 档"里的位置：

| | V4-Flash-0731 | Kimi K3 | Step 3.7 Flash |
|---|---|---|---|
| 总参数 | 304B | 2.8T | 198B（含 1.8B ViT）|
| 激活参数/token | 13B | 104B | 约 11B |
| 上下文 | 百万级 | 262K | 256K |
| 是否原生多模态 | 否 | 否 | 是（含 ViT）|

激活参数上 Step 3.7 和 V4 差不多、比 K3 小一档；总参数上 Step 3.7 比 V4 还小 100B，比 K3 小一个数量级。**这是三家里"最小的一个"** —— 也就意味着它是家用机上最容易跑的一个。128GB 的 Mac 上，mlx-lm 走动态量化路径基本能装下。

◆ 2. 三家的第一条分岔：注意力机制怎么办

━━━━━━━━━━━━━━━━━━━━

大模型跑起来最贵的一块，从来都是注意力——KV cache 会随上下文长度线性膨胀，一百万 token 上下文的 KV cache 传统架构下动辄几百 GB。三家对这个问题给出了三条完全不同的答案。

**V4 的答案：压缩序列。** CSA（Compressed Sequence Attention）+ HCA（Hybrid Cache Attention）这套机制，把 KV cache 多条压一条。50K 上下文场景下，KV cache 从传统 GQA 的 40.7GB 压到 228MB—— **压了约 180 倍** 。代价是注意力语义有点动，但换来了百万 token 上下文在家用机上"顺便"就能开的红利（166 期精读过，https://mp.weixin.qq.com/s/iLObYwtZYqCWwRRYJVcpyA ）。

**K3 的答案：3/4 的层根本不做全局注意力了。** 93 层里 69 层是 KDA（Kimi Delta Attention，线性注意力的一种），24 层是 MLA（标准全局注意力）。KDA 不存历史 token 的 KV cache，而是维护一个固定大小的状态矩阵，每来一个新 token 更新一次。**你可以想象成"3 层用便签速记、1 层认真翻账本"** —— 前三层用便签就够，第四层再回头对账本。这样整体开销大幅下降，但每 4 层保留一次全局校验（264 期精读过，https://mp.weixin.qq.com/s/W6CUq0xrJP3MdPBXw56v4A ）。

**Step 3.7 的答案：老老实实用 GQA，不压不换。** 45 层解码层，每 4 层一组，组内 1 层全注意力 + 3 层滑动窗口（窗口固定 512 token），比例也是 3:1。KV cache 用标准 8 头 GQA，没有任何低秩压缩。

这里 Step 3.7 有一个反直觉的设计—— **query head 数量不对称** ：全注意力层 64 个 query head，滑窗层反而升到 96 个。论文管这个叫"free lunch"：滑窗场景下 query 数量增加几乎不增加延迟（因为瓶颈是显存带宽不是算力），256K 上下文下 decode/prefill 延迟只多 0 到 8%。 **"反正 IO 已经卡住了，闲着也是闲着，多做点计算又不吃亏"** —— 这个思路挺有意思。

────────────────────

💡 三家为什么走这么不同的路—— **赌的是未来"什么资源会先见底"**

- **V4 赌存储先见底** → 所以砸精力压缩 KV
- **K3 赌注意力算力先见底** → 所以砸精力换线性
- **Step 3.7 赌吞吐延迟先见底** → 所以砸精力保证投机解码能跑

三种赌注下的三种设计。**没有哪个是错的——分别对应了三种不同的"未来大模型主要用来干什么"的预期。** V4 押的是"长文档理解、超长上下文 agent"（KV 存储是瓶颈），K3 押的是"高吞吐 API 服务"（算力是瓶颈），Step 3.7 押的是"低延迟 agent 交互"（吐字速度是瓶颈）。

━━━━━━━━━━━━━━━━━━━━

────────────────────

Step 3.7 的这条路线，好处是 **投机解码（speculative decoding）能跑得特别顺** —— 因为 GQA 的注意力语义是完整的，draft token 的并行验证只需要 KV masking，不需要额外的 state-update 逻辑。论文原文说得直接：他们评估过 linear attention 路线（K3 那条），但那类方案的 state-update 机制会让投机解码的 draft tree 并行验证变得很复杂，所以放弃了。 **这不是"我们做不到"，是"我们不想为了做到而牺牲吐字速度"** 。

━━━━━━━━━━━━━━━━━━━━

◆ 3. 三家的第二条分岔：MoE 路由怎么设计

━━━━━━━━━━━━━━━━━━━━

MoE 这一层，三家的差别小一些，但也各有讲究。

| | V4-Flash | K3 | Step 3.7 |
|---|---|---|---|
| 路由专家数 | 256 | 896 | 288 |
| 共享专家数 | 1 | 2（全宽）| 1 |
| Top-k（每 token 激活）| 6 | 16 | 8 |
| 每 token 激活比例 | 2.3% | 1.8% | 2.8% |
| 门控函数 | sqrt(softplus) | sigmoid | sigmoid × 3.0 |

三家都学了 DeepSeek 的作业——细粒度专家（专家中间维度都比常规小）+ 共享专家（放一个"什么 token 都过"的兜底路径）。这套配方 166 期讲过，现在几乎是行业默认。

差别在**激活比例**：K3 最激进（1.8%，896 里只叫 16 个），V4-Flash 中庸（2.3%），Step 3.7 相对保守（2.8%）。**激活比例越低 = 更省算力但对路由稳定性要求越高。** K3 的 2.8T 参数配 1.8% 激活比，本质是"仓库开得极大但每次只叫一小撮出来干活" —— 这个玩法对路由训练的稳定性提了极高要求，K3 报告里有大量篇幅讲怎么让这套稀疏路由不崩（264 期讲过）。

Step 3.7 的 2.8% 激活比更保守，工程风险更小—— **用的是"288 个专家、每次叫 8 个"这种四平八稳的配置** ，重点不在稀疏极限，而在门控本身的稳定性（比如强制 FP32 计算门控打分、路由打分乘 3.0 放大信号）。

**三家路由策略的共同点是学 DeepSeek，差别在"稀疏到什么程度"这条旋钮上各自的取值** 。K3 拧到极致，Step 3.7 拧得温和，V4 在中间。

━━━━━━━━━━━━━━━━━━━━

◆ 4. 家用机跑得起吗——三家对比

━━━━━━━━━━━━━━━━━━━━

回到 268 期的主题：家用机部署。三家在这条战线上都有生态支持，但成熟度不同。

**V4-Flash-0731（300B 级）** —— 生态最成熟，四条部署路：
- **ds4/DwarfStar**：Redis 之父 antirez 手写的 C 引擎，Metal/CUDA/ROCm 三后端全覆盖，M5 Max 128GB 上约 26 tok/s
- **mlx-lm 2bit-DQ**：mlx 社区发布的动态量化版，M5 Max 约 34 tok/s、M3 Ultra 约 30-34 tok/s
- **SSD 流式加载邪道**：有人在 48GB 内存的 Mac 上搞专家权重的 SSD 流式加载，5 tok/s 能跑
- **DGX Spark 双机**：tonyd2wild 的 recipe，vLLM TP=2 原生精度约 40 tok/s

**Kimi K3（2.8T 级）** —— 家用机基本吃不下：2.8T 总参数即使 2bit 量化也要 700GB+ 存储，家用机走不通。K3 的主战场是 API 服务和数据中心，家用机部署目前只有极小规模的"象征性"支持（比如个别 4bit 量化版本在超大内存工作站上勉强跑，速度非常慢）。

**Step 3.7 Flash（200B 级）** —— 因为规模最小，家用机路径最舒服：
- **HuggingFace Transformers**：官方支持
- **mlx-lm**：128GB 内存 Mac 直接跑，规模比 V4 小 100B，速度应该略快（我没自己实测，等 mlx 社区跑分）
- **vLLM / SGLang**：数据中心路径也全支持
- **llama.cpp**：GGUF 量化版有社区维护

**规模决定家用机友好度：V4-Flash > Step 3.7 > K3**（越小越容易）。但从**能力密度**看反过来：K3 每 token 用 104B、V4 用 13B、Step 3.7 用 11B——K3 的智能最厚实但需要数据中心，V4/Step 3.7 是"家用机能跑但激活量薄一半"的配置。

**Step 3.7 在家用机档里的独特位置是——最小 + 原生多模态** 。V4-Flash 只有语言模型，Step 3.7 自带 1.8B ViT，天然能看图。128GB 家用机上想跑一个能理解图片的开源大模型，Step 3.7 目前是唯一选择。

◆ 5. 合上账本

━━━━━━━━━━━━━━━━━━━━

把三家的赌注并排放一下：

| | 押的是 | 代表设计 | 家用机友好度 |
|---|---|---|---|
| **V4** | 上下文会爆，先压 KV | CSA + HCA | ★★★（304B 但激活 13B）|
| **K3** | 注意力太贵，换线性 | KDA + MLA 3:1 | ★（2.8T 太大）|
| **Step 3.7** | 吐字速度是硬指标 | GQA + 投机解码焊死 | ★★★★（198B 最小）|

三条路都是当前开源大模型架构演化的主流答案，各自赌未来某个瓶颈会先见底。**读者不需要选边站** —— 这三家的存在恰恰说明"大模型架构应该怎么设计"这个问题**没有唯一答案**，取决于你打算把模型主要用在什么场景。

对家用机玩家而言：
- **想跑超长上下文** → V4，KV 压缩红利在这一档
- **想跑最强单机智能** → 走不到 K3，退而求其次选 V4 或等 K3 出更小的兄弟
- **想跑多模态 + agent** → Step 3.7，规模最小 + 自带视觉 + 为 agent 场景优化

三个选择互不冲突，看你机器多大内存、想干什么活。

━━━━━━━━━━━━━━━━━━━━

◆ 尾声：架构分岔不是坏事

━━━━━━━━━━━━━━━━━━━━

有一段时间业界担心开源大模型会"殊途同归"——所有家都学 DeepSeek 的作业，最后长成一个样子。这半年的实际情况是相反的： **V4、K3、Step 3.7 都是从 DeepSeek 的基础配方（细粒度 MoE + 共享专家）出发，但在注意力这一层各自往不同方向走出去了** 。

分岔的好处是 **生态可以按需选择** 。用户手里的机器不同、任务不同、对延迟/吞吐/上下文长度的偏好不同—— **只要有三条不同赌注的路线，就总有一条能对上你的需求** 。如果所有开源大模型都长得一样，反而会出现"你只有一个选择，不满意也没辙"的窘境。

这一期就当是给 268 期的家用机部署热潮补一条支线： **V4 不是唯一选择，Step 3.7 也不是"另一家类似的模型"，三家分别代表了对未来大模型场景的三种不同判断** 。至于哪种判断最终会被证明对，得再等一两年，看哪个瓶颈真的先在实际部署里见底。

在此之前，都值得跑一跑。

◆ 技术名词速查

━━━━━━━━━━━━━━━━━━━━

| 术语 | 一句话解释 |
|------|-----------|
| MoE（混合专家） | 参数分成多个"专家"，每个 token 只叫一小撮干活的稀疏架构 |
| 激活参数 | 每生成一个 token 实际计算过手的参数量（不等于总参数）|
| KV cache | 注意力机制存储历史 token 表示的缓存，随上下文长度线性膨胀 |
| GQA（Grouped Query Attention）| 多个 query head 共享一组 KV head，减少 KV cache 体积 |
| CSA / HCA | V4 的注意力压缩机制，把 KV cache 多条压一条（166 期讲过）|
| KDA（Kimi Delta Attention）| K3 的线性注意力，不存 KV cache 只维护固定大小状态矩阵（264 期讲过）|
| 滑动窗口注意力 | 每个 token 只看最近 N 个历史 token，Step 3.7 用 512 |
| 投机解码 | 小模型先"猜"几个 token，大模型批量验证，提高吐字速度 |
| ViT（Vision Transformer）| 处理图像的 Transformer 分支，Step 3.7 自带 1.8B ViT |
