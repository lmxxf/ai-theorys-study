【ROCm vs Vulkan】AMD 显卡跑大模型，为什么换个后端就变了？

━━━━━━━━━━━━━━━━━━━━

◆ 第一章：出字更快，却不一定更早开口

━━━━━━━━━━━━━━━━━━━━

最近看到一篇讨论：AMD 显卡跑大模型，用 Vulkan 居然比用 ROCm 快。

这句话很容易让人停下来。ROCm 是 AMD 自家的计算软件栈；Vulkan 在我的印象里，更多是游戏设置里和 DirectX 并排出现的名字。专业干计算的，怎么输给了搞图形的？

回看原测，更有意思的却是另一件事：**不少测试里，Vulkan 每秒吐出的 token 更多，ROCm 却更早吐出第一个 token。** 同一个“快”字，分开看竟然能指向两个赢家。

这组测试来自 Phoronix，Michael Larabel 于 2026 年 10 月 5 日发表，原文在这里： https://www.phoronix.com/review/lemonade-vulkan-rocm 。测试使用 Lemonade 2026.39.1，本次调用的 llama.cpp 版本是 b10825；通过本地 AI 服务切换 ROCm 与 Vulkan 两种后端，分别在两台 AMD 机器上比较。

一台是装有 Radeon AI PRO R9700 独立显卡的 System76 Thelio Major；另一台是使用 Ryzen AI Max+ 395、内置 Radeon 8060S 图形核心的 Framework Desktop。每台机器内部切换后端，两台的系统环境不同，不能把它们混成一场显卡排名。

取原文的几个代码调试（code-debug）场景，只看哪边更快：

| 设备 | 模型 | 生成吞吐更高 | 首 token 等待更短 |
| :--- | :--- | :--- | :--- |
| Ryzen AI Max+ 395 | Qwen3-14B-GGUF | Vulkan | ROCm |
| Radeon AI PRO R9700 | Qwen3-14B-GGUF | Vulkan | ROCm |
| Radeon AI PRO R9700 | Qwen3.5-4B-GGUF | Vulkan | Vulkan |
| Radeon AI PRO R9700 | Qwen3-Coder-Next-GGUF | ROCm | ROCm |

同一张 R9700，换个模型就能出现三种结果。这里列的是原评测这些场景的胜负，不是各模型在所有任务上的固定排名。

**模型变了，赢家也会变。连“Vulkan 管出字、ROCm 管起步”都不能当成通用口诀。**

我家正好有张 RX 9070 XT，16GB 显存，整机 48GiB 内存。原本想照着选个更快的后端，看完倒觉得，先得弄清楚自己究竟在选什么。

◆ 第二章：选后端，换掉的是什么

━━━━━━━━━━━━━━━━━━━━

模型文件里存的是权重。让它回答问题，还需要软件把这些数读出来，安排矩阵乘法、注意力计算，再把结果变成下一个 token。

同样一条数学式子：

`Y = X × W`

X 是输入，W 是模型权重，Y 是结果。写下来只有一个乘号，落到 GPU 上却要决定很多事：每批处理多少行、矩阵切成多大的块、哪些数据先放进片上小容量的快速存储、多少线程一起干、什么时候等待前面的工作完成。

**后端就是负责把这些运算安排到某类硬件上的实现。** 数学任务一样，具体程序可以很不一样。

这次测试里的几个名字，分别处在不同位置：

| 名字 | 在这次测试中做什么 |
| :--- | :--- |
| Lemonade | 提供本地 AI 服务、管理模型和运行配置，调用下面的推理引擎 |
| llama.cpp | 加载模型、组织推理过程，通过不同后端执行运算 |
| ROCm／HIP 路径 | 利用 AMD 计算软件栈运行 GPU 程序；HIP 是其中的编程接口 |
| Vulkan 路径 | 利用跨厂商的图形与计算接口，提交 GPU 计算任务 |

所以，Lemonade 和 llama.cpp 不是这里互相比赛的两个选手。Lemonade 包在外面，这次让里面的 llama.cpp 换两条执行路径。

Vulkan 也不只会画三角形。它能运行计算着色器，也就是在 GPU 上执行通用计算的程序。图形接口出身，并不妨碍它做模型需要的乘法。

问题就变得具体了：**llama.cpp 为这个模型、这种精度、这张显卡写的两套实现，哪套更合适？**

比如，量化模型把权重压成低比特数值，省显存、少搬数据，但计算时还要按量化格式读取和还原数值。可以先展开到中间缓冲区再算，也可以边读边解码，把几道操作合在一起。不同安排，会改变临时数据量、显存访问次数和并行效率。

这类差异，足以让同一张卡跑出不同速度。某条路径在大矩阵上做得好，未必在很小的一批输入上也占优势；某种量化格式优化得充分，换一种格式也可能重新洗牌。

从机制上看，算子的实现、量化处理、内存访问和驱动都有可能影响结果。原评测没有逐项分析这些成本，我们还不能替它认定是哪一处造成了差距。不过，“自家的软件就该自动最快”这个直觉，已经不够用了。**厂商提供计算能力，软件还得把眼前这份工作安排好。**

◆ 第三章：读题和答题，不是同一种负载

━━━━━━━━━━━━━━━━━━━━

模型处理输入和生成答案，是两种不同的工作。

你输入一段已经写好的代码，让模型找错误。代码里的 token 都已知，可以成批送入模型，建立后面生成需要的状态。这叫 **预填充（prefill）** 。

开始回答以后，下一个 token 要接着前面已经生成的内容往下算。这叫 **解码（decode）** 。

还是看 `Y = X × W`。处理一批已知输入时，X 可以有很多行。同一块 W 读进来，可以给这批输入反复使用；批量足够大时，更容易发挥 GPU 并行做乘法的能力。

单人聊天、一次生成一个 token 时，X 往往小得多。对于稠密模型，不少权重仍要参与这一轮运算，但同一批权重能服务的输入少了。此时，即使 GPU 还有乘法能力闲着，也可能要等数据从显存送过来。上下文较长时，读取注意力缓存还会增加负担。

**一边是拿到一批数据后集中算，一边是不断取数据、算一小步、再继续。** 它们都用了矩阵乘法，最值得优化的地方却可能不同。

这也解释了为什么不能只看显卡宣传页上的算力。峰值算力描述在适合的精度、指令和负载下，一秒最多能做多少运算；聊天时是否能喂满这些计算单元，还取决于模型和软件的安排。

当然，预填充也需要搬数据，解码也需要计算。多人请求合成批次后，解码对权重的复用又会增加。这里说的是常见的工作差异，不是给两个阶段各贴一张永远不变的标签。

再回来看那组“出字速度与首字等待各有胜负”的结果，就没那么奇怪了。一条后端可能更擅长处理批量输入，另一条可能更擅长后续的小批量生成。**这是解释现象的可能方向，还不是这次评测已经查明的原因。**

尤其要注意，图里的“首 token 时间”并不等于纯预填充时间。用户发出请求后，还可能经过服务层调度、输入准备等步骤；缓存是否复用、模型是否已经加载，也会改变等待。要定位到预填充本身，得把这些时间单独量出来。

💡 先开口，还是先说完？

设首 token 等待时间为 T，后续平均生成速度为 r，整段回答有 N 个 token。粗略估计：

`回答总用时 ≈ T + (N − 1) / r`

这里忽略网络显示等额外开销，把后续速度近似看成稳定值。

假设 A 起步更快，B 后续生成更快。那么回答很短时，A 省下的等待可能更重要；回答越来越长，B 每一步积累的优势才有机会把起步损失追回来。

对聊天来说，早一点看到回应会影响体感；让模型生成一大段代码，最后什么时候结束同样重要。若大部分等待都花在读长输入上，仅提高输出速度也救不了整个请求。

所以，看到“每秒多少 token”，还得接着问一句：**这是读输入的速度，还是写输出的速度？我这次主要在等哪一段？**

────────────────────

把首内容等待和后续生成分别记录下来，才能知道换后端究竟改变了哪段体验。

◆ 第四章：回到家里的 9070 XT，准备怎么测

━━━━━━━━━━━━━━━━━━━━

这篇评测给我的直接收获，是本地跑模型时，后端值得自己换一次试试。通用接口不等于一定慢，专用计算栈也不等于每项负载都自动占优。

但原测跑在 Linux，我家是 Windows；R9700 和 RX 9070 XT 也不是同一张卡。这些结果提供了一个值得验证的问题，家里的胜负还得家里的机器来回答。

我准备先选一份能连同上下文缓存、工作缓冲一起装进 16GB 显存的 GGUF 模型，优先看 Qwen3-14B 的合适量化版本。两边用同一份文件，固定模型校验值、输入、上下文长度、采样设置和输出长度，尽量从同一份 llama.cpp 源码构建 HIP 与 Vulkan 后端。

先让权重全部留在 GPU，确认选中的是 9070 XT。这次暂时不把 Strata 的 CPU 专家计算混进来，否则一边换后端、一边换内存分工，很难知道差异从哪里来。

测试不用铺很大。选短提示和较长提示两档，关掉前缀缓存、MTP 等投机生成，暖机后交错跑两种后端，每组至少重复三次。记录首 token 等待、输入处理速度、输出生成速度和总用时，也记录实际生成了多少 token。

如果现成软件给两条后端打包了不同引擎版本，就把版本差异写下来。这仍然能回答“我现在装哪套更好用”，只是还不能把全部差异都归到后端接口上。

目前还没有这台机器的对比结果。先把要测的事情缩到这一件：**同一个模型在同一张卡上，换掉执行路径后，等待究竟少在哪一段。**
