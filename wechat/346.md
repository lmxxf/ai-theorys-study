◆ 第一章：老熟人都住哪儿——`vendor/` 子模块与 `TileKernels` 算子包

━━━━━━━━━━━━━━━━━━━━

很多人进了 `DeepInfer` 仓库第一个疑问是：里面为什么挂了这么多算子库？之前听说过的那些开源库，在这套框架里算什么角色？

其实只要想明白一件事，这份列表就根本不用死记硬背：**`DeepInfer` 的首要任务是让 `DeepSeek-V4.1-Flash` 跑起来；而 `V4.1-Flash` 身上改过的每一处独门架构，都必须有对应的底层算子去执行——把这几个库拼在一起，刚好就是跑通一整台 `V4.1-Flash` 前向传播的完整零件表，少一个都转不起来。**

我们可以顺着一个词元流过 `V4.1-Flash` 网络的顺序直接对号入座：
- **进层先过 4 流残差通道** （流形超连接 mHC）→ 需要 `TileKernels` 里的 `mhc` 算子；
- **在第 2 层和第 15 层查 196B 的词组表** （Engram）→ 需要 `DeepEP` 跨卡拉取行向量，配合 `TileKernels` 里的 `engram` 算子做门控；
- **进注意力前，闪电索引器从历史里挑 512 个位置** （DSA Indexer）→ 需要 `DeepSelect` 算极速 TopK；
- **算跨层共享的压缩稀疏注意力与滑动窗口** （CSA2 + SWA）→ 需要 `FlashMLA`；
- **进 MoE 专家层：选专家、跨卡分发、算低精度矩阵乘与激活量化、跨卡汇总** → 依次对应 `TileKernels`（路由与 SwiGLU 量化融合）、`DeepEP`（全对全通信）和 `DeepGEMM`（FP8/MXFP4 矩阵乘与 Mega MoE）；
- **最后词表采样与 DSpark 投机猜词** → 需要 `DeepSelect` 与引擎内置的 `tilelang_ops`。

搞清楚了“为什么必须有它们”，再看它们在仓库里是怎么摆放的，以及**每个仓库到底是用什么编程语言和工具链写出来的**。

我们先用一张表把本次涉及的 9 个核心仓库（含昇腾分仓）的语言环境与编译工具链摆在一起：

| 仓库名称 | 挂载位置 / 引入方式 | 核心编程语言 | 编译器与底层运行环境 |
|---|---|---|---|
| `DeepInfer`（引擎主仓） | 主仓库根目录 | Python 3.12 + C++20 + TileLang | GCC ≥ 13.0、`pybind11 3.0`，PyTorch 2.13（`CUDA 13.2` 或 `torch-npu` + `CANN 9.2`） |
| `deepseek-recipe` | 独立仓库 / `pip` 包 | Rust（Edition 2024）+ Python 绑定 | Rust `1.97.1` 工具链、`PyO3`、OpenCV（图像预处理）、`axum`（HTTP 服务） |
| `FlashMLA` | `vendor/FlashMLA` | CUDA C++ + 昇腾 Ascend C | 英伟达 `nvcc`（CuTe 模板 + PTX）与华为昇腾 `CANN 9.2` 毕昇编译器（`bisheng`）同仓 |
| `DeepGEMM` | `vendor/DeepGEMM` | CUDA C++20 + CuTe / PTX | 英伟达 `nvcc`（CUDA 13.1+），针对 SM90 / SM100 的 TMA 与 `tcgen05` 指令运行时 JIT 编译 |
| `DeepGEMM-Ascend` | `vendor/DeepGEMM-Ascend` | Ascend C + C++20 + TileLang | 华为 `CANN 9.2`（`bisheng` + `ld.lld`），封装昇腾矩阵乘加原语（MAD）与协程流水线 |
| `DeepEP` | `vendor/DeepEP` | CUDA C++ + PTX | 英伟达 `nvcc` + `NVSHMEM` / GPUDirect RDMA（IBGDA），负责跨卡与跨机低延迟通信 |
| `DeepEP-Ascend` | `vendor/DeepEP-Ascend` | Ascend C + C++20 | 华为 `bisheng` + `DeepJIT` 运行时编译，调用 `HCCL/HCOMM`、`UBMEM` 与 `URMA` 通道 |
| `DeepSelect` | `vendor/DeepSelect` | C++20 + CUDA（`.cu`）+ Ascend C（`.asc`） | 自研跨平台头文件库 `kerutils`（统一封装 SM80/90/100 与昇腾内联指令），双后端同仓编译 |
| `TileKernels` | `pip` 包（`tile-kernels==2.1.0`） | Python 3.12 + `TileLang 0.1.15` DSL | 领域专用语言（DSL），不手写 C++，由 TileLang 编译器自动生成 CUDA 或昇腾机器码 |

顺着这张表点进源码，最直观的切入点就是 `DeepInfer` 仓库里的子模块构建脚本 `scripts/build_vendor.sh`：

```bash
case "${DEEPINFER_ACCELERATOR:-nvidia}" in
  nvidia)
    BUILD_TARGET=CUDA
    PACKAGES=(DeepSelect FlashMLA DeepEP DeepGEMM)
    INSTALL=(deep_select flash_mla deep_ep deep_gemm)
    ;;
  ascend)
    BUILD_TARGET=ASCEND
    PACKAGES=(DeepSelect FlashMLA DeepEP-Ascend DeepGEMM-Ascend)
    INSTALL=(deep_select flash_mla deep_ep deep_gemm)
    ;;
esac
```

短短十几行脚本，把 DeepSeek 是怎么在推理栈里同时推进英伟达与华为昇腾 950（Ascend 950）双平台适配展示得很清楚—— **四类核心算子与通信依赖都提供了对应的昇腾实现，根据底层耦合程度分成了“独立建仓”和“同仓双后端”两种组织形式，最终安装出来的 Python 包名（`INSTALL` 数组）在两个平台上完全一致** （当然，目前两个后端的细节特性尚未百分之百对齐，例如 `FlashMLA` 的融合归一化旋转量化核、`DeepEP-Ascend` 的 CPU 驻留 Engram 与图捕获、以及 `DeepInfer` 的批次无关确定性采样，当前仍标为仅限英伟达或实验性支持）。

具体分为两大块：

────────────────────

**第一块：`vendor/` 目录下的 6 个 Git 子模块** （C++20 / CUDA / Ascend C 重型武器库）

打开 `vendor/` 文件夹，里面共登记了 6 个外部算子与通信子模块。执行 `./build.sh` 编译时，`scripts/build_vendor.sh` 会先初始化子模块，再根据环境变量 `DEEPINFER_ACCELERATOR`（`nvidia` 或 `ascend`）挑选对应平台的 4 个包在本地打成 wheel 安装：

1.**2025 年 2 月开源周发布的三大基础库**：
- `vendor/FlashMLA`：负责多头潜在注意力（Multi-head Latent Attention，MLA）与第二代压缩稀疏注意力（Compressed Sparse Attention 2，CSA2）的计算内核。它是用 **CUDA C++ 与昇腾 Ascend C** 写的，主仓库内部已同时包含英伟达与华为昇腾两套代码分支。
- `vendor/DeepGEMM`：负责低精度矩阵乘法。我们在 176 期（ https://mp.weixin.qq.com/s/e1GKi53IociZnfHX1Ie9_w ）讲过它在 GPU 编程五层塔里的位置与数据中心卡指令绑定，在 240 期（ https://mp.weixin.qq.com/s/7ROESDoxhexsMWL9HVz8wA ）讲过怎么把分块缩放反量化融进矩阵乘。它完全不用 Python DSL，而是用 **原生 CUDA C++20 + 英伟达 CuTe 模板 + 内联 PTX 汇编** 手写而成；在 V4.1 里，它不仅算 8 比特浮点（FP8）和微缩放 4 比特浮点（MXFP4）矩阵乘，还承担了把专家层揉在一起算的 `Mega MoE` 融合算子。
- `vendor/DeepEP`：负责混合专家（Mixture of Experts，MoE）跨卡专家并行（Expert Parallelism，EP）的全对全（All-to-All）分发与汇总通信，底层用 **CUDA C++ 配合 NVSHMEM 和 GPUDirect RDMA** 直接操纵网卡与显存。

2.**2026 年 9 月 30 日为华为昇腾 950 平行设立的两个专属子模块**：
- `vendor/DeepGEMM-Ascend` 与 `vendor/DeepEP-Ascend`。这是整套代码里硬件味最浓的地方——它们是用 **C++20 与华为昇腾 Ascend C** （`.asc` 内核文件，要求 C++20 支持 `std::format`）编写的，编译时调用华为 `CANN 9.2` 工具包里的 **毕昇编译器** （`bin/bisheng` 与 `bin/ld.lld`）。
- 其中 `DeepGEMM-Ascend` 对昇腾芯片的矩阵乘加原语（Matrix Multiply-Add，MAD）做了一层轻量级 C++ 抽象，把繁琐的分形矩阵布局（Fractal Layouts）、地址对齐和基于协程的流水线（Coroutine-based pipelining）藏在底下，对外暴露出与英伟达版一模一样的 `deep_gemm` Python 包名；
- 而 `DeepEP-Ascend` 则在华为 **Ascend 950DT** （A5，整机型号 Atlas 850E）超节点上调用 `HCCL/HCOMM`、`UBMEM` 与 `URMA` 远端内存通道，并通过 DeepSeek 另一个自研小工具 **`DeepJIT`** （`deepseek-ai/DeepJIT`）在首次调用时把 Ascend C 算子即时编译成机器码。在官方指定的 Ascend 950DT 与测试网络配置下，8 到 32 卡专家并行时其 FP8 分发（Dispatch）带宽测得 **335 到 375 GB/s** （达到物理有效负载带宽上限的 90% 至 95%），128 卡下也能保持 **313 到 320 GB/s**。

3.**2026 年 9 月 10 日随 V4.1 周期新放出的 `vendor/DeepSelect`**：
- 这是专门为稀疏注意力（DeepSeek Sparse Attention，DSA）里的闪电索引器（Lightning Indexer，我们在 242 期 https://mp.weixin.qq.com/s/iRTyUmab0SXS3HnzxkcAGw 手搓过它的算子逻辑）和词表采样器定制的 TopK 算子库。
- 为什么放着 PyTorch 原生的 `torch.topk` 不用，非要单写一个仓库？因为在 V4 与 V4.1 里，索引器每一步都要从几万乃至几十万个历史位置里挑出得分最高的 `topk=512` 个槽位，而且**只需要知道挑中了哪 512 个下标，根本不需要对这 512 个数做严格排序，也不需要返回具体的浮点数值**。
- 打开 `DeepSelect/csrc/` 目录，它的语言结构非常讲究：底下垫着一个自研的跨平台 C++20 头文件库 `3rdparty/kerutils/`（同时封装了英伟达 SM80/SM90/SM100 的 `.cuh` 内联指令和昇腾的 `kerutils_for_ascend_npu.h`），上面并列着 `cuda_kernels/`（预生成了几十个 `.cu` 模板实例）和 `ascend_kernels/kernel.asc`（昇腾内核，甚至在 `setup.py` 里专门加了一行 `-mllvm -cce-aicore-dcpreload-args=false` 编译参数来绕开一处昇腾硬件预取缺陷），官方测试相比原生 `torch.topk` 可实现 **2 到 20 倍** 的加速。

────────────────────

**第二块：纯 Python + `TileLang` 编写的 `TileKernels` 与引擎内置 `tilelang_ops/`**

除了上面 6 个用 C++20 / CUDA / Ascend C 手搓的重型子模块，大模型里还有几十个细碎但极其卡显存带宽的算子。在这些算子上，DeepSeek 没有再去手写两套底层 C++，而是全部采用 **Python 3.12 + 领域专用语言 `TileLang 0.1.15`** 编写，收拢在两个地方：

一是通过 `requirements.txt` 直接 `pip` 引入的独立开源仓库 **`TileKernels`** （`https://github.com/deepseek-ai/TileKernels`，包名 `tile-kernels==2.1.0`，9 月 30 日刚加上昇腾 950 后端）。为什么同样是 DeepSeek 自家的独立算子仓库，前面那 6 个要挂进 `vendor/` 子模块按平台构建，而 `TileKernels` 却能直接走 `pip` 安装？因为这个仓库 **本身全是纯 Python 源码** （真正的底层机器码是由 `TileLang` 在运行时即时编译生成的），自身无需分发预编译的 C++ 扩展，打成纯 Python 包直接装最省事。打开它的目录树，你会发现每个子文件夹底下都成对躺着 `*_cuda.py` 和 `*_asc.py` 两份实现（例如 `sinkhorn_cuda.py` 与 `sinkhorn_asc.py`），在运行时自动识别当前硬件平台（如检测昇腾设备节点）二选一编译，里面全是老熟人：

- `tile_kernels/engram/`：我们在 49 期（ https://mp.weixin.qq.com/s/4DqR-WYNf2ww61MDJVAFZw ）讲过的 Engram 词组记忆表，包含多头哈希计算、融合归一化与上下文门控算子；
- `tile_kernels/mhc/`：我们在 244 期（ https://mp.weixin.qq.com/s/IpmdCFVbfZwVwmQno815LA ）讲过的流形超连接（Manifold Hyper-Connections，mHC），包含 Sinkhorn 矩阵双随机归一化与残差混合算子；
- `tile_kernels/moe/` 与 `tile_kernels/quant/`：我们在 246 期（ https://mp.weixin.qq.com/s/EwUO9tVfrpCrcwsyPI42uw ）、247 期（ https://mp.weixin.qq.com/s/jjYk4lV-qhZpqAYge0tx6A ）和 239 期（ https://mp.weixin.qq.com/s/OozibTbTLlDiBhh57NOv0A ）分别写过的 MoE 路由门控、SwiGLU 激活函数与逐词元/逐块 FP8/FP4 量化融合算子。

二是直接写在 `DeepInfer` 引擎内部的 `deepinfer/model_executor/layers/tilelang_ops/` 目录。点进去可以看到结构极其工整的 `cuda/` 和 `asc/` 两个平行文件夹，各自装着近 30 个算子脚本（涵盖分页 KV 缓存读写、投机解码重排、采样融合、结构化输出掩码等），在运行时根据当前硬件平台自动二选一加载。

💡 解开一个老疑惑：权重仓库自带的 `inference/kernel.py` 与生产级引擎到底是什么关系？

以前 DeepSeek 发布模型权重（如 V4 和 V4.1）时，Hugging Face 权重仓库里都会附带一个几百行的 `inference/` 文件夹（里面是 `model.py` 和一个用 `TileLang` 写的单文件 `kernel.py`）。

很多人曾经误以为那个 `inference/` 就是 DeepSeek 自己跑模型的推理程序，甚至奇怪：“为什么官方脚本里只见 `TileLang`，压根没调用大名鼎鼎的 `DeepGEMM`？”

今天对照 `DeepInfer` 的源码，这层窗户纸就彻底捅破了：
- 权重仓库自带的那个 `inference/` 只是给同行看清数学逻辑的 **门口塑料样板间** ——没有连续批处理（Continuous Batching）、没有分页缓存管理，为了代码短平快可读，干脆把矩阵乘、稀疏注意力和超连接等函数全塞在一个 `kernel.py` 里交差。
- 而今天开源的 `DeepInfer` 才是机房里真刀真枪干活的 **重型机床**。在这台真机床里，**原生 CUDA C++ 手写的 `DeepGEMM` 与基于 `TileLang` 的 `TileKernels` 根本不是二选一的替代关系，而是同框分工的搭档。**

最直观的例子就在 `deepinfer/model_executor/models/v4_modules/mhc_ops.py`（流形超连接算子）开头的那几行导入代码里：

```python
from deep_gemm import tf32_hc_prenorm_gemm
from tile_kernels.mhc.expand_kernel import expand_to_mhc_fwd
from tile_kernels.mhc.pre_split_mixes_kernel import mhc_pre_split_mixes_fwd
from tile_kernels.mhc.sinkhorn_kernel import mhc_sinkhorn_fwd
```

你看，在同一个模块内部：
- **凡是重计算、吃矩阵单元的矩阵乘法** （如 FP8/MXFP4 专家矩阵乘，以及上面这行 `tf32_hc_prenorm_gemm` 分块归约矩阵乘），统统交给 C++/汇编级调优的 `DeepGEMM`；
- **凡是卡显存带宽、逻辑细碎、且需要同时跨越英伟达与华为昇腾双平台的非矩阵乘算子** （如 Sinkhorn 双随机归一化、残差分支展开与合并、Engram 哈希门控、SwiGLU 量化融合），则全部交给 9 月新开源的 `TileKernels`（以及专门负责极速 TopK 的新库 `DeepSelect`）。

这也顺带解释了为什么 DeepSeek 会在生产环境里重用 `TileLang`：重型矩阵乘和跨卡通信值得专门投入人力去维护 `DeepGEMM-Ascend` 和 `DeepEP-Ascend` 两个独立仓库；而剩下大几十个细碎融合算子如果也用 CUDA C++ 和昇腾 Ascend C 各手写一遍，工程维护成本会成倍膨胀。用 `TileLang` 封装成 `TileKernels`，在 9 月 30 日补齐昇腾后端后，同一套 Python 接口就能在英伟达 SM100 和昇腾 950 上同时跑出接近硬件带宽上限的性能。

至于开源出来的算子库和 DeepSeek 内部自用版差多少，官方也在 `doc/inference_deployment_qa.md` 里交了底：开源的 `DeepGEMM`、`FlashMLA` 等与内部版本大体相同，在索引器和 Mega 系列上有少许差异，其中 `FlashMLA` 缺少一处手调的底层汇编（Streaming ASSembly，SASS）优化，导致单个解码注意力算子慢 **5% 到 10%** ，但在官方对应的端到端整网对比下，整体性能差距 **最多不超过 5%** 。

◆ 第二章：首次公开的引擎本体——`DeepInfer` 往 vLLM 里塞了哪些真家伙？

━━━━━━━━━━━━━━━━━━━━

在仓库的致谢一栏里，DeepSeek 写得很实在：`DeepInfer` 最初主要基于 `vLLM` 构建，并吸收了 `SGLang` 与 `TensorRT-LLM` 的设计思路。从源码结构能直接看出，围绕 `DeepSeek-V4.1-Flash` 的特殊架构，这套引擎做了大量专门定制。

从语言环境上看，`DeepInfer` 主仓采用的是 **Python 3.12 与 C++20** （配 PyTorch 2.13，要求 GCC ≥ 13.0，通过 `pybind11 3.0.1` 编译为 `deepinfer._C` 扩展）的双层架构：吃 CPU 延迟的批次调度器、序列状态管理、输入元数据拼装和图计时器（`csrc/engine/` 与 `csrc/graph_timer/`）全部用 C++20 编写，在编译时通过 `CUDAExtension`（CUDA 13.2）或华为 `torch_npu` 的 `NpuExtension`（CANN 9.2）分别链接到底层硬件；而模型的层间拓扑、权重加载和分布式通信编排则写在 `deepinfer/` 的 Python 目录里。

打开 `csrc/` 和 `deepinfer/` 两个目录，能看到四处专门为 V4.1 深度定制的核心实现：

────────────────────

**1. 对比我们在 308 期（ https://mp.weixin.qq.com/s/Rsx8_ygHyXbN6JI1QTNxMw ）读过的权重仓参考脚本：线上真正的 `engram.py` 与 `yoco.py` 是怎么写的？**

前文 308 期分析 `V4.1-Flash` 架构时，我们读的是随模型权重附带的简化参考脚本（`inference/engram.py` 与 `inference/model.py`），当时还在感慨“不知道 DeepSeek 线上机房内部实际跑的是哪一套”。这次在 `deepinfer/model_executor/models/v4_modules/` 目录下，终于能看到生产级代码的真身，而且可以看到 **`TileLang` 算子在生产链路里同样挑了大梁**。

**第一处是 196B 的 Engram 词组表，生产版到底比默认 Demo 高级在哪儿？**
之前权重仓库自带的 Demo 程序为了代码简单，做法非常粗暴：直接把 196B 的大表当成普通参数塞进 GPU 显存，等前向传播走到第 2 层和第 15 层时，现场停下来查表、再调一次阻塞式的 `all_reduce` 把所有卡的结果加起来——不仅吃光显存，GPU 还得停下来干等跨卡通信。

而打开 `DeepInfer` 的 `deepseek.py` 和 `v4_modules/engram.py`，生产级实现（以英伟达路径为例）做了三处脱胎换骨的升级：
- **一是进第 0 层之前就提前发起异步预取，让搬运尽量与前面的计算重叠**：前文 308 期我们读技术报告时，报告提过一句“靠确定性寻址在后台提前预取”。这次看 `deepseek.py` 第 180 至 190 行，代码写得明明白白——因为查表只依赖输入的词元 ID、不依赖中间层算出来的结果，引擎在**还没进入 40 层 `for` 循环之前**，就先用 `TileLang` 算子一口气把第 2 层和第 15 层要查的哈希地址全算出来，立刻调用 `engram_runtime.fetch(hashes)` 发起跨卡远端内存异步拉取，拿回两个延迟回调钩子（`embed_hook`），等真正走到第 2 层和第 15 层时再执行钩子消费结果；
- **二是默认开启 CPU RDMA 存储，写入通信缓冲区后当场释放原参数张量**：在 `deepseek.py` 第 473 行与 `userbuffer.py` 里可以看到，Engram 参数默认加载在 `cpu` 内存上（`use_cpu_rdma_storage` 默认开启），初始化时将权重写入 `DeepEP` 管理的 `EngramBuffer` 存储区后，当场调用 `release_storage()` 释放原参数张量；
- **三是 FP8 压缩传表加原地融合门控**：生产版把词组表压成 FP8 存储，并将缩放因子每 4 个打包进一个 32 位整数传输；数据拉回来后，直接调用 `TileKernels` 里的 `engram_gate_fwd` 原地（`inplace=True`）一次性算完归一化、门控打分和残差相加（同时自动跳过图像词元），省去了 Demo 里好几次中间张量的显存读写。

**第二处是滑动窗口有界回放（SWA Bounded Replay）在代码里怎么切。**
先回忆一下前文 308 期第四章讲过的核心背景：**为什么会需要“回放”这件事？**
因为在 DeepSeek 的线上推理系统里，两种缓存的寿命是完全不同的——长上下文的 **CSA2 全局块级缓存** 会写进 3FS 固态硬盘保留好几天；而 **滑动窗口缓存** （Sliding Window Attention，SWA，每层只看最近 128 个词元）只在活跃会话的几分钟内有用，从来不进持久化磁盘，过几分钟就会被内存回收掉。

当用户隔了一会儿发来下一轮对话时，历史的 CSA2 全局缓存直接从磁盘加载回来了，但那份 SWA 窗口缓存已经没了。由于滑动窗口的依赖会跨层传递（这一层的 128 个词元依赖上一层各自的 128 个词元），如果要把 20 层网络的 SWA 窗口恢复得一丝不差，理论上得把历史末尾 `20 × 128 = 2,560` 个词元重新算一遍。为了省掉这笔冤枉钱，DeepSeek 设计了 **有界回放** ——直接把窗口截断在重算片段内部，每次只重算最后 **128 个词元** 来近似重建 SWA 窗口。

之前权重仓库自带的 Demo 推理程序是单轮一次性从头算到尾、算完就退出的脚本，自然不存在“SWA 几分钟后被回收、又从磁盘加载 CSA2 缓存重建上下文”的场景；而在这次开源的 `DeepInfer` 里，这套机制在两个地方真正落地成了代码：

- **一是历史 SWA 缓存被回收后的前缀回退重算** （Encoder SWA bounded replay）：当下一轮请求从 3FS 磁盘命中了长度为 `L1` 的 CSA2 块级缓存，却发现内存里对应的前 20 层 SWA 缓存已经被回收时，引擎直接把命中位置往回退一个块（`L1 - 128`），将原样复用的磁盘 CSA2 缓存与重新计算的末尾 128 个词元（连同未缓存的新后缀）拼在一起跑前向，只花 128 个词元的常数级回放开销就把丢掉的 SWA 窗口补齐；
- **二是长文预填充进入后 20 层解码器时的物理截断** （Decoder SWA bounded replay）：在 `yoco.py` 与 `csrc/engine/input_metadata/prepare_tensor_input_v4.cpp` 里，因为后 20 层解码器共用编码器末层隐藏状态投出的全局缓存，后半段需要逐层补齐的只有各自的 SWA 窗口。当开启 `DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE=compact` 并配合示例配置 `DEEPINFER_YOCO_PREFILL_KEEP_TOKENS=140` 时，引擎在跨入第 21 层的边界处调用 `yoco_boundary_compact`（底层调用 `tilelang_ops/gather.py` 里的 `TileLang` 收集算子），将进入后半段主干计算的序列截短为只保留末尾 **140 个词元** （覆盖 128 的滑动窗口与最大投机回退余量）。

这样一来，长提示词在预填充跨入后 20 层时只需计算尾部一百多个词元，直接把总预填充计算量砍掉了将近一半。仓库里的 `examples/yoco/yoco_equiv.py` 则提供了两级验证工具，用来在给定配置与固定轨迹下核对“物理截断（compact）”与“用注意力掩码模拟截断（mask）”在对数概率（logprob）和草稿头置信度上逐位等价。

────────────────────

**2. 给 DSpark 投机解码装上“算力精算师”：`csrc/engine/mtp_varlen.hpp` 与 `models/mtp/dflash.py`**

我们在 236 期（ https://mp.weixin.qq.com/s/fQc0hRxEIZxkPzGTDhj78g ）讲过 DeepSeek 与北大联合提出的 `DSpark` 投机解码：挂一个轻量级的 `DFlash` 草稿头（代码在 `deepinfer/model_executor/models/mtp/dflash.py`），每一步一口气先猜出后面 5 个候选词元（默认 `DEEPINFER_USE_NEXTN_DECODE=5`），再交给主模型批量验证。

但在真实的线上大并发场景里，投机解码有个很现实的痛点：**当并发数太高、GPU 算力已经跑满时，盲目多猜几个词送去给主模型“验证”的算力损耗，反而会大于猜中带来的收益。**

比如有些请求正写到高熵转折点，小弟猜的第 2 个词元大概率就错了，可如果还是死板地固定把 5 个草稿词元全塞进主模型验证，后面那 3 个陪跑词元纯属白烧主模型的算力。

为了解决这个损耗，这次开源的 `csrc/engine/mtp_varlen.hpp` 和 `tilelang_ops/schedule_mtp_varlen.py` 给投机解码加了一套 **基于置信度的变长验证机制**：
小弟每步虽然还是先猜 5 个词元，但同时会用一个置信度头（Confidence Head）预估每个位置的接受率。在送去给主模型验证之前，调度器结合实测的硬件吞吐曲线与累积接受率分配总预算，由 GPU 上的 `TileLang` 算子为每条请求选出边际收益最高的候选前缀长度—— **把后面把握太低的陪跑词元截掉，不送去验证了。**

我们从官方 `doc/inference_deployment_qa.md` 的 64 路专家并行（EP64/DP64）测试表里挑出低、中、高三档并发一看就明白了：

| 单卡并发请求数 | 每步送去验证的词数（固定 vs 动态） | 最终成功猜中的词数（固定 vs 动态） | 动态调度的估算吞吐变化 |
|---:|---|---|---:|
| 16（低并发，算力闲置） | 固定 5 个 → 动态 **4.44 个** | 3.32 个 → 3.24 个 | **-1.5%** |
| **60 线上主力工况** | 固定 5 个 → 动态 **3.58 个** | 3.30 个 → 3.21 个 | **+5.4%** |
| 96（高并发，算力吃紧） | 固定 5 个 → 动态 **3.24 个** | 3.30 个 → 3.15 个 | **+11.0%** |

这张简表把账算得非常清楚：
- 并发只有 16 的时候，GPU 算力本来就闲着，多验几个词根本不费事，砍短了反而少猜中一点，所以微亏 `-1.5%`；
- 但到了单卡 60 乃至 96 并发的高负载工况下，GPU 算力已经饱和，“验证”本身成了沉重的负担。这时动态机制把每步送去验证的平均草稿词数从 5 个砍到了 **3.24 到 3.58 个** （少验了约三成草稿词），而最终真正猜中的词数几乎没少（60 并发下只从 `3.30` 变成 `3.21`，96 并发下为 `3.15`），估算吞吐直接提升了 **5.4% 到 11.0%** 。

────────────────────

**3. 零开销异步调度与专家动态洗牌：`csrc/engine/zos.cpp` 与 `model_executor/eplb/`**

再看引擎底座的两个核心目录：

一个是 `csrc/engine/zos.cpp`，全称 **零开销批次调度器** （Zero-Overhead Scheduler，ZOS）。常规推理框架每跑一步，都要走“CPU 排班 → GPU 前向与采样 → GPU 同步回 CPU → CPU 后处理”，在 CPU 忙活后处理和排下一步班的那几毫秒里，昂贵的 GPU 只能干等着。`zos.cpp` 借鉴了 SGLang 和 NanoFlow 的异步重叠设计：当 GPU 正在算第 `N` 步的前向和采样时，CPU 在后台同时把第 `N+1` 步的排班、算子下发以及第 `N-1` 步的输出后处理全部干完，消除这类因同步等待 CPU 排班与后处理带来的空转气泡。

另一个是 `deepinfer/model_executor/eplb/`（包含 `policy.py` 与 `shuffle.py`），即 **专家并行负载均衡** （Expert-Parallel Load Balancer，EPLB）。MoE 模型最怕冷热不均——某几个热门专家被挤爆，其他卡上的冷门专家闲死。`eplb/` 的解法是：每张 GPU 除了托管自己份内的常驻专家，还额外预留几个“冗余专家槽位”（预填充阶段每卡默认留 4 个冗余槽，每 100 步统计一次热度，每 1,000 步重新分配一次；解码阶段在 64 卡并行下每卡留 1 个冗余槽、凑齐每卡 7 个路由专家，每 1,000 步统计，每 10,000 步重分）。一旦决定调整，直接通过 NVLink 对称内存（`symm_mem`）在卡间把热门专家的权重复制过去；在官方给出的几组实测中，最大卡与平均卡的词元负载比（`moe_lb`）约为 **`1.045` 到 `1.090`**。

────────────────────

**4. 批次无关推理与确定性采样：`tests/models/test_batch_invariant.py`**

在 README 的特性列表里，还有两组很多开发者平时不太留意、但对工程复现与强化学习很有用的功能（当前均限英伟达平台）：**批次无关推理** （Batch-invariant inference）与 **确定性采样** （Deterministic sampling）。

熟悉 GPU 编程的人都知道，浮点数加法不满足结合律（`(a + b) + c` 未必严格等于 `a + (b + c)`）。平时线上推理时，同一条用户请求，跟 3 条请求拼成一个批次算，和跟 50 条请求拼成一个批次算，底层矩阵乘和归约算子的切分顺序不同，算出来的对数概率（logprob）在小数点后几位就会出现微小漂移。

而在 `DeepInfer` 里，设置环境变量 `DEEPINFER_BATCH_INVARIANT=1` 即可保证不同批次组合下的模型前向结果一致；若进一步关闭变长投机（`DEEPINFER_ENABLE_MTP_VARLEN=0`）并向 `SamplingParams` 传入固定的采样种子（`seq_seed`），就能在相同输入与参数下得到完全一致的生成结果。这不仅方便线上复现问题与回归测试（如 `tests/models/test_batch_invariant.py`），也能减少强化学习采样与重算之间的数值漂移干扰。

◆ 第三章：另一个新仓库 `deepseek-recipe`——为什么非要用 Rust 重写一套消息编译器？

━━━━━━━━━━━━━━━━━━━━

看完 `DeepInfer`，再看这次同步开源的第二个仓库：`deepseek-ai/deepseek-recipe`。

很多媒体把它简单概括成“把 API 请求转成模型输入的小工具”。但只要读过我们的 295 期（ https://mp.weixin.qq.com/s/lCpYoqH_CwE5o52ECySMhQ ），就会明白这件事有多重要：**大模型从来没见过什么 JSON 格式的 `messages` 数组，它看到的永远是一串拼好了特殊控制符的一维词元编号** （Token ID）。

过去一年，不少团队自己在本地用开源框架部署模型时，常会遇到一个现象：明明加载的是同一个满血权重，为什么自己搭的 API 在跑复杂工具调用（Tool Call）或多轮代码智能体时，表现不如官方 API 稳定？

一个常见隐患就出在聊天模板（`chat_template`）与协议解析细节上——多拼了一个换行符、历史回合里的 `<think>` 思考块没按训练时的规矩剥离、或者工具定义写进提示词的格式差了一点，模型看到的词元序列就容易偏离后训练分布。

这次 DeepSeek 干脆把自家官方 API 线上真正跑的那套编解码库 `deepseek-recipe` 完整交了出来。

看一下它的语言环境配置（根目录 `Cargo.toml` 与 `rust-toolchain.toml`）：整个仓库是用 **Rust 2024 版** （Edition 2024，指定工具链版本 `1.97.1`）编写的高性能工作区，包含 6 个核心库/绑定包与 2 个演示程序（`encoding-decoding-demo` 与基于 `axum` 的 `server-rs`，另有工作区外的 `server-py`；多模态图像预处理直接绑定底层的 **OpenCV C++ 库** `deepseek-recipe-image/src/opencv.rs`，分词器基于 Hugging Face 的 Rust 版 `tokenizers`，并用 `aho-corasick` 做多模式匹配）；同时在 `deepseek-recipe-python/` 目录下通过 **`PyO3`** 封装了完整的 Python 原生扩展（`pip install deepseek-recipe` 即可在 Python 3.10+ 里直接调用，核心转换与解析逻辑直接由 Rust 原生扩展执行）。

打开它的 Rust 源码目录，里面解决了三个核心工程问题：

────────────────────

**1. `deepseek-recipe/src/protocol/`：一套内部表示，原生衔接三种主流 API 协议**

打开这个目录，里面并排放着三个协议转换模块：
- `openai/chat_completion/`：传统的 OpenAI 聊天补全接口（含 `prefix` 续写）；
- `openai/responses/`：OpenAI 新一代智能体专用的 Responses 接口，**支持 `apply_patch` 代码补丁工具、工具命名空间和客户端工具搜索** （client-executed tool search，V4.1 支持） **的工具定义与请求/响应转换**；
- `anthropic/messages/`：Anthropic Claude 的 Messages 接口，**支持延迟工具加载** （deferred tool loading，V4.1 支持） **等协议格式的转换**。

不管外部开发者用哪套协议连进来，Rust 转换器都会先把请求统一转成内部的 `Conversation` 结构，再走同一套 `deepseek-recipe-encoding/src/v4/`（内含 `dsv4.rs` 与 `dsv41.rs`）渲染成标准的模型提示词。

顺带一提，当请求未指定 `max_tokens` 时，代码会在检查上下文余量的同时提供三档默认输出上限（`resolve_max_tokens`）：不开启思考模式时默认 `8,192`，开启思考模式默认 `65,536`，开启思考模式且推理强度设为 `max` 档时默认为 **`131,072`**。

────────────────────

**2. `deepseek-recipe-encoding/`：从根上堵死“特殊词元注入”与分段并行分词**

如果用传统的“先把模板拼成一整个长字符串，再丢给分词器（Tokenizer）转成 ID”的做法，会同时撞上两个大坑：

第一个坑是 **控制符注入漏洞**。如果用户在提问里、或者网页抓取工具返回的文本里包含 `<｜User｜>`、`<｜image｜>` 或 `</think>` 这几个字符，普通分词器会直接把它们识别成特殊控制词元（Special Token），导致攻击者可以伪造对话角色，或者骗过解析器提前截断思考链。

`deepseek-recipe` 的做法非常干净：**在构建提示词的阶段，直接把系统合法插入的特殊词元及其精确位置记录下来，编码时直接映射为对应的特殊词元 ID；而用户输入、工具返回结果和工具参数里的文本，一律只允许使用基础词表** （Base Vocabulary） **编码。** 而在输出侧，当推理后端以词元 ID 流（`InferenceChunk::Tokens`）回传并挂载分词器时，解析器直接按特殊词元 ID 识别 `</think>` 与工具标签里的 `｜DSML｜`——哪怕模型在正文里用普通词元拼出了同名字符，也会被当作普通字面文本保留，不会误触发思考结束或工具调用。

第二个坑是 **超长上下文的分词耗时**。既然特殊词元的坐标与边界在拼装提示词时已经全部已知，而字节对编码（Byte-Pair Encoding，BPE）不会跨越特殊词元边界合并，`deepseek-recipe` 直接省掉了在普通正文里扫描匹配特殊词元的步骤，对特殊词元隔开的各个普通文本段做独立并行编码，最后按原顺序拼接，从而降低超长上下文请求的分词延迟。

────────────────────

**3. `deepseek-recipe/src/stream/`：把大模型吐出的词元实时转回给用户的流式状态机**

上面第 2 点管的是“进”（把用户请求编码喂给大模型），而 `src/stream/` 管的是“出”（把大模型生成的词元实时解析并推送给用户客户端）。

大模型在生成回答时，是一个词元一个词元往外吐的；而且模型在调用工具时，内部吐出的是 DeepSeek 自己训练用的 `｜DSML｜` 格式标签，外部客户端（比如 OpenAI 或 Claude 的 SDK）根本不认识，必须由服务端在半路实时拦截、转换成标准的 API 流式事件（SSE）发给用户。

在流式输出的过程中，经常出现一个 3 字节或 4 字节的 UTF-8 中文字符被劈在两个词元分块（Chunk）中间，或者半截 `｜DSML｜` 工具调用标签、一段几千字的代码参数分几十次才吐完。

为此，`src/stream/` 目录下的 `decoder.rs`、`output_parser.rs` 和 `processor.rs` 用 Rust 配合完成流式解析：遇到不完整的 UTF-8 字符时，先由 `decoder.rs` 缓冲相关词元攒齐后再送交解析器；解析器在跨思考、正文与工具参数阶段时采用 **增量式 KMP 字符串匹配算法** 识别分隔标记，哪怕当前分块正好停在半个标签中间，也会保留匹配进度，等下一个分块到达时接着往下比，无需回头重复扫描前面的文本。一旦从模型输出里解析出工具名称，就立刻向用户客户端推送事件，后面的长字符串参数边生成边按段做 JSON 转义流式下发，无需等模型把整个工具调用闭合就能让用户提前看到第一段参数。

◆ 第四章：故意留白的拼图——哪三样线上基建没进仓库，但交了底？

━━━━━━━━━━━━━━━━━━━━

把 `DeepInfer` 和 `deepseek-recipe` 的源码树翻完，我们最后再看一眼 `DeepInfer` 首页明确列出的“完整推理服务所需、但未包含在本次开源版本中”的三样东西：

1.全局 KV 缓存存储系统（`A KV cache system`）；
2.视觉 / 预填充 / 解码分离式部署框架（`VE/Prefill/Decode disaggregation`）；
3.跨数据并行副本的负载均衡器（`Load balancing across data-parallel replicas`）。

官方解释得很坦白：这三块代码与 DeepSeek 内部的机房基建深度耦合，暂时没法直接抽成通用源码；但在仓库自带的 `doc/inference_deployment_qa.md` 部署问答（以及 DeepSeek 官方知乎专栏同步发表的《DeepSeek V4.1 Flash 推理系统》技术文章）里，官方把这三块黑盒的线上真实运行参数全盘交了底。对于做系统架构的人来说，这几组数字的价值一点不比源码低：

────────────────────

**1. 96% 的线上缓存命中率，背后是 100 PiB 的 3FS 固态硬盘池**

我们在 107 期（ https://mp.weixin.qq.com/s/Np4jMAm5wUHNbPo6L8nReA ）讲过 DeepSeek 的 `DualPath` 存储搬运架构和早在 2025 年 2 月就已开源的 `3FS` 分布式文件系统，也在 241 期（ https://mp.weixin.qq.com/s/0fhN7wzofQDdW8hBaDLJwA ）算过为什么多轮智能体（Agent）时代九成以上的输入都是在重复发送历史上下文。

这次官方直接公布了 `V4.1-Flash` 线上服务的真实账单：
- **线上平均输入缓存命中率高达 96%** （命中的前缀词元直接复用缓存，无需重复做完整的预填充计算）。
- 在同一套线上统计下，如果不计缓存命中，每张 GPU 的输入吞吐为 **6 万词元/秒**；而在计入 96% 缓存命中后，每张 GPU 的输入吞吐直接冲到了 **150 万词元/秒** （整整 **25 倍**；此外在离线测试中，单张 GPU 不带缓存的预填充峰值吞吐约为 **8.6 万词元/秒** ），线上平均首字延迟（TTFT）压到了 **400 毫秒**，生成速度达 **230 词元/秒** （代码场景下达 **300 词元/秒** ）。

支撑起 96% 命中率的工程条件，是 **把缓存留够 72 小时以上**。
官方披露，他们的 `3FS` 分布式文件系统为 KV 缓存提供了约 **100 PiB** （约 11.3 万 TB） **的 SSD 存储池**，把智能体（Agent）流量的缓存保留时间（TTL）设为 **3 天**，把网页/App 聊天（Chatbot）流量的缓存保留时间设为 **7 天** （因为聊天流量的长尾复用极重，把 7 天缩短到 3 天就会损失聊天流量 0.5% 到 1% 的缓存命中率）。

具体到硬件配比上，官方给出的标准配置是：**每台 KV 缓存存储服务器插满 20 块 30.73 TB 的 NVMe SSD** （单机提供至少 40 GB/s 读取和 5 GB/s 写入吞吐），采用 `10+2` 纠删码（每次读取同时向组内 11 个存储节点发请求，任意 10 个返回即可解码还原，不怕单点网络抖动）；按共享存储池折算下来，**线上每 1 张推理 GPU 背后，平均对应着约 14.4 TB 逻辑容量的 SSD 缓存空间** （实际物理容量还要更大）。

当请求命中 3FS 上的块级缓存时，独立进程异步把数据从 3FS 拉进主机共享内存，再由引擎内的后台线程逐层与前向计算重叠搬进显存。而且因为 CUDA 原生的拷贝引擎（Copy Engine）在处理细碎的 KV 缓存块时效率不高，他们干脆用支持 GPU 直接远程内存访问（GPUDirect RDMA，GDR）的网卡直接走 PCIe 把数据灌进显存，一点不占 GPU 的计算核心（SM）。

────────────────────

💡 顺带复习前文 308 期的两份缓存：全局 KV 落硬盘，前 20 层窗口 KV 在内存暂存几分钟

先用两句话把 `V4.1-Flash` 里 **CSA2 全局缓存** 与 **128 滑动窗口缓存** （SWA KV）的关系唤醒：
- **生成与计算上**：两份缓存从词元诞生起就走两套独立的投影矩阵同时算出（不存在“滑出窗口后再把 SWA 约化成 CSA2”），数学形状都是 512 维；算注意力时，代码直接把 **本层的 128 条窗口 KV** 和 **闪电索引器挑出的 512 条全局 KV** 拼成 640 条，一起做一次 `softmax`。
- **共享与精度上**：全局 KV 是跨层共用的（整网只有 4 个产出入口），压成 4 比特（FP4）攒全篇历史，每词元仅占 **890 字节**；而 SWA 窗口 KV 在推理运行时是 **40 层全勤、每层各算各的一份**，保持 8 比特（MXFP8，每层每词元 528 字节），但每层只是个留有少量投机回退余量的 128 词元环形缓冲区，满了直接原地覆盖。

这跟前文 308 期我们讨论的逻辑完全一致：全局 KV 走长尾复用，所以落进 3FS 固态硬盘留好几天；而 SWA 窗口 KV 只在活跃会话的几分钟内有用，不进持久化硬盘，过了几分钟自然就扔了。这次的部署问答和 `cache_engine.py` 里的 `StateBlock` 只是给出了它在内存里的具体数字：

一轮对话结束时，引擎把 **后 20 层解码器的 SWA** 当场丢弃（下一轮预填充靠“有界回放”顺手重算末尾 128 个词元即可）；而 **前 20 层编码器的 SWA** 在跨越 128 词元整数倍边界时，会暂存一份 **约 1.41 MB** （`20 层 × 134 词元 × 528 字节`）的快照在推理服务器的主机内存里，下一轮请求如果派到了别的机器，直接走机房 **400G 虚拟局域网** （VLAN）跨机拉取。几秒内连续调工具时直接命中内存免重算；隔了几分钟内存快照被淘汰后，就靠 3FS 硬盘上的全局缓存加回退 128 词元的有界回放兜底。

────────────────────

**2. 从前文 107 期 DualPath 到今天的 EPD 三分离：架构减法如何改变了机房部署？**

老读者看到开头那张官方系统架构图，肯定会联想起前文 107 期讲过的 `DualPath` 论文。把今天这套 `V4.1-Flash` 线上系统跟当时的 `DualPath` 放在一起对比，能清楚看到两处变化：

**第一处变化，是从“PD 两分离”扩展成了“EPD 三分离”。**
以前纯文本模型只有预填充（Prefill）和解码（Decode）两拨机器；到了原生多模态的 `V4.1-Flash`，他们把不到 5 亿参数的视觉编码器（VE）也单独拎了出来，围绕最普通的商业货架硬件分成了三摊：
- **视觉编码器** （VE）：图片预处理和 ViT 编码是纯粹的单卡计算，不需要大集群通信，所以单独分出来部署在单卡实例上，官方甚至直接建议“用更便宜的 GPU 来跑 VE 就够了”；
- **预填充** （Prefill）：计算密集型，用普通的 **8 卡服务器**，只开 **2 到 8 路专家并行** （EP2–8 / DP2–8），只要显存装得下，并行度越小越好；
- **解码** （Decode）：访存带宽密集型，用 **64 到 128 卡的超节点**，开满 **64 到 128 路宽专家并行** （Wide-EP，EP64–128 / DP64–128），靠把几十张卡拼成一个大通信域来聚拢并发、减少每步搬运专家权重的显存流量。线上预填充与解码的 GPU 数量配比大约是 **`1:1`** （最小高效部署单元是 64 卡预填充配 64 卡解码），且解码端的组内负载均衡算法直接沿用了 `DualPath` 论文里的双维配平策略（同时配平请求数与总 KV 长度，把短请求派给总缓存长的卡、长请求派给总缓存短的卡）。

**第二处变化，是 V4.1 的 KV 极限压缩大幅减轻了存储 I/O 与跨机房传输压力。**
前文 107 期讲 `DualPath` 时，因为旧模型的 KV 缓存太大，单台预填充机器的存储网卡读取压力极重，专门设计了借道闲置解码机器帮忙读盘转发的第二通路。而 `V4.1-Flash` 把落盘 KV 砍到了上一代的 **八分之一** （全局 KV 每词元仅 890 字节），存储读取压力大幅减轻，公开的线上架构图里展示的也是从 3FS 直连预填充、算完传给解码、生成完再由解码写回 3FS 的直接路径。甚至因为 KV 体积大幅缩水，官方明确表示现在预填充和解码在技术上完全可以放在 **不同的数据中心机房** 里跑（每 8 张 GPU 预留约 400 Gbps 机房互联带宽即可；DeepSeek 自己的线上推理节点就部署在相邻的不同数据中心里，只是跨机房要额外考虑光纤被施工挖断这类可靠性风险）。

────────────────────

**3. 抛弃“前缀亲和路由”，拿二次方程给每一步算时间预算**

在很多开源推理集群里，路由器为了凑缓存命中率，必须把同一个用户的后续请求固定派给上一次算过它的那台机器（即前缀亲和路由，Prefix-affinity Routing），结果经常导致有的机器排长队、有的机器闲着。

而在 DeepSeek 的架构里，因为所有块级缓存都住在独立的 3FS 存储池里，连 1.41 MB 的 SWA 缓存都能走 400G 网络跨机拉取，**任何一台预填充机器都能命中任何历史前缀**。于是负载均衡器彻底解除了路由绑定，分两层做动态配平：
- **第一层在集群与机器之间** （按长度分四档分桶）：按请求总长度分成 `<16K / 16–64K / 64–256K / ≥256K` 四个分桶，根据上一轮各档位的算力消耗比例动态调整机器配额，谁有空闲配额就把请求派给谁；
- **第二层在一台多卡预填充机器内部** （拿二次方程按历史缓存长度给每张卡匀工作量）：这说的是进入 MoE 专家层之前的任务分派——在算注意力时，8 张卡上的注意力权重是一模一样的（各管各的请求队列），只是算完注意力后需要同步汇合进后面的跨卡 MoE 专家层。因为不同用户背着的旧历史缓存长度（`c`）不同，同样算几千个新词元（`q`），旧缓存长的算得慢、旧缓存短的算得快。为了让 8 张卡尽量同时算完注意力，调度器直接用一条预先拟合好的二次耗时方程 `cost(q, c)` 来分配工作量：新请求进门时，挑当前队列预估总耗时最短的卡塞进去；每一步开算时，给 8 张卡定下同一个以纳秒记账的时间预算（`compute_quota_limit`），每张卡从自己队列里依次取请求，遇到一顿吃不完的长请求就当场解二次方程反求出刚好用满剩余时间预算的新词元数 `q` 切出来算（旧缓存长的少切点，旧缓存短的多切点，上限 32,768），尽量拉齐 8 张卡每一步的预计耗时。

靠着这套从全局分桶到单卡解方程对齐步调的精细配平，DeepSeek 线上真实集群跑出了相当于完美均衡离线基准测试 **约 80%** 的有效吞吐率。

◆ 尾声：开源的拼图是怎么一块块合拢的

━━━━━━━━━━━━━━━━━━━━

把今天看到的这两座新仓库和那份部署问答合在一起，再回头看过去一年半的时间线，你会发现 DeepSeek 的开源节奏从来不是心血来潮的“突然搞大事”：

2025 年 2 月，他们先放出了 `FlashMLA`、`DeepGEMM`、`DeepEP` 和 `3FS`——那是给社区看 **单点算子与底层存储能榨出多少硬件极限**；
2026 年 6 月到 9 月，随着 V4 与 V4.1 架构演进，他们陆续放出了 `DSpark`、`DeepSelect` 和基于 `TileLang` 的 `TileKernels`——那是把 **稀疏注意力索引、词组查表、流形超连接以及英伟达与华为昇腾双后端** 封装成标准积木；
到了今天，当 `DeepSeek-V4.1-Flash-1017` 的模型权重与后训练管线尘埃落定，他们交出了 `DeepInfer` 和 `deepseek-recipe`——把所有积木插进同一个底盘，顺手用 Rust 把官方 API 的协议转换与分词防注入逻辑原样打包。

外行看热闹，看到的是一篇篇“刚刚、王炸”的惊叹号；内行看目录树，看到的是一套从模型架构减法（CED / CSA2 / Engram / FP4）到系统工程落地（100 PiB 3FS / EPD 三分离 / 变长投机验证 / 零开销异步调度）严丝合缝咬合在一起的工业级账本。
