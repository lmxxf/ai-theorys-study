【Strata】12GB 显卡，怎样调动整台电脑跑千亿模型？

━━━━━━━━━━━━━━━━━━━━

◆ 第一章：显卡装不下，为什么还能跑

━━━━━━━━━━━━━━━━━━━━

最近看到一个叫 Strata 的开源项目，首页写得很直接：一张 12GB 起步的游戏显卡，就能在自己的电脑上跑 125B 参数的模型。

125B 是 1250 亿。哪怕每个参数只占半个字节，光参数也得 62.5GB。12GB 显卡怎么放？再往下看，作者还给了每秒几十到九十多个 token 的输出速度，已经到了可以日常聊天、写代码的范围。

这就值得读一读了。

项目是 Niko1221/Strata（ https://github.com/Niko1221/Strata ）。我们这次看的是项目文档和实现，没有在本机安装测速。它目前围绕 **Qwen3.8-Flash-Next** 及其衍生版本做优化：模型自己怎样省计算，电脑里的显卡、处理器、内存和固态盘又怎样接力，两个条件凑在一起，才有这个结果。

Qwen 这台机器，293 期（ https://mp.weixin.qq.com/s/jb-ibVHAG3wKbtoiX5SStA ）讲过。先把今天需要的几块结构重新摆出来。

| 部件 | 规模 | 每次处理一个 token 怎么用 |
| :--- | :--- | :--- |
| 模型主干 | 125B 参数 | 混合专家架构，每层只选一小部分专家 |
| N-gram 词组嵌入表 | 另有约 51B 参数 | 根据相邻 token 算出地址，取少数几行 |
| 多 token 预测模块 | 另有约 4B 参数 | 预测后续 token，给主干提供待验证的草稿 |

所以，项目说的“125B 模型”指主干。把词组表加上是约 176B，但那 51B 主要是查表；多 token 预测模块还另算。**参数总数描述存了多少东西，每一步要搬多少、算多少，还得看参数怎样被调用。**

主干有 48 层，每层 512 个路由专家，处理一个 token 时选其中 10 个，另外还有共享专家。这就是 **混合专家（Mixture of Experts，MoE）** ：输入表示先经过路由器打分，选中的专家分别计算，再按路由权重把结果加起来。

`48 × 512 = 24,576 个路由专家`

这里的“512 选 10”发生在每一层。一个 token 要一路经过 48 层，不能把它理解成整台模型只启动 10 个专家。

但即便如此，计算量也已经小了很多。同一层没有选中的那 502 个专家，当下不用算。问题从“每一步把所有参数都读一遍”，变成了“这一步需要的专家在哪里，怎样尽快拿到结果”。

这正是 Strata 的入口。

普通的稠密模型，每一步大部分权重都要参与运算。权重放在内存里、计算放在显卡上，就可能反复受制于两边的传输速度。MoE 给了另一种安排：少数常用专家留显存，其他专家放内存，按当前路由分配工作。

**12GB 不是整台模型的住处，而是其中最快、也最贵的一层工作空间。**

◆ 第二章：显存放热门专家，内存里的 CPU 也干活

━━━━━━━━━━━━━━━━━━━━

先看一个 token 走到某层时发生什么。

路由器选出 10 个专家。其中几个已经在显存，显卡直接计算；另外几个在系统内存，处理器可以就地计算，也可以把其中一部分传到显卡计算。两边完成后，把各专家的输出按权重合起来，继续进入下一层。

这里多出来的关键动作是 **CPU 也计算专家**。系统内存不只是显卡的仓库，处理器也承担一部分乘法。

![Strata 常规专家计算分工：显卡计算缓存命中的专家，未命中部分由 CPU 就地计算或经 PCIe 传给 GPU，最后合并输出；新版尾部省略开关在后文另讲](assets/338/expert-placement.svg)

| 位置 | 主要放什么、做什么 |
| :--- | :--- |
| 显存与 GPU | 注意力等主干运算、常用专家，以及本轮分配给显卡的专家 |
| 系统内存与 CPU | 保存大量专家权重，计算一部分未命中显存缓存的专家 |
| 固态盘 SSD | 保存模型文件；词组嵌入表按地址取行、提前读取 |

把专家送上显卡，要经过 **PCIe（Peripheral Component Interconnect Express），也就是主板连接显卡的高速通道**。显卡算得快，但传输要花时间；CPU 算得慢一些，可权重已经在旁边的内存里。哪边先做完，得把搬运和计算一起算。

Strata 因而不是固定地说“显存之外全部交 CPU”，也不是“所有专家必须搬上 GPU 才能算”。它把未命中的专家分给两边，尽量让两个队伍差不多同时完成。较新的 NVIDIA 路径还会根据实际测到的 CPU 处理速度调整这个比例。

我们平时说“这张卡多少算力”，容易漏掉这一层：**一次生成的延迟，可能由最晚交卷的那个部件决定。** GPU 早算完了，仍然得等 CPU；CPU 还有空，GPU 却在等传输，同样浪费。

为什么显存里可以优先放“热门专家”？因为专家被调用的频率不平均。项目用专家使用情况来安排缓存，把更可能反复用到的留在显存里。缓存命中时，既省一次传输，也省 CPU 的工作。

不过，专家路由要等输入走到那一层才知道。下一层会选谁，并不能只看当前 token 的编号就完全确定。这与那张 51B 的词组表恰好相反。

────────────────────

💡 51B 参数的表，每一步只取几行

Qwen 的词组嵌入会根据最近两个、三个 token 的组合，计算若干个表内地址，取回对应向量，再注入主干。

总表很大，每次访问却很小。原架构每个 token 取 16 个、每个 160 维的向量；若按每个数 2 字节算，就是：

`16 × 160 × 2 = 5,120 字节，约 5KB`

这描述的是取回向量的规模。实际磁盘读取还受 I/O 对齐粒度影响，量化文件也有自己的存储格式，不能直接把它当成磁盘流量。

Strata 使用的量化词组表文件约 28.8GB，留在 SSD 上，由专门的读取线程按地址取行。默认路径采用直接读取，绕过操作系统的页缓存；最近的 token 一确定，就能算出要查的行，适合提前准备，把等待与其他计算重叠。

**一张 28.8GB 的表，不等于每生成一个 token 都要从 SSD 读 28.8GB。** 它之所以适合住得远，是因为地址好算，每次取用又少。

────────────────────

这也是为什么不能把 Strata 概括成“模型全放固态盘，边读边算”。常规低比特配置下，大批专家权重仍然靠系统内存承载；长期放在 SSD 上按行取用的，是那张很大的词组表。专家容量超过内存、不得不频繁从 SSD 调入，是另一种更慢的配置。

同样，内存也不会因为有 GPU 缓存就自动少占同样多。默认驻留方式会在系统内存保留专家，再把热门部分复制进显存；项目另有低内存模式，才会利用显存容量减少 CPU 一侧保留的专家。

读到这里，“12GB 显卡跑千亿模型”已经有了具体轮廓：显卡、CPU、内存、SSD 各自接住适合自己的部分，软件负责把它们串起来。

◆ 第三章：一次猜几个字，怎样省下调度时间

━━━━━━━━━━━━━━━━━━━━

电脑里几位选手能一起干活，还剩一个问题：如果每生成一个 token，就让它们集合、分工、等齐、再集合一次，调度也会成为负担。

Strata 用了 Qwen 自带的 **多 token 预测（Multi-Token Prediction，MTP）** 模块。

先让一个额外的预测模块猜后面几个 token，主干一次验证这一串。假设草稿猜了三个，前两个都通过，第三个没通过，就接收前面的正确前缀，从出错的位置按主干结果继续。用户看到的是验证后被接收的输出。

这叫 **推测解码（speculative decoding）** 。它的好处在于，把原本需要一轮一轮进行的部分工作，合到一个验证窗口里完成。专家权重、传输和调度的开销，就有机会由多个最终输出 token 分摊。

但它也有一笔成本：草稿模块本身要运行。猜得越准，一轮接收越多，越划算；猜错得多，验证还是要做，收益就缩小。因此，同一台电脑面对代码、聊天、不同采样设置，输出速度会不同。

项目的速度表默认开启 MTP。把那张表读成“普通逐 token 解码就有这个速度”，会漏掉很重要的一部分。

另外，“快”至少分两段。

**第一段，读完你送进去的内容。** 你贴一份长代码或几万 token 的文档，模型要先处理它们、建立后续生成需要的状态。这叫预填充（prefill）。

**第二段，开始逐步输出。** 这叫解码（decode），就是我们盯着聊天窗口看到的出字速度。

预填充同时处理许多 token，可能会用到一层里的大量专家，适合成批调度、成批传输。解码每一步只涉及少数 token，专家缓存、CPU 分工和草稿接受率就更显眼。同一套模型，这两个阶段的瓶颈并不一样。

下面只摘作者同一个 0.1.26 版本、同一台机器的三行结果，便于比较：RTX 5070 12GB、Ryzen 5 7600、64GB DDR5-5200、Windows；开启 MTP、使用贪心解码，关闭图片功能。

| 量化版本 | 短上下文输出速度 | 约 32K 输入的处理速度 |
| :--- | ---: | ---: |
| Q2_0 | 93.0 token/秒 | 2,171 token/秒 |
| IQ3_XXS | 61.6 token/秒 | 1,745 token/秒 |
| IQ3_S | 53.3 token/秒 | 1,624 token/秒 |

表里的短上下文测试，是 **输入 3,562 个 token，再生成 256 个 token**，不是连续生成 4K token。项目首页后来更新的 Q2_0 成绩使用 0.1.36，不能与这里当成完全同一版测试。

以 Q2_0 的 32K 处理速度粗算：

`32,000 ÷ 2,171 ≈ 14.7 秒`

原始测速记录里，这一格的首 token 延迟是约 16 秒；到约 128K 输入时，约 62 秒。首次送入长材料，先得等它读完。后面每秒输出九十多个 token，并不能抹掉前面的等待。这个估算也不包含启动加载、排队和其他服务开销。

后续对话如果复用了之前的状态，可以少读许多旧内容；首次打开长文档，则没有这份便宜。所以聊天工具有没有保留上下文、请求是不是复用前缀，也会影响实际体感。

这组作者实测，已经说明低显存机器可以达到流畅出字的速度。但它不是所有 12GB 显卡的共同成绩：CPU、内存带宽、显卡与主板的连接速度都在工作，同样显存容量，换台电脑还得重新量。

◆ 第四章：省下来的资源，分别付了什么代价

━━━━━━━━━━━━━━━━━━━━

读完机制，再看安装页面，我反而觉得应该先看系统内存，再看显卡。

| 系统内存 | 对 12GB／16GB 显卡机器的常见选择 |
| :--- | :--- |
| 32GB | 主要是删减专家的 Coder 版 |
| 48GB | 可以考虑保留完整专家的 Q2_0、IQ2_XS |
| 64GB | 低比特版本选择较全；较大的 IQ3_S 仍要给系统和上下文留余量 |

这里的“完整专家”，仍然是量化模型。

默认主线里的 2-bit、3-bit，是用更少的比特表示权重。原来一个数用 16 位，现在大幅压低存储精度，省空间、省传输，代价是数值被近似。量化名称也不等于整个文件每个参数整齐地只占 2 或 3 位：还有分组信息、缩放参数，不同矩阵也会按敏感度分配不同精度。Q2、IQ3 首先是量化档名。

**“所有专家都在”和“原始精度都在”，是两回事。** Q2_0 快，不足以单独说明它对中文写作、复杂推理、长代码修改都与原模型一样。

Coder 又多走了一步：每层 512 个路由专家只保留 256 个，仍然每次选 10 个。保留哪些，根据以代码为主的数据挑选。这样明显缩小专家权重，也更容易适配 32GB 内存。

它因此有明确的用途偏向。项目自己也提醒，非代码任务和非英语能力会受影响。我们写中文公众号，恰好不能只拿代码演示来替代自己的使用场景。

存储空间也得一起算。两份模型分片合计约 58 到 84GB，词组表包括在里面；MTP 草稿层另要约 6GB，图片功能还会增加文件。某些 CPU 和量化组合，首次启动还会生成额外的优化文件，Q2_0 的一种路径就可能再写约 40GB。首页“约 80GB 空间”只能当入口提示，实际要按选择的格式和启动路径留量。

还有一项容易藏在版本更新里的取舍。

0.1.42 的 NVIDIA CUDA 路径在适用配置下默认加入了 **路由尾部跳过（route tail skip）** ：在一轮多 token 验证中，如果某个未缓存到显存的专家，在窗口各 token 的路由排名里都足够靠后，就可能直接略过它。

文档给的默认判断是排名值达到 7 及以后。满足条件时，该专家既不传输，也不计算，贡献记作零，其他专家的权重保持原值，不重新归一化。已经在显存里的专家仍照常计算。

这就不仅是把同一份计算换个地方执行了，**它确实少算了一部分专家贡献**。项目提供了小规模的分布差异和任务测试，也提供 `STRATA_ROUTE_TAIL_SKIP=0` 关闭这项功能。前面那张 0.1.26 的测速表早于这个默认行为，不能把新版的取舍倒填进旧版成绩。

从这里能看到，Strata 的提速其实包含不同性质的工作：缓存、调度、并行是在安排资源；量化是在压缩数值；Coder 是删减专家；尾部跳过是在部分步骤减少计算。它们可以叠加，但各自付出的代价要分别理解。

最后还有适用范围。Strata 是围绕 Qwen3.8-Flash-Next 这套结构打造的专用引擎，借用了 ggml 这个张量计算库的底层能力，再自己安排执行与调度。它支持这个模型的多种量化和衍生版本，不等于把任意一个千亿模型文件交给它，都能得到同样的效果。

我读完最有收获的地方，恰好就在这个“专用”上：模型已经提供了稀疏专家、可按地址查取的词组表、预测后续 token 的模块，推理引擎继续顺着这些结构，把整台电脑的资源利用起来。

以前看本地模型，我往往先问“显存能放下多大”。Strata 提醒我再加几个问题：每一步到底要用哪些参数？这些参数从哪里读？谁来算？哪些等待可以重叠？

**模型容量能不能跨过显存边界，答案藏在这些具体的数据流里。**
