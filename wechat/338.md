【Strata】48GB 内存＋16GB 显存，怎样跑起 Qwen3.8-Flash-Next？

━━━━━━━━━━━━━━━━━━━━

◆ 第一章：显卡装不下，为什么还能跑

━━━━━━━━━━━━━━━━━━━━

最近很火的 Strata，能让游戏显卡跑起千亿模型。正好我家有一张 **RX 9070 XT，16GB 显存，配 48GB 系统内存**。这次真把它装起来了：模型能跑，预测专家的 LoRA 也训练了，结论却是暂时别开预取。先从最基本的问题讲起：模型放在哪里，又怎样算？

这篇就按这台机器的内存与显存容量来算，模型选 **Qwen3.8-Flash-Next 的 Q2_0 量化版，保留全部路由专家**。这是本文选定的完整专家量化方案，不是所有版本、所有上下文长度的统一最低要求。更小内存可以靠删专家或更多磁盘调入继续挤，先不把那些路线混进来。

项目是 Niko1221/Strata（ https://github.com/Niko1221/Strata ）。实机是 Windows 11 原生环境，Core Ultra 7 270K Plus，48GiB 内存、6000MT/s，NVMe 固态盘；CPU 走 AVX2，显卡走 AMD 的 HIP 计算接口，引擎版本 0.1.43。下面先讲数据怎样流，再看实测怎样修正最初的猜想。

先说明精度：Q2_0 是低比特量化档名，不同矩阵按敏感度分配精度，不是原始 16 位权重。它保留完整专家；另一个更省内存的 Coder 版每层只保留一半专家，这次没有用。Strata 也是针对这套 Qwen 架构的专用引擎，复用了 ggml 张量计算库的能力，不是任意千亿模型都能这样放进去。

Qwen 这台机器，293 期（ https://mp.weixin.qq.com/s/jb-ibVHAG3wKbtoiX5SStA ）讲过。把结构、下载大小和运行去向放在一起看：

| 部件 | 参数规模 | 本次下载大小 | 运行时放在哪里、怎样用 |
| :--- | :--- | ---: | :--- |
| 模型主干 | 125B | 主模型分片约 37.6GB | 约 34GB 专家权重进入系统内存，热门专家另在显存缓存；注意力等常用模块放显存，每层只计算选中的路由专家及共享专家 |
| N-gram 词组嵌入表 | 另约 51B | 约 28.8GB | 留在 SSD，根据相邻 token 的组合按需取少数几行 |
| 多 token 预测模块（MTP） | 另约 4B | 另下载约 6GB | 所需运行部分加载到显卡，预测后续 token，交给主干验证 |

**前两份模型文件合计约 66.4GB，加上草稿模块约 72GB 磁盘空间；它们并不需要全部装进系统内存。** 文件是存下来的权重，运行时还要给上下文缓存、临时空间和系统开销留余量，下载大小不等于内存或显存占用。

所以，项目说的“125B 模型”指主干。把词组表加上是约 176B，但那 51B 主要是查表；多 token 预测模块还另算。**参数总数描述存了多少东西，每一步要搬多少、算多少，还得看参数怎样被调用。**

主干有 48 层，每层 512 个路由专家，处理一个 token 时选其中 10 个，另外还有共享专家。这就是 **混合专家（Mixture of Experts，MoE）** ：输入表示先经过路由器打分，选中的专家分别计算，再按路由权重把结果加起来。

`48 × 512 = 24,576 个路由专家`

这里的“512 选 10”发生在每一层。一个 token 要一路经过 48 层，不能把它理解成整台模型只启动 10 个专家。

但即便如此，计算量也已经小了很多。同一层没有选中的那 502 个专家，当下不用算。问题从“每一步把所有参数都读一遍”，变成了“这一步需要的专家在哪里，怎样尽快拿到结果”。

这正是 Strata 的入口。

普通的稠密模型，每一步大部分权重都要参与运算。权重放在内存里、计算放在显卡上，就可能反复受制于两边的传输速度。MoE 给了另一种安排：少数常用专家留显存，其他专家放内存，按当前路由分配工作。

**16GB 显存不是整台模型的住处，而是其中最快的一层工作空间。48GB 内存和 SSD 一起，才接住完整的模型文件。**

◆ 第二章：显存放热门专家，内存里的 CPU 也干活

━━━━━━━━━━━━━━━━━━━━

先看一个 token 走到某层时发生什么。

路由器选出 10 个专家。其中几个已经在显存，显卡直接计算；另外几个在系统内存，处理器可以就地计算，也可以把其中一部分传到显卡计算。两边完成后，把各专家的输出按权重合起来，继续进入下一层。

这里多出来的关键动作是 **CPU 也计算专家**。系统内存不只是显卡的仓库，处理器也承担一部分乘法。

![Strata 常规专家计算分工：显卡计算缓存命中的专家，未命中部分由 CPU 就地计算或经 PCIe 传给 GPU，最后合并输出；新版尾部省略开关在后文另讲](assets/338/expert-placement.svg)

把本文这台 48GB＋16GB 电脑的常规驻留方式列出来：

| 位置 | 放什么 | 容量怎样分 |
| :--- | :--- | :--- |
| 48GB 系统内存 | 全部专家权重，CPU 可以直接读取计算 | 专家约 34GB；项目另按约 10GB 估算系统与其他程序余量，合起来约 44GB |
| 16GB 显存 | 注意力、路由器等常用模块、草稿模块、上下文缓存、运算缓冲区，剩余空间缓存热门专家 | 专家缓存大小由启动时可用显存和上下文设置决定 |
| SSD | 完整下载文件，以及运行时按行读取的词组表 | 词组表约 28.8GB，不需要整体装入系统内存 |

**显存里的热门专家，是内存中那 34GB 专家的副本。** 常规模式下，不能拿 48GB＋16GB 相加，就当成一块互不重复的 64GB 权重空间。这次确实装下了，但实际余量比纸上相减紧得多。

显存分配可以写成：

`专家缓存空间 = 16GB − 常用模块 − 上下文缓存 − 运算缓冲区 − 其他显存占用`

首次以 4K 上下文启动，日志里全部专家实际占 **31.64GiB，约合十进制 33.98GB**。GiB 按 1024 换算，GB 按 1000 换算，后面的运行分配统一看 GiB。

显卡缓存最终只有 **4688 个槽、6.04GiB，按体积约占全部专家的 19%**。MTP 草稿模块另占 799MiB，草稿词表头再占 178.4MiB。常用模块、上下文和缓冲区都要分显存，不能继续拿“也许剩 8 到 10GB 给专家”当实际结果。

短问答跑完，系统可用内存约 2.14GiB，Windows 提交额度余量约 1.25GiB。后者是系统还能承诺分配的内存额度，还受页面文件等影响。后来的预取对照采用 64K 上下文配置，把长期专家缓存固定为 **3437 槽、4.43GiB，约 14%**。这两个比例属于两次不同配置，不是显卡的固定属性。

**只缓存了约两成权重，不等于只命中两成调用。** 热门专家反复被选中，调用命中率可以高得多。这里的容量按字节算，混合精度让不同层的专家大小不同，也不能直接用槽数比例替代体积比例。GPU 缓存未命中，更不等于操作系统缺页：权重可能好好地待在 RAM 里，CPU 可以直接算。

把专家送上显卡，要经过 **PCIe（Peripheral Component Interconnect Express），也就是主板连接显卡的高速通道**。显卡算得快，但传输要花时间；CPU 算得慢一些，可权重已经在旁边的内存里。哪边先做完，得把搬运和计算一起算。

Strata 因而不是固定地说“显存之外全部交 CPU”，也不是“所有专家必须搬上 GPU 才能算”。它把未命中的专家分给两边，尽量让两个队伍差不多同时完成。较新的 NVIDIA 路径还会根据实际测到的 CPU 处理速度调整这个比例。

常规驻留路径还会使用锁页内存：让这批物理内存保持可供设备访问，便于显卡通过直接内存访问（Direct Memory Access，DMA）取数据，减少中转。再用异步传输，让搬下一份权重和算手头这份工作重叠。这省的是等待，并没有突破 PCIe 的带宽上限。**整轮延迟仍可能由最晚完成的那一边决定。**

不过，专家路由要等输入走到那一层才知道。下一层会选谁，并不能只看当前 token 的编号就完全确定。这与那张 51B 的词组表恰好相反。

────────────────────

💡 51B 参数的表，每一步只取几行

Qwen 的词组嵌入会根据最近两个、三个 token 的组合，计算若干个表内地址，取回对应向量，再注入主干。

总表很大，每次访问却很小。原架构每个 token 取 16 个、每个 160 维的向量；若按每个数 2 字节算，就是：

`16 × 160 × 2 = 5,120 字节，约 5KB`

这描述的是取回向量的规模。实际磁盘读取还受 I/O 对齐粒度影响，量化文件也有自己的存储格式，不能直接把它当成磁盘流量。

Strata 使用的量化词组表文件约 28.8GB，留在 SSD 上，由专门的读取线程按地址取行。默认路径采用直接读取，绕过操作系统的页缓存；最近的 token 一确定，就能算出要查的行，适合提前准备，把等待与其他计算重叠。

**一张 28.8GB 的表，不等于每生成一个 token 都要从 SSD 读 28.8GB。** 它之所以适合住得远，是因为地址好算，每次取用又少。

────────────────────

这也是为什么不能把 Strata 概括成“模型全放固态盘，边读边算”。常规低比特配置下，大批专家权重仍然靠系统内存承载；长期放在 SSD 上按行取用的，是那张很大的词组表。专家容量超过内存、不得不频繁从 SSD 调入，是另一种更慢的配置。

项目另有低内存模式，利用显存减少 CPU 一侧保留的专家。本次采用的是完整专家驻留 RAM 的路线，不把缺页读盘和正常的 CPU/GPU 分工混在一起。

◆ 第三章：一次猜几个字，怎样省下调度时间

━━━━━━━━━━━━━━━━━━━━

电脑里几位选手能一起干活，还剩一个问题：如果每生成一个 token，就让它们集合、分工、等齐、再集合一次，调度也会成为负担。

投机解码的原理，132 期（ https://mp.weixin.qq.com/s/0eLtEaX8_dDD7l6OuKlAhg ）已经讲过：先猜一串 token，再由主模型批量验证。Strata 用的是 Qwen 自带的 **多 token 预测（Multi-Token Prediction，MTP）** 模块来生成草稿。

先让一个额外的预测模块猜后面几个 token，主干一次验证这一串。假设草稿猜了三个，前两个都通过，第三个没通过，就接收前面的正确前缀，从出错的位置按主干结果继续。用户看到的是验证后被接收的输出。

这次放到 Strata 里看，关注的是它怎样摊薄搬运成本：把原本一轮轮进行的部分工作合到一个验证窗口里，专家权重读取、传输和调度的开销，就有机会由多个最终输出 token 分摊。

但它也有一笔成本：草稿模块本身要运行。猜得越准，一轮接收越多，越划算；猜错得多，验证还是要做，收益就缩小。因此，同一台电脑面对代码、聊天、不同采样设置，输出速度会不同。

项目的速度表默认开启 MTP。把那张表读成“普通逐 token 解码就有这个速度”，会漏掉很重要的一部分。

另外，“快”至少分两段。

**第一段，读完你送进去的内容。** 你贴一份长代码或几万 token 的文档，模型要先处理它们、建立后续生成需要的状态。这叫预填充（prefill）。

**第二段，开始逐步输出。** 这叫解码（decode），就是我们盯着聊天窗口看到的出字速度。

────────────────────

💡 前面的字还没算完，后面的字为什么能一起算？

先用普通 Transformer 的四个输入位置、相邻两层来看。图中从上往下是计算先后，同一排的四个位置可以并行：

![Prefill 的并行关系：每层先并行生成四个位置的 Q、K、V，再并行计算各位置 attention；位置 4 读取本层已经生成的 KV1 到 KV4，不依赖位置 1 到 3 的本层 attention 输出。各位置更新表示后，下一层重复同样流程。](assets/338/prefill-parallel.svg)

**先并行算好本层 Q/K/V，再并行算 attention。** 位置 4 需要位置 1、2、3 的 K/V，这些在上一道投影步骤就已经产生；它不用等位置 1、2、3 的 attention 算完。因果遮罩（causal mask）只让它读当前位置及之前的 K/V。

attention 的结果经过残差和前馈更新，形成下一层输入。下一层又能由各位置的输入，并行生成自己这一层的新 Q/K/V。**层与层有先后，同一层的各个位置不用排队。**

到了本层 MoE 的输入，真实路由器才给批内各 token 选专家。此时可以把都选中专家 A 的 token 归到一起，让 A 的权重搬一次、多用几次。这里是已知输入的批量计算，不是在预测专家。

Qwen3.8 还混有门控 DeltaNet（Gated DeltaNet）线性注意力层，其中有状态递推，不能把整网都当成普通注意力完全并行。它需要专门的分块、扫描等实现；项目也有相关实验，并非每个实验开关都适合这张家用卡。

────────────────────

同一套模型，在不同阶段采用的安排也不同：

| 场景 | Strata 怎样安排计算与搬运 | 省下什么、受什么限制 |
| :--- | :--- | :--- |
| 生成时，选中的专家已在显存 | GPU 直接用缓存中的权重计算 | 不必重新搬这份权重；效果取决于当前任务的缓存命中率 |
| 生成时，专家在内存，分给 CPU | CPU 原地计算，与 GPU 上的专家并行，再合并结果 | 省去把这份专家权重传上显卡的开销；受 CPU 和内存带宽限制 |
| 生成时，专家在内存，分给 GPU | 通过 PCIe 传权重，GPU 计算；根据两边处理速度调整分工 | 利用 GPU 的空余能力，但要付传输时间；传上去计算不等于一定长期留在缓存 |
| MTP 一次验证多个 token | 按各 token 的实际路由，把使用同一专家的计算组织到一起；同一份权重可服务窗口内多个 token | 有机会摊薄读取、传输和调度成本；路由越分散、草稿接受越少，收益越有限 |
| 首次读入长输入（prefill） | 把输入分块，以 GPU 批量计算为主，专家按批经 PCIe 流入，搬运与计算重叠 | 一次搬入的专家能给一批 token 使用；涉及的专家多，长文仍有明显等待 |
| 较短的输入块 | 新版单 GPU CUDA 路径在适用条件下，让 CPU 分担部分专家计算 | 小批量时减少 GPU 搬运与等待；内存余量不足等情况会停用，不能套到所有设备 |
| 对话继续、专家冷热变化 | 按使用情况调整显存中的热门专家 | 后续调用可能更容易命中；切换任务后，旧的热门集合未必仍合适 |

这里的短输入分工，默认针对小于 1,024 token 的输入块，并有设备与内存条件。它与生成阶段的 CPU/GPU 分工是两项不同的调度策略。

前面的表是机制说明。真到我家这张卡上，第一道坎出在读长输入。

首次短中文问答输出 42 个 token，生成速度 73.1 token/秒；一道抽红球概率题输出 15 个 token，66.3 token/秒，答对了 3/5。两次都开着 MTP。这说明安装跑通了，还不能拿这么短的回答代表长任务。

扩大到 64K 上下文，批量预填充却在 HIP 路径上报错。换过参数仍未解决，最终用 `--prefill 128 --short-read 65536`，让输入走已有的验证窗口，绕过出错的批量路径。根因还没定位，这是一条跑通了的兼容路线。

我拿自己那份很长的 AGENTS.md 做长输入测试。这份文件积累了大量个人工作上下文，加上问题共 **33,699 个输入 token，等了 305.672 秒才看到第一段内容**，输入处理速度 110.3 token/秒。模型答对了文档里的定位问题，但第一次读完，实实在在等了五分钟。这个长度来自我的个人用法，普通项目的 AGENTS.md 完全可以短得多。

随后沿同一前缀追问，复用了 33,692 个 token，只新读 41 个，**首内容等待降到 0.485 秒**，也答对了。

两次体验差别很大。后一次的快，是复用了已经处理过的前文；换一篇长材料，仍然要重新读。这组 110.3 也不是正常批量预填充的性能上限，而是当前兼容路径的实际速度。拿它直接和作者另一台 NVIDIA 机器的批量结果相比，解释不了是谁慢在哪里。

◆ 第四章：提前预测下一层会用哪些专家

━━━━━━━━━━━━━━━━━━━━

我更关心的是专家搬运：**能不能在下一层开始计算之前，就知道它会用到哪些专家，把需要的权重提前准备好？** 这才是我们动手做实验的起点。

Strata 已有路由前瞻（router lookahead）：当前层还在计算，就用当前层输入喂给下一层现成的路由器，猜接下来需要的专家。在专家不能全放内存的路径上，它可以预读文件页；默认关闭的前瞻预取（Foresight）则把预测专家搬进 GPU 临时槽。

我家 Q2_0 的专家已全在 RAM，这次研究的是后者：能不能早点把需要的权重传给显卡，减少等待？真实计算仍由原路由器决定，预测错了只是没帮上忙，不能拿预测结果替换模型的真实选择。

我的第一个猜想，是复用当前层已经算好的路由分数，加两张小矩阵来修正：

`当前层真实分数 = xW_当前`

`预测下一层分数 = xW_当前 + (xA)B`

这就是低秩适配（Low-Rank Adaptation，LoRA）的形式：冻结模型和原路由，只训练 A、B。x 是当前层输入，A 先把 2560 维压到 16 维，B 再投到 512 个专家分数。中间维度 16 就是这次的秩。

如果能直接复用已有的 `xW_当前`，额外矩阵乘法量约为原路由投影的 3.75%。这是当时想省算力的依据。但相邻层的专家编号没有天然对应，当前层专家 7 和下一层专家 7 并不一定做相近的事，这个修正能不能学出来，得测。

第一轮用 AGENTS.md 的不重叠片段，分开训练、调参和测试。每次预测 10 个专家，看覆盖下一层真实前 10 个专家的比例：

| 预测方式 | 训练前覆盖率 | 训练后覆盖率 |
| :--- | ---: | ---: |
| 当前层分数加 LoRA | 2.04% | 51.04% |
| 当前层输入，提前使用下一层路由器，再加 LoRA | 62.15% | 62.81% |

第一行从 2% 涨到 51%，看上去很大，却还没超过原样借用下一层路由器的 62.15%。**从一个很弱的起点进步很多，不等于比现成办法好。** 当前层省算力方案到这里只做了离线测试，没有接进运行时测速。

接下来我们沿第二条路线继续：

`预测下一层分数 = xW_下一层 + (xA)B`

仍然只训练旁支，目标集中在**不在显存里的专家**：已经缓存的不用再预取。下面的“未缓存专家覆盖率”，统计的是预测覆盖了多少 GPU 尚未缓存、但真实路由选中的专家。

先用自己那份 AGENTS.md 的片段训练一版，再找了我们自己写的 30 篇长文做训练，另留长文用于调参和测试。按整篇分开，不把同一篇的相邻片段分到两边。每对相邻层是否采用 LoRA，由调参集决定；没有改善的就保留原路由器。

在同一组长文测试集上，预测 10 个未缓存候选的结果是：

| 预测器 | 未缓存专家覆盖率 |
| :--- | ---: |
| 原下一层路由器 | 70.36% |
| 30 篇长文训练的新 LoRA | **74.31%** |

新旁支比原路由器多覆盖 **3.95 个百分点**的未缓存专家，三篇测试长文都提高。最终 22 对层用 LoRA，25 对仍用原路由器。至少在这份留出材料上，预测已经变准了。

剩下的才是最想知道的问题：**更准，能不能更快？**

━━━━━━━━━━━━━━━━━━━━

◆ 第五章：猜准了，也未必值得搬

━━━━━━━━━━━━━━━━━━━━

这次没有停在离线命中率。我们把下一层路由器预测和 LoRA 真正接进独立的 HIP 实验引擎，CPU 用 AVX2 在异步线程计算预测，再交给预取复制流。模型权重和真实路由都没改；数值对照和复制回读通过后，才开始计时。

前面“只多 3.75% 矩阵计算”的口算，属于复用当前层分数的方案。这里重新在 CPU 算的是 `xW_下一层`，没有复用当前层已经算出的分数，因此不能套用那个额外计算量比例。

为比较预取本身，四组使用同一独立实验引擎，都关掉 MTP 和其他草稿，关掉前缀复用，也关掉路由尾部跳过。尾部跳过是新版的一项近似加速：对验证窗口里排名始终靠后、又未缓存的专家，直接省去它的贡献。这次设置 `STRATA_ROUTE_TAIL_SKIP=0`，让原路由选中的专家都参与计算。

四组的长期专家缓存同样固定为 3437 槽、4.43GiB。预取组三组额外分配每层 16 个临时槽，不预取组没有这块空间，**但长期缓存没有被缩小**。所以不能把这轮变慢解释成“预取挤掉了热门缓存”。

输入沿用同样四份 AGENTS 片段，947 到 1539 个 token，每次输出 128 个，三轮交错顺序跑，共 48 次请求。加载和统一暖机不计时，表中按总 token 数除以总用时汇总：

| 配置 | 输入处理速度（token/秒） | 纯自回归生成（token/秒） |
| :--- | ---: | ---: |
| A：不预测、不预取 | **111.38** | **57.50** |
| B：原下一层路由器预测＋预取 | 106.60 | 55.07 |
| C：旧的未缓存目标 LoRA＋预取 | 106.24 | 55.10 |
| D：长文 LoRA＋预取 | 106.60 | 55.41 |

**不预取最快。** 新 LoRA 比普通预取的生成速度高约 0.6%，各轮变化并不稳定；相对不预取，仍慢约 3.64%。输入处理也没有追回来。这部分仍走前面那条兼容读取路径，不是批量预填充的上限。

测速用的是原 AGENTS 片段，离线提高 3.95 个百分点测的是长文，两者不是同一套材料。预取组的输出哈希也会随运行变化：同样提示、同样输出长度，不等于每次生成完全相同的 token 序列。因此那一点点 0.6%，还不能归功于长文训练提高了预测率。

第三轮有一次 Windows 提交额度只余 0.3GiB，临时预取空间申请失败。释放资源后，按原配置补齐第三轮全部四组；成功但较慢的记录也都保留。48GiB 跑通是一回事，留多少稳定余量是另一回事。

看到这里，我的理解变了：**猜中哪个专家会被用到，不等于值得把它搬上 GPU。** 那份权重原本就在 RAM，CPU 本来就能算。提前搬运还要付预测、复制、同步的成本；如果来得不够早，或者搬完也没省掉关键等待，结果就是多干了活，整轮却更慢。

这解释与目前的结果相容，但还没有把每一项成本分离出来。我们没测完美预测，也不能说所有预取都没用。现在能落地的判断很明确：**我家这台机器、这组配置，整套预取是净负收益，先关掉合理。** 训练让预测更准这件事成立在那份测试集上；把它变成端到端加速，是另一道工程题。

第一次短问答开 MTP 的七十多 token/秒，也不能和这里关闭草稿的五十多直接相除，当成 MTP 加速比：上下文、缓存容量、提示和输出长度都变了。完整的任务质量评测、不同秩以及持续后台更新，还没有做，就先不替它们写结论。

这次真正学到的，是不能只盯着自己刚优化的那个指标。**模型能装下、专家能猜中、回答能更早完成，是三个需要分别兑现的结果。**
