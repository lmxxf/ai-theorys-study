把日历往回翻一周，有两件事挨得非常近：

- **10 月 15 日** ，英伟达在 Hugging Face 上放出了新一代开源多模态推理模型 **`NVIDIA-Nemotron-3.5-Super-VL-120B-A12B`** （连同 `NVFP4` 量化权重与 `LiLiCorr` 投机解码草稿头）；
- **10 月 16 日** （仅仅隔了一天），英伟达联手微软、华硕、戴尔、惠普、联想、微星六家 PC 厂商，正式开卖预装 Windows on Arm 系统的消费级 **RTX Spark** 笔记本（迷你台式机随后在 11 月跟进）；

我们在 210 期 https://mp.weixin.qq.com/s/WKVRvtr3wt19w7hJm-no7Q 专门讲过 RTX Spark 的机器底子：它和开发者手里那台售价四千多美元的“小金盒子” **DGX Spark** 用的是同源芯片（20 核 Grace Arm CPU + Blackwell GPU + **最高 128GB LPDDR5X 统一内存** ）。但从 Linux 工作站变成消费级 Windows 产品时，老黄砍掉了 DGX Spark 身上最核心的一根血管—— **200Gbps 的 ConnectX-7（CX7）高速直连网口** 。

在我家里，两台 DGX Spark 靠一根 200G 网线直连，就能跨机分片凑出合计 256GB 的内存池，稳稳跑起 284B 总参数的 `DeepSeek-V4-Flash`。而砍掉高速网口、换上 Windows 的 RTX Spark，没了现成的高速双机扩展通道，日常基本只能守着 **单机 128GB 统一内存** 过日子。

问题随之而来：128GB 单机装不下 284B 的 `DeepSeek-V4-Flash`，也塞不进 300B 级别的旗舰模型；可老黄又急需在 Spark 家族铺货的时候，向市场展示“单台 128GB 机器本地流畅运行百亿级多模态智能体（Agent）+ 百万词元（1M token）上下文”。

多大尺寸的模型，压成 4 比特后刚好能塞进 128GB 统一内存、又不至于退化成几十亿参数的玩具？

老黄今年 3 月在 `Nemotron 3 Super` 上选定的那个 **`120B`（激活 `12B`）** 尺寸，此刻正好派上了用场。这次赶在 RTX Spark 开卖前夜放出的 `3.5 Super VL`，就是在 3 月那颗 120B 纯文本底座上接上视觉编码器、补齐多模态后训练与 `NVFP4` 量化打造出来的。

◆ 第一章：先算 128GB 单机的内存分配——71 GiB 权重放进去还剩多少？

━━━━━━━━━━━━━━━━━━━━

我们先借着这套面向单台 `DGX Spark（GB10）` 的官方配置，算一算一颗 `120B` 模型在 128GB 统一内存机器里是怎么分地盘的。

现在开源界给 MoE 大模型做 4 比特量化，普遍采用“专家层用低精度、敏感组件留高精度”的混合方案（比如 `DeepSeek-V4`、`GLM-5.3-Flash`、`Qwen3.8-Flash-Next` 和 `MiMo-V2.6` 都是如此）：**只把参数占大头、对量化相对皮实的 MoE 专家层压成 FP4，而把对误差敏感的注意力层、线性状态层、路由器、词表头和视觉编码器留在 FP8 或 BF16。**

打开 `Nemotron 3.5 Super` 的量化配置文件 `hf_quant_config.json` 和技术报告第 4.1 节的表 12，老黄用的也是这套标准的 `MIXED_PRECISION`（混合精度）三档配方：

1.**压成 `NVFP4`（每 16 个元素配 1 个 FP8 缩放因子，实际每元素占 4.5 bit）的**：40 层主干 MoE（以及 MTP 层里的 MoE）的路由专家与共享专家矩阵（`experts.*.up_proj` 和 `down_proj`）；
2.**保留 `FP8`（8 bit）的**：40 层 Mamba-2 的进出投影（`in_proj`、`out_proj`）、8 层注意力的查询/键/值/输出投影（`q_proj`、`k_proj`、`v_proj`、`o_proj`）以及词表输出头 `lm_head`（报告第 4.3 节测出 `lm_head` 一项就占了全网近一半的 FP4 误差敏感度）；
3.**保留 `BF16`（16 bit）的**：词表嵌入层（`embeddings`）、Mamba-2 的一维卷积核（`conv1d`）、MoE 的路由器（`gate`）与潜空间进出投影矩阵（`fc1_latent_proj`、`fc2_latent_proj`）、多词元预测模块（`mtp`）的融合投影与注意力层、以及整座视觉编码器（`vision_model`）和视觉投影层（`mlp1`）。

按这套混合精度算下来，全模型实际存储密度是 **平均每参数 4.82 比特（4.82 BPE，计入视觉与 MTP 后总参数为 124.453B，张量净载荷 74.987 GB）** 。拉下 Hugging Face 上 `NVFP4` 仓库的 88 个 `.safetensors` 分片一算，静态权重文件体积正好是 **75.01 GB（合 69.86 GiB）** ，再加上配套的 `LiLiCorr` 投机草稿头 **1.32 GB（1.23 GiB）** ，光静态模型文件就占去了 **71.09 GiB** 。

现在，我们把这 71.09 GiB 放进一台 128 GiB 统一内存的 Spark 机器里，看看官方给出的 GB10 专属启动脚本：

```bash
vllm serve nvidia/NVIDIA-Nemotron-3.5-Super-VL-120B-A12B-NVFP4 \
  --max-num-seqs 1 \
  --gpu-memory-utilization 0.75 \
  --max-num-batched-tokens 8192 \
  --speculative_config.model nvidia/NVIDIA-Nemotron-3.5-Super-VL-120B-A12B-NVFP4-LiLiCorr \
  --speculative_config.num_speculative_tokens 7 \
  --speculative_config.method dflash \
  --mamba-backend flashinfer \
  --mamba-ssm-cache-dtype float16 \
  --enable-mamba-cache-stochastic-rounding \
  --enable-mamba-shared-prefix-checkpoint \
  --video-pruning-rate 0.5 \
  --tool-call-parser qwen3_coder
```

我们在前文 210 期讲过，统一内存设备的 CPU 和 GPU 共用同一个内存池，必须给操作系统、CPU 进程、图像视频解码以及文件加载缓存留出安全垫。因此脚本里把 `--gpu-memory-utilization` 设成了 `0.75`——也就是让 vLLM 动用约 **96 GiB** （128 × 0.75）。

96 GiB 扣掉约 71 GiB 的静态权重（本体 + 草稿头），留给运行时激活值、注意力 KV 缓存和 Mamba 状态缓存的余量，**大约是 25 GiB** 。

因为 Spark 本来就是个人桌面单机，脚本直接把并发设成了 `--max-num-seqs 1`（单人使用不需要多并发，正好把单机有限的内存带宽全留给 `LiLiCorr` 一次并行验证 7 个草稿词）。同时，为了支持多轮 Agent 对话的前缀复用（`--enable-mamba-shared-prefix-checkpoint`），vLLM 不能只留当前最后一步的 Mamba 状态，而必须每隔一段词元就把 40 层 Mamba 的循环状态（单次 SSM 状态在 FP32 下占 160 MiB）存一份分页快照（报告第 5.3 节指出，1 页 Mamba 状态缓存占的字节数至少相当于约 4K 词元的注意力 KV 缓存）。

于是在这套配置里可以看到两项配套设置：
- **第一，把 Mamba 的循环状态缓存从 `float32` 砍半成 `float16`（报告在数据中心部署中也采用了同一设置）** ：在模型的 `config.json` 里，默认写的是 `mamba_ssm_cache_dtype: float32`，因为循环状态每一步都在累乘累加，低精度易累积舍入误差。为了省下一半的状态缓存体积与读写带宽（单次 SSM 状态从 160 MiB 降到 80 MiB），这里直接改用 `float16`，再额外打开随机舍入（`--enable-mamba-cache-stochastic-rounding`，用 5 轮 Philox 随机数发生器把截断误差抖成零均值噪声）来维持精度；
- **第二，宣传页上的“1M 上下文”，在 `LiLiCorr` 卡片的部署说明里给出的上限是约 112K** ：如果你点进配套的 `LiLiCorr` 模型卡片看输入说明，会发现一行小字——`The target model supports up to 1M tokens of context. The serving configuration below sets a 114,688-token limit.`（目标模型支持最高 1M 词元上下文，但下方的部署配置将上限设为 114,688 词元。）

算清了这笔内存分配，再往后看它的模型结构，你就会发现它身上的每一处设计都在围绕同一个目标使劲：**如何在塞下 120B 参数的前提下，把每个词元的运行时缓存、激活维度和访存带宽压到最小。**

◆ 第二章：主干拓扑——别人“一对算一层”，老黄“半层算一层”凑出 88 层

━━━━━━━━━━━━━━━━━━━━

之前我们在 292 期 https://mp.weixin.qq.com/s/qGbCm3qJB6SNumftansUtw 读智谱的 `GLM-5.3-Flash`，在 293 期 https://mp.weixin.qq.com/s/jb-ibVHAG3wKbtoiX5SStA 读阿里的 `Qwen3.8-Flash-Next`，在 308 期 https://mp.weixin.qq.com/s/Rsx8_ygHyXbN6JI1QTNxMw 读 `DeepSeek-V4.1-Flash`。不管各家怎么改注意力，有一条规矩是全行业通用的：**每一层（Layer）内部，都由“1 个序列混合模块（Attention 或线性注意力）+ 1 个前馈网络（FFN 或 MoE）”成对捆绑组成。**

比如 `DeepSeek-V4.1-Flash` 有 40 对“注意力 + MoE”，它的层数就叫 **40 层** ；`GLM-5.3-Flash` 有 45 对，就叫 **45 层** 。

但如果你打开 `Nemotron 3.5 Super` 的 `config.json`，看到里面写着 88 层，千万别以为它的网络深度是 DeepSeek 的两倍多——因为 **老黄把“半层”单独算成了“一层”** 。

在它的 `layers_block_type` 数组里，一共列出了 **88 个平级模块（Block）** ，每一层里只装一个子模块：
- 比如 `layers.0` 里面只有一个光杆 `mamba`（Mamba-2 状态空间模块），后面**不带** MoE；
- `layers.1` 里面只有一个光杆 `moe`（混合专家模块），前面**不带** Mamba 也不带 Attention；
- `layers.7` 里面只有一个光杆 `attention`（分组查询注意力模块），后面同样**不带**自己的 MoE。

如果我们用 `M` 代表 Mamba-2、用 `A` 代表 Attention、用 `E` 代表 MoE，把这 88 个平级模块的真实排列顺序打出来，长这样：

```text
# 全网 88 个平级 Block 的排列序列（M=Mamba-2, A=Attention, E=Latent MoE）：
MEMEMEMAEMEMEMEMAEMEMEMEMAEMEMEMEMEMAEMEMEMEMEMAEMEMEMEMEMAEMEMEMEMEMAEMEMEMEMAEMEMEMEME

# 统计数量：
# M (Mamba-2)   = 40 层（只做状态空间序列混合，不含 MoE）
# E (Latent MoE)= 40 层（只做混合专家通道变换，不含 Mamba/Attention）
# A (Attention) =  8 层（仅位于第 7、16、25、36、47、58、69、78 号模块，不含 MoE）
```

仔细看上面那串字母，把老黄的“半层计数法”换算回全行业通行的“一对算一层”口径，底牌立刻就露出来了：
- 全网总共只有 **40 个 `M`** 和 **40 个 `E`** ，基础骨架其实就是 **40 层标准的 `M → E`（Mamba-2 配 MoE）** ；
- 至于那仅有的 **8 个 `A`（Attention）** ，连独立的 MoE 都没分到——它们只是在第 7、16、25、36、47、58、69、78 这 8 个位置上，像插片一样塞进了 `M` 和 `E` 中间，变成了 **`M → A → E`** （即词元先过一层光杆 Mamba，出来不进 MoE，紧接着再过一层光杆 Attention，最后两人共用后面的同一个 MoE）。

换句话说，**按 DeepSeek 或 Qwen 的数法，这台号称“88 层”的模型，本质上只是一台 40 层的 Mamba-MoE 模型，外加在其中 8 层中间塞了 8 片不带 FFN 的光杆注意力** 。因为把每个子模块都单独算作一层来编号，纸面层数直接从 40 层膨胀到了 88 层。

一直追更的老读者看到这里肯定会心一笑——我们在 343 期 https://mp.weixin.qq.com/s/5fkFYzqLEkwEuDXvxtNqlw 分析老黄的 DLSS 5 神经网络（“诚实的丁鱥” 71 块 152 层、“疯狂的杜鹃” 31 块 76 层）时，就撞见过相似的命名习惯：常见的 Transformer 口径习惯把“注意力 + FFN”合起来叫 1 层；而在老黄自家的字典里，无论是显卡驱动部门写的 `HNetCpp` 渲染网，还是大模型部门写的 `NemotronH`，**都喜欢按更细的执行模块来给 `Layer` 编号** 。在 DLSS 5 里，他把 1 个 ViT 块里的前馈展开、前馈收缩、QKV、注意力和输出投影切开算成 5 层（8 个块数成 40 层）；到了这台 120B 大模型里，他又把 Mamba、Attention 和 MoE 各自单列成层，40 行标准结构顺手就翻倍成了 88 层。老黄家的 `Layer` 计数习惯，从图形部门到 AI 部门还真是自成一派。

💡 为什么 Mamba-2 和 Attention 可以这么混搭？

用两句话就能分清这两种模块的分工：
1. **Mamba-2（状态空间模型，State Space Model）** ：像一个边读书边在固定大小的笔记本上做摘要的人。不管前面的文章是 1 千字还是 100 万字，它的笔记本大小永远不变（在这台模型里是 128 个头 × 64 维 × 128 状态维 = 固定 104.8 万个浮点数）。好处是长文推理省内存、省算力；坏处是笔记本容量有限，遇到需要一字不差回翻前文第 35 页某句话的任务（大海捞针或跨文件精确核对），摘要里找不回来。
2. **Attention（注意力层）** ：像把整本书所有页码摊在桌上随时回翻。每多读一个词，桌上的 KV 缓存就要多存一行，内存随长度线性增长，但能做到精确回查。

国内的 Qwen3.8 和 GLM-5.3 选择每 3 层线性模块配 1 层注意力（3 比 1），而英伟达为了在长上下文里把 KV 缓存压到最小，把比例降到了 **40 比 8（即 5 比 1，每 5 个 Mamba 才配 1 个 Attention）** 。

────────────────────

光把注意力层数砍到 8 层还不够，我们再把第 7 层（第一个 Attention 层）和第 0 层（第一个 Mamba-2 层）的矩阵形状拉出来对账（按我们一贯的行向量右乘 `x @ W` 习惯，统一写成 `[输入维, 输出维]`）：

```python
# === 第 7 层：GQA 注意力模块（全网仅 8 层） ===
# 隐藏维 hidden_size = 4096，单头维度 head_dim = 128
q_proj: [4096, 4096]  # [4096] -> [4096]，32 个查询头 (32 × 128 = 4096)
k_proj: [4096,  256]  # [4096] -> [256]，仅 2 个键头 (2 × 128 = 256)
v_proj: [4096,  256]  # [4096] -> [256]，仅 2 个值头 (2 × 128 = 256)
o_proj: [4096, 4096]  # [4096] -> [4096]，输出投影回 4096 维

# === 第 0 层：Mamba-2 模块（全网共 40 层） ===
# 128 个 Mamba 头 × 64 维 = 8192 内部维，状态维 ssm_state_size = 128，分成 8 组 (n_groups = 8)
in_proj:  [4096, 18560] # [4096] -> [18560]，一次投出：门控 z(8192) + 输入 x(8192) + B(1024) + C(1024) + 步长 dt(128)
conv1d:   [10240, 1, 4] # 对 x(8192) + B(1024) + C(1024) = 10240 维做核宽为 4 的因果一维卷积
out_proj: [8192,  4096] # [8192] -> [4096]，状态扫描后压回 4096 维
```

看清 `k_proj` 和 `v_proj` 的形状 `[4096, 256]` 了吗？

这 8 层注意力不仅层数少，连每层的 KV 头都抠到了极限：**32 个查询头（Q）只配了 2 个键值头（KV），也就是 16 比 1 的分组查询注意力（Grouped-Query Attention，GQA）** ——每 16 个 Q 头共用同一份 K 和 V（我们在 322 期 https://mp.weixin.qq.com/s/HpX5uMf7UmYk12WthUcOrg 写小米 MiMo-V2.6 的全局层时见过同样的 16 比 1 比例，但小米有 48 层注意力，而老黄只有 8 层）。而且和前文 292 期的 `GLM-5.3-Flash` 一样，这 8 层注意力 **完全不加旋转位置编码（NoPE）** ，词与词的先后顺序全靠夹在中间的 40 层 Mamba-2 替它记。

这样一番“砍层数 + 砍 KV 头”下来，它的主干注意力 KV 缓存小到了什么程度？我们可以当场算出来：
- 每经过 1 个词元，单层 Attention 需要存 `2 个头 × 128 维 × 2（K 和 V）= 512 个数`；
- 全网只有 8 层 Attention，所以每个词元在全网一共只产生 `8 × 512 = 4,096 个数` 的注意力 KV 缓存；
- 如果按 `BF16`（每元素 2 字节）算，1M（1,048,576）词元的注意力 KV 缓存是 **8 GiB** ；按官方量化配置默认开启的 `FP8`（每元素 1 字节）存储，**1 个词元只占 4 KB，1M 上下文的注意力 KV 缓存加起来只有整整 4 GiB** （如果用报告第 4.5 节探索的 `NVFP4` KV 缓存，更是只有 **2.25 GiB** ）。

作为对比，前文 322 期按 `BF16` 口径算过：同样在 1M 上下文下，`Qwen3.8-Flash-Next` 的注意力 KV 缓存约 **24 GiB** ，`GLM-5.3-Flash` 约 **11 GiB** ，`DeepSeek-V4-Flash` 约 **6.72 GiB** （若同样折算为 `FP8` 则各减半为约 12 GiB、5.5 GiB 和 3.36 GiB）。老黄在报告第 5.2 节测试中能在 GB200 上跑出“吞吐量是 Qwen3.8 的 1.90 倍”，除了 MTP 接受长度和潜空间专家通信更小之外，这 8 层 2 头带来的超小注意力 KV 体积也是重要功臣。

至于代价是什么——全网 88 个模块里只有 8 层能回头看全貌，且每层只有 2 个 128 维的 KV 通道，这根被捏得极细的管道到底漏掉了多少复杂上下文细节，第六章看跑分表自有分晓。

━━━━━━━━━━━━━━━━━━━━

◆ 第三章：Latent MoE 与 DeepSeek 路由——把九成参数关进 1024 维的“小黑屋”

━━━━━━━━━━━━━━━━━━━━

看完了 40 层 Mamba-2 和 8 层 Attention，它们加起来的参数量其实还不到 7B。这台模型号称 `120B` 总参数，剩下的 **约 115B 参数** 全都装在另外 40 层混合专家（MoE）模块里。

我们直接把第 1 层（第一个 MoE 层）的权重名称和矩阵形状（按 `x @ W` 的 `[输入维, 输出维]`）拉出来：

```python
# === 第 1 层：Latent MoE 模块（全网共 40 层，每层 512 个路由专家 + 1 个共享专家） ===
# 1. 路由器（沿用 DeepSeek 风格的无辅助损失偏置路由，n_group = 1 不分组直接 512 选 22）
gate:                         [4096, 512] # [4096] -> [512]；直接在 512 个专家里挑 Top-22（注意 config 里 n_groups=8 是 Mamba 分组，MoE 的 n_group=1）
gate.e_score_correction_bias: [512]       # FP32，DeepSeek 标志性的无辅助损失负载均衡动态偏置项

# 2. 潜空间路由专家（Latent MoE：进专家前先从 4096 维压扁到 1024 维）
fc1_latent_proj:              [4096, 1024] # [4096] -> [1024]，所有专家共享的入场降维矩阵（压扁 4 倍）
experts.0..511.up_proj:       [1024, 2688] # [1024] -> [2688]，512 个专家全住在 1024 维里，激活函数为 ReLU²（无 gate_proj）
experts.0..511.down_proj:     [2688, 1024] # [2688] -> [1024]，22 个激活专家在 1024 维里加权求和
fc2_latent_proj:              [1024, 4096] # [1024] -> [4096]，所有专家共享的出场升维矩阵

# 3. 共享专家（不走潜空间，直接在 4096 维上计算）
shared_experts.up_proj:       [4096, 5376] # [4096] -> [5376]
shared_experts.down_proj:     [5376, 4096] # [5376] -> [4096]
```

这一层里藏着两样东西：一样是向 DeepSeek 借来的路由机制，另一样是老黄为了省带宽自己加的“缩骨功”。

**第一样：DeepSeek 风格的无辅助损失偏置路由。**
看那行 `gate.e_score_correction_bias: [512]`，熟悉 DeepSeek 架构的读者一眼就能认出来——这就是 DeepSeek-V3 首创的 **无辅助损失负载均衡（Aux-Loss-Free Load Balancing）** ：不往训练损失函数里强加会损害模型智力的负载均衡惩罚项，而是给每个专家配一个动态调整的偏置项 `e_score_correction_bias`，哪个专家太闲就把它的偏置调高一点，哪个太忙就调低一点。同时结合 `norm_topk_prob: True, routed_scaling_factor: 5.0` 对选中的 22 个专家权重做归一化与缩放（顺带提个读 `config.json` 容易踩的小坑：里面同时有 `n_groups: 8` 和 `n_group: 1` 两个字段，带 `s` 的 `n_groups: 8` 是前面 Mamba-2 的状态分组，而 MoE 路由器读的是不带 `s` 的 `n_group: 1`，也就是不对专家分组、直接在全部 512 个路由专家里挑 22 个）。

**第二样：把 DeepSeek 注意力里的“低秩瓶颈”搬进 MoE——潜空间混合专家（Latent MoE）+ `ReLU²` 双矩阵。**
这里正好顺便复习一个我们在 247 期 https://mp.weixin.qq.com/s/jjYk4lV-qhZpqAYge0tx6A 专门算过、平时极容易看糊涂的维度细节：

以前看稠密模型（Dense，比如 LLaMA-3-8B），整层只有 1 个大 FFN，维度变化是标准的“先升后降”（`4096 → 14336 → 4096`）。到了 `DeepSeek-V4-Flash` 这种细粒度 MoE（256 选 6 个路由专家 + 1 个共享专家 = 7 个激活专家），如果你只盯着**单个专家**的代码看，会发现它的 `up_proj` 是 **`4096 → 2048`** ，`down_proj` 是 **`2048 → 4096`** （`V4.1-Flash` 同理，是 `5120 → 2304 → 5120`）——单看一个专家，中间维度 `2048` 怎么比主干 `4096` 还小，变成“先降后升”了？

秘诀在于 **要把同时激活的 7 个专家并排拼起来看** ：单看 1 个专家中间只有 `2048` 维，但 **7 个激活专家并排算下来，整层的有效中间总宽度相当于 `7 × 2048 = 14,336` 维** ，相对于 `4096` 维主干道依然是标准的“先升后降”。

但还要注意 DeepSeek 这套做法的一个前提：**虽然每个小专家中间很窄，但每个专家的进门和出门，依然是直接连在 `4096` 维主干道上的** （每个专家各自握着 `[4096, 2048]` 的矩阵）。至于“先用一张共享矩阵压到 1024 维、算完再用共享矩阵升回来”的低秩瓶颈思路，DeepSeek 是在 169 期 https://mp.weixin.qq.com/s/mnbaXhQmQjDAyGD1dDdq5Q 讲过的 **MLA 注意力层（如输出侧 `o_lora_rank = 1024`）** 里用的。

再看老黄在 `Nemotron 3.5 Super` 里遇到了什么麻烦：他每层设了 512 个路由专家、每步要激活 **22 个** （每个专家中间维 `2688`，22 个并排拼起来总中间宽度高达 `22 × 2688 = 59,136` 维）。如果让这 512 个专家的进出口都直接连在 `4096` 维主干道上，光专家参数就会暴涨 4 倍突破 400B，单机 128GB 根本塞不下，跨卡还要收发 22 份 `4096` 维向量。

于是老黄把类似 MLA 的 **“1024 维共享低秩投影”搬到了 MoE 的大门口** ，不让 512 个专家直接连 `4096` 维主干道，而是先在门口把主干道掐细成一条 `1024` 维的“小胡同”，走完 **四步（`4096 → 1024 → 2688 → 1024 → 4096`）** ：
1. **进胡同前先共享缩骨 4 倍（`4096 → 1024`）** ：词元进路由专家之前，先乘一张全层共用的降维矩阵 `fc1_latent_proj [4096, 1024]`，把 `4096` 维主干向量压扁成 **`1024` 维** （`moe_latent_size: 1024`）；
2. **512 个专家全住在 1024 维小胡同里做“先升后降”（`1024 → 2688 → 1024`）** ：每个专家的进出口都只有 `1024` 维，在内部升到 `2688` 维。而且老黄放弃了 SwiGLU，改用平方整流线性单元 **`ReLU²`** （即先取 `max(0, x)` 再平方），省掉了第三张门控矩阵 `gate_proj`，每个专家只剩 `up_proj [1024, 2688]` 和 `down_proj [2688, 1024]` 两张表；
3. **出胡同后再共享升维（`1024 → 4096`）** ：被选中的 22 个专家在 `1024` 维胡同里算完并加权求和后，最后只乘一次共用的升维矩阵 `fc2_latent_proj [1024, 4096]`，恢复成 `4096` 维加回残差流（注意：主干残差流、路由器打分 `gate` 以及旁边的 1 个共享专家 `4096 → 5376 → 4096` 都不走这条潜空间胡同，依然直接在 `4096` 维主干道上运算）。

我们来算一算这招“潜空间缩骨功”带来的参数分布：
- 1 个路由专家的参数量 = `2 × 1024 × 2688 = 5,505,024`（约 550.5 万参数）；
- 1 层 512 个路由专家 = `512 × 550.5 万 ≈ 28.186 亿参数`（加上共享专家与潜投影约 28.71 亿）；
- 全网 40 层 MoE 合计 = **`40 × 28.71 亿 ≈ 1148 亿（114.8B）参数`** （其中 512×40 个路由专家独占 **112.7B** ）。

这个数字相当震撼：**在这台名义 120B（计入视觉与 MTP 约 124.5B）的大模型里，超过九成的参数（112.7B，占名义 120B 的 94%）全都被关在 `1024` 维的狭窄潜空间里；真正在 `4096` 维主干道上直接读写的（40 层 Mamba-2 + 8 层 Attention + 40 个共享专家 + 词表头），全部加起来还不到 8B 参数。**

从刷吞吐量的角度看，这招确实省事：因为每个路由专家极小，每次激活 22 个专家总共只动用 `40 × 22 × 550.5 万 ≈ 4.84B` 参数，加上主干的 7B 多，每词元总激活参数刚好控制在 **12B** ；而且专家进出只搬运 1024 维向量，通信量和访存开销直接砍掉四分之三。

但如果我们把第二章的 **16 比 1 GQA 注意力** 和第三章的 **Latent MoE** 摆在一起看，就会发现老黄在架构设计上干了一件颇为拧巴的事：**他在本可以用 MLA 保留多头键值视角自由度的注意力层用了老式的 2 头 GQA，反倒在用来“背知识”的 MoE 路由专家大门口，加了一道 1024 维的共享低秩漏斗。**

我们可以拿 168 期 https://mp.weixin.qq.com/s/YqcTnIrGKEYZ2n-sMAelKg 讲过的多头潜在注意力（MLA）和 312 期 https://mp.weixin.qq.com/s/n9v-PvAT_fDIFLd-t05FDg 《老靳学线代③线性无关与秩》里的几何常识，给这两处设计对一下账：

1. **注意力层：2 头 GQA vs MLA 的键值自由度** ：
   同样是每词元每层存 512 个数的缓存，DeepSeek 的 MLA 是存一个 512 维的共享潜向量，但每个查询头还保留各自独立的键值还原投影（推理时吸收进 Q 和 O 矩阵）——几十个头在键值侧还能提取各自不同的子空间特征。而老黄在全网仅有的 8 层注意力上用了 **32 个 Q 头配 2 个 KV 头（16 比 1 GQA）** ：虽然 16 个查询头各自还有独立的查询矩阵 `Q_i`、能算出不同的注意力权重分布，但它们在键值侧被迫共用完全相同的 128 维 `K` 和 `V` 表征，表征自由度大打折扣。

2. **MoE 路由专家层：独立进出 vs 共享 1024 维窄门** ：
   为什么 DeepSeek 的 MoE 不在专家门口搞共享降维？因为路由专家是模型存放各领域细碎知识的词典。在 DeepSeek 里，虽然单个专家中间只有 `2048` 维，但 **几百个专家各自拥有独立的 `[4096, 2048]` 进出矩阵** ——不同专家可以从 `4096` 维残差流的不同子空间方向读写信息。
   可老黄的 Latent MoE，却让 **同一层的全部 512 个路由专家共用同一张进门矩阵 `fc1 [4096, 1024]` 和同一张出门矩阵 `fc2 [1024, 4096]`** 。按前文 312 期讲过的矩阵的秩（Rank）的铁律——“点菜配比完全自由，但输出永远跑不出矩阵的行张成的空间”：
   - 进门乘完 `fc1`，`4096` 维输入向量里至少有 **`3072` 维的核空间（零空间，Nullspace）方向在进入路由专家前就被投影抹掉了** （虽然原始残差、路由打分和共享专家还能绕过这道门，但本层的 512 个路由专家对这 3072 个方向是完全失明的）；
   - 出门乘完 `fc2`，不管那 512 个路由专家肚子里塞了多少参数、选了哪 22 个出来组合，**本层路由专家分支加权求和后的输出，永远被限制在 `fc2` 那 1024 行张成的低维子空间里（秩 ≤ 1024）** 。

当然，不同模型之间的跑分差距还受预训练语料和后训练配方的多重影响，不能把单一结构直接画等号成全部原因；但看到这台挂着 `120B` 名头、路由专家占了 `112.7B` 的大模型，在后面第六章专门测冷门知识储备的 `AA-Omniscience`（全知测试）里准确率只考出 **26.20%** （比 `DeepSeek-V4-Flash` 的 **44.95%** 低了近 19 个百分点），你很难不去怀疑：每层拿一张秩为 1024 的共享门板把 512 个路由专家卡在四分之一的通道里，到底让这 `112.7B` 参数损失了多少吞吐知识的能力。

至少从架构取向上看，DeepSeek 决定在哪里压维度，优先考虑的是 **“哪里信息冗余高、压了尽量不伤表征自由度”** ；而老黄这套设计，处处透着 **“哪里压一截最省跨卡通信带宽、最能把自家显卡的每秒词元柱状图刷高”** 。

━━━━━━━━━━━━━━━━━━━━

◆ 第四章：视觉前厅与投机后厨——从 InternVL、DeepSeek 到源码里的祖传乌龙

━━━━━━━━━━━━━━━━━━━━

今年 3 月 GTC 大会上，老黄发过一版纯文本的 `Nemotron 3 Super 120B-A12B`。这次 10 月的 `3.5 Super VL`，是在 3 月那版纯文本底座上蒸馏、续训，并在后训练阶段“半路出家”缝上了视觉编码器和全套投机解码组件。

打开仓库自带的推理源码 `modeling_nemotron_h_omni.py`，你会发现这间前厅和后厨简直是一座开源技术博览馆，甚至还留着两处让人忍俊不禁的工程抓痕。

────────────────────

**第一处：视觉前厅——自研 C-RADIO 塔 + 书生 InternVL 的像素洗牌 + 两处源码彩蛋**

为了让纯文本底座看懂图片和视频，老黄在前面接了一座自研的 `C-RADIO` 视觉编码器（32 层 ViT-Huge，隐藏维 `1280`，图像块 `patch_size = 16`；因为它是用 CLIP、DINOv2、SAM 等多个视觉老师联合蒸馏出来的，所以开头带了 3 个类别词元 `cls_token` 和 7 个寄存器词元 `register`）。

视觉塔输出的向量是 `1280` 维，怎么既省词元又高效地塞进 `4096` 维的语言主干？看 `config.json` 里的这两行配置：

```json
"downsample_ratio": 0.5,
"image_tag_type": "internvl",
"video_pruning_rate": 0.7
```

老黄没有自己造轮子，而是直接搬来了上海人工智能实验室 **InternVL（书生·万象）** 的标准方案—— **2×2 像素洗牌下采样（Pixel Shuffle）** ：
- 一张 `512 × 512` 的图片进 ViT，按 `16 × 16` 切成 `32 × 32 = 1,024` 个视觉块，每个块是 `1280` 维；
- 接着调 `pixel_shuffle(scale_factor=0.5)`，把空间上相邻的 `2 × 2 = 4` 个视觉块直接拼成 1 个块：高和宽各减半（变成 `16 × 16 = 256` 个视觉词元，**词元数量直接砍掉四分之三** ），通道维度则乘以 4（变成 `1280 × 4 = 5120` 维）；
- 最后过一个两层投影网络 `mlp1`（`5120 → 20480 → 4096`，中间用 `RMSNorm` 和 `ReLU²`），再用我们在 295 期 https://mp.weixin.qq.com/s/lCpYoqH_CwE5o52ECySMhQ 讲过的 `masked_scatter` 算子，把这 256 个 `4096` 维向量原位塞进文本序列的 `<image>` 占位符（token id 为 18）里。
- 至于视频输入，源码先按 `video_temporal_patch_size = 2` 把相邻两帧打包成一个时间片，随后的 `compute_retention_mask` 函数保留第一个时间片的全部词元，把后续时间片跟前一个时间片同一位置的向量算 **余弦相似度（`cosine_similarity`）** ，在整个视频范围内统一排序，把变化最小（最相似）的词元按设定比例删掉（`config.json` 默认剪枝率 `video_pruning_rate = 0.7` 即删掉 70%，第一章的官方启动命令则覆写为 `0.5` 即删掉 50%）。

最逗的是我们在 `modeling_nemotron_h_omni.py` 源码里翻出来的两处工程痕迹：

1.**没删干净的音频支架** ：这台模型明明是个只支持图文和视频的 VL（Vision-Language）模型，但源码第 72 行到第 135 行却完整写着 `NemotronH_Omni_Reasoning_V3SoundEncoder`（封装 Parakeet 语音编码器）和 `sound_projector` 的前向逻辑，只是在 `config.json` 里把 `sound_config: null` 关掉了。
2.**注释里交底的 Megatron 配置继承副作用（源码第 188 至 195 行）** ：在视觉投影器 `NemotronH_Omni_Reasoning_V3VisionProjector.__init__` 里，有一段长达 8 行的英文注释，翻译过来是这么说的：

> “为了镜像复现 Megatron 的训练行为：当语言模型开启多词元预测（MTP）时，Megatron-Core 的 TransformerBlock 会在所有由同一份共享 config 构建的模块最后一层末尾放一个最终的 LayerNorm—— **这其中包括了视觉塔，因为视觉塔的 config 从语言模型那里继承了 `mtp_num_layers` 参数** 。因此视觉塔的输出在进投影层之前被做了一次 LayerNorm。只要语言模型的 `num_nextn_predict_layers > 0`，我们就在这里加上一个 `vision_final_layernorm`。”

读到这段注释实在让人忍俊不禁：因为训练时语言模型和视觉塔共用了同一份配置，给语言模型开 MTP 时顺带让视觉塔也继承了 `mtp_num_layers`，结果在视觉塔屁股后面多挂了一个 `LayerNorm [1280]`；到了导出 Hugging Face 推理代码时，干脆写个 `if num_nextn_predict_layers > 0` 判断，把这个因为共享配置多出来的归一化层原样保留了下来。

**第二处：投机解码后厨——内置 DeepSeek 式 MTP ＋ 外挂 `LiLiCorr` 并行草稿头 ＋ 借鉴 Kimi K3 的检查点**

因为这台模型有 88 个平级模块（哪怕只算 40 层 Mamba + 40 层 MoE 的主路径也有 80 次串行模块调用），单词元自回归生成的延迟并不低。为了把生成速度提上去，老黄在模型里同时塞了 **两套投机解码方案** ：

**第一套（内置，供数据中心高并发使用）：DeepSeek-V3 同款多词元预测头（MTP）。**
它的 `language_model.mtp` 权重结构是：
- 把主干最后一层的输出向量过 `hnorm [4096]`，把下一个位置的词嵌入向量过 `enorm [4096]`，两者拼成 `8192` 维后，用 `eh_proj [8192, 4096]` 压回 `4096` 维；
- 后面紧跟 1 层 Attention（`mtp.layers.0`）和 1 层 Latent MoE（`mtp.layers.1`）。
这套“分别归一化 → 拼接 → 线性降维 → 单层变换”的电路，从结构到命名都与 DeepSeek-V3 的 MTP 如出一辙。老黄在 3 月的 3.0 版本里放了两个独立的 MTP 头，到了 3.5 版则砍掉第二个头，只留一个头做 **递归自回归猜词（Recursive MTP）** ，并在训练时把前面几步生成的合成隐藏状态混进输入里（Hidden-state mixing），缓解多步猜词的分布漂移。

**第二套（外挂，供 DGX Spark / RTX Spark 单机低并发使用）：借鉴 `DFlash` 的并行草稿头与借鉴 Kimi K3 的前缀检查点。**
为什么有了内置 MTP，在第一章的 Spark 单机启动脚本里却不用，非要额外挂一个 1.23 GiB 的外挂草稿头 `LiLiCorr`？

原因很简单：**内置的递归 MTP 每多猜一个词都要串行跑一遍，猜 7 个词的延迟随长度累加；而在 Spark 单机（`--max-num-seqs 1`）上算力闲置、瓶颈在内存带宽，最划算的是像我们在 236 期 https://mp.weixin.qq.com/s/fQc0hRxEIZxkPzGTDhj78g 讲过的并行投机解码那样，一次前向同时把未来 7 个位置的候选词全猜出来，再用一个轻量级关联头把前后合拍的词串成句子交给主模型一次性验证** （老黄家的以色列团队借鉴开源 `DFlash2` 的动态卷积机身，在顶上加了个余弦关联头并取名叫 `LiLiCorr`；其 `config.json` 沿用了 `model_type: qwen3` 与 `dflash_config` 的兼容结构，第一章启动命令里填的也是 `dflash`）。

而在 Mamba 混合架构上跑投机解码和多轮对话前缀缓存，最头疼的是那 40 层滚动覆盖的 Mamba 状态怎么保存和回退。报告第 5.4 与 5.5 节给出的方案同样是“借力打力”：投机回退靠缓存输入小向量的 `ReplaySSM`，而预填充阶段导出状态检查点的机制，报告第 5087 行直接坦白道：

> `Internal prefill checkpointing was initially implemented in vLLM for Kimi K3. Building on that work, we adapted the shared checkpoint builder and exporter to Mamba-2 in PR #57329.`（内部预填充检查点机制最初是在 vLLM 中为 Kimi K3 实现的；我们在该工作的基础上，将其改造适配到了 Mamba-2。）

💡 既然 Mamba、KDA（Kimi）和 GDN（Qwen）都是一步步更新状态的，它们凭什么能并行算、又怎么存前缀缓存？

平时看惯了“状态一步步往后传”的示意图，很容易产生两个疑问：一是这类模型能不能像 Transformer 那样并行处理整段词元？二是它们的前缀缓存怎么存？

**1. 为什么能并行计算？——拿掉非线性激活，分块整理成矩阵乘法**

老古董 RNN 不能并行，是因为每一步更新状态都要套一层非线性函数 `S_t = tanh(α_t × S_{t-1} + X_t)`，前一步不算完，后一步就没法化简。

而无论是老黄用的 **`Mamba-2`** ，还是 Kimi 与智谱用的 **`KDA`（Kimi Delta Attention）** 、阿里 Qwen 用的 **`GDN`（Gated DeltaNet）** ，核心都是把状态外面的 `tanh` 非线性外壳拿掉了，改成了对旧状态 `S_{t-1}` 的纯线性变换（以 Mamba-2 的最简形式为例）：

`S_t = α_t × S_{t-1} + k_tᵀ × v_t`

一旦没有了 `tanh`，把几步展开就会发现，当第 `t` 个词拿查询向量 `q_t` 去读状态 `S_t` 时，利用矩阵乘法结合律把 `q_t × (k_iᵀ × v_i)` 括号一挪，就能变成 **`(q_t × k_iᵀ) × v_i`** ——带上因果掩码和累计衰减权重后，在数学上就能整理成类似注意力的分块矩阵乘法（KDA 和 GDN 因为多了按 `k_t` 方向擦除旧值的 Delta 规则，块内还要额外解一步三角依赖，但同样能化归为分块矩阵运算）。以这台 Mamba-2 配置的 `chunk_size = 128` 为例，预填充时把序列切成小块，**块内直接用 GPU 的 Tensor Core 矩阵乘法并行算完** ，只在块边界传递状态 `S`。

**2. 怎么存前缀缓存与投机回退？——边界拍快照 + 缓存小向量**

既然块内能并行算，麻烦就只剩“存”：40 层 Mamba 的一份 SSM 状态 `S` 在 FP16 下占 80 MiB，不可能像 Attention KV 那样每个词都存一份。解法就是分两头省：
- **多轮前缀缓存（借自 Kimi K3）** ：趁着预填充按块并行扫描时，让逻辑块刚好对齐缓存页边界，在边界处顺手把那一份 80 MiB 的状态快照写进缓存池，不用为了存检查点再跑第二次前向；
- **投机解码回退（ReplaySSM）** ：一次并行验证 7 个草稿词时，不往显存写 7 份 80 MiB 的完整状态，只把这几步轻量级的 `k_i, v_i, α_i` 小向量记在小缓冲区里；如果部分草稿词被拒绝，只需回退缓冲区计数指针，等缓冲区满了或需要时再用 Tensor Core 重建状态写回即可。

────────────────────

你看，连底层推理引擎里省掉二次前向传播的检查点导出器，都是直接站在 `Kimi K3` 的肩膀上改出来的。

**第一，120B 这个身段在排行榜上的位置相当尴尬：往上打不过两三千亿的国产 Flash，往下没跑赢 27B 的千问小钢炮。**
你看开头那张 AA 排行榜截图：
- 往上看，国产开源主力 `MiMo-V2.6-Pro` 考了 **46 分** ，`DeepSeek V4.1 Flash 1017`、`Qwen3.8 Max`、`GLM-5.3 (max)` 全在 **45 分** ，`Kimi K3` **44 分** ，`GLM-5.3-Flash` **42 分** ；
- 往下看，阿里那颗只有 **27B** 总参数的小模型 `Qwen3.8 27B (xhigh)` 也考出了 **34 分** ，比 120B 的 Nemotron 高出整整 8 分。
只有当你把目光局限在“40B 到 150B”这一小截几乎没几家新旗舰扎堆的区间里时，这颗 26 分的 120B 模型才能靠体量差勉强找回一点面子。

**第二，为什么它吃了四家中国名师的轨迹，综合实力还是拉不开？因为蒸馏轨迹保得住部分专项题，却补不上知识容量、长文细节和复杂 Agent 的短板。**
- 在部分单题或特定基准上（比如 `GPQA-Diamond` 89.52、`SWE-bench Pro` 51.78，或者规则合成的 `GraphWalks` 图遍历 89.71），靠着 Kimi K3、DeepSeek-V4-Pro 和 GLM-5.2 的高质量蒸馏轨迹，它确实超过了自家的上一代大块头 `Nemotron 3 Ultra`（550B-A55B，GPQA 为 86.99、SWE-bench Pro 为 49.66）；
- 可一旦进入考察 **“广博知识储备、真实长文综合回查、多步复杂环境交互”** 的深水区，差距立刻显现：
  1. **冷门知识答对率偏低（`AA-Omniscience` 准确率仅 26.20%，`MMLU-ProX` 仅 76.91%）** ：虽然它在答不出时倾向于拒答（因此非幻觉率 69.96% 较高），但纯看知识题答对的比例，比 `DeepSeek-V4-Flash`（44.95%）低了整整 18.75 个百分点；
  2. **真实长文与复杂文档解析掉队（`AA-LCR v1.1` 仅 68.62%，`GDP.pdf` 仅 6.6）** ：虽然宣传支持 1M 上下文，且在机械寻路的合成图遍历题 `GraphWalks` 上拿了高分，但一到需要跨多篇真实长文档（约 100K 词元）综合对比线索的 `AA-LCR`，比三家国产 Flash 齐刷刷低了约 10 到 11 分；到了复杂 PDF 办公任务 `GDP.pdf`，更是只有 6.6 分（Qwen3.8 自测 17.4 / AA 15.6，GLM-5.3 自测 14.8 / AA 15.4）；
  3. **长链条复杂 Agent 考场大比分落后** ：在英伟达自己的离线测试表里，`AutomationBench-AA` 只拿到 **32.44** （Qwen3.8 是 72.06，GLM-5.3 是 70.17，差了一倍多）；`AA-Briefcase-Lite` 只有 **1137** （GLM-5.3 是 1785，Qwen3.8 是 1636）；`DeepSWE` 只有 **24.65** （GLM-5.3 是 57.77，Qwen3.8 是 55.57）；而在最新最难的 `Terminal Bench 4 [offline]` 上，更是只考出了尴尬的 **1 分** （同表里 Qwen3.8 为 20.71、GLM-5.3 为 15.15）。至于人类盲测 `Text Arena Elo`（风格控制下预览分 1420），不仅被 `GLM-5.3-Flash`（1474 分）拉开五十多分，甚至没跑赢谷歌那颗只有 26B 总参数、4B 激活的 `Gemma-4-26B-A4B`（1438 分）。

◆ 结语：卖铲子的人熬的汤，终究是为了卖铲子

━━━━━━━━━━━━━━━━━━━━

把 `Nemotron 3.5 Super VL 120B-A12B` 从头到尾看一遍，其实一点都不难理解老黄和英伟达团队的工程取舍。

如果你把它当成一家模型公司冲击智能上限的旗舰作品，那它身上的毛病简直可以用 **“本末倒置、舍近求远、将错就错”** 十二个字来概括：本可用 MLA 兼顾键值视角自由度的注意力层只留 8 层 2 头老式 GQA，用来背知识的 MoE 路由专家反倒在门口焊上 1024 维共享窄门（本末倒置）；内置了递归 MTP 到了单机低并发下又嫌串行慢，还得外挂 `LiLiCorr` 草稿头并给 Mamba 状态配套一堆回放机制（舍近求远）；甚至连训练时因共享配置让视觉塔多继承出来的 `LayerNorm`，也在推理代码里写个 `if` 原样保留（将错就错）。最后吃遍了中国四大开源家族（Qwen、Kimi、DeepSeek、GLM）的后训练轨迹，在 AA 智能指数上还是只考出 26 分，被它自己的老师们甩在身后。

但如果你换个视角—— **把它看作英伟达芯片与 TensorRT-LLM / vLLM 推理团队联手打造的“官方标准演示负载（Demo Workload）”** ，它身上的每一处拧巴设计就全都顺理成章了：

1. **在云端（GB200 / Vera Rubin VR200）** ，因为只有 8 层 2 头注意力和 1024 维潜空间专家，它的单请求缓存极小、通信极轻，在报告设定的 20 轮交互负载与并发条件下，配合内置 MTP 和 `ReplaySSM` 就能在 PPT 上画出“单卡每秒输出 4,856 词元、吞吐量是 Qwen3.8 的 1.9 倍”的漂亮柱状图；
2. **在端侧（以 128GB 统一内存为核心卖点的 DGX Spark 与刚上市的 RTX Spark 平台）** ，它那 69.86 GiB 的 `NVFP4` 混合精度身板，刚好能伴随 1.23 GiB 的 `LiLiCorr` 草稿头一起放进单机 128GB 内存里——哪怕背后得把 Mamba 状态砍成 FP16、在示例配置里把上下文限在 112K，至少在单机跑起来的那一刻，屏幕上真的能展示“120B 多模态大模型本地流畅运行”的招牌。

说到底，DeepSeek、Qwen、Kimi 和智谱做模型，命门在于“模型本身聪不聪明、能不能把活干对”；而老黄做模型，很大一部分任务是 **“证明你刚花几千美元买回去的那台新机器，刚好能跑起一个名字里带 120B 和 1M 的大家伙，而且每秒吐字速度特别快”** 。

不过换个角度想，对我们这些平时一点点抠模型原理的学习者来说，看这台“学渣”模型反倒成了意外之喜。平时读 DeepSeek 这种优等生的图纸，因为它每一步都做得很顺，顺着看下来只会觉得理所应当；反倒是老黄自费几百张 GB200 的电费端出来的这台拼盘模型，成了一份绝佳的“大家来找茬”活体复习卷——把我们之前学过的统一内存安全垫（前文 210 期）、老黄数层法（前文 343 期）、MLA 与 GQA 的视角差异（前文 168 期）、MoE 激活专家并排总宽度（前文 247 期）、矩阵的秩与零空间（前文 312 期）、视觉词元填空（前文 295 期）、并行投机草稿头（前文 236 期）以及多教师在线蒸馏（前文 286 期）一口气全串起来复习了一遍。

好模型教你“标准答案长啥样”，渣模型让你思考“为什么非得是这个答案”——拿老黄这锅“百家饭”当一回架构总复习的考卷，倒也算物尽其用了。

◆ 速查表

| 模块 / 概念 | 一句话解释 |
|---|---|
| 88 层平级混合主干（`NemotronH`） | 不按传统“注意力+FFN”成对捆绑，而是分成 40 层 Mamba-2、8 层 GQA 注意力与 40 层 Latent MoE 共 88 个平级模块（32 组 `M→E` 加 8 组 `M→A→E`） |
| 16 比 1 无位置编码注意力（NoPE GQA） | 全网仅 8 层注意力，每层 32 个查询头共用 2 个键值头，靠 Mamba-2 记顺序；1M 上下文下全网注意力 KV 缓存在 BF16 下为 8 GiB、默认 FP8 下为 4 GiB |
| 潜空间混合专家（Latent MoE） | 路由采用无辅助损失偏置（`n_group=1` 直接 512 选 22），进路由专家前先从 4096 维压到 1024 维并用 `ReLU²` 省去门控矩阵，路由专家占 112.7B 参数 |
| 4.82 BPE 混合精度 `NVFP4` | MoE 专家压 NVFP4，Mamba/注意力/输出头留 FP8，潜投影/视觉/MTP 注意力与融合层留 BF16，静态权重文件加草稿头共占 71.09 GiB |
| `vision_final_layernorm` | 训练时因语言模型与视觉塔共用 Megatron 配置对象，开启 MTP 时视觉塔末尾也带上了 LayerNorm，推理代码通过 `if` 判断复现该层 |
| `LiLiCorr` 并行草稿头与 `ReplaySSM` | 单机低并发下一次并行猜 7 个槽位各 Top-8 候选词并用余弦相似度串成句；Mamba 投机解码只缓存轻量输入小向量，拒绝词元时回退指针、按需重建状态 |
