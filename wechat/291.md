【Agentic RL】一件真活，怎么变成模型的训练题

━━━━━━━━━━━━━━━━━━━━

◆ 这次不讲工厂，只看工位

━━━━━━━━━━━━━━━━━━━━

282 期（ https://mp.weixin.qq.com/s/4aDzx6lxkVxTUSj8NnCSYA ）已经讲过，2026 年这轮 Agentic RL（智能体强化学习）的难点，正在从模型挪到环境：题得能运行，结果得能验证，还要像真实工作。

283 期（ https://mp.weixin.qq.com/s/qBGsQ75RQYExZW1Vj0BhIg ）又往前追了一步：几万道训练题从哪来。GitHub 仓库、知识图谱、模拟工作区，都是造题的原料。

这两期讲的都是工厂。可我读完还有个很朴素的问题：**一件真正送进训练的 Agent 任务，到底长什么样？**

不是论文里那种“给定问题，输出答案”，也不是我们平时在对话框里说一句“帮我改个 bug”。模型开工时，桌上究竟摆着什么？它干到什么程度才算交活？最后那个奖励又从哪儿来？

GLM-5.3 在 8 月 14 日的官方文章（ https://z.ai/blog/glm-5.3 ）里，正好给了一个机器学习基础设施任务。官方没有放出这道题的完整提示词、环境镜像和判分代码，只描述了任务类型与生产流程。**所以这期不假装复原内部样本，只把公开的零件按一件活的生命周期摆整齐。**

━━━━━━━━━━━━━━━━━━━━

◆ 开工时，模型拿到的不是一道题

━━━━━━━━━━━━━━━━━━━━

这件活的目标听起来很像我们公司的真实工单：**把一套机器学习训练系统跑快，同时不能弄错结果。**

在 GLM 举的例子里，模型可能拿到与工程师相同的工作环境：

- 计算集群；
- 存储系统；
- 内部文档；
- 代码库；
- 以前跑过的实验结果。

然后它得自己完成一整条链：在训练栈里找瓶颈，提出修改，动手实现，跑实验，最后交付一个可测量的端到端加速，并证明原有正确性没有被破坏。

官方说，这类任务有些相当于一名有经验的工程师好几天的工作量。

这里有个容易混在一起的地方：**“任务”不等于那段文字要求。** 那段要求只是工单，真正的训练单元还得带上工作现场。

────────────────────

💡 一件 Agent 训练任务，至少有四样东西

**初始状态**：代码当前是什么版本，集群和存储里原本有什么，哪些实验已经跑过。

**可用工具**：终端、代码编辑、测试命令、集群接口、文档和实验系统。

**目标**：不是“写一段优化建议”，而是交付可测量的端到端加速，同时守住正确性。

**判分器**：活干完以后，自动判断目标有没有真的达成。

少了后两样，这只是聊天；少了前两样，这只是考卷。四样凑齐，才是一个能送进强化学习的环境。

────────────────────

这也解释了官方为什么强调环境里有“多步依赖”和“隐藏状态”。

多步依赖很好懂：不先读代码，就不知道该测哪里；不先跑基线，就不知道优化了多少；不改实现，也就没有新实验可跑。后一步建立在前一步留下的状态上。

隐藏状态也不是神秘的“模型内心”。它是**环境里没有直接写在题面上的事实**：真正的瓶颈在哪、某个改动会不会破坏正确性、测试结果会怎样。模型得靠读文件、跑命令和做实验，把这些事实一点点翻出来。

所以 Agent 任务的输入，不是一条长 prompt。更接近一个已经摆好的现场：**文字只负责告诉你要干什么，环境负责藏着答案。**

━━━━━━━━━━━━━━━━━━━━

◆ 交活不是交一份标准答案

━━━━━━━━━━━━━━━━━━━━

传统编程题很好判：输出和答案对上，或者单元测试全绿，就给分。

这件基础设施任务没有唯一解。你可以换计算内核（kernel），可以改通信，可以调整数据流水线，也可以组合几处小优化。只要端到端确实变快、正确性没坏，都可能算完成。

于是判分器不能问“你写得和参考答案一样吗”，只能问两件事：

1. **真的变快了吗？** 跑同一套基准，测端到端结果。
2. **东西还对吗？** 跑正确性检查，防止模型靠少算、漏算或者改口径换速度。

这就是“答案”和“结果”的区别。答案是某一条预先写好的路径；结果是环境运行之后留下的事实。

GLM 的公开文字还披露了一处很有意思的边界：**判分器合成时看不到参考解。**

我原先把这句话理解成“怕模型迎合标准答案”，不够准确。更直接的理解是：这里本来就允许多种实现。判分器若绑死某份参考修改，就可能把另一条同样有效的优化错判成失败。它该检查任务目标，不该检查模型有没有抄老师的做法。

至于模型会不会钻判分空子，GLM 的办法是把实际解题轨迹拿回来找漏洞：如果模型什么正事都没干，却从某条缝里拿到了奖励，就修判分器，再测。

━━━━━━━━━━━━━━━━━━━━

◆ 判分器也得先参加入职体检

━━━━━━━━━━━━━━━━━━━━

一个自动生成的判分器，不能写完就上岗。GLM 给它安排了三类检查：已知正解检查（`oracle`）、空操作检查（`no-op`）和未解决状态检查（`unsolved-state`）。

按这些名字能做的最保守理解是：已知正确的完成状态应该通过；什么都不做不能通过；已知还没解决的状态也不能通过。

但官方只公布了三类检查的名字，没有解释 `no-op` 与 `unsolved-state` 在他们内部具体怎样构造、怎样区分。仅凭三个名字，不能再替它们编一套更整齐的内部分工。

这三道检查共同解决的是一个工程问题：**先拿我们知道结果的样本，校准这个二元判分器。** 正样本不能漏，负样本不能放水。通过以后，它给出的 0 或 1 才能直接当强化学习奖励。

到这里，一件活才算真正造完：

1. 研究型 Agent 从真实工作里收集任务模式；
2. 流水线把模式做成能运行的长程环境；
3. 裁判 Agent 亲自试做，确认任务不是无解；
4. 合成判分器，再用正反样本和解题轨迹查漏；
5. 通过检查的任务与判分器，进入训练数据流。

前四步都在**造训练题**。真正被训练的模型，还没出场。

这一点是我这次最想弄明白的：研究型 Agent、裁判 Agent、被训练的 Agent，都是“Agent”，但不是同一个工位。前两个在出卷组，最后一个才是考生。

━━━━━━━━━━━━━━━━━━━━

◆ 真正训练时，这件活会被反复开工

━━━━━━━━━━━━━━━━━━━━

等任务进入训练，流程反而朴素了。

被训练的模型拿到一份任务环境，在里面读文档、改代码、跑命令、看结果，直到它认为完成或者耗尽预算。环境记录整条操作轨迹，判分器在最后运行，给出 0 或 1。训练系统再拿这批轨迹更新模型。

下一轮，新模型再进新的任务实例里干活。

GLM 没公开这一个任务具体采样多少条轨迹、每条跑多少轮、奖励怎样并入总损失；这些不能从一句“二元奖励（binary reward）”里猜出来。能确认的是，他们把数学、代码、沙箱、判分器和长程环境都当作**数据生成侧**的不同来源，接进同一套 slime 训练数据流，而不是每来一类新任务就重写一次训练循环。

所以 287 期讲的异步流水线，和今天这件具体任务刚好能扣上：

- 291 期看的是**一条轨迹里面有什么**；
- 287 期看的是**成千上万条长短不一的轨迹，怎样在集群里流动**。

一个是工位，一个是整厂，不是同一篇。

━━━━━━━━━━━━━━━━━━━━

◆ “真实工作”还有一道没跨过去的线

━━━━━━━━━━━━━━━━━━━━

GLM 把这类任务称作真实的专家工作单元，这个方向成立，但边界也得留着。

公开文章给的是一个**任务类型示例**，不是一份可下载、可复现的完整训练样本。外界目前看不到它的具体工单、初始镜像、集群接口、参考完成状态和判分器代码，也不知道其中多少环节需要人工修订。

官方自己也承认，环境生成与验证仍需要相当数量的人在回路里工作；让它们更自主，是下一步。

这句话比“人正在往外撤”更准确。现在被自动化掉的，是一部分重复造环境、试做和检查的劳动；人仍在决定什么任务值得练、什么结果算完成，以及判分器的漏洞有没有堵住。

作为一把公开的尺子，SWE-bench Pro 可以帮我们感受这个尺寸：它收了 41 个活跃维护的开源与商业代码库、1,865 个问题，任务往往要专业工程师花几小时到几天完成。它和 GLM 的内部训练环境不是同一批东西，也不能证明 GLM 的训练样本质量；它只说明“几小时到几天的一件活”已经是可以被公开整理和评测的任务尺度。

━━━━━━━━━━━━━━━━━━━━

Agentic RL 里的一道训练题，不是一段 prompt 加一个标准答案。

它是一块能回到初始状态的工作现场：有工具、有材料、有藏在环境里的事实，还有一个只看活儿干没干成的判分器。

真正昂贵的也不再只是“让模型多做几次题”，而是先把真实工作压成这种机器能反复开工、反复验收的形状。
